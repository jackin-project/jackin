# 03 — Reference implementations and delivery directions
Vetted: 2026-08-20
Questions: Which current open-source implementations provide reusable patterns for canonical account grouping, native macOS interaction, state and refresh ownership, accessibility and testing, native delivery, and shared CLI/TUI projections; which patterns conflict with the settled constraints; and what distinct implementation directions remain?
Informs: unified-agent-usage
Method: web (primary public repository source and official docs)

## Findings

### Research baselines

- The inspected revisions were CodexBar [`e7779924f98a3c1533fd517bf91f3d4d49f14f64`](https://github.com/steipete/CodexBar/tree/e7779924f98a3c1533fd517bf91f3d4d49f14f64), native OpenUsage [`70acd4f4e9cc79951d83f416295e22ef43b9696b`](https://github.com/robinebers/openusage/tree/70acd4f4e9cc79951d83f416295e22ef43b9696b), TermRock [`29a16b5bff84ea8609854711b774e87acbc456cc`](https://github.com/tailrocks/termrock/tree/29a16b5bff84ea8609854711b774e87acbc456cc), and terminal OpenUsage [`fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0`](https://github.com/janekbaraniewski/openusage/tree/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0). These immutable revisions are the anchors for repository findings below. (confidence: HIGH)

### Canonical account grouping

- Native OpenUsage separates provider account identity from source/default status. Its registry reconciles observations by `(provider family, identityKey)`, preserves a minted stable record ID, derives later IDs from a SHA-256 digest, and treats “default” as a mutable badge rather than part of identity. This is a proven shape for jackin❯: source paths remain observations on a canonical account, not durable account identity. The implementation currently covers its own provider families and therefore is pattern evidence, not evidence that all eight jackin❯ host surfaces can expose a stable identity. — [ProviderAccountsStore.swift, lines 4–58](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Stores/ProviderAccountsStore.swift#L4-L58), [lines 80–180](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Stores/ProviderAccountsStore.swift#L80-L180), [ProviderAccountAssembly.swift, lines 57–96](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Services/ProviderAccountAssembly.swift#L57-L96) (confidence: HIGH)
- Native OpenUsage stamps cached snapshots with the resolved identity, and its application and reader paths reject cache entries on identity mismatch. That prevents a source changing accounts from displaying the previous account’s last-good data, while keeping cache identity metadata outside the provider wire snapshot. — [ProviderSnapshotCache.swift, lines 4–12](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Stores/ProviderSnapshotCache.swift#L4-L12), [lines 82–150](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Stores/ProviderSnapshotCache.swift#L82-L150), [UsageReader.swift, lines 79–95](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Services/UsageReader.swift#L79-L95), [WidgetDataStore.swift, lines 173–186](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Stores/WidgetDataStore.swift#L173-L186), [lines 277–292](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Stores/WidgetDataStore.swift#L277-L292) (confidence: HIGH)
- CodexBar’s fleet projection groups snapshots by `accountKey`, chooses the freshest remote snapshot per account, hides a remote account when an equivalent local key is present, and applies deterministic tie-breaking. Its tests cover local/remote duplication, distinct accounts, freshest-wins, and equal-time ordering. This is reusable projection behavior after canonical identity is resolved. — [FleetAccountMenuProjection.swift, lines 10–63](https://github.com/steipete/CodexBar/blob/e7779924f98a3c1533fd517bf91f3d4d49f14f64/Sources/CodexBar/FleetAccountMenuProjection.swift#L10-L63), [FleetAccountMenuProjectionTests.swift, lines 8–41](https://github.com/steipete/CodexBar/blob/e7779924f98a3c1533fd517bf91f3d4d49f14f64/Tests/CodexBarTests/FleetAccountMenuProjectionTests.swift#L8-L41), [lines 43–133](https://github.com/steipete/CodexBar/blob/e7779924f98a3c1533fd517bf91f3d4d49f14f64/Tests/CodexBarTests/FleetAccountMenuProjectionTests.swift#L43-L133) (confidence: HIGH)
- CodexBar’s proposed multi-account design models provider-neutral identity as a source plus opaque ID and keeps email display-only; adapters own identity derivation. Its fallback source-issued slot is scoped to one source. This is design evidence rather than implementation proof: the boundary is reusable, but the slot cannot by itself be jackin❯ durable canonical identity when the same real account is discovered through multiple sources. — [Claude multi-account design, lines 70–144](https://github.com/steipete/CodexBar/blob/e7779924f98a3c1533fd517bf91f3d4d49f14f64/docs/claude-multi-account-and-status-items.md#L70-L144) (confidence: HIGH)
- Terminal OpenUsage instead defines an account as a provider configuration instance with a user/configuration ID. Manual entries win only on the same `(provider, id)`, while detected entries with other IDs are appended. That supports several intentional configurations, but it does not prove canonical deduplication of one real account found through distinct configuration sources. — [Accounts, lines 6–31](https://github.com/janekbaraniewski/openusage/blob/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0/docs/site/docs/concepts/accounts.md#L6-L31), [lines 50–83](https://github.com/janekbaraniewski/openusage/blob/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0/docs/site/docs/concepts/accounts.md#L50-L83) (confidence: HIGH)

### Native status-item, popover, and window interaction

- CodexBar keeps provider status items stable by assigning autosave names and reusing items across toggles, preserving operator-arranged menu-bar positions. Its overview row can focus the corresponding provider menu, matching the settled split between a glanceable provider item and a complete overview. — [UI architecture, lines 10–17](https://github.com/steipete/CodexBar/blob/e7779924f98a3c1533fd517bf91f3d4d49f14f64/docs/ui.md#L10-L17) (confidence: HIGH)
- CodexBar uses a template status icon, dims stale/error state, bounds its loading animation, updates refresh state in place, and makes repeated refresh clicks share active work. Its status-item vending code registers an item before installing callbacks, preventing re-entrant creation of a duplicate item. — [UI architecture, lines 51–69](https://github.com/steipete/CodexBar/blob/e7779924f98a3c1533fd517bf91f3d4d49f14f64/docs/ui.md#L51-L69), [StatusItemController+StatusItemVending.swift, lines 5–29](https://github.com/steipete/CodexBar/blob/e7779924f98a3c1533fd517bf91f3d4d49f14f64/Sources/CodexBar/StatusItemController%2BStatusItemVending.swift#L5-L29) (confidence: HIGH)
- Native OpenUsage uses one `NSStatusItem`, left-click to toggle the dashboard, and right-click for a context menu. It hosts SwiftUI in a key-capable, non-activating `NSPanel`, explicitly because its prior popover could not reliably support keyboard interaction. The panel performs first-frame layout before focus and tears down hover/focus state on close. This is evidence for the interaction details, not evidence to replace jackin❯ desktop’s settled native popover without reproducing the keyboard defect. — [StatusItemController.swift, lines 5–25](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/App/StatusItemController.swift#L5-L25), [lines 51–127](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/App/StatusItemController.swift#L51-L127), [lines 241–355](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/App/StatusItemController.swift#L241-L355) (confidence: HIGH)
- Apple states that standard SwiftUI, UIKit, and AppKit navigation, sheets, popovers, and controls automatically adopt Liquid Glass, and advises removing custom backgrounds/effects before adding custom glass. Apple’s AppKit guidance limits glass to important top-level floating controls. Thus the supported native direction is system material and controls around the retained information architecture; custom-painted glass is not required for current platform appearance. — [Adopting Liquid Glass](https://developer.apple.com/documentation/TechnologyOverviews/adopting-liquid-glass), [Build an AppKit app with the new design](https://developer.apple.com/videos/play/wwdc2025/310/) (confidence: HIGH)

### State representation and refresh ownership

- Native OpenUsage normalizes provider results into a snapshot with plan, usage lines, refresh time, a successful-partial warning, and a categorized error factory. Its data store independently tracks rendered last-good snapshots, per-provider refreshing state, provider errors, and timestamps from which staleness is derived. This proves that stale presentation, refreshing, partial-warning, and error need not collapse into one nullable payload. — [ProviderSnapshot.swift, lines 3–21](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Models/ProviderSnapshot.swift#L3-L21), [lines 69–87](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Models/ProviderSnapshot.swift#L69-L87), [WidgetDataStore.swift, lines 71–86](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Stores/WidgetDataStore.swift#L71-L86), [lines 169–223](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Stores/WidgetDataStore.swift#L169-L223) (confidence: HIGH)
- Native OpenUsage retains last-good data after refresh failure and surfaces a warning or “Outdated” age rather than erasing usable quota. Its provider header separately renders spinner, warning accessibility label, and stale age. This maps to the settled stale-last-good and recoverable-error states, provided the semantic values continue to come verbatim from Rust. — [Refreshing, lines 33–50](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/docs/refreshing.md#L33-L50), [ProviderSectionHeader.swift, lines 70–100](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Views/ProviderSectionHeader.swift#L70-L100) (confidence: HIGH)
- Terminal OpenUsage is the strongest external match for centralized refresh ownership: a daemon continuously collects and persists provider snapshots, exposes a unified read model over a Unix-domain socket, and leaves the TUI as a thin read-model client. The server polls accounts concurrently with timeout/backoff and ingests account-keyed results; the client contains only socket/read-model operations. — [Daemon overview, lines 6–84](https://github.com/janekbaraniewski/openusage/blob/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0/docs/site/docs/daemon/overview.md#L6-L84), [server_poll.go, lines 12–137](https://github.com/janekbaraniewski/openusage/blob/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0/internal/daemon/server_poll.go#L12-L137), [client.go, lines 23–117](https://github.com/janekbaraniewski/openusage/blob/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0/internal/daemon/client.go#L23-L117) (confidence: HIGH)
- Terminal OpenUsage’s view runtime ensures the daemon is available, reads only its read model, and broadcasts changed frames after fingerprinting. Its TUI carries monotonic request IDs and ignores older or wrong-window responses, including not-ready frames that would overwrite usable data during refresh. These patterns prevent presentation races without moving freshness authority into the view. — [runtime.go, lines 63–97](https://github.com/janekbaraniewski/openusage/blob/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0/internal/daemon/runtime.go#L63-L97), [lines 148–255](https://github.com/janekbaraniewski/openusage/blob/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0/internal/daemon/runtime.go#L148-L255), [model_input.go, lines 240–260](https://github.com/janekbaraniewski/openusage/blob/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0/internal/tui/model_input.go#L240-L260) (confidence: HIGH)
- CodexBar’s coordinator is a useful single-process single-flight reference: it stores running refreshes and waiters, coalesces callers into existing work, and resolves them from one task. It does not establish cross-process authority, so the algorithm belongs inside the jackin❯ broker rather than inside each CLI, desktop, console, or Capsule presentation. — [ProviderRefreshCoordinator.swift, lines 3–76](https://github.com/steipete/CodexBar/blob/e7779924f98a3c1533fd517bf91f3d4d49f14f64/Sources/CodexBar/ProviderRefreshCoordinator.swift#L3-L76), [lines 129–198](https://github.com/steipete/CodexBar/blob/e7779924f98a3c1533fd517bf91f3d4d49f14f64/Sources/CodexBar/ProviderRefreshCoordinator.swift#L129-L198), [UsageStore+Refresh.swift, lines 145–163](https://github.com/steipete/CodexBar/blob/e7779924f98a3c1533fd517bf91f3d4d49f14f64/Sources/CodexBar/UsageStore%2BRefresh.swift#L145-L163) (confidence: HIGH)

### Prohibited reference patterns

- Native OpenUsage’s dashboard includes total spend, token/cost breakdown, provider cost ranking, and a 30-day usage trend. Terminal OpenUsage promotes spend/history analytics and quota-pace projections. TermRock’s `MetricsDashboard` pattern is explicitly designed for sparklines, time ranges, comparisons, and trends. Those domain patterns conflict with jackin❯ usage surfaces; only neutral layout/state primitives are reusable. — [native OpenUsage dashboard, lines 17–48](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/docs/dashboard.md#L17-L48), [terminal OpenUsage README, lines 217–232](https://github.com/janekbaraniewski/openusage/blob/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0/README.md#L217-L232), [usage projections, lines 1–60](https://github.com/janekbaraniewski/openusage/blob/fb1bc96cdb5fa8e0cf42dbee31e7ca468cbdb1b0/docs/site/docs/guides/usage-projections.md#L1-L60), [TermRock metrics_dashboard.rs, lines 4–25](https://github.com/tailrocks/termrock/blob/29a16b5bff84ea8609854711b774e87acbc456cc/crates/termrock/src/patterns/metrics_dashboard.rs#L4-L25) (confidence: HIGH)
- Native OpenUsage’s CLI can construct providers and force a refresh, while its application store separately owns timer/manual refresh, in-flight guards, cache, and backoff. Copying that ownership split would create an independent CLI refresh authority, contrary to the settled one-broker rule; only its shared projection/serialization boundary is reusable. — [Architecture, lines 23–31](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/docs/architecture.md#L23-L31), [Refreshing, lines 3–31](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/docs/refreshing.md#L3-L31), [WidgetDataStore.swift, lines 191–312](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Stores/WidgetDataStore.swift#L191-L312) (confidence: HIGH)
- Terminal OpenUsage documents that registered tiles persist through unknown/error states and keep retrying, and its durable database feeds the read model. Inference against jackin❯’s settled current-discovery membership rule: copying those persistence semantics wholesale could retain accounts no longer in current discovery. ## Candidate directions
