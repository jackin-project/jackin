## Codex and Z.AI window classification

- **Codex needs duration-first classification with a constrained slot fallback.** Upstream explicitly documents the failure case: a temporarily sole weekly limit can occupy `primary_window`. OpenUsage first matches an exact known duration (5 hours or 1 week), then uses historical primary→session and secondary→weekly mapping only when duration is absent or unfamiliar. This preserves semantic identity under slot movement without guessing that every novel duration is one of the two headline windows. — [CodexUsageMapper.swift, lines 106–176](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Providers/Codex/CodexUsageMapper.swift#L106-L176) (confidence: HIGH)
- The current crate retains both HTTP `limit_window_seconds` and app-server `windowDurationMins`, but assigns the main response's primary and secondary objects directly to Session and Weekly. Additional per-limit-ID objects repeat that positional assumption. The architecture therefore carries sufficient duration evidence but does not use it for semantic classification. — `crates/jackin-usage/src/usage/codex.rs:431-468`, `crates/jackin-usage/src/usage/codex.rs:519-565`, `crates/jackin-usage/src/usage/codex.rs:646-686` (confidence: HIGH)
- **Z.AI should classify recognized percentage-limit entries by their explicit `(unit, number)` duration, not by array position or shortest/longest rank.** The upstream Z.AI plugin proves the quota endpoint and raw auth-header convention, but labels every `TOKENS_LIMIT` as “5 Hour”; OpenUsage recognizes both current `CREDIT_LIMIT` and legacy `TOKENS_LIMIT`, maps sub-day durations to Session and multi-day durations to Weekly, rejects malformed recognized entries, and ignores unknown units. — [official query-usage.mjs, lines 44–60 and 87–123](https://github.com/zai-org/zai-coding-plugins/blob/0446d0bb0bc537d97d3ab3664c4b8b9c4a0e1254/plugins/glm-plan-usage/skills/usage-query-skill/scripts/query-usage.mjs#L44-L60), [lines 87–123](https://github.com/zai-org/zai-coding-plugins/blob/0446d0bb0bc537d97d3ab3664c4b8b9c4a0e1254/plugins/glm-plan-usage/skills/usage-query-skill/scripts/query-usage.mjs#L87-L123), [ZAIUsageMapper.swift, lines 63–92 and 109–144](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Providers/ZAI/ZAIUsageMapper.swift#L63-L92) (confidence: HIGH for endpoint/fields and classifier behavior; MED for undocumented provider stability)
- The current Z.AI adapter sorts by duration, calls the shortest token entry Session only when two exist, and always calls the longest/sole token entry Weekly. A sole 5-hour entry is therefore mislabeled Weekly; malformed or unknown durations can also acquire meaning through array cardinality. — `crates/jackin-usage/src/usage/zai.rs:123-164`, `crates/jackin-usage/src/usage/zai.rs:183-219` (confidence: HIGH)
- Planning fixtures can therefore freeze this explicit combination: exact recognized duration owns semantic classification; historical Codex slot names are fallback only when duration is unavailable/unrecognized; Z.AI has no positional fallback because its array has no semantic slot contract; malformed recognized durations remain structured invalid/unclassified evidence rather than fabricated headline identity. This is a finding from the demonstrated contracts, not a new product decision. (confidence: HIGH for Codex; MED-HIGH for Z.AI)

## Grok supported source

- **The supported REST source is the Grok CLI proxy, not the direct `grok.com` grpc-web scan.** Official Grok Build exposes ACP method `x.ai/billing`, but its handler itself performs authenticated `GET {cli_chat_proxy_base}/billing?format=credits`, using the CLI access key, token-auth marker, user ID, and client-version headers. It decodes JSON into the complete current/legacy billing shape: percentage, current weekly/monthly period, on-demand cap/usage, prepaid balance, unified-billing flag, and subscription tier enrichment. — [billing.rs, lines 1–12 and 60–124](https://github.com/xai-org/grok-build/blob/19d42e35c07a9c9244f03f6df0c4c353f970d4f9/crates/codegen/xai-grok-shell/src/extensions/billing.rs#L1-L12), [lines 148–161 and 200–278](https://github.com/xai-org/grok-build/blob/19d42e35c07a9c9244f03f6df0c4c353f970d4f9/crates/codegen/xai-grok-shell/src/extensions/billing.rs#L148-L161) (confidence: HIGH)
- ACP is consequently a supported transport facade over the same REST contract, but spawning an agent process adds lifecycle/RPC failure modes and does not yield a richer quota payload. OpenUsage calls the identical stable CLI route directly at `https://cli-chat-proxy.grok.com/v1/billing?format=credits`, calls `/v1/settings` for tier metadata, and shares the CLI token-refresh path. — [GrokUsageClient.swift, lines 34–81](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Providers/Grok/GrokUsageClient.swift#L34-L81), [provider contract, lines 31–33](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/docs/providers/grok.md#L31-L33) (confidence: HIGH)
- The crate currently tries ACP first, then posts a bearer token to the direct `grok.com/grok_api_v2.GrokBuildBilling/GetGrokCreditsConfig` grpc-web endpoint and wire-scans protobuf. That fallback is not the route demonstrated by the official CLI source, has a narrower percent/reset projection, and broadens protocol fragility without broadening the trusted credential type. — `crates/jackin-usage/src/usage/grok.rs:417-426`, `crates/jackin-usage/src/usage/grok.rs:434-501`, `crates/jackin-usage/src/usage/grok.rs:528-672` (confidence: HIGH)
- Secrets boundary remains unchanged: local Grok CLI auth file; access/refresh credential types only; values never enter projection, logs, IDs, or fixtures. REST uses the same credential material the official CLI handler uses. (confidence: HIGH)

## OpenCode Go contract

- **Authentication is an API credential stored under provider entry `opencode-go` in OpenCode's data-directory `auth.json`, sent as `Authorization: Bearer …`.** OpenCode's current auth schema defines API records as `{type:"api", key, metadata?}` and stores the file at the global data path with mode `0600`; OpenUsage reads only the non-empty `opencode-go` API entry and treats absent, unreadable, malformed, and present-but-wrong-shape states distinctly. — [OpenCode auth schema/storage, lines 10–35 and 58–89](https://github.com/anomalyco/opencode/blob/11e8110f9e6863369d361d31f601cecc8202c9c6/packages/opencode/src/auth/index.ts#L10-L35), [OpenCodeAuthStore.swift, lines 21–51](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Providers/OpenCode/OpenCodeAuthStore.swift#L21-L51) (confidence: HIGH)
- **The endpoint is now implemented upstream:** `GET https://opencode.ai/zen/go/v1/usage`. It requires an exact Bearer token, resolves that key internally to `userID` plus `workspaceID`, requires an active Go entitlement, and returns `{usage:{rolling,weekly,monthly}}`; each window contains `status` (`ok` or `rate-limited`), integer `percent`, and ISO-8601 `resetsAt`. Rolling uses the configured duration and last-update timestamp; weekly uses calendar week bounds; monthly uses subscription-anchored month bounds. — [usage route, lines 10–111 and 113–157](https://github.com/anomalyco/opencode/blob/11e8110f9e6863369d361d31f601cecc8202c9c6/packages/console/app/src/routes/zen/go/v1/usage.ts#L10-L111), [subscription calculations, lines 53–153](https://github.com/anomalyco/opencode/blob/11e8110f9e6863369d361d31f601cecc8202c9c6/packages/console/core/src/subscription.ts#L53-L153) (confidence: HIGH)
- Failure semantics are explicit: missing or rejected key is HTTP 401 with typed `AuthError`; valid key without Go entitlement is HTTP 403 with typed `EntitlementError`; a successful response is HTTP 200 JSON. OpenUsage additionally treats malformed success payloads as invalid response and requires numeric percent for all three windows. — [usage route, lines 10–29, 55–71, and 95–110](https://github.com/anomalyco/opencode/blob/11e8110f9e6863369d361d31f601cecc8202c9c6/packages/console/app/src/routes/zen/go/v1/usage.ts#L10-L29), [OpenCodeUsageMapper.swift, lines 14–50](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Providers/OpenCode/OpenCodeUsageMapper.swift#L14-L50) (confidence: HIGH)
- **Stable account identity is not exposed by the response.** The server internally resolves both workspace and user IDs but serializes neither; local `auth.json` supplies only provider entry/type/key, and the key is a secret that must not become a canonical ID. Thus the supported contract proves one credential binding and three stable window names, but not a durable cross-source account identifier or display label. Planning must preserve a typed provisional/unresolved identity until non-secret provider evidence exists; `opencode-go`, source path, key fingerprint, or discovery ordinal cannot be claimed as the real account. — [usage route, lines 31–53 and 73–93](https://github.com/anomalyco/opencode/blob/11e8110f9e6863369d361d31f601cecc8202c9c6/packages/console/app/src/routes/zen/go/v1/usage.ts#L31-L53), [auth schema, lines 23–27](https://github.com/anomalyco/opencode/blob/11e8110f9e6863369d361d31f601cecc8202c9c6/packages/opencode/src/auth/index.ts#L23-L27) (confidence: HIGH)
- The current crate has no OpenCode fetch, auth resolver, or buckets: it always returns `Unsupported` with an adapter-pending error. — `crates/jackin-usage/src/usage.rs:658-683` (confidence: HIGH)

## Settled-contract verification

- **Codex `individual_limit`: verified provider contract, missing crate extraction.** Current official app-server protocol carries `individualLimit` inside every rate-limit snapshot with string `limit`, string `used`, integer `remainingPercent`, and epoch `resetsAt`; official tests include it on the main Codex limit. The crate's app-server structs omit the field entirely. This supports the settled monthly money-cap window without token pricing/history. — [official account protocol, lines 547–576 and 671–690](https://github.com/openai/codex/blob/39073ca3a758224488aa3da99b1d5bfec37a8091/codex-rs/app-server-protocol/src/protocol/v2/account.rs#L547-L576), [official rate-limit fixture](https://github.com/openai/codex/blob/39073ca3a758224488aa3da99b1d5bfec37a8091/codex-rs/app-server/tests/suite/v2/rate_limits.rs), `crates/jackin-usage/src/usage/codex.rs:519-565` (confidence: HIGH)
- **Claude extra windows: verified as shape families, not a frozen key catalog.** The crate now handles authoritative `limits` entries for `session`, `weekly_all`, and arbitrary named `weekly_scoped` models, backfills legacy `five_hour`, `seven_day`, Sonnet, Opus, and Routines windows, and surfaces rotating unknown top-level keys only when they are positive dollar-budget quota allocations. OpenUsage independently demonstrates Fable under `limits` and capped `extra_usage`. Unknown plain utilization windows remain intentionally unproven rather than auto-promoted. — `crates/jackin-usage/src/usage/claude.rs:699-760`, `crates/jackin-usage/src/usage/claude.rs:909-999`, `crates/jackin-usage/src/usage/claude.rs:1020-1080`, [ClaudeUsageMapper.swift, lines 26–36 and 126–171](https://github.com/robinebers/openusage/blob/70acd4f4e9cc79951d83f416295e22ef43b9696b/Sources/OpenUsage/Providers/Claude/ClaudeUsageMapper.swift#L26-L36) (confidence: HIGH for implemented families; MED for undocumented future aliases)
- **Z.AI plan endpoint: verified reference behavior, undocumented provider stability.** `/api/biz/subscription/list` is a best-effort plan-name request; quota remains usable when it fails. - **MiniMax money cap: presentation contract verified; provider extraction not verified.** F22 is explicitly a design fixture proving how a provider-supplied cap renders. Current MiniMax response structs contain plan titles and interval/weekly count/percent/reset fields only; no inspected primary/reference source established actual MiniMax money field names or endpoint shape. Planning must retain F22 as canonical projection/presentation proof, but cannot describe a MiniMax money-cap adapter as source-ready. — `native/Design/UnifiedAgentUsage/Fixtures.md:363-372`, `crates/jackin-usage/src/usage/minimax.rs:76-144` (confidence: HIGH for fixture and current gap; LOW for provider availability)
- **`Not started`: semantics verified only where provider evidence is explicit.** OpenUsage documents a source where an untouched rolling 5-hour window is distinguishable and suppresses the reset countdown, but that evidence is Antigravity-specific, not a generic 100%-remaining rule and not proof that Codex, Z.AI, Grok, OpenCode, Claude, or MiniMax expose the same state. OpenCode's successful payload has only `ok|rate-limited`, percent, and reset; it does not expose untouched state. ## Planning proof obligations now made concrete

- Codex fixtures need swapped-slot, sole-weekly-in-primary, missing-duration fallback, unfamiliar-duration fallback, and conflicting-duration/slot cases for both main and additional limit IDs.
- Z.AI fixtures need sole 5-hour, sole weekly, reordered dual windows, current `CREDIT_LIMIT`, legacy `TOKENS_LIMIT`, malformed duration, unknown unit, and independent `TIME_LIMIT` cases.
- Grok transport fixtures need REST success for current and legacy JSON shapes, 401/403 refresh-once behavior, settings failure with usable billing, malformed billing, and proof no production grpc-web wire scan remains a supported source.
- OpenCode fixtures need absent/unreadable/malformed/wrong-shape local auth, 401 `AuthError`, 403 `EntitlementError`, 200 rolling/weekly/monthly parsing, malformed/missing window values, stable window IDs, and explicit provisional identity without deriving identity from secret material.
- The existing provider-focused Rust suites are useful parser regression lanes, but none proves these target contracts end to end; zero matching tests must remain a failed gate under the verification-ledger rule. No tests were run for this read-only evidence chapter because no current fixture claims the newly enumerated cases. (confidence: HIGH)

## Closed research questions

1. Codex uses exact known duration first and slot only as a missing/unfamiliar-duration fallback; Z.AI uses recognized explicit duration with no positional fallback.
2. Grok's official implementation establishes CLI-proxy REST as the underlying supported quota contract; ACP is its facade, while direct grpc-web wire scanning is not the demonstrated supported lane.
3. OpenCode Go uses the `opencode-go` API credential and a stable rolling/weekly/monthly response/error contract, but exposes no durable non-secret account identity; the canonical graph must represent that limitation explicitly.

These findings close desk research. Authenticated payload capture remains implementation fixture/proof work, not an open product decision.
