# 02 — Apple-native design and distribution evidence
Vetted: 2026-08-20
Questions: What do current primary Apple sources establish for a macOS 26 menu-bar status-item app with a popover, retained two-pane Usage window, Settings, native lists/tables and explicit data states; what are the current API/version gates for keyboard, focus, accessibility, localization, and multi-display behavior; and what do Apple and Homebrew currently require or verify for direct distribution?
Informs: unified-agent-usage
Method: web (official Apple and Homebrew primary sources; Context7 tools were unavailable in this session)

## Findings
### What macOS 26 Liquid Glass behavior belongs to system components?
- An app linked with the Xcode 26 SDK receives the macOS 26 design in standard controls and structural components; an Xcode 16-built app keeps its earlier appearance when run on macOS 26. Apple identifies standard SwiftUI/AppKit bars, sheets, popovers, controls, `NavigationSplitView`, `NSToolbar`, and `NSSplitView` as the system-owned path that automatically adopts Liquid Glass and adapts it for overlap, focus, Reduce Transparency, and Reduce Motion. — [Adopting Liquid Glass](https://developer.apple.com/documentation/TechnologyOverviews/adopting-liquid-glass), [Platforms State of the Union, WWDC25](https://developer.apple.com/videos/play/wwdc2025/102/) (confidence: HIGH)
- Apple defines Liquid Glass as the functional layer for controls and navigation, not the content layer. Its current guidance says to remove custom backgrounds that interfere with standard navigation components and to limit custom glass to important functional elements. — [Adopting Liquid Glass](https://developer.apple.com/documentation/TechnologyOverviews/adopting-liquid-glass) (confidence: HIGH)
- The custom SwiftUI APIs `glassEffect(_:in:)` and `GlassEffectContainer` and the AppKit classes `NSGlassEffectView` and `NSGlassEffectContainerView` are available on macOS 26.0+. Apple says nearby custom glass elements typically use one container for visually correct shared sampling and rendering; `NSGlassEffectView.contentView` is the supported embedding relationship, and arbitrary sibling/subview z-order is not guaranteed. — [`glassEffect(_:in:)`](https://developer.apple.com/documentation/swiftui/view/glasseffect(_:in:)), [`GlassEffectContainer`](https://developer.apple.com/documentation/swiftui/glasseffectcontainer), [`NSGlassEffectView`](https://developer.apple.com/documentation/appkit/nsglasseffectview), [`NSGlassEffectContainerView`](https://developer.apple.com/documentation/appkit/nsglasseffectcontainerview), [`contentView`](https://developer.apple.com/documentation/appkit/nsglasseffectview/contentview) (confidence: HIGH)
- On macOS 26, AppKit automatically puts interactive toolbar items on glass and groups toolbar controls by control type. `NSToolbarItem.Style`, `backgroundTintColor`, `NSView.LayoutRegion`, `NSView.prefersCompactControlSizeMetrics`, and SwiftUI `ToolbarSpacer` are current toolbar/layout APIs; Apple describes `isBordered = false` for noninteractive toolbar text/status that would otherwise resemble a button. — [Build an AppKit app with the new design](https://developer.apple.com/videos/play/wwdc2025/310/), [`NSToolbarItem.Style`](https://developer.apple.com/documentation/appkit/nstoolbaritem/style-swift.enum), [`backgroundTintColor`](https://developer.apple.com/documentation/appkit/nstoolbaritem/backgroundtintcolor), [`NSView.LayoutRegion`](https://developer.apple.com/documentation/appkit/nsview/layoutregion), [`prefersCompactControlSizeMetrics`](https://developer.apple.com/documentation/appkit/nsview/preferscompactcontrolsizemetrics), [`ToolbarSpacer`](https://developer.apple.com/documentation/swiftui/toolbarspacer) (confidence: HIGH)
- AppKit’s macOS 26 sidebar/inspector appearance is owned by `NSSplitViewController` plus correctly constructed sidebar/inspector `NSSplitViewItem`s. `NSSplitViewItemAccessoryViewController` and top/bottom accessory attachment APIs are macOS 26.0+; the explicit `NSScrollEdgeEffectStyle` and `preferredScrollEdgeEffectStyle` customization APIs are macOS 26.1+, while Apple describes automatic scroll-edge effects beneath toolbar, titlebar, and split-item accessories in the macOS 26 design. — [Build an AppKit app with the new design](https://developer.apple.com/videos/play/wwdc2025/310/), [`NSSplitViewItemAccessoryViewController`](https://developer.apple.com/documentation/appkit/nssplitviewitemaccessoryviewcontroller), [`NSScrollEdgeEffectStyle`](https://developer.apple.com/documentation/appkit/nsscrolledgeeffectstyle), [`preferredScrollEdgeEffectStyle`](https://developer.apple.com/documentation/appkit/nssplitviewitemaccessoryviewcontroller/preferredscrolledgeeffectstyle) (confidence: HIGH)
- Apple’s macOS 26 mini, small, and medium control metrics are taller than their earlier metrics. Standard controls acquire current metrics automatically; `prefersCompactControlSizeMetrics` opts a view subtree into macOS 15-and-earlier compact metrics. — [Build an AppKit app with the new design](https://developer.apple.com/videos/play/wwdc2025/310/), [`prefersCompactControlSizeMetrics`](https://developer.apple.com/documentation/appkit/nsview/preferscompactcontrolsizemetrics) (confidence: HIGH)

### What do current native status-item, popover, retained-window, and Settings APIs own?
- SwiftUI `MenuBarExtra` is macOS 13.0+. It owns a persistent system-menu-bar control; `.menuBarExtraStyle(.window)` owns a “popover-like window” for data-rich standard controls, while `.menu` owns a pull-down menu. Its string/image initializers use the supplied title for accessibility, `isInserted` tracks user removal, `LSUIElement = true` suppresses Dock/app-switcher presence for a menu-bar-only app, and a menu-bar-only app terminates if the user removes its extra. — [`MenuBarExtra`](https://developer.apple.com/documentation/swiftui/menubarextra), [`MenuBarExtraStyle`](https://developer.apple.com/documentation/swiftui/menubarextrastyle) (confidence: HIGH)
- The AppKit equivalents are `NSStatusBar.system.statusItem(withLength:)`/`NSStatusItem` and `NSPopover` (the latter macOS 10.7+). `NSStatusItem.button` owns the status-bar control; `NSPopover` owns anchoring, automatic positioning, movement with its positioning view, transient/semitransient/application-defined dismissal behavior, and optional detachment. — [`NSStatusItem`](https://developer.apple.com/documentation/appkit/nsstatusitem), [`NSPopover`](https://developer.apple.com/documentation/appkit/nspopover) (confidence: HIGH)
- Apple’s `NSStatusBar` reference says status items occupy scarce space, are not guaranteed to remain available, and are to be used sparingly with a preference that lets people hide them. Apple’s popover HIG describes a popover as transient, limits it to a small amount of information or a few related tasks, calls for one popover at a time, and distinguishes explicit dismissal for multiple-selection content. — [`NSStatusBar`](https://developer.apple.com/documentation/appkit/nsstatusbar), [Popovers](https://developer.apple.com/design/human-interface-guidelines/popovers) (confidence: HIGH)
- SwiftUI `Window` is macOS 13.0+ and represents one unique window. The system lists it in the Window menu, and `openWindow(id:)` brings the existing singleton to the front instead of creating another instance. `OpenWindowAction` is macOS 13.0+. — [`Window`](https://developer.apple.com/documentation/swiftui/window), [`OpenWindowAction`](https://developer.apple.com/documentation/swiftui/openwindowaction) (confidence: HIGH)
- `NavigationSplitView` is macOS 13.0+ and owns two- or three-column selection-driven navigation. Apple’s split-view guidance says the selected item in each leading pane remains persistently highlighted to preserve the relationship with detail, and macOS split panes have system dividers and resizing behavior. — [`NavigationSplitView`](https://developer.apple.com/documentation/swiftui/navigationsplitview), [Split views](https://developer.apple.com/design/human-interface-guidelines/split-views) (confidence: HIGH)
- SwiftUI `List` is macOS 10.15+ and owns single-/multi-row selection. SwiftUI `Table` is macOS 12.0+ and owns rows, columns, selection, scrolling, system scrollbar preference, and sortable-column state; when sort descriptors change, the application still sorts the source collection. — [`List`](https://developer.apple.com/documentation/swiftui/list), [`Table`](https://developer.apple.com/documentation/swiftui/table) (confidence: HIGH)
- SwiftUI `Settings` is macOS 11.0+ and causes SwiftUI to own the app-menu Settings item, settings presentation/removal, and equivalent keyboard shortcut. `SettingsLink` and environment `openSettings` are macOS 14.0+ and bring the already-open Settings scene forward. Apple’s macOS HIG identifies Command-Comma, an App-menu Settings item, a stable noncustomizable pane toolbar, the active-pane title, disabled minimize/zoom controls, and restoration of the last pane as the native Settings behavior. — [`Settings`](https://developer.apple.com/documentation/swiftui/settings), [`SettingsLink`](https://developer.apple.com/documentation/swiftui/settingslink), [`openSettings`](https://developer.apple.com/documentation/swiftui/environmentvalues/opensettings), [Settings](https://developer.apple.com/design/human-interface-guidelines/settings) (confidence: HIGH)

### What native components express loading, empty, stale, and error states?
- SwiftUI `ProgressView` is macOS 11.0+ and owns determinate and indeterminate system progress presentation. Apple’s loading guidance assigns determinate progress to work with knowable duration and indeterminate progress otherwise, and says content or placeholders appear as soon as possible instead of a blank surface. — [`ProgressView`](https://developer.apple.com/documentation/swiftui/progressview), [Loading](https://developer.apple.com/design/human-interface-guidelines/loading) (confidence: HIGH)
- SwiftUI `ContentUnavailableView` is macOS 14.0+ and is the system component for content that cannot display because of cases including an empty list, no search results, or a network error; it carries a label, description, and optional actions. — [`ContentUnavailableView`](https://developer.apple.com/documentation/swiftui/contentunavailableview) (confidence: HIGH)
- Apple’s feedback guidance distinguishes passive, contextual status from interruptive alerts: status belongs near the item it describes, while alerts are for critical and ideally actionable information. Its alert guidance explicitly uses cached or placeholder data plus a nonintrusive problem label for startup connectivity failure, rather than an alert. — [Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback), [Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts) (confidence: HIGH)
- Apple’s writing guidance says empty screens expose clear next actions, and error messages appear close to the problem, avoid blame, and state what can be done. The cited guidance does not assign “stale last-good” a separate standard component; within these sources it is expressed as contextual status/feedback beside retained content. — [Writing](https://developer.apple.com/design/human-interface-guidelines/writing), [Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback) (confidence: HIGH)

### What are the current keyboard, focus, VoiceOver, contrast, transparency, and motion contracts?
- Apple’s macOS HIG treats keyboard shortcuts and keyboard-only operation as platform expectations. SwiftUI `keyboardShortcut(_:)` is macOS 11.0+; on macOS the system resolves a shortcut through the key window, main window, then command groups, and activating it is equivalent to the control’s primary action. — [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos/), [`keyboardShortcut(_:)`](https://developer.apple.com/documentation/swiftui/view/keyboardshortcut(_:)) (confidence: HIGH)
- SwiftUI `FocusState` and `focused` are macOS 12.0+ and own observation/programmatic movement of focus. Apple documents that binding the same focus value to two views is ambiguous because programmatic focus selects the first bound view and emits a runtime warning; one view may validly bind to different focus values. Focus-driven activation on macOS is available only when the user enables all-controls keyboard navigation. — [`FocusState`](https://developer.apple.com/documentation/swiftui/focusstate), [`FocusInteractions.activate`](https://developer.apple.com/documentation/swiftui/focusinteractions/activate) (confidence: HIGH)
- SwiftUI introspects standard navigation, list, text-field, slider, and button components and supplies basic accessibility labels and values automatically. Custom elements can add `accessibilityLabel`, `accessibilityValue`, and `accessibilityHint`; Apple’s VoiceOver evaluation criteria require every common task to be navigable and operable without sighted help and all controls to have concise, accurate labels. — [SwiftUI accessibility modifiers](https://developer.apple.com/documentation/swiftui/view-accessibility), [VoiceOver evaluation criteria](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/voiceover-evaluation-criteria) (confidence: HIGH)
- SwiftUI environment values `accessibilityReduceTransparency`, `accessibilityReduceMotion`, `accessibilityDifferentiateWithoutColor`, and `colorSchemeContrast` are macOS 10.15+. Reduce Transparency means mainly-window backgrounds are opaque; Reduce Motion means avoiding large, especially three-dimensional animations; `colorSchemeContrast` updates between standard and increased contrast and cannot be overridden by the app. — [`accessibilityReduceTransparency`](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducetransparency), [`accessibilityReduceMotion`](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion), [`accessibilityDifferentiateWithoutColor`](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilitydifferentiatewithoutcolor), [`colorSchemeContrast`](https://developer.apple.com/documentation/swiftui/environmentvalues/colorschemecontrast) (confidence: HIGH)
- The AppKit equivalents are `NSWorkspace.accessibilityDisplayShouldReduceTransparency` and `.accessibilityDisplayShouldIncreaseContrast` (macOS 10.10+), `.accessibilityDisplayShouldReduceMotion` (macOS 10.12+), and `accessibilityDisplayOptionsDidChangeNotification` for changes. — [`NSWorkspace`](https://developer.apple.com/documentation/appkit/nsworkspace), [`accessibilityDisplayShouldReduceTransparency`](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldreducetransparency), [`accessibilityDisplayShouldIncreaseContrast`](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldincreasecontrast), [`accessibilityDisplayShouldReduceMotion`](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldreducemotion) (confidence: HIGH)
- Apple says system-defined colors carry accessible variants for Increase Contrast and light/dark appearance, and the current SwiftUI documentation directs color/image-only contrast variants into the asset catalog. The HIG also requires information not rely on one sensory channel such as color alone and identifies Accessibility Inspector as the audit tool for the accessibility representation. — [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility/), [`colorSchemeContrast`](https://developer.apple.com/documentation/swiftui/environmentvalues/colorschemecontrast) (confidence: HIGH)
- SwiftUI’s `DynamicTypeSize`/`dynamicTypeSize` API exists on macOS 12.0+, but Apple’s current API discussion says users cannot change it on macOS and it does not affect text size; the current Typography HIG states “macOS doesn’t support Dynamic Type.” The macOS typography baseline is 13-point default and 10-point minimum, while the Accessibility HIG separately states that text enlargement can be supplied through custom UI on platforms without Dynamic Type. — [`dynamicTypeSize`](https://developer.apple.com/documentation/swiftui/environmentvalues/dynamictypesize), [Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility/) (confidence: HIGH)
- Apple’s motion HIG says standard components can adjust motion for accessibility/input settings; custom motion is optional, must not be the sole carrier of important information, and must not hold interaction hostage until animation completes. — [Motion](https://developer.apple.com/design/human-interface-guidelines/motion) (confidence: HIGH)

### What is the current localization contract?
- Xcode String Catalogs are an Xcode 15+ build-tool feature rather than a deployment-target API. Current Xcode discovers most SwiftUI literals accepted as `LocalizedStringKey`, extracts localizable strings on build, supports plural and device variants, and identifies `LocalizedStringResource` as the type for passing localized values outside a view plus `String(localized:)`/`AttributedString(localized:)` for runtime strings. — [Localizing and varying text with a string catalog](https://developer.apple.com/documentation/xcode/localizing-and-varying-text-with-a-string-catalog), [Discover String Catalogs, WWDC23](https://developer.apple.com/videos/play/wwdc2023/10155/) (confidence: HIGH)
- Apple states that system UI frameworks and standard layouts automatically reverse in right-to-left locales in the common case; localization also covers locale-aware plural, number, date, and currency formatting rather than translation alone. — [Right to left](https://developer.apple.com/design/human-interface-guidelines/right-to-left), [Localization](https://developer.apple.com/documentation/xcode/localization) (confidence: HIGH)

### What do primary sources establish for multiple displays and retained placement?
- `NSScreen.screens` returns the current displays, must not be cached, and changes are announced by `didChangeScreenParametersNotification`. `screens[0]` is the primary display with the menu bar and origin `(0, 0)`, while `NSScreen.main` is the screen containing the keyboard-focused window and can differ. — [`NSScreen.screens`](https://developer.apple.com/documentation/appkit/nsscreen/screens) (confidence: HIGH)
- `NSPopover` automatically positions itself relative to its anchor and moves when that positioning view moves. This is the primary-source behavior available for a popover anchored to an `NSStatusItem.button`; the API does not require application-computed display coordinates. — [`NSPopover`](https://developer.apple.com/documentation/appkit/nspopover) (confidence: HIGH)
- SwiftUI `defaultWindowPlacement(_:)` and `WindowPlacementContext` are macOS 15.0+; the context exposes `defaultDisplay.visibleRect` for display-relative initial placement. AppKit `NSWindow.setFrameAutosaveName` owns automatic frame persistence, and AppKit restoration uses a unique identifier, frame-autosave name, restoration class, and `isRestorable`. — [`defaultWindowPlacement(_:)`](https://developer.apple.com/documentation/swiftui/scene/defaultwindowplacement(_:)), [`WindowPlacement`](https://developer.apple.com/documentation/swiftui/windowplacement), [`setFrameAutosaveName(_:)`](https://developer.apple.com/documentation/appkit/nswindow/setframeautosavename(_:)), [Restoring your app’s state with AppKit](https://developer.apple.com/documentation/appkit/restoring-your-app-s-state-with-appkit) (confidence: HIGH)
- Apple’s macOS guidance treats window movement, resizing, hiding/showing, and multi-display extension as user-controlled behavior; its launch guidance says window state and location are among the previous-state details restored on relaunch. — [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos/), [Launching](https://developer.apple.com/design/human-interface-guidelines/launching/) (confidence: HIGH)

### What are the current direct-distribution, notarization, and Homebrew verification facts?
- For distribution outside the Mac App Store, Apple defines Developer ID Application as the certificate for a Mac app and Developer ID Installer as the certificate for a signed installer package. A Developer ID signature plus Apple notarization ticket lets Gatekeeper verify integrity, developer identity, and Apple’s malware scan result. — [Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/), [App code signing process in macOS](https://support.apple.com/guide/security/sec3ad8e6e53/web) (confidence: HIGH)
- Apple’s current notarization prerequisites are valid code signatures on every executable, the applicable Developer ID certificate, Hardened Runtime on app and command-line targets, a secure timestamp, no true `com.apple.security.get-task-allow`, linkage against the macOS 10.9+ SDK, and well-formed XML ASCII entitlements. Hardened Runtime is mandatory for notarization; App Sandbox is optional for direct distribution. — [Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Preparing your app for distribution](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution), [Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime) (confidence: HIGH)
- Apple accepts macOS apps, non-app bundles, UDIF disk images, and flat installer packages for notarization; existing ZIP archives can also be submitted, but a ticket cannot be stapled directly to a ZIP. `notarytool` is the supported command-line uploader (`altool` uploads have been rejected since 2023), and `stapler` attaches the ticket to an app, bundle, disk image, or flat package for offline Gatekeeper lookup. — [Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow) (confidence: HIGH)
- Apple documents `codesign --verify --deep --strict --verbose=2` for recursive signature validation and `spctl -a -t exec -vv`/current `spctl -vvv --assess --type exec` for Gatekeeper-policy assessment. Its end-to-end Gatekeeper test is the exact shipped package downloaded so it receives quarantine, installed into `/Applications`, then launched; successful local signature/notary commands alone do not reproduce that first-launch boundary. — [TN2206: macOS Code Signing In Depth](https://developer.apple.com/library/archive/technotes/tn2206/), [Resolving common notarization issues](https://developer.apple.com/documentation/security/resolving-common-notarization-issues) (confidence: HIGH)
- A Homebrew cask needs `version`, `sha256`, `url`, `name`, `desc`, `homepage`, and at least one artifact stanza such as `app`; Homebrew prefers HTTPS, an immutable versioned release URL, and a checksum whenever possible. An official-cask download must be published by the developer or a publicly endorsed source, must work on the latest macOS it declares, and must not require Gatekeeper or SIP bypass. — [Cask Cookbook](https://docs.brew.sh/Cask-Cookbook), [Acceptable Casks](https://docs.brew.sh/Acceptable-Casks), [Adding Software to Homebrew](https://docs.brew.sh/Adding-Software-to-Homebrew) (confidence: HIGH)
- Homebrew’s current cask contribution proof is `HOMEBREW_NO_INSTALL_FROM_API=1 brew install --cask <CASK>`, `brew uninstall --cask <CASK>`, and `brew lgtm --online`; `brew lgtm --online` runs the relevant online/new-cask audit checks, and Homebrew separately instructs inspection of installed files and user-visible output rather than relying only on exit status. — [How to Open a Homebrew Pull Request](https://docs.brew.sh/How-To-Open-a-Homebrew-Pull-Request), [Adding Software to Homebrew](https://docs.brew.sh/Adding-Software-to-Homebrew) (confidence: HIGH)
- Homebrew verifies a cask’s pinned SHA-256 when present, but its current security documentation says casks install vendor-prebuilt applications under a weaker vendor-trust model than bottles, with `sha256 :no_check` permitted in specified cases. Inference from the separate Homebrew and Apple trust models: cask audit/install does not replace Developer ID, notarization, stapling, or Gatekeeper assessment of the public artifact. — [Homebrew Security and Supply Chain](https://docs.brew.sh/Supply-Chain-Security), [Cask Cookbook](https://docs.brew.sh/Cask-Cookbook), [Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/), [Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) (confidence: HIGH)

## Dead ends and contradictions
- Context7 was required as the first documentation source, but this session exposed neither `resolve-library-id` nor `query-docs`; no Context7 result could be obtained. Research continued only with official Apple and Homebrew primary sources.
- Apple names `MenuBarExtra`’s `.window` style a “popover-like window,” not an `NSPopover`. The public API documentation does not promise `NSPopover` behavior, delegate hooks, detachment, or class identity for that SwiftUI scene.
- Apple exposes `DynamicTypeSize` to macOS code from macOS 12, but its current API documentation says users cannot change the value on macOS and it does not resize text; the current HIG explicitly says macOS does not support Dynamic Type.
- Homebrew’s official-cask policy requires operation without bypassing Gatekeeper, but it does not state a blanket policy that every accepted cask must be Developer ID-signed and notarized. Developer ID/notarization are the separate Apple direct-distribution trust requirements in scope here.
- macOS 27 beta API/reference material was excluded. Findings and gates above are limited to stable macOS 26 behavior and APIs available through macOS 26.x.

## Open unknowns
- Apple’s public `MenuBarExtra`, `NSStatusItem`, and `NSStatusBar` documentation does not specify which physical display hosts an item when menu bars appear on multiple displays, nor whether opening a separate singleton Usage window from that item chooses the item’s display.
- Apple documents automatic `NSPopover` anchoring and movement, but not the multi-display relocation behavior of SwiftUI’s `.menuBarExtraStyle(.window)` popover-like window.
- No current Apple primary source found a dedicated stale-last-good or partial-provider-error component/API, or a system announcement API specifically for an asynchronously replaced quota table. The cited guidance covers contextual status, cached/placeholder content, progress, unavailable content, and critical alerts.
- Apple’s current macOS HIG establishes legibility sizes and permits custom text-enlargement UI, but no primary source found a systemwide, user-changeable macOS equivalent to Dynamic Type for a SwiftUI desktop app.
