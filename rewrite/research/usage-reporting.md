# Provider usage reporting specification

Status: proposal for review, 2026-11-04. Repository baseline: jackin `feature/openshell-native` at `506751063660608df0b4f45af65b24f2928282bf` (2026-11-05). The usage crates, account core, CLI usage command, design, and plan were inspected at this baseline. The companion proposal and decision trail added in the later branch commit `b75ee11e3` were reviewed for overlap; that commit did not change those implementation paths. [DESIGN.md](../DESIGN.md) remains authoritative; the implementation status below reflects this baseline. Sanitized results from explicitly authorized, read-only live checks are recorded below. Credential values and raw responses are not included. A credential was accidentally exposed in an earlier research tool result; the incident is described below without reproducing its value. Provider documentation can change; recheck it before implementing.

## Scope and evidence rules

This specification covers how Jackin obtains and reports provider usage, limits, balances, and costs. The companion [agent-provider proposal](agent-provider.md) covers account records and agent bindings; shared identity and credential boundaries are described here only as they affect usage collection. Both proposals remain subordinate to DESIGN.md.

A provider name, a crate, a fixture, or a successful request for one account does not establish support for every product, account, region, or authentication method. The global subscription update below narrows the scope and records the latest request evidence. This report distinguishes **verified** repository behavior and official documentation, **inference** from those facts, **proposal**, and **unknown**. “Undocumented” means this research did not find a provider-supported contract for the exact endpoint, not that access is forbidden by definition. A vendor's UI is not a machine API. Each future support claim names the exact product, credential, metric, endpoint, version, and evidence date.

Current Jackin distinguishes the AI service provider from an OpenShell provider credential object. Accounts have a provider and credential source. Codex is the only supported agent. Usage collectors operate on the host and read credentials from Jackin accounts; they do not use the OpenShell gateway and do not refresh login tokens. D10, D25, and D26 in [DESIGN.md](../DESIGN.md) define these boundaries. The baseline contains collectors for Claude, Codex, Cursor, Gemini, Grok, Kimi, MiniMax, OpenCode, OpenRouter, and Z.AI; Amp, Antigravity, Hermes, and Muse report unsupported. Presence of a collector or fixture does not establish that its provider contract is reliable or its behavior matches a provider subscription.

The CLI display is evidence that its interface showed windows; the direct HTTP result remains a failed independent read and cannot be compared field by field.

The installed Kimi Code 2.4.1 bundle's managed usage function appends `/usages` to its configured coding base URL and sends a bodyless GET with `Authorization: Bearer <access token>` and `Accept: application/json`; it uses an eight-second timeout. The source default is `https://api.kimi.com/coding/v1`, while `KIMI_CODE_BASE_URL` can override the base. The checked global login used the `.ai` base above; do not silently substitute regions. Before its usage fetch, the client calls its freshness helper, which can refresh the login. The later direct read below used the existing token without calling that helper or refreshing it. Installed source and a single-account live read do not establish a public API guarantee. The Cloudflare header on the earlier control response is evidence of an edge component, but does not prove the specific reason for that 403. Do not bypass access controls or interpret a 403 as expired credentials or zero quota.

The installed managed-usage parser reads `usages.limit_5h` and `usages.limit_7d`, including `used_ratio` and `reset_time`; it also recognizes monthly and optional wallet fields. In the installed 2.4.1 bundle, both `/usage` and `/status` call the managed-usage loader for the selected managed provider, which reaches that same fetcher. The user-provided display therefore shows the CLI's own managed quota path, but the runtime's exact token freshness or environment at that moment and the cause of the independent 403 remain unknown. The current [Jackin Kimi collector](../../crates/usage/jackin-usage-provider-kimi/src/lib.rs) instead fixes its host to `.com` and parses legacy `usage` and `limits[]` shapes. Neither shape nor host should be assumed equivalent to the operator's `.ai` account without successful product-matched evidence.

In the installed 2.4.1 parser, wire `usages.limit_5h`, `limit_7d`, `limit_month_total`, and `limit_month_code` map to optional five-hour, weekly, monthly-total, and monthly-code entries. Each requires a finite numeric `used_ratio` or a string coercible by JavaScript `Number` to a finite value; a nonempty `reset_time` string is optional. The `/usage` renderer clamps a finite ratio to 0–1, multiplies it by 100, rounds it, and labels the result used; it parses the reset string with `Date.parse` for a relative duration. It skips omitted windows. Its monthly breakdown treats an absent code ratio as zero when deriving another component; do not copy that assumption into Jackin, because absence is not verified zero. These are version-specific client behaviors; preserve original valid values and unknowns rather than assuming the provider contract guarantees every bound or timestamp format.

The installed 2.4.1 OAuth toolkit resolves its home from nonempty `KIMI_CODE_HOME`, otherwise the user's `.kimi-code` directory. Its default managed provider is `managed:kimi-code`; its default OAuth reference resolves to the storage name `kimi-code` and file `<kimi-home>/credentials/kimi-code.json`. The source validates the storage name as a basename before constructing the filename. The token wire shape includes `access_token`, `refresh_token`, `expires_at`, `scope`, `token_type`, and `expires_in`; the installed parser treats `expires_at` as Unix seconds. Resolve the configured provider and region first, read only the selected access token in memory, and treat missing or expired credentials as unavailable. Do not print or copy the file, use the refresh token, or assume this default path covers every configured profile. This storage recipe is installed-source evidence; the later scoped-slot request below is the live evidence for this account.

## Existing architecture and corrections

The [facade model](../../crates/usage/jackin-usage/src/model.rs) is schema 1: each named account has one provider, freshness, and either windows or an unavailable reason. Its `WindowKind` also represents credits and spending. A `Percent` is restricted to 0–100, and the facade clamps reported percentages into that range. The Codex collector also clamps individual-limit remaining amounts to zero with `Money::clamped_at_zero`. Therefore the current facade cannot preserve all provider-reported overage or negative remaining amounts. It cannot represent both successful observations and a failure from another endpoint, distinguish stale data from the cause of refresh failure, or describe scope and source precisely. An empty window list must not mean zero usage. Preserving provider-reported overage without clamping is a proposed future behavior, not current behavior.

The [host](../../crates/usage/jackin-usage/src/host.rs) runs up to four accounts concurrently, caches for 120 seconds, or 300 seconds for Claude, honors a retry hold after rate limiting, and can return stale data on transient failure. [Cache](../../crates/usage/jackin-usage/src/cache.rs) writes private mode 0600 under a lock and merges edits. Its fingerprint includes provider and credential source location; for a 1Password source it also includes the optional account selector. It does not include the identity of the credential material at that source. Replacing a credential at the same path, environment name, or 1Password reference and account can show the old account's cached data. Concurrent same-account completions can overwrite a newer result. Fix identity and ordering before expanding support. Do not hash low-entropy secrets as a durable identity.

[Credential resolution](../../crates/usage/jackin-usage/src/credential.rs) reads environment, `op read` (including the configured optional account selector), a file, or Codex login. It infers login JSON by a leading `{` and does not refresh. [Dispatch](../../crates/usage/jackin-usage/src/dispatch.rs) maps both HTTP 401 and 403 to expired login, including API-key and permission failures. [OpenRouter](../../crates/usage/jackin-usage-provider-openrouter/src/lib.rs) tolerates credits 403 without a partial-result reason. Inspect the Grok collector's signed-cent magnitude and missing on-demand defaults against the real contract before treating either as a valid balance. Inspect OpenCode's fixed 30-day monthly duration against actual calendar and response semantics. These are correctness investigations, not claims that the upstream contract has been proven.

The current resolver does not automatically read every installed agent's credential store. [Claude's parser](../../crates/usage/jackin-usage-provider-claude/src/lib.rs) accepts a raw token or login JSON with `claudeAiOauth.accessToken` or `claudeAiOauth.access_token`, but does not resolve the observed Keychain login itself. [Codex](../../crates/usage/jackin-usage-provider-codex/src/lib.rs) reads `tokens.access_token` from login JSON and receives the ChatGPT account context separately; the special source resolves `<codex-home>/auth.json`. [OpenCode Go's parser](../../crates/usage/jackin-usage-provider-opencode/src/lib.rs) accepts a raw token or an `opencode-go` entry in login JSON, but cannot directly consume the observed SQLite credential table. [Gemini's parser](../../crates/usage/jackin-usage-provider-gemini/src/lib.rs) accepts a token or JSON `access_token` and optional `expiry_date`, not the observed Antigravity Go-keyring record; its Code Assist requests are also different from the Antigravity quota-summary request. Z.AI, MiniMax, and OpenRouter dispatch require the resolver's token variant rather than a login variant; this does not generally validate the token format or accept an arbitrary agent database record. A discovered login does not itself establish a usable Jackin credential source. Any future adapter must resolve the selected product-specific source securely without printing secrets or assuming that a credential for one product covers another.

The [CLI](../../crates/jackin/src/commands/usage.rs) reports every configured account, uses cached mode, and prints text or schema 1 JSON. Before text output, window labels and amount units pass through terminal-text sanitization. It exits successfully for per-account unavailability, and a successful empty window list prints no account line. [P6.3](../PLAN.md) marks the port complete, not all vendor integrations validated. The only recorded live provider run is [Codex P6.3](../evidence/P6.3-usage-codex.md): one ChatGPT account returned a weekly window and credits; no refresh was performed. Fixture data do not establish vendor support. The planned console uses the external `jackin-console` application through `jackin-tui`; [D27](../DESIGN.md) assigns screens, wording, and visual approval to terminal-components-baseline. The current [console bridge](../../crates/jackin-tui/src/console.rs) is a stub. Usage wiring in P9.3 and live console proof in P9.5 remain unchecked in [PLAN.md](../PLAN.md). No new jackin-local renderer is appropriate.

## Proposed design

### Alternatives and recommendation

1. Extend `LimitWindow` and keep provider-specific exceptions. Small initial diff, but it preserves false equivalence between credits, expense and rate windows and cannot express partial failure. Reject.
2. Store raw vendor JSON and let CLI and console interpret it. Retains details but duplicates provider logic, leaks sensitive fields, and makes stable output impossible. Reject.
3. Recommend a typed facade with explicit per-account capability and observation records. Provider adapters own parsing, scope and source semantics. CLI and console consume the same report. This keeps the existing facade and layer boundary while replacing the schema rather than adding a compatibility shim.

Proposal: the usage facade needs a stable non-secret account identity and enough product, region, account-type and credential-source context to distinguish collections. The account record and agent or workspace bindings belong to the companion agent-provider proposal rather than a second schema here. Multiple accounts of one provider remain independent. A launch's account selection does not imply the usage credential has the same scope, and usage failure never blocks a launch. Deduplicate only when the vendor provides a reliable shared scope identity; never sum accounts with overlapping organization or project scope by default. This requires an explicit amendment to D25/D26 and account configuration before implementation, not an implicit expansion of D04's Codex-only agent policy.

A report has a generation timestamp, version, account ID, provider product, credential capability, collection time, source classification and exact scope. Each observation is one of: rate or quota window (metric, resource/model, scope, period or explicit boundaries, used and limit or remaining, unit and reset); balance/credits (exact decimal amount, unit/currency and scope); or spending (exact decimal, currency, period and scope). Keep vendor-reported used and remaining independently. Compute a derivative only when units, interval and semantics are compatible and label it derived. Preserve overage, negative balances, unlimited and unknown distinctly. Do not fabricate a reset from a monthly label or infer a total from a percentage. Use integer decimal coefficients and scale or equivalent exact decimal representation for money and credits; validate range and unit. Each capability has `available`, `unsupported`, `not_configured`, `permission_denied`, `authentication_failed`, `expired`, `rate_limited`, `temporarily_unavailable`, or `invalid_response`, plus safe details and optional retry time. Add banked reset inventory as a separate observation, including count, optional individual expiry, covered pools and freshness, as detailed in the global subscription research below. A result can contain observations and per-capability failures simultaneously. Unsupported means evidence for the exact product and method is absent or prohibits implementation, not that the vendor has no possible interface.

### Credentials and trust

Resolve only the selected typed source at request time. Reuse `op` for 1Password and preserve existing private host sources where authorized. Separate API, admin, management and subscription credentials; never upgrade privileges or use an inference key as an admin key implicitly. Config stores references and non-secret metadata, not token values. A source location is not a credential identity. Prefer an explicit account identity or credential generation controlled by the user and invalidate the cache on credential replacement. An explicit user-managed generation alone cannot detect external rotation. Persistent cache reuse is permitted only when an authoritative source supplies a non-secret revision that changes on every credential replacement, or when a fresh authenticated response proves the same stable account identity. Otherwise withhold cached observations before a fresh fetch; an explicit rebind clears old data but does not make undetectable later rotation safe. Do not persist a secret-derived fingerprint. Secret-bearing requests use TLS and provider-defined URLs; the shared client disables redirects and emits safe errors. Successful JSON responses are capped at 1 MiB before parsing. Never log headers, token strings, raw responses, account IDs or provider error bodies without a verified redaction policy. Usage data itself is sensitive; store only the minimum normalized data in a private file and support deletion.

Default to no token refresh, consistent with D25. A future refresh implementation requires an official documented grant, explicit ownership, secure storage and atomic rotation, concurrency control, revocation handling, and evidence that it cannot silently invalidate another client. A gateway-held launch token is not automatically accessible to host collectors. Establish a supported and secure host credential source or report unavailable. Do not extract gateway secrets, scrape browser cookies, borrow undocumented client identities, or send consumer subscription credentials to arbitrary endpoints. The existing undocumented direct requests need an explicit product and security decision before continued default polling; vendor documentation and allowed use must be established independently. Opt-in alone is not proof of authorization.

### Collection, cache and failure semantics

Proposal: dispatch each supported provider-product-auth capability through a bounded, cancellable read-only adapter. Each declares supported source, endpoint, data scope, timeout, minimum interval and request budget. Coalesce concurrent refreshes by account identity and credential generation. Use a global concurrency cap and per-provider limits; respect `Retry-After` as either seconds or HTTP date, with a bounded retry deadline and jittered exponential backoff for transient read-only failures. Never retry authentication, permission or invalid-response failures automatically. A cancelled request must not commit partial cache data as fresh. The current shared HTTP client disables redirects and caps successful JSON responses at 1 MiB. The proposed report should preserve valid per-endpoint partial success and continue other accounts after one failure.

Cache normalized observations with source, scope, fetch time, identity generation and expiry, in the existing private atomic locked store. Re-read and compare generation and fetch time under the lock so older concurrent responses cannot overwrite newer observations. Define explicit per-provider TTLs once policy is known; treat current 120/300 seconds as existing behavior, not verified vendor rate limits. On transient failure, show stale observations with original fetch time and the current failure; never present them as fresh. On account removal, source change, authorization failure, or identity mismatch, invalidate or withhold data rather than leak a previous account's results. Cache corruption becomes a visible recoverable error rather than fabricated empty usage. Network traffic occurs only on an explicit report or a documented console refresh schedule, with manual refresh still respecting server backoff.

### CLI and console

Proposal: `jackin usage` shows each configured account and scope, every available measurement with units and reset, source freshness, and explicit unsupported or partial reasons. Add account/provider filters and an explicit refresh option with behavior specified before implementation. `--json` returns a versioned structured report with machine-readable statuses, exact decimal strings, timestamps and no raw secrets. Replace schema 1 directly under the no-compatibility rule. Use exit 0 when every selected account has all requested supported capabilities available, including an empty selection; exit 2 for partial results or unsupported capabilities; exit 1 when selected accounts have no available capability because collection or configuration failed; and exit 130 on cancellation. Unsupported-only selection exits 2. A manual refresh bypasses TTL but honors provider backoff and `Retry-After`; if held, report rate-limited with any permitted stale data. Do not turn a single provider's error into missing rows. Stable ordering is by account ID and measurement identity. An empty set is shown as no observations, never as zero.

The console consumes the same facade and renders the same partial, stale, unsupported, scope, reset and privacy semantics. Extend the baseline's `jackin-console` backend model and approved screens in its own repository when needed, with D27 visual reviews and unchanged approved baselines. It must not create a second usage model or polling loop in `jackin-tui`.

### Desired data and reset semantics

For every subscription account, collect the vendor-reported plan, scope, model or shared pool, each available period, used and remaining amount or percentage, and the precise scheduled reset time. A rolling five-hour window is not a daily limit. A fixed 30-day duration is not necessarily a calendar month. A model can share a pool with other models; do not invent separate balances. Distinguish unavailable, not reported, not applicable, and zero. Preserve source timestamps, absolute UTC instants and unknown timezone; localize only for display.

Represent a banked reset separately from scheduled window resets and spendable credits. A banked reset has an available count, optional individual expiry, eligibility, affected windows or model pools, and observation time. Count-only responses remain count-only. Keep the reported count independent from detail rows. Codex explicitly permits a detail list shorter than the count because the backend may cap it; label the list incomplete, preserve valid supplied expiries, and never invent missing dates. If different requests return incompatible snapshots, preserve their timestamps and mark reconciliation uncertain. Never expose redemption IDs in output or persist them when not needed for display. Reporting is read-only; redeeming, buying, and changing settings are outside this specification.

[OpenAI](https://help.openai.com/en/articles/20001498-how-resets-work-in-codex) documents banked, automatically applied and purchased resets as different operations. Banked expiry is per offer, and a reset can change the next scheduled window boundary. [Anthropic](https://support.claude.com/en/articles/17007452-what-is-a-limit-reset) documents optional limit resets and expiry where applicable; its weekly schedule remains on its usual day and time. Neither source proves that all plans have banked resets. For other providers, “not found” means research found no verified banked-reset contract, not that a reset cannot exist.
