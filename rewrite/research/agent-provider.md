# Proposed agent and provider integration specification

Status: research and per-pair evidence for [D29](../DESIGN.md), with observations through 2026-11-06. D29 replaces the earlier Codex-only D04 and defines the current twelve-tuple catalog. This document does not amend the design or, by itself, establish that any additional tuple is launchable. The evidence is a snapshot, not a lockfile; recheck releases and documentation before implementation.

## Proposed product decisions

- Jackin retains the Codex and ChatGPT-login launch path. D29 catalogs twelve explicit tuples, including unavailable and vendor-blocked entries; a tuple becomes launchable only when it meets its required evidence gates. The earlier [P0.3](../evidence/P0.3-codex.md) records a Linux arm64 live proof, but does not independently certify subscription billing or absence of paid fallback. It is a historical baseline, not automatic certification for additional tuples.
- A launch chooses an agent, provider product, account, and model. A reviewed catalog defines which combinations can run. Requested but unverified combinations remain visible with a reason; they cannot launch.
- The gateway holds launch credentials. An integration that cannot meet the credential and network boundary, vendor authorization, and subscription-only billing requirements remains unavailable. Use stock OpenShell with custom profiles when it satisfies those requirements. The current MVP research and verification use stock OpenShell only; the earlier fork option is not part of these tests.
- Detach, process restart, sandbox restart, and conversation resume are separate actions. Jackin must not claim a conversation resumed without verifying it.
- Each launch has its own agent state. Resuming in a different launch is unavailable until a secure state-transfer contract is implemented and verified for that integration.
- Provider usage reporting is a separate specification. This proposal changes no usage behavior.

## Scope and evidence grades

This specification covers installing, configuring, launching, and operating the requested coding agents with subscription-backed provider access only. API keys are in scope only when they are explicitly issued for the selected subscription and use its allowance. Provider usage checks belong in the separate usage-reporting specification.

This proposal separates the coding-agent executable, inference service, account, credential mechanism, and model. A documented integration is a candidate, not proof that Jackin or OpenShell supports it. **Documented** below means an official source describes the pairing. **Candidate** means there is some relevant official evidence but the exact pairing, authentication, or protocol is not established. **Unverified** includes ambiguous identity and missing documentation. **Supported** means all acceptance evidence in this document exists for the exact version, platform, authentication, and combination. No requested new combination has that evidence. An upstream statement that a model API is OpenAI-compatible does not establish support for the Responses API, tool calls, streaming, or this sandbox.

Historical repository observations below were taken from jackin `feature/openshell-native` at `e7424c03a`; the current checkout has since advanced under D29. The related role branches inspected were [sentinel](https://github.com/jackin-project/jackin-sentinel/tree/20cadb5c6962f96d3a69acc0c90f0fe15982332b), [agent-smith](https://github.com/jackin-project/jackin-agent-smith/tree/4e056e1a56d44be1359bc2b19d6897ab0a759833), and [the-architect](https://github.com/jackin-project/jackin-the-architect/tree/ffb366968004e1c00437b56ea73d6ea7c6be8189). Sentinel has setup and preflight hooks, Agent Smith has a preflight hook, and the Architect manifest has neither. All three manifests disable Docker. The role repositories show why a generic manifest is not enough. Compose the role and integration policies subject to D10's provider-host closure, and reject collisions rather than allowing role rules to weaken the credential boundary.

## Subscription-only contract

A successful model reply is not evidence that the subscription paid for it. Each integration record must name the subscription product, account, region, eligible agent, supported credential and issuer, model, provider endpoint, and vendor evidence that the method is authorized. Distinguish a plan-specific API key from a separately billed API key. Do not claim support until a dedicated account's documented plan or vendor billing evidence confirms the request used the intended subscription. Never require a hidden paid inference fallback as a test. If the billing source cannot be verified, show the integration as unverified.

Jackin must not silently fall back to API billing, credits, a different subscription, a different account, model, or provider when a plan is exhausted or authentication fails. Reject configurations that permit automatic paid fallback unless the provider offers a verifiable way to disable it. If Jackin cannot prevent or verify that fallback, the integration is unavailable under this specification. An exhausted plan stops with an actionable message. Account setup and launch show the selected subscription product and any unresolved billing uncertainty; a secret's format alone is not proof of entitlement.

### Claude subscription and the host Keychain

The operator wants to use the Claude subscription already signed in on the computer. Old Jackin implemented this workflow. At `470fc5d6`, [`jackin-instance-agents/src/claude.rs`](https://github.com/jackin-project/jackin/blob/470fc5d6/crates/services/jackin-instance-agents/src/claude.rs) reads the host credential file first and falls back to the matching macOS Keychain entry when the selected home is the real host home. [`claude_keychain.rs`](https://github.com/jackin-project/jackin/blob/470fc5d6/crates/core/jackin-core/src/claude_keychain.rs) derives the service for default and custom Claude config directories. Old Jackin stages a private per-instance credential file, forwards it read-only, and [`runtime_setup/forward.rs`](https://github.com/jackin-project/jackin/blob/470fc5d6/crates/apps/jackin-capsule/src/runtime_setup/forward.rs) copies it into the writable sandbox Claude home with mode `0600` at first seed or if missing. This is credential copying, not a mount of macOS Keychain. The real credential is available inside the old sandbox. This code inspection does not establish that refresh is synchronized back to Keychain.

Investigate the requested host-login workflow as the first option. The preferred workflow reads the selected host Keychain login and makes that login available to Claude in the sandbox, with authentication changes reflected on the host. A gateway-mediated mechanism is preferable if it preserves normal Claude behavior; a sandbox credential copy is a candidate only with an explicit, reviewed change to D10. The ownership comparison below records the refresh race that the design must solve. The unmerged [OpenShell PR 2285](https://github.com/NVIDIA/OpenShell/pull/2285) proposed host Keychain import, gateway refresh, and request injection; its author reported a subscription-backed run. It used an older routing architecture and is not proof that stock `v0.1.6` or Jackin supports the flow. Determine whether stock profile, header and refresh facilities can reproduce it; this research does not use a fork. Verify actual Claude Code behavior, entitlement, token ownership, required headers and endpoints, account selection, expiry, and current Anthropic authorization without exposing credentials. Do not treat the PR or old Jackin as permission to copy secrets into the sandbox.

Host-login reuse has a refresh-ownership problem. The [agent-deck incident](https://github.com/asheshgoplani/agent-deck/issues/2153) reports that a copied rotating Claude credential caused host logout after sandbox refresh. This is evidence of a risk in that project, not proof that old Jackin experienced it. Prove host and sandbox can run concurrently, restart, refresh and log out without invalidating each other; otherwise report the limitation rather than claiming seamless sync. [OpenShell issue 3331](https://github.com/NVIDIA/OpenShell/issues/3331) proposes a separate gateway-owned grant to avoid sharing another client's refresh lineage. It remains an upstream proposal and its Claude adapter depends on a supported Anthropic client contract.

A bounded host-only `claude auth status` check reported logged-in status and a first-party subscription login; its output was parsed in memory and reduced to booleans, with no account or credential values recorded and no model request. This is evidence of the CLI's reported host auth state, not proof of available quota, an OpenShell login or permission to route the subscription through the gateway. The command may refresh OAuth credentials; the operator authorized refresh risk for Claude. Anthropic's [setup documentation](https://docs.anthropic.com/en/docs/claude-code/getting-started) distinguishes subscription login from the Console API path.

Other implementations are useful comparisons. [Docker Sandboxes](https://docs.docker.com/ai/sandboxes/agents/claude-code/) has the user start Claude `/login`; its [credential documentation](https://docs.docker.com/ai/sandboxes/configuration/credentials) describes host-side OAuth and proxy injection. Those docs do not say it imports the existing Claude Keychain entry. [claude-docker](https://github.com/ajsutton/claude-docker#credential-sync) describes copying a host Keychain login into a container and synchronizing refresh back; the guest receives reusable material. These examples do not authorize changing Jackin's OpenShell-only execution engine or D10 boundary. [Anthropic's policy](https://code.claude.com/docs/en/legal-and-compliance) permits end-user sign-in to the unmodified CLI, while restricting third-party credential intermediation. Whether a user-owned host import through Jackin's gateway is permitted needs clarification for the intended deployment; do not assume either permission or prohibition.

Anthropic's [gateway documentation](https://code.claude.com/docs/en/llm-gateway#subscriptions-and-gateways) says that setting only `ANTHROPIC_BASE_URL` can route requests through a gateway while the saved Claude subscription login stays active; a gateway credential or `apiKeyHelper` instead takes precedence. It says a pass-through gateway must forward the OAuth capability in `anthropic-beta`. This documents a subscription-aware gateway configuration, but it does not establish how the unmodified CLI obtains a placeholder instead of the real host credential inside an OpenShell sandbox. Supplying the real saved credential to the guest would conflict with D10, and the separate restrictions on third-party credential intermediation still require interpretation for Jackin's topology. The stock OpenShell integration and safe host refresh are not proven by this documentation.

The [Anthropic gateway compatibility guide](https://code.claude.com/docs/en/llm-gateway-protocol) says to forward `anthropic-beta` unchanged and allow new capability values; dropping the OAuth capability causes authentication failure. Do not hardcode a version-specific header list from this documentation. Historical Jackin forwarded the credential file opaquely, so its old code does not establish a Claude Code `2.1.317` OAuth JSON schema.

Anthropic's [CLI reference](https://code.claude.com/docs/en/cli-reference) documents `claude auth status` as a login and authentication-method check. The reviewed documentation does not establish that its result verifies the selected subscription account or entitlement. Treat it as a possible preflight signal, not proof that a host login matches the intended browser account. It was not run for this check.

Separate historical usage research recorded a point-in-time match between a Claude Keychain login and an operator-provided account candidate. Its [endpoint binding](https://docs.nvidia.com/openshell/v0.1.7/how-it-works/providers/profiles) limits where a static credential can resolve. The earlier Claude synthetic test below used `x-api-key` and does not prove the OAuth path. ### Claude login design comparison

The operator prefers the standard Claude login already stored in the host Keychain, made available to the sandbox with changes synchronized back, as old Jackin did for initial credential forwarding. Investigate that workflow as the primary design, including an extended Jackin supervisor or an OpenShell change when necessary. A user-created `claude setup-token` remains an optional alternative, not the default. A new login grant for the same account is not the same thing as copying the existing Keychain grant. The available evidence does not prove that Anthropic issues independent grants in this exact flow, that OpenShell can mediate them, or that any option guarantees uninterrupted authentication.

| Approach | What it does | Assessment |
|---|---|---|
| Import the existing refresh token and write rotations back | Gateway and host both hold the same login lineage; after gateway refresh Jackin tries to update Keychain. | Do not promise this preserves the host login. The unmodified host can refresh at the same time. A lock only Jackin honors cannot prevent that race, and a crash between rotation and write-back can lose the current token. [Agent Deck's report](https://github.com/asheshgoplani/agent-deck/issues/2153) shows this failure class. |
| Read the host access token only | A host-side reader observes the current Keychain access token; host Claude remains the only refresh owner, and the gateway injects the observed token. | Research hypothesis for the exact existing login, not a supported design. It needs a safe, documented read path and prompt handling. The sandbox fails when the host has not refreshed, the Keychain is unavailable, the token changes between observation and use, or propagation is stale. It must never copy the refresh token or start a second refresher. Confirm current Anthropic authorization. |
| Claude setup token | User authorizes a separate long-lived subscription token with `claude setup-token`; Jackin puts it at the gateway and the sandbox sees a placeholder. | Optional stock-OpenShell candidate for model requests, not the preferred host-login workflow. [Anthropic](https://code.claude.com/docs/en/authentication) documents a one-year token for eligible subscription plans, but not Remote Control or claude.ai connectors. #### Preferred host-login workflow to design

The intended experience is one selected Claude account, reused from the host Keychain, without a separate setup token or browser login for each sandbox. This is a proposed workflow, not behavior that current Jackin or OpenShell has proven.

1. A host-side Jackin credential supervisor selects the Claude Keychain item for the configured `CLAUDE_CONFIG_DIR` and establishes the account identity without logging secret material. It establishes an authenticated transport to the component receiving that login; the gateway is the preferred receiver when using placeholder injection.
2. Prefer gateway credential substitution and placeholder files when the unmodified Claude CLI can use them. Investigate a trusted mediation mechanism that captures and safely coordinates normal Claude refresh, not a second independent refresher blindly using the same refresh token. The existing in-sandbox [`jackin-start`](../../crates/jackin-image/images/jackin-start) is a PTY/process supervisor and cannot directly access macOS Keychain; a host-side component or an OpenShell extension is required. Define its lifecycle across detached sessions, host or gateway restart, and remote gateways.
3. If transparent sandbox-to-host sync is required, treat the sandbox output as untrusted. Require authenticated, account-bound communication; verify identity and generation against trusted provider or host evidence rather than trusting guest-supplied values; reject ambiguous or replayed updates; serialize participating operations; and write changes to Keychain only when the update is confirmed current. No atomic compare-and-swap against arbitrary native Keychain writers has been established. Do not send secrets through terminal output, logs, sandbox labels, or user-visible errors. A design that copies real reusable tokens into the sandbox changes D10 and must describe that exposure explicitly in the authoritative design before implementation.
4. A mismatch, missing or locked Keychain, expired credential, failed validation, interrupted rotation, or ambiguous ownership must stop propagation and give a clear recovery path. Never overwrite a newer host login with an older sandbox credential. Preserve the sandbox and project work when authentication fails.

**Unresolved technical gate:** neither a host-side lock, a compare-before-write check, nor a supervisor that the host Claude process does not use can serialize a refresh already in progress in unmodified host Claude. Once one side consumes a rotating refresh token, writing the result back can be too late for the other. Prove a mechanism that coordinates *all* refresh actors or prove a supported vendor behavior that makes the race safe. Until then, do not claim the preferred sync workflow guarantees that the host login survives. Do not silently fall back to another account, a new grant, or an API key. If reliable coordination is impossible, document that result and compare explicit alternatives, including a separate grant or setup token, without treating them as the operator's default.

Required proof uses a dedicated account and sanitized outcomes: concurrent host and sandbox refresh at the same expiry, multiple sandboxes, writes racing with host re-login and logout, Keychain locked, gateway reconnect, process death between token exchange and persistence, stale write-back, account switching, revocation and restart. Confirm host and sandbox remain authenticated to the intended subscription when the workflow reports success. Test the data path and secret exposure on stock OpenShell. Until vendor authorization and the refresh ownership contract are established, no live credential handling or production support is implied by this proposal.

[Docker Sandboxes documentation](https://docs.docker.com/ai/sandboxes/agents/claude-code/) says the user starts `/login` in Claude. Its [credential documentation](https://docs.docker.com/ai/sandboxes/configuration/credentials) says OAuth runs on the host and the proxy handles refresh. The [kit documentation](https://docs.docker.com/ai/sandboxes/customize/kits-v2/) describes intercepting token responses, replacing access and refresh tokens with sentinels in the sandbox, and injecting the real access token for allowed resource hosts. Docker documents an opt-out that sends the real token to the sandbox; it does not meet D10. [Docker's contributed Claude kit description](https://github.com/docker/sbx-kits-contrib/blob/main/claude/README.md#api-key-or-claude-subscription) describes Claude initiating a normal token refresh that the proxy mediates and remasks; the README also says the contributed kit cannot currently load while the built-in kit owns its name. Treat that as implementation documentation, not independent proof of the current built-in runtime. Docker's public documentation does not establish that it imports the existing Claude Code Keychain entry, uses an independent grant, or guarantees the host login remains valid. API-key configuration must not silently override subscription OAuth. A user-reported [Docker issue](https://github.com/docker/sbx-releases/issues/144) describes account-selection and proxy-override problems, so correct account binding also needs explicit tests.

OpenShell `v0.1.6` [documents gateway-owned OAuth refresh](https://docs.nvidia.com/openshell/v0.1.6/how-it-works/providers/profiles), including rotated token storage and a stable placeholder for automatic refresh. It does not establish an approved Claude login bootstrap or automatic interception equivalent to Docker's flow. Profile `auth_style` and header metadata do not by themselves cause a client to send a placeholder. Prove the exact Claude request headers and token-response interception or login mechanism. If stock OpenShell cannot support a vendor-authorized independent grant, document the missing capability as a blocker for this research. Never copy Docker's runtime or introduce Docker as an execution engine.

Before selecting host-login sync, host-token observation, a setup token, or a dedicated grant, verify with a dedicated test account: the actual subscription and account identity; host and sandbox working concurrently across relevant expiry, refresh, and renewal events; under current D10, no real refresh token copied or exposed in the sandbox, with non-secret sentinels allowed; if the design proposes changing D10, explicitly test and disclose credential exposure; correct selected account when two accounts exist; host Keychain locked or missing; gateway restart, disconnect, and crash during refresh; refresh replay, rotation, reauthorization, revoke, and logout; stale access token and failed refresh; and no API-key or paid fallback. Inspect only sanitized state and results. Include a negative test that another sandbox cannot use the credential. A failed or ambiguous refresh must fail closed and offer reauthentication without overwriting the host login. Check vendor terms and supported identity before live testing. These tests are proposed, not performed.

### Stock OpenShell for this research

**Proposed Kimi expiry handoff; not yet tested.** A host supervisor could treat the host-managed credential and its expiry as authoritative. After publishing the corresponding access token to the OpenShell provider and observing `--wait` readiness, it could send only the nonsecret expiry through a fixed guest helper invoked with sandbox exec. The helper would retain the opaque placeholder and empty refresh token, validate the expected file and write a temporary sibling before replacing the guest file. A guest-controlled file is never authoritative for the host; validation alone does not protect against a malicious sandbox or pathname races. Stock OpenShell's [sandbox interface](https://github.com/NVIDIA/OpenShell/blob/v0.1.7/proto/openshell.proto) exposes exec, but this design has not been exercised, and the manually edited expiry in the synthetic test above is not evidence of safe synchronization.

The proposed order is provider activation first, guest expiry second, and process launch after both are confirmed. If publication fails or its result is uncertain, stop and reconcile rather than advance the guest expiry. A crash after provider activation but before the guest write leaves the expired guest unable to start; on restart, reconcile against host-owned credential generation and expiry before retrying. These are design requirements, not proven atomicity across gateway and guest. The supervisor must serialize handoffs per account, bind expiry to the selected account and credential generation, and establish a trustworthy way to identify the gateway’s active generation after an uncertain receipt. `--wait` alone has not been shown to provide that binding. Already-running clients and concurrent launches require separate coordination or evidence; a future expiry does not establish that a credential remains valid after revocation, logout or account switching. A synthetic test must exercise interrupted writes, uncertain provider-update receipts, concurrent launches, restart and a hostile or modified guest file before the approach can be considered reliable. No real provider token or refresh token may be sent to the guest; a guest write or compromised helper can still cause denial of service.

**Gateway persistence caveat.** An SDK request made in memory does not by itself keep provider credentials off disk: the gateway's default credential store persists encrypted envelopes. OpenShell 0.1.7 source supports `sqlite::memory:` with a single retained connection and skips the usual on-disk WAL setup; its database credential driver can take an ephemeral key-encryption key from a configured environment variable instead of creating its default key file. This is a candidate for a temporary, nonpersistent provider store, not a tested guarantee: SQLite temporary-file behavior, logs, error paths, supervisor caches and process restart still need a bounded synthetic test. The stock VM driver also writes generated internal supervisor/bootstrap authentication material into its private runtime; that is distinct from the user's external provider credential but must be included in the trust-boundary inventory. An in-memory gateway loses its stored provider state on restart and must be reprovisioned. See the pinned [SQLite store](https://github.com/NVIDIA/OpenShell/blob/v0.1.7/crates/openshell-server/src/persistence/sqlite.rs), [credential driver](https://github.com/NVIDIA/OpenShell/blob/v0.1.7/crates/openshell-driver-db-credstore/src/lib.rs) and [VM driver](https://github.com/NVIDIA/OpenShell/blob/v0.1.7/crates/openshell-driver-vm/src/driver.rs).


[OpenShell 0.1.7 documents](https://github.com/NVIDIA/OpenShell/blob/v0.1.7/docs/how-it-works/providers/profiles.mdx) an `external` credential refresh strategy and `stable_placeholder: true`. A host-side adapter may update a gateway credential value while a running sandbox process retains its original opaque placeholder. The next request uses the new value only after the supporting supervisor activates the update. Placeholder validity remains bound to the sandbox, provider, credential and effective endpoint. Provider replacement or endpoint-boundary changes require a new placeholder; this feature cannot be combined with gateway-managed refresh for the same credential.

**Proposed use:** where a vendor-authorized local interface can provide the current access token without consuming or refreshing the host's refresh token, a host adapter could publish that access token to OpenShell. The host agent remains the sole refresh owner and the sandbox sees only a placeholder. This is a hypothesis for host-login reuse. It does not solve how an inactive host agent refreshes an expired token, how to safely access a Keychain entry, whether observation is supported, or whether a vendor permits mediation. An adapter must fail closed on stale tokens, account changes, logout, revoked authorization, and gateway disconnection; it must not claim that observing an old token refreshes it.

[Codex 0.166.0 source](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/app-server/src/external_auth.rs) implements an external app-server auth bridge that receives access tokens from its host application and requests another token after an unauthorized response. That is not a documented way to extract the existing host CLI login, and delivering a real token to an app-server inside the sandbox would conflict with D10. It is not proof of compatibility with OpenShell placeholder injection. The documented [omp broker and gateway](https://github.com/can1357/oh-my-pi/blob/main/docs/auth-broker-gateway.md) is another candidate for the requested omp product. Its gateway can shield provider tokens, but direct broker clients can receive access tokens; an OpenShell deployment and account isolation still need proof. Neither route authorizes running the agent outside OpenShell.

### Fastest path to the preferred host-login proof

The operator asked to leave Codex and omp untouched while they are running. Start with the other agents. An access-token-only experiment is a possible shorter path to an initial request: supply the current access token and account identifier to a static or externally updated provider, omit the host refresh token entirely, and enforce token expiry. Vendor authorization, a safe credential source, and an eligible subscription account are still required before a live test.

A separately issued gateway grant can be tested as an alternative, but it is not proof of existing host-login reuse. The deferred Codex test requires an eligible account, a vendor-authorized access-token source, and safe refresh behavior; it is not authorized while the operator's Codex instance is running. Apply the same account, refresh and gateway acceptance gates to each requested agent/provider; reuse the proven fixture machinery, not the result of a different pairing.

### Reproducible MVP procedure

For a candidate that clears its vendor and billing gates, use this procedure. These are proposed steps, not commands already run against a subscription:

1. Start a fresh stock OpenShell 0.1.7 VM gateway with its matching driver, on isolated ports and state. Use authenticated transport for any real credential. Verify the gateway version before testing.
2. Build an image with the exact released Linux agent artifact and architecture using Jackin's BuildKit-only image path. Verify artifact provenance and checksum. Configure a private agent home and no inherited host credentials, API-key variables or project settings that can override the selected subscription. Do not place real secrets in the image.
3. Import a narrow custom provider profile when the agent supports sending an opaque placeholder. Bind it to the selected provider's documented subscription endpoints and the agent's actual process tree. Configure the real subscription credential through an approved gateway secret interface without command-line values or logs. Do not assume a static profile supports browser login or OAuth refresh.
4. For an eligible account, set the plan-specific provider, region, an included model and its minimum accepted reasoning effort. Verify no paid fallback, another stored account, or other provider can take precedence. For OAuth, identify who owns refresh. A new device grant is not host-login reuse.
5. Send one short prompt through the real agent in the sandbox. Record only sanitized agent version, selected account identifier if non-secret, model, provider endpoint, billing evidence, result and exit status. Check that no real provider credential is accessible in guest files, environment, process arguments or output when claiming D10 compliance.
6. Test denied wrong destinations, missing and wrong account credentials, restart, expiry and refresh, logout, and account switching. For host-login reuse, verify host and sandbox remain usable after a safe refresh; use a separate dedicated test account and preserve a recovery method. Never infer concurrent safety from Jackin-only locking.
7. Delete only the temporary MVP sandbox, gateway, provider, fixture and image created for the run. Record failures and unresolved conditions; do not mark a pair verified until all required evidence exists.

A direct browser or device login inside a sandbox may be a useful comparison, but it creates a separate grant and normally places real authentication material in the guest. Under current D10 it cannot be described as a compliant host-login synchronization path. It also does not prove a gateway-managed subscription path.

## Current architecture and proposed model

At the historical `e7424c03a` snapshot, D04 defined one `AgentSpec` and one provider per agent. [`agent.rs`](https://github.com/jackin-project/jackin/blob/e7424c03a/crates/jackin-core/src/agent.rs) embeds Codex binary, helper, state, auth and OpenShell profile. [`provider.rs`](https://github.com/jackin-project/jackin/blob/e7424c03a/crates/jackin-core/src/provider.rs) maps a provider back to at most one agent. [`config/select.rs`](https://github.com/jackin-project/jackin/blob/e7424c03a/crates/jackin-core/src/config/select.rs) derives provider from the agent before selecting an account. [`plan.rs`](https://github.com/jackin-project/jackin/blob/e7424c03a/crates/jackin-session/src/plan.rs), [`accounts.rs`](https://github.com/jackin-project/jackin/blob/e7424c03a/crates/jackin-session/src/accounts.rs), [`files.rs`](https://github.com/jackin-project/jackin/blob/e7424c03a/crates/jackin-session/src/files.rs), and [`launch/run.rs`](https://github.com/jackin-project/jackin/blob/e7424c03a/crates/jackin-session/src/launch/run.rs) contain Codex-specific launch and credential behavior. [`jackin-image`](../../crates/jackin-image/) installs and scans Codex, and [`policy.rs`](https://github.com/jackin-project/jackin/blob/e7424c03a/crates/jackin-openshell/src/policy.rs) builds its provider policy. CLI help and reports also name Codex. The current launch planner implements the ChatGPT-login path and rejects API-key launches, although D10 describes an intended API-key mode. See [`plan.rs`](https://github.com/jackin-project/jackin/blob/e7424c03a/crates/jackin-session/src/plan.rs). The [plan](../PLAN.md) describes a staged rewrite and live gates. These are design observations, not claims that every planned screen is already implemented. Current [D04 and D29](../DESIGN.md) and the [tuple catalog](../../crates/jackin-core/src/agent.rs) supersede the historical one-provider-per-agent model; implementation and launch coverage must be assessed against the current checkout.

Recommend a closed, versioned integration catalog. An **agent** describes executable artifacts, supported platforms, lifecycle, state layout and capabilities. An **inference provider** describes the service and API endpoints. An **integration** is an explicitly validated agent, provider, protocol, authentication mode and platform tuple, with model configuration and policy requirements. An **account** identifies a provider and credential reference, not an agent. A **role** supplies trusted tools, hooks, environment, policy and optional compatible integration constraints. A **launch** records the exact integration version, agent artifact digest, account ID, model, role revision, image identity and gateway. A **session** records sandbox identity separately from any agent conversation ID and its persistence scope. An OpenShell provider is the gateway credential object, distinct from the inference provider and from a Jackin account.

| Option | Benefit | Cost and decision |
|---|---|---|
| One provider per agent, more enum variants | Small extension to existing code | Cannot represent the requested many-to-many pairs or distinguish auth modes. Reject. |
| Generic arbitrary command and endpoint | Quick experiments | Cannot establish executable identity, credential confinement, session semantics or compatibility. Reject as a supported interface. |
| Closed catalog of agent adapters and explicit integration tuples | Exhaustive validation and exact evidence per pair | More explicit maintenance. Recommend. Unknown tuples fail before image build or credential use. |

D29 has since adopted an explicit twelve-tuple catalog; the historical option comparison above explains the rationale, not a request for a compatibility shim. Catalog entries need reviewed, agent-specific adapters where behavior differs; no generic claim follows that every OpenAI-compatible provider works. Keep the OpenShell SDK boundary in `jackin-openshell` and Docker invocation in `jackin-image`.

### Proposed records and lifecycle

The catalog is compiled and versioned with Jackin rather than downloaded or loaded from a project. Each integration row names an agent release and digest per target, a provider product and region, wire protocol, allowed auth variants, allowed model identifiers or a model discovery rule, binary paths, configuration generator, state and session contract, required hosts and ports, and the evidence record. A row is enabled only for subscription products, targets and authentication variants with passing evidence, including verified subscription billing and no automatic paid fallback. Represent `documented`, `experimental`, `supported`, and `unavailable` separately in development records; production selection permits only rows that pass the applicable subscription gates, except that the current Codex launch retains its existing behavior until the product design is separately changed. It lists requested unverified rows as disabled with their reason. Provider compatibility is not a Cartesian product. Arbitrary user-configured endpoints and commands are outside this proposal.

A persistent account record holds a stable local ID, label, provider product, region and auth variant, non-secret metadata, and gateway credential object references. It must never contain credential material. A binding names an integration and account together; model selection is validated against that binding. Defaults reference IDs, not display names. Renaming an account does not change a running launch. An account whose gateway objects are missing or stale is an error; do not silently choose another account. Changes to credential material require synchronization to each configured gateway under the existing D26 lock and rollback rules. The exact cross-gateway atomicity and revocation protocol require design and live proof before implementation.

A launch record fixes the integration revision, image digest, policy digest, role revision, account ID, provider product, model, target and gateway before the first sandbox mutation. The launch ID and these fields fence retries; a retry with mismatched identity fails without altering the existing sandbox. It does not store credentials. Terminal attachment has independent connection and PTY state. The agent process has its own running, exited and failed states. A conversation reference is optional, agent-specific and scoped to an account and workspace. Its state stays in that launch's sandbox. A new launch does not implicitly inherit it; cross-launch resume is unavailable until an agent-specific transfer, ownership, retention, deletion, and credential-exclusion contract has passed its gates. Detaching only closes an attachment. Process restart uses the same validated launch identity; conversation resume requires a valid agent-owned reference and confirms the restored conversation. A stopped existing sandbox can be started under the same launch identity, as D07 specifies. A missing sandbox is not silently recreated as an existing session; report the loss and offer a new launch. Concurrent attachments and a restart need a single authoritative supervisor and explicit conflict handling, preserving D07 and D09 fencing.

### Proposed commands and console choices

The exact syntax is illustrative and subject to CLI review. A concrete form is `jackin account add --provider <provider> --auth <method> --name <label>`, followed by `jackin load --role <role> --agent <agent> --provider <provider> --account <name> --model <model>`. A provider that offers distinct products, such as Kimi Code membership and Kimi Platform API, must expose them as distinct choices or require an explicit product qualifier. The account wizard collects secrets only through a private input path and synchronizes credential objects to every configured gateway under D26; it must not echo them. A browser or device login is offered only after its token transfer and refresh path meets D10. If the chosen gateway cannot support it, explain the specific missing capability before collecting a credential.

Resolve selections in this order. All explicit values constrain the candidate set together and are never silently replaced. If an explicit account is supplied without a provider, derive the provider product from that account before applying defaults. Conflicting explicit values fail before any build or credential use.

1. Resolve the agent from an explicit flag, then the workspace default, then the role default, then the global default. If none is set, use Codex as the initial default. An explicit or stored value that is unavailable produces an error naming it.
2. Resolve the provider product from an explicit flag, then the matching workspace binding, role binding, and agent default. If none exists and exactly one supported provider is compatible, use it. Otherwise ask in an interactive flow or return an ambiguity error in non-interactive mode. Do not substitute a different provider for an incompatible selection.
3. Resolve the account from an explicit flag, workspace binding, role binding, provider default, then a sole compatible account. A binding that names a missing or incompatible account fails with its source and repair action; do not skip to a lower priority. If no account exists, offer account setup interactively and return an actionable error otherwise.
4. Resolve the model from an explicit flag, then matching workspace, role, and account defaults, then the integration's reviewed default. Reject a model not allowed for that provider product or account. A provider entitlement error remains visible; do not silently switch models.

For example, an explicit `--provider` that conflicts with an explicit account fails before any build or credential use. Two compatible accounts without a default require a choice. A saved default that is no longer available fails with its source instead of changing a user's selection. Persist choices only on an explicit save, not as a side effect of launch.

Account registration requires at least one configured gateway and requires all configured gateways to be reachable. Validate the local account fields and supported auth mode first; do not make a paid inference request merely to check a credential. When the provider supplies a safe, documented credential validation method, use it; otherwise record validation as unverified. Under the existing D26 locking and rollback rules, create credential objects on every configured gateway before making the account selectable. If a gateway is unavailable or a write fails, report it, roll back newly created objects, and do not publish the account. Report any rollback failure and the affected gateway for recovery. Replacements and removals must retain the current D26 safety checks. Running launches retain their selected identity; revoking or replacing its credential may interrupt them and must be reported before the change.

The console uses the same catalog and selection function as the CLI. The launch form shows the resolved role, agent, provider product, account, model and gateway, and disables incompatible choices with the reason. Existing workspace defaults are visible and may be changed explicitly. An already-running instance displays its fixed identity even if defaults change. Attach and detach refer to the PTY. For an exited process, restart reruns the role preflight and starts the agent process in its existing sandbox, preserving D09. A failed preflight leaves the sandbox available for inspection and export. A running process is not restarted implicitly. Resume is a separate action offered only for a verified integration and matching retained state. If state is missing, incompatible, or restoration cannot be confirmed, show an error and offer an explicit new conversation; never silently start one. Starting a stopped sandbox does not by itself promise conversation resume. Export invokes the existing guarded project export and reports conflicts or recovery refs. The console must never infer that a successful process start restored a conversation. Unsupported tuples show no credential-entry flow and no silent fallback.

## Credentials, policy and files

Account registration selects the subscription product, provider, region or endpoint profile, authentication method and a non-secret label. Subscription keys and token material go only to a gateway credential object or another explicitly proven secret boundary. Never put real credentials in images, role manifests, logs, labels, exports, command arguments, or the specification. The requested Claude host-Keychain login import is an explicit account setup option to investigate; it is not a reason to place real credentials in the sandbox. OAuth, browser, device and subscription-key methods need separate support records. Refresh ownership, rotation, revocation, synchronization, concurrent sessions, account switching and expiry behavior must be proven per method. If gateway substitution cannot handle a CLI's credential format or refresh, mark that method unavailable rather than placing secrets in the sandbox or adding an unreviewed proxy.

[P0.3](../evidence/P0.3-codex.md) observed that an unrelated `curl` or `python3` process could not use the Codex credential, while `curl` launched by Codex could use it through the proxy. The binary rule covers descendants. The replacement is destination-based: another policy rule that independently permits the same host can also receive substitution. Preserve and test D10 host closure against overlapping role rules, wildcards, ports, and binaries for every integration. Therefore, injected credentials are hidden from direct reads but are usable by agent-launched processes for permitted destinations. A malicious project instruction, hook, or plugin can exploit that authority. Do not claim process isolation prevents use of the credential by an agent child.

Generate minimal egress rules for the exact integration and auth flow, separate from role policy. Record DNS names, ports, TLS and redirects, model, login, token refresh, telemetry and update endpoints from official evidence and network observation. Network observations can reveal missing hosts but cannot establish authorization to allow them. The current [D10](../DESIGN.md) host-based substitution and binary-bound policy must be checked for header format, child processes, proxies and token refresh for each tuple. The OpenRouter Claude guide uses `ANTHROPIC_BASE_URL=https://openrouter.ai/api`, an auth token, and an explicitly empty `ANTHROPIC_API_KEY`; cached login conflicts are a concrete reason to isolate account state. Z.AI's [Codex guide](https://docs.z.ai/devpack/tool/codex) uses its Responses endpoint and distinguishes individual, team, and standard API keys. Its plaintext bearer-token example conflicts with D10 and must not be copied. The [OpenCode guide](https://docs.z.ai/devpack/tool/opencode) selects the coding-plan provider separately and offers `/share`, which can publish conversation history and needs explicit user action. [Grok settings](https://docs.x.ai/build/settings) describe `https://api.x.ai/v1`, but this is not proof of a complete endpoint list. [Antigravity installation](https://antigravity.google/docs/install?tab=cli) and [troubleshooting](https://antigravity.google/docs/cli-troubleshooting) describe login and keyring constraints that may block headless sandbox use.

The role manifest must name a role instruction asset separately from an agent's user configuration. For each supported integration, the adapter must declare a reviewed mapping from that asset to an instruction mechanism the agent actually reads. If the role requires instructions and the adapter has no verified mapping, fail before launching; do not silently omit or translate them. The mapping guarantees delivery, not enforcement. If the agent permits project configuration to replace or suppress the mapped role instructions, the adapter must detect and reject that configuration before launch; if detection is not reliable, the integration remains unavailable for roles requiring instructions. Project instructions remain project-controlled and cannot override the network policy or credential boundary. Their precedence relative to role instructions must be recorded and tested for each adapter. Role setup and preflight hooks retain D11's execution and failure rules; agent-discovered project hooks and plugins are separate code execution and must be disclosed before use. The existing Agent Smith Codex-specific preflight requires an explicit role change before another agent can consume its instructions.

Each adapter must inventory home and state directories, configuration precedence, project reads and writes, instruction files, plugin discovery, hooks, caches and remote service state before support. Mount or create only required paths. Keep credentials out of export and isolate mutable home by launch and account unless a documented, tested sharing contract requires otherwise. Project code, agent-generated commands, plugins and hooks are untrusted relative to the host and gateway. A role is trusted as described in [D05 and D11](../DESIGN.md). Explicitly disclose which role and project hooks execute, preserve the existing project upload and git export safeguards in D08, and never treat a conversation transcript as equivalent to exported project work. Plugin network access is subject to the same policy; no automatic plugin installation is implied by this proposal.

## CLI and console behavior

Proposed CLI and TUI behavior is the same selection model. Account add lists available provider and auth methods, checks credentials only when a safe documented validation method exists, and records a named account without printing secrets. Otherwise it reports validation as unverified. Launch chooses role, agent, provider, account and model, with explicit arguments taking precedence over compatible workspace bindings, role bindings, provider defaults, and finally a sole compatible account. This preserves the selection order in `crates/jackin-core/src/config/select.rs` while validating the full integration tuple. An ambiguous set without a default is an error. An explicit incompatible choice fails with the exact missing or unsupported tuple and available alternatives. It never silently changes provider, model or account. TUI selectors show availability and the reason a choice is disabled. D27 places console screens and state in baseline `jackin-console`; `jackin-tui` bridges its backend. The new selector therefore requires an explicit baseline design change and review, while preserving approved visuals and following the baseline workflow.

Launch displays the selected identity and policy summary before starting. Detach leaves the sandbox and PTY running. Attach reconnects to that PTY. Restart clearly distinguishes restarting the process from resuming a stored conversation, and fails visibly if the promised conversation cannot be found. Export retains D08's guarded git-based project export and excludes credentials and agent state by default. An optional future transcript export needs its own explicit privacy and format contract. Account switching applies to new launches; a running session cannot silently change its identity. Removing an account must report dependent sessions and gateway objects and follow a separately specified, safe lifecycle.

## Verification gates and milestones

1. Inventory and approve exact product identities and one integration tuple. Record artifact digests, architecture, endpoint set, auth and source revisions. The user identified omp and Kimi Code. Verify Muse account entitlement and the selected native service before enabling its integration.
2. Specify the catalog and selection contract. Hermetic public-interface tests cover valid and invalid tuples, selection precedence, account isolation, config identity, policy composition, and failure without credential disclosure. Follow the repository's independent test-plan and red/green review rules before writing tests.
3. Add one adapter and immutable artifact through the existing build boundary. Prove image identity, role assembly, binary scan, config and state isolation without a live network. Use fakes only at the external boundaries named in the repository rules.
4. Run `xtask e2e` against a real OpenShell gateway for the exact tuple, using a dedicated test account when available. Prove authentication, model request and streamed tool use, terminal resize and detach/reattach, process restart, and, where advertised, non-interactive result and exit status and named conversation resume with a recognizable prior marker; also prove guarded project export, denied unlisted egress, and credential non-disclosure. Exercise expiration or rotation where the auth method supports it. Record gateway, image, policy, artifact, model, platform, timestamps and sanitized results. Never record secret values.
5. Add one more tuple only after its separate policy, auth and live evidence pass. A passing agent with one provider does not confer support on the next provider. Repeat after material version, protocol, endpoint or authentication changes. If a vendor does not document an operation, record it as unavailable until verified and supported intentionally.

Before calling any combination supported, evidence must identify the subscription plan and prove the request consumed its intended allowance without paid fallback, as well as include official product identity, stable immutable release and supported architecture, license and distribution review, exact executable, proof of each advertised interactive, non-interactive and resume capability or an explicit unavailable status, credential lifecycle, allowed network hosts, configuration and state inventory, policy escape and secret-leak checks, hermetic behavior tests, independent review, and reproducible live gateway results. A provider's marketing page, API compatibility claim, mock TUI entry, unit test, or a successful one-shot text response alone is insufficient. The live Kimi and Grok requests above used host access tokens in isolated gateways; neither passed all subscription support gates. Credential values were not recorded.

## Decisions and open questions

The recommended decision is a closed tuple catalog with distinct account and session identities. The practical blocker is not UI enumeration but proof that each CLI's authentication and network behavior can satisfy D10 without exposing credentials. Resolve account entitlements, licenses, stable artifact hashes, Linux architecture coverage, official endpoint inventories, OAuth refresh and gateway injection, and state and plugin trust before implementation. The baseline checkout needs updating before implementation. A separately reviewed product decision must amend the Codex-only rule and authoritative design before any implementation starts.
