## 1. Architecture

Components (S:docs/about/architecture.mdx, "What Each Piece Does" table and "Inside the Sandbox Boundary"):

- **Gateway** (`openshell-gateway`, crate `openshell-server`): control plane and authentication boundary. Stores sandboxes, providers, policies, workspaces in SQLite/Postgres. Authenticates with mTLS, OIDC, or gateway JWT. As of v0.1.6 it refuses to start with no auth unless `allow_unauthenticated_users = true` (S release notes, PR #4821).
- **Compute driver**: provisions the workload and a separate supervisor, builds the isolation boundary. Built-in: `docker`, `podman`, `kubernetes`, `vm` (libkrun microVM), `mxc` (Windows, not qualified). Extension drivers use `proto/compute_driver.proto`. One gateway = one driver (S:docs/how-it-works/sandboxes/runtimes.mdx intro).
- **Supervisor** (`openshell-supervisor*` crates): trusted side. Runs the OPA network policy proxy, DNS, credential injection, SSH server for attach/exec, log push, and the gateway session. It is injected by the driver, not baked into the workload image.
- **Sandbox** (`openshell-sandbox`): capability-free process inside the boundary. It owns the agent as a child, applies Landlock and seccomp, and relays TCP/DNS to the supervisor over an authenticated HTTP/2 channel (Unix socket for Docker/Podman, TCP for Kubernetes, vsock for VM).
- **Policy engine**: network policy in the supervisor proxy (deny by default, per-binary, L7 inspection); filesystem via Landlock; process via seccomp and non-root identity. The gateway also has a formal-verification "prover" that checks agent-proposed rules (S:docs/how-it-works/policies/prover.mdx).
- **Providers**: gateway-stored credentials plus a profile (endpoints, binaries, refresh). The sandbox receives opaque placeholders; the proxy swaps in the real value only for the profile's endpoints (S:docs/how-it-works/providers/overview.mdx "How Credential Injection Works").
- **Workspaces**: access/isolation boundary for sandboxes, providers, policies. Every public request carries `workspace_scope` (S:proto/README.md "Workspace scope"; S:docs/how-it-works/workspaces.mdx).

### Local gateway on macOS

- Installer on Apple Silicon: Homebrew formula, tap `nvidia/openshell`; launchd service via `brew services`; endpoint `https://localhost:17670`; mTLS bundle generated by `openshell-gateway generate-certs` (S:install.sh:8-25; S:tasks/scripts/release.py:360-500; S:docs/about/installation.mdx "macOS"). Only Apple Silicon is published (S:install.sh:720-730).
- The generated gateway config is `[openshell] version = 2 / [openshell.gateway]` with no `compute_driver` (S:tasks/scripts/release.py, `post_install`, about line 430). With no driver set, the gateway auto-detects Kubernetes, then Podman, then Docker. The VM driver is never auto-detected (S:docs/how-it-works/sandboxes/runtimes.mdx "Select a Compute Driver"; S:crates/openshell-server/src/lib.rs:1587, 1624-1640, which errors "no compute driver configured and auto-detection found no suitable installed driver").
- So the default macOS path needs **Docker Desktop (or a Podman machine)**. Support matrix: "macOS (Docker Desktop), Apple Silicon: Supported" (S:docs/about/support-matrix.mdx:56). Docker Desktop 28.0+. Linux kernel modules (Landlock ABI 3, seccomp notify) then run inside Docker Desktop's Linux VM (support-matrix.mdx:196). No colima or k3s requirement in the docs; Podman machine sockets are auto-found on macOS (runtimes.mdx "Podman Driver").
- **No-Docker path on macOS**: the formula also installs and codesigns `openshell-driver-vm` with the `com.apple.security.hypervisor` entitlement (S:release.py:455-467). Setting `compute_driver = "vm"` in `~/.config/openshell/gateway.toml` runs each sandbox in a libkrun microVM using Hypervisor.framework. It needs `brew install e2fsprogs` (S:docs/how-it-works/gateways/configuration.mdx "Check local VM host tools") and a `linux/arm64` image. The VM driver pulls images straight from a registry with `oci-client`; a local Docker/Podman engine is optional and only consulted first (S:crates/openshell-driver-vm/src/driver.rs:3508-3532 "falling back to registry", pull at ~3979). Status: README says "Experimental" (S:crates/openshell-driver-vm/README.md line 3) while the docs call it "Supported for VM-backed sandboxes" (support-matrix.mdx driver table). Not run here.
- Linux: `.deb`/`.rpm`/snap, systemd user service; Docker or Podman driver; VM driver on KVM.

### Recommendation

Use **`openshell-sdk` at tag `v0.1.6`** for all control-plane work, and its `raw` module (`raw_grpc_fresh()`) for the RPCs the curated layer lacks (providers, policy, logs, forwarding). Reasons, each cited:

1. It is the same transport the CLI uses (S release notes: "The CLI now connects to gateways through the shared Rust SDK transport", PR #4817), so TLS/mTLS/OIDC edge cases are covered upstream.
2. mTLS client identity exists in v0.1.6: `ClientIdentity { certificate, private_key }` and `ClientConfig.client_identity` (S:crates/openshell-sdk/src/config.rs:47-60, 95-105), applied at `S:crates/openshell-sdk/src/transport.rs:134`. This is absent at v0.1.5 (`git grep ClientIdentity v0.1.5 -- crates/openshell-sdk` returns nothing). The local Homebrew gateway uses mTLS, so this matters.
3. The SDK does no filesystem access and no active-gateway lookup (S:crates/openshell-sdk/README.md intro, config.rs header). jackin reads the cert bundle itself from `~/.config/openshell/gateways/<name>/mtls/{ca.crt,tls.crt,tls.key}` (S:docs/how-it-works/gateways/authentication.mdx "mTLS") and passes explicit gateway URL plus workspace on every call. That satisfies "no global active gateway".
4. `raw` exposes all generated tonic clients, so `request_id` and `expected_resource_version` can be set (curated request-ID helpers are explicitly "not part of this contract yet", S:docs/sdk/api-errors.mdx, "Durable request admission").

Costs to accept:
- Pulls `openshell-core` (vendored `protoc`, `protoc-bin-vendored` in `S:crates/openshell-core/Cargo.toml:66`) and requires Rust 1.94+ / edition 2024.
- Stability: SDK is pre-1.0 and not on crates.io. Pin the tag and the gateway to the same release ("Use the SDK and gateway from the same OpenShell release", rust.mdx).
- Upstream docs conflict with source: `docs/sdk/rust.mdx` says the Rust SDK "does not support mTLS client certificates", but `config.rs`/`transport.rs` implement it. Source wins (README of the crate agrees with source).

Fallback if the git dependency is unacceptable: vendor `proto/*.proto` at the tag and generate with `tonic-prost-build`. This loses the SDK's TLS/OIDC/edge transport code. Not recommended.

### Important SDK gap: attach, upload, download, SSH forward use the SSH tunnel, not plain gRPC

At v0.1.6 the CLI implements these by spawning the **system `ssh` binary** with `ProxyCommand=openshell ssh-proxy`, where `ssh-proxy` opens `ForwardTcp` with `SshRelayTarget` using a token from `CreateSshSession`:
- Attach to the canonical main process: `ssh -tt ... -s sandbox openshell-main` (S:crates/openshell-cli/src/ssh.rs:226-231 `Command::new("ssh")`, 277-294 `main_attach_command`). Supervisor side: subsystem `openshell-main` (S:crates/openshell-supervisor-process/src/ssh.rs:748).
- Upload: subsystem `openshell-upload-v1` (S:crates/openshell-core/src/upload.rs:17; S:ssh.rs:1250-1330 `ssh_tar_upload`, `ssh_upload_command`).
- `ssh-proxy`: S:ssh.rs:1950-2000.

`examples/sync-files.md` claims the transfer "does not require ssh"; the v0.1.6 source spawns `ssh`. Source wins.

Options for jackin: (a) hand the terminal to `openshell sandbox connect/upload/download` as child processes (v1, least code); (b) implement the SSH client in-process with `russh` (the supervisor uses `russh = "0.64.1"`, S:crates/openshell-supervisor-process/Cargo.toml:26) over a `ForwardTcp` stream. (b) is feasible but unproven here.

## 3. Policy model

Schema (S:docs/how-it-works/policies/schema.mdx): top-level `version: 1`, `filesystem_policy`, `landlock`, `process`, `network_policies`, `network_middlewares`. Unknown fields and duplicate keys are rejected. Max 4 MiB.

- **Filesystem** (Landlock, startup only): `read_only`, `read_write`, `include_workdir`. Paths are absolute, <=256 entries. Landlock `compatibility`: `best_effort` (default) or `hard_requirement`. Mandatory baseline protects `/.openshell` and needs Landlock ABI 3 (default-policy.mdx "Protected Paths"). Baseline `/usr /lib /etc /app /var/log /proc /dev/urandom` (ro) and `/tmp /dev/null` (rw) are added automatically when the effective policy has any network rule, including provider-contributed ones (default-policy.mdx "Baseline Filesystem Paths").
- **Process** (startup only): `run_as_user`, `run_as_group` (`sandbox` or numeric 1..4294967294; root rejected). Seccomp user-notify and a capability-free workload are fixed by the runtime.
- **Network** (live): map of rules; each has `endpoints` and `binaries`. Binary match is by real executable path (symlinks do not match; children of a listed binary inherit the rule). OpenShell records a hash of each executable on first use and denies later connections if the file at that path changes (network-rules.mdx line 76). Endpoint: `host` (wildcards need 3 labels), `port`, `protocol` (`rest|websocket|graphql|mcp|json-rpc|tcp`), `enforcement` (`enforce|audit`, default `audit`), `access` (`read-only|read-write|full`) or `rules`/`deny_rules`, `allowed_ips`, `tls: skip`, credential rewrite flags. Loopback, link-local, metadata (169.254.169.254) are never allowed.
- **Startup vs live**: sandbox-scope `UpdateConfig` may change only `network_policies`; filesystem, landlock, process must match creation (proto comment at S:proto/openshell.proto:2859-2863; policy table "Takes effect").
- **Inference routing**: removed. `openshell inference`, route APIs and `inference.local` are gone (S:docs/upgrade/0-1-0.mdx:97; docs/how-it-works/inference.mdx "Migrate from Managed Inference Routes"). Model access is: attach a provider, let the client call the provider's native endpoint. Provider-profile endpoints are composed into the effective policy as `_provider_*` rules.

### Minimal Codex policy (hosts confirmed upstream)

Confirmed Codex hosts (S:providers/codex.yaml and S:examples/codex-app-server/codex.yaml, `endpoints:`): `api.openai.com:443`, `auth.openai.com:443`, `chatgpt.com:443`, `ab.chatgpt.com:443` (header says: inference, token refresh, experiment lookups). Binaries: `/usr/bin/codex`, `/usr/local/bin/codex`, `/usr/lib/node_modules/@openai/**`, `/usr/local/lib/node_modules/@openai/**`.

Base policy (set at create time):

```yaml
version: 1
filesystem_policy:
  include_workdir: true
  read_only: [/usr, /lib, /etc]
  read_write: [/tmp]
landlock:
  compatibility: hard_requirement
process:
  run_as_user: sandbox
  run_as_group: sandbox
network_policies: {}
```

With the `codex` provider attached, its imported profile contributes the four endpoint rules and the credential binding; the base policy adds no network access of its own. If you also want the hosts visible in the base policy (for example no provider), use this, but keep the settings identical to the profile because endpoints that can match the same host and port must agree on `protocol`, `enforcement` and credential settings (schema.mdx "Endpoint Constraints"):

```yaml
network_policies:
  codex:
    endpoints:
      - { host: api.openai.com,  port: 443, protocol: rest, access: read-write, enforcement: enforce }
      - { host: auth.openai.com, port: 443, protocol: rest, access: read-write, enforcement: enforce }
      - { host: chatgpt.com,     port: 443, protocol: rest, access: read-write, enforcement: enforce }
      - { host: ab.chatgpt.com,  port: 443, protocol: rest, access: read-write, enforcement: enforce }
    binaries:
      - { path: /usr/bin/codex }
      - { path: /usr/local/bin/codex }
      - { path: "/usr/lib/node_modules/@openai/**" }
      - { path: "/usr/local/lib/node_modules/@openai/**" }
```

Not confirmed: whether Codex needs other hosts (package/update checks, GitHub, MCP servers, WebSocket transport to `chatgpt.com`; `protocol: rest` inspection may reject WebSocket upgrades). Test with `openshell logs N --source sandbox` and the policy advisor (`openshell rule get N --status pending`).

## 4. Built-in agent support

- **Codex**: OpenShell ships an *example* provider profile (`S:providers/codex.yaml`), not a compiled-in one. "OpenShell does not compile them into any binary and no gateway loads them on its own" (S:providers/README.md). A new gateway has an empty catalog; import with `openshell profile lint -f` then `openshell profile import -f`. Copy and adjust `binaries` to your image layout.
- A more complete flow is upstream-maintained at `S:examples/codex-app-server/` (README, `codex.yaml`, `Dockerfile`, `start-codex-app-server`). It: builds an Ubuntu 24.04 image with `nodejs npm`, a `sandbox` user with home `/sandbox`, `npm install -g @openai/codex`; imports the profile; creates the provider from the host `~/.codex/auth.json` fields (`CODEX_AUTH_ACCESS_TOKEN`, `CODEX_AUTH_ACCOUNT_ID`); moves the refresh token into gateway-only refresh material (`provider refresh configure --strategy oauth2-refresh-token --material client_id=... --secret-material-env refresh_token=...`, then `refresh rotate`); runs `sandbox create --provider codex --detach --no-tty --expose 4500 -- start-codex-app-server`. The launcher writes `~/.codex/auth.json` containing only the opaque placeholders (`auth_mode: chatgptAuthTokens`, empty `refresh_token`, fake non-secret ID token). So the real token is never written into the sandbox.
- A second upstream pattern: `S:scripts/agents/runtime/harnesses/codex/exec.sh` writes `auth.json` from placeholders with `auth_mode: "chatgpt"`.
- `openshell sandbox create -- codex`: the part after `--` is `SandboxSpec.command`, the canonical main process, run directly (no shell parsing) in the image (S:proto/openshell.proto:1074-1080, `command = 12`). It does **not** select a provider: "A provider is attached only when you name it. OpenShell does not derive one from the trailing command" (S:docs/how-it-works/providers/overview.mdx "Auto-Discovery Shortcut"). The image must already contain `codex`. With `--provider codex` and no existing provider named `codex`, the CLI offers to create one from local discovery if a `codex` profile is imported (`--auto-providers` skips the prompt). S:skills/openshell-cli/SKILL.md:104 shows `--from <image> --provider codex -- codex`.
- Default shell, tty: with no trailing command the main process is a retained-PTY login shell (sandbox overview).
- **Grok/xAI**: no profile, image, or mention at v0.1.6 or on `main` (searched `grok`, `xai`, `api.x.ai`; only unrelated "ngrok" matches). Out of scope now.

## 5. Images

- OpenShell does not need a special base image. "OpenShell accepts standard Linux OCI images"; default `nvcr.io/nvidia/base/ubuntu:24.04` (minimal, no agent CLIs) (S:docs/about/support-matrix.mdx "Workload Images").
- Supervisor and sandbox binaries are staged by the driver from trusted images (`ghcr.io/nvidia/openshell/sandbox`, `.../supervisor`), selectable only by gateway config (`sandbox_runtime_image`, `supervisor_image`), never by the sandbox request (S:runtimes.mdx "Select a Compute Driver"). Release note: images no longer need `iproute2` or `nftables` (S release notes, PR #3967).
- Image rules (S:examples/bring-your-own-container/README.md): the image `CMD`/`ENTRYPOINT` is replaced; pass the command after `--`; declare a non-root `USER` (images without `USER` run as UID/GID 1000 on Docker/Podman; root is rejected unless policy sets `run_as_user`); workspace is `/sandbox` or the image `WORKDIR`; `bash` is used when present, else a detected shell.
- Arbitrary OCI image built elsewhere: yes. `--from registry/img:tag`. The gateway/driver must be able to pull it. Remote gateway: push to a registry it can reach. Docker driver: local image in the Docker daemon also works. VM driver: local Docker/Podman engine first (optional), then registry (driver.rs:3508 onward).
- Build story without jackin running Docker: OpenShell has none. `--from ./Dockerfile` was removed in 0.1.0 (S:docs/upgrade/0-1-0.mdx; sandbox overview warning). Options: (1) publish a prebuilt Codex image from CI to a registry (GHCR) and reference it by digest; (2) `docker export` to a rootfs tar for a local VM-driver gateway only; (3) the user's own engine builds it (outside jackin). Option 1 fits jackin: it never runs Docker. Pin by digest; VM driver boots digest-pinned images from local cache without contacting the registry (release notes, PR #4582).
- Verify image contents: SBOM attestations exist for gateway/supervisor images (docs/security/verify-image-contents.mdx).

## 7. Gaps and blockers

1. **Persistent sessions across detach**: supported for the main process. Create with `tty=true` and the agent as `command`; attach by SSH subsystem `openshell-main`; detach keeps it running; reattach replays up to 1 MiB and one attachment owns stdin (sandbox overview). Gaps: (a) attach is SSH-based, so an in-process ratatui terminal needs `russh` over `ForwardTcp`, or a terminal handoff to `openshell sandbox connect`; (b) the main process dies with the sandbox and `restart_policy` replacement "does not restore process memory or terminal history"; (c) one stdin owner at a time; (d) which drivers support foreground attach is checked at create time and unsupported drivers reject it, so use `--detach` (overview; I did not find the per-driver capability list, so this is unverified). Alternative that needs only gRPC: run `tmux` in the image and use `ExecSandboxInteractive` (my suggestion, not upstream).
2. **Multiple sandboxes per user**: supported. Many sandboxes per workspace, label selectors, paging, `all_workspaces` for admins. Local gateway without OIDC roles treats the user as platform admin (workspaces.mdx note). Limits: VM driver has fixed vcpus/mem per VM; on Docker Desktop all sandboxes share one Linux VM.
3. **Mount a local project directory**: no first-class feature. Default is copy: `sandbox upload` / `create --upload` (tar, `.gitignore` filtered) and `download`; no continuous bidirectional sync. Bind mounts exist only through `--driver-config-json` and require gateway-operator opt-in: Docker `enable_bind_mounts = true` plus `resource_admission.enabled = false`; VM (libkrun virtiofs) same opt-in, max 32 mounts on arm64, read-only by default, not with GPU; the docs warn that bind mounts can bypass workspace isolation and filesystem policy (S:runtimes.mdx "Docker Mounts", "MicroVM Mounts"). Docker Desktop on macOS adds file-sharing/ownership caveats not checked here. Recommendation: use upload/download in v1; treat bind mount as an explicit unsafe mode.
4. **Codex credentials**: needs the placeholder-aware `auth.json` writer (see section 4); that launcher is jackin's responsibility, since OpenShell ships none for a plain `codex` run. Whether the placeholder form works for interactive Codex with `chatgpt` login (not `app-server`) is unproven here.
5. **macOS without Docker**: depends on the VM driver, labelled experimental in its README, plus e2fsprogs and a manually edited gateway.toml. Unrun.
6. **SDK distribution**: git dependency only, Rust 1.94+, same-release coupling, protocol churn between prereleases (v0.1.6 notes list accepted protobuf breaks; PR #4976).
7. **Auth bootstrap**: gateway refuses to start unauthenticated; client must load the mTLS bundle from disk. For `localhost` the cert SANs include localhost (authentication.mdx).
8. **No image build or Dockerfile support** in OpenShell; jackin needs a registry-publish pipeline.
