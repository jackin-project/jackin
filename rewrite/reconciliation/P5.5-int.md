## The create-time validation that I4 cites

OpenShell v0.1.6, commit `ac7f615` (`compatibility.lock.toml`):

- `crates/openshell-server/src/grpc/sandbox.rs:586-597`: `CreateSandbox` runs `validate_no_reserved_provider_policy_keys`, `validate_and_canonicalize_policy`, then `validate_policy_safety` on the policy.
- `crates/openshell-server/src/grpc/validation.rs:1016-1041`: both wrappers turn violations into `policy contains unsafe content: ...` (the text of the V4 live test).
- `crates/openshell-policy/src/lib.rs:1326`, `:1413-1491`: `validate_sandbox_policy`. For an endpoint with `protocol: tcp` (`l7_validate::is_explicit_tcp_protocol`, case-insensitive), a host that parses as `std::net::IpAddr` gives `TcpEndpointIpLiteral` (`:1480`), and any other host must pass `validate_tcp_dns_host_selector` (`:1709`) or it gives `InvalidTcpEndpointHost`.
- `crates/openshell-policy/src/lib.rs:1874`: `validate_and_canonicalize_sandbox_policy`.

Reach: `openshell-policy` is a dependency of `jackin-openshell`, so jackin calls the function and copies no rule. `crates/jackin-openshell/src/policy/yaml.rs` `check_sandbox` has called it since P7.3-int (`PolicyError::Gateway`).

The premise of the replaced I4 row ("role check accepted that policy") does not hold for the policy of the live test. The 095213282 binary refuses `host: 198.18.0.2`, `protocol: tcp`, `tls: skip` with exit 1 and the gateway's own text. The adversary roles that role check accepted (`synth_gw`, `nip_alias`, `gw_lan`) have no `protocol: tcp` line, and the gateway accepts those at create (`explicit_tcp` is false, so neither check runs). With the line added, `synth_gw` and `gw_lan` are refused before and after; `nip_alias` is a DNS name and is accepted by both.

The three non-canonical spellings of 198.18.0.2 (`3323068418`, `0xc6120002`, `198.18.2`, quoted so YAML reads a string) are not `IpAddr` values in Rust. The gateway's create check accepts them as tcp endpoint hosts, and so does role check, with the same verdict. Unquoted, YAML reads `3323068418` and `0xc6120002` as integers and role check reports `invalid host` with an empty name. The runtime later sends such a name to `getaddrinfo` (the reviewer's finding, inferred, not run here). Refusing them would be a rule stricter than the gateway's; see Suggestions in the report.

## Differences from the plan and decisions

- I4 needed no source change; see above. The tests pin it.
- I5 splits the new names. The daemon pieces `docker-proxy` and `dockerd-rootless.sh` are refused in both forms, because no role needs them beside a remote engine. The client names `docker-compose`, `docker-buildx`, `buildctl` and `ctr` are refused only with the capability off, as the orchestrator asked, so a role that installs its own compose plugin still builds with the capability on. The scan sees "off" as the absence of `--allow-tool`.
- The new control-character `find` runs after the three existing finds, so the tests that fail the Nth `find` keep their counts. A fourth stub (`n -eq 3`) covers it.
- I2 adds `GatewayError::UnsafePath { path }`. It joins the exhaustive matches in `tests/gateway/status.rs` (count 21 to 22), `support.rs` and `error_text.rs`.
- I3 changes the type of the Docker label from a port to port plus fingerprint, and removes it from `PlannedLabels`. About a dozen fixture lines in openshell, session and testkit lost `docker: DockerLabel::Off` or gained the `DockerLabel::Off` argument of `complete`. The JSON views now print `{"engine":{"port":2376,"ca":"<16 hex>"}}`; the review asked for "engine" without a fingerprint, which needs a view type of its own and was not in scope. The fingerprint is a hash of a public certificate.
- The fingerprint algorithm hashes sorted, de-duplicated DER certificates (the review's normalisation). For one certificate it is `sha256(DER)`, the orchestrator's wording.
- `DockerCapability::label()` is gone; `certs::bind` builds the label from the port and the CA read.
- The ENV check reads `ENV` after `Reader` has joined continuations, so the reported line is the first line of the instruction.
- Secret scanners: the `EC PRIVATE KEY` block of the `ecparam` fixture is assembled from a body constant and a split armor string, so `kingfisher --staged` and `gitleaks protect --staged` report no finding. The key is a throwaway generated for the test.
