## P10.2 fix round 2

Base: `73683ae2c`. Input: the verified adversarial findings in `/private/tmp/claude-501/plans/P10.2-interrogate.md` (head `9a2042556`). All values are fake.

### Why the design allowed finding 1

`plan_account_edits(&Config, edits)` took any config, so the caller read the config before the account lock and the plan inherited that stale read. Three decisions then depended on it: Offline or Gateway, the set of gateways, and (for `gateway rm`) whether any account lock was needed at all. `GatewayPlan::apply` re-read the config under the lock, but only for the effects. It could not change the gateway set or the Offline path that the caller had already chosen. `OfflinePlan::apply` took no lock. `Session::remove_gateway` took locks for the login accounts of a pre-lock read.

The fix removes the enabling condition. A plan can only be built by `plan_account_edits(&AccountDesk, edits, cancel)`, which takes the account locks, reads the config under them, and only then chooses Offline or Gateway. The plan owns the locks (`FileLock`) and the locked `Config`, so the locks end when the plan is applied or dropped. `GatewayPlan::config()` is the only config the caller can build `Gateways` from, and `GatewayPlan::apply` refuses a gateway set that does not match it. `plan_gateway_removal` locks every login account and locks again until the set of login accounts under the locks is a subset of the locked set, then returns `Offline` or `Online`. `Session::remove_gateway`, `gateway_holds_providers` and `Session::hold_accounts` are deleted.

### Tests that moved to the new API

`accounts edit`, `failed_add`, `race`, `stale_launch` and `peers` call `plan_account_edits(&world.desk(), ...)`. The tests that run `plan_account_edits` register the home gateway in the config first (`support::registered`), as production has it, because `apply` now refuses a home gateway the config lacks. `race::two_adds_of_one_name_...` now loses at the plan step (the lock wait ends in `DuplicateName`) before any gateway call. The `cli` tests that add a `claude` or `codex` account with `env:NAME` set that variable in the harness environment.

### Residual

- `gateway add` takes no account lock, and a new login account that is not in the config yet is not in the set that `gateway rm` locks. A `gateway rm` that runs between the config read and the publish of an `account add` (or a launch) of a new login account can leave that account's provider on the removed gateway. Closing it needs one lock for the gateway set that `gateway add|rm`, a gateway-reaching account edit and a launch all take. D26 does not ask for it.
- The new tests have not had an independent test-reviewer red/green pass (AGENTS.md, Tests). The brief named the probes as the red tests; the CLI and session tests above are new.
