### Decided behaviour change (M2)

`jackin workspace add` used to store a lexically normalised path and accepted a path that did not exist. It now stores the real path and fails for a path that is missing or is not a directory. The test `role_workspace::workspace_add_stores_the_docker_flag_and_an_absolute_path_and_ls_pins_the_shape` pinned the old behaviour: it added `proj/one` and `../two` without creating them. It now creates both directories first, and it expects the same stored paths (the test world is already canonical). `config_io` and the duplicate-name case of `role_workspace` create their directories for the same reason. AGENTS.md says jackin keeps no compatibility, so a config that holds a lexical path gets no migration: `workspace_for` still compares the stored path with the current directory, so such a workspace is not found from its real path until it is added again.

### Decisions the brief did not fix

- The CLI has no `workspace rename`. The guard covers `workspace rm` in the CLI, and delete and rename in the console.
- The guard needs every configured gateway. When the config holds a gateway and the workspace exists, `workspace rm` connects to all of them, as account removal does (D26). A gateway it cannot reach stops the command and names `jackin gateway rm <name> --offline`; an unreachable home gateway gives the connect error. A config with no gateway skips the check. The check and the config write are two steps, so a launch between them can still create a sandbox for the removed workspace. This is the same accepted shape as the guarded purge (D08).
- Restore is `Session::power(Start)` and a refresh, as the brief says. D09 makes `jackin-start` write `waiting` on every start, so Codex does not run until `jackin attach --restart`. The row therefore stays `restore available`, and the demo attach that follows the console Restore reports `not running`. Starting Codex again from the console needs the restart path of `Session::restart_agent` and a bounded wait for the `waiting` state; it is not built here (see the backlog items).
- Prewarm picks the gateway and the role as `jackin build` does without a role: the default gateway, the workspace default role, else the only allowed role. It never forces a rebuild.
- The console cannot give a revision for a Git role, so the role follows the default branch of the remote. `jackin role add --rev` still takes one.
- `jackin build` now goes through `jackin_session::build_observed`, so the CLI and the console share one progress loop.
- The docs pages `guides/workspaces.mdx`, `guides/sandboxes.mdx` and `guides/security-model.mdx` state the new behaviour.
- The `screen` check of `xtask` flagged a `"workspace"` literal in the prewarm code (C2). `Config::require_workspace` in `jackin-core` now builds the error, so the screen text comes from a domain crate.
- A CSI that the filter holds back is buffered up to 256 bytes. A longer one is dropped whole, which no real SGR, cursor or mode sequence reaches.
- The console launch of an unsaved directory now resolves the directory through `HostPath::canonical_dir` before it looks for a saved workspace.

## P13.3 interrogate: image

Adversary A found two D05 bypasses in the image build. Both came from one design fault: the guarantee that the role image ends on `FROM construct` and sets no Docker engine client variable rested on `validate_dockerfile`, a second parser of BuildKit's grammar. Any difference between the two parsers is a bypass. The fix checks what BuildKit built.

### Findings and causes

1. HIGH. A role `Dockerfile` could end on any base. jackin read a heredoc where BuildKit read none (an unterminated quote on the heredoc line, a space after `<<`, an expansion in the delimiter, a doubled escape at line end, a backslash followed by VT or FF), skipped the lines to a delimiter that never came, and never saw the real `FROM ubuntu:24.04`. A full build delivered an image whose RootFS layer 0 is `ubuntu:24.04`.
2. MEDIUM. `ENV D\=X DOCKER_HOST=...` sets `DOCKER_HOST` in the final image. BuildKit picks the key-value form with `strings.Contains(words[0], "=")` and splits each word at its first `=`. jackin honoured the escape, read the legacy form, and checked only `D\=X`. The same holds for `A\=`, `\=` and each form under `ONBUILD`.

### Change

- `ImageEngine::inspect(&ImageId)` is the new boundary call. `BuildxEngine` runs `docker image inspect --format {{json .}} <id>` (the allowed `ImageInspect` subcommand, by image ID so a moved tag cannot change what is read) and parses `RootFS.Layers`, `Config.Env` and `Config.OnBuild`. An unreadable or malformed reply is `EngineError::InspectUnreadable`, never a pass.
- `ensure_held` checks the role image after the role build and before the derived build, and the final image after the derived build. It also checks the final image on a cache hit, because `--load` puts the final tag in the engine before the check runs, and `rmi` is not an allowed subcommand, so a refused image stays under its tag. Without the cache check, the second launch would deliver it.
- Rules, in `inspect.rs`: the layers start with the construct layers (an empty construct layer list fails closed); no `Config.Env` name starts with `DOCKER_` or `BUILDX_` (`EnvName::is_engine_client`); no `Config.OnBuild` trigger is an `ENV` (at any `ONBUILD` depth) that names such a variable or a name that expands one. The `OnBuild` rule reuses the text rule. It is defence in depth: a trigger that slips past it still lands in the final `Config.Env`, which is exact.
- A failure is `ImageError::Rule { stage, image, rule }` with `ImageRule::{NotBuiltOnConstruct, EngineClientEnv, EngineClientOnBuild}`. `ensure_image` returns no image.
- The text validator stays as the early, friendly error. Two cheap rules now match BuildKit: the ENV form is `word.contains('=')` with a split at the first `=`, and a line continues only when the line, minus trailing spaces and tabs, ends in the escape character and the character before it is not the escape character (BuildKit's `([^\\])\\[ \t]*$`). The heredoc rules are not changed. The image check is the guarantee.
- `FakeEngine` gains `craft_inspect(stage, ImageInspect)` and an honest default (construct layer first, a layer of its own, an ordinary `PATH`).

### Test plan (for the test-reviewer)

Behaviour: a role or final image is delivered only when its layers start with the construct layers and its config sets no engine client variable. Positive: an image on construct with benign names (`MY_DOCKER_HOST`, `DOCKERHOST`, `docker_host`) and benign triggers (`RUN make`, `ENV FOO=1`). Negative: another base, construct layer not first, no layers, `DOCKER_HOST`/`DOCKER_CONFIG`/`BUILDX_BUILDER`/a bare `DOCKER_CONTEXT` in Env, four OnBuild triggers (including `ENV D\=X DOCKER_HOST=...` and `ENV $NAME=x`), each at the final stage too, the repeat call not served from cache, and the unreadable inspect replies. No other test covers it, because every earlier test used an engine whose images had no config. The two validator rows cover the cheap rules.

### Red lines

Text validator, before the fix (`mbx nextest run -p jackin-image --test dockerfile`):

- `env_may_not_name_the_docker_engine_client_in_the_final_stage`: `an escaped equals sign in the first word: "FROM construct\nENV D\\=X DOCKER_HOST=tcp://evil.example:2375\n"` `left: Accepted` `right: EngineClientEnv(2, "DOCKER_HOST")`
- `an_onbuild_env_is_checked_as_the_env_it_defers`: the same row under `ONBUILD`, `left: Accepted`.
- `only_an_unescaped_escape_followed_by_blanks_continues_a_line`: `a doubled escape ends the instruction: "FROM construct\nRUN true \\\\\nFROM ubuntu:24.04\n"` `left: Accepted` `right: NotConstruct(3, "ubuntu:24.04")`.

Image check, with the inspect result read but its verdict dropped (`mbx nextest run -p jackin-image --test image_io --no-fail-fast rules::`): `Summary 7 tests run: 2 passed, 5 failed`. Each of the five failed with `expected an image rule error, got Ok(BuiltImage { tag: ImageTag("jackin.invalid/sentinel:a8133336c7fa8b57"), ... source: Built })`: the layers, Env, OnBuild, final image and buildx-parse tests. The two that passed are the ordinary-config control and the unreadable-inspect test, which exercises the new boundary only.

### Real engine (OrbStack, builder `orbstack`)

`mbx run -p jackin-session --example build_images -- --role-dir <dir> --role-name probe-f2 --calls 1` with the f2 trigger (`FROM construct`, `RUN true <<EOF # "`, `FROM ubuntu:24.04`) built the role stage and ended with `Error: Rule { stage: Role, image: ImageId(Sha256("691e9341...")), rule: NotBuiltOnConstruct }`, exit 1. No `StageStarted(Derived)` event and no final tag. The role image has one layer, `sha256:107ffca6...`; construct layer 0 is `sha256:9a354992...`.

Control: `FROM construct AS role` (`probe-ok`, two calls) built `Built`, then `Cache` on the second call, which re-verified the cached image against the real `docker image inspect` output. Nothing was run with `docker run`. The probe tags (`jackin.invalid/role/probe-f2:*`, `jackin.invalid/role/probe-ok:*`, `jackin.invalid/probe-ok:*`) were removed with `docker rmi`; the engine image list is identical to the list before the run.

### Not covered

- The adversary's probe files were removed before this work, so the f3 (space after `<<`), expansion-delimiter and VT/FF heredoc triggers were not rebuilt on the real engine. They fail the same rule, because the check reads the built layers, not the text. The fake-engine rows craft that result.
- The BuildKit oracle and the Go toolchain were not available, so the two cheap validator rules follow the regex and the `strings.Contains` rule given in the brief, not a fresh run against BuildKit.
- `rewrite/DESIGN.md` D05 still says the text validation is the guard. The orchestrator should add the built-image check, the cache-hit check, and the `ImageError::Rule` rule names.
