## Decisions applied and choices made

1. The order of the work: the Rust tests and the scan first, then the live runs. The live run found the `/etc/codex` defect below, so the Dockerfile and its test changed after the first gate run.
2. E1 as decided (row 146): Codex installs in the trusted stage and the scan byte-compares both installed files with it. The `chown` repair step still runs through role tools; the scan is its gate (L3d repairs, L3e is refused).
3. The id rule is the successor of the last id (D09). The host half is `jackin-core/tests/supervisor.rs:155-185`; no host test was added.
4. `find -perm /mode` is not accepted by the macOS `find` (`illegal mode string`), so the scan uses the POSIX forms `-perm -4000`, `-perm -020`. The plan review had measured it with the shell's `find` function, which is `bfs`.
5. Odd names: a credential-like variable whose name is outside `[A-Za-z_][A-Za-z0-9_]*` is recorded as `INVALID_NAME other`. dash drops such names from the environment it passes on, so `jackin-start` also reads its own initial environment from `/proc/$$/environ` (a seam in the test). The probe turns it into FAIL.
6. The record is `jackin-env-kinds 1`, `attempt N`, then `main NAME KIND` lines, then `codex NAME KIND` lines, each part sorted in byte order and without duplicates. The sort runs in awk, so `jackin-start` calls only `/usr/bin/awk`, `/usr/bin/tr` (startup only) and `/bin/mv` by absolute path.
7. The probe `VERSION` and the schema `schema` constant are unchanged. The new facts field is required, so an old probe fails the schema.
8. Trailer: the brief asked for `Claude Opus 5.5`; the commits carry `Claude Sonnet 5.5`, the model that wrote them (the harness attribution rule).

## Found by the live runs and not by tests

1. `COPY --chmod=0644 file /etc/codex/config.toml` makes the created directory `/etc/codex` mode 0644. The sandbox user could not enter it and Codex exited 1 at start (`state` went to `exited 1 1`; the p72 image kept `running 1`). Fixed with `--chmod=u=rwX,go=rX`; a static test pins the line and L1 checks the directory modes in the image layers. The scan does not check that a directory is searchable.
2. `jackin build sentinel` refuses the real sentinel worktree: `the build context cannot hold CLAUDE.md: it is a symbolic link`. The role's `.dockerignore` is not applied to the listed context. L5 therefore ran on a scratch copy of the sentinel HEAD without the symlink. The cause is in the role context listing, outside this task.
3. A planted `/usr/local/bin/codex` symlink or setuid file is replaced by the trusted `COPY` and the build passes with the trusted file in the image (L4a, L4c). The scan is the gate for what happens after the `COPY`: L4d shadows `chown` so the derived repair step overwrites codex, and the scan refuses it.

2. `INVALID_NAME` on Linux: dash drops the name, so the record relies on `/proc/$$/environ`. Reading it works in the sandbox (`L8-self`), but no sandbox could be created with a name outside the alphabet (OpenShell was not asked to). The Rust test uses the seam.
3. The Rust `jackin-start` tests ran under macOS `/bin/sh` (bash 3.2 in posix mode) and, as a one-off, under `/bin/dash` (16 of 16). The Linux CI run is the first with Ubuntu dash and mawk through nextest; the live sandbox ran the script under dash and mawk.
4. The `getcap` stub stands for the external libcap program in the Rust tests; the real `getcap` ran only in the live builds.
5. A Codex login or a provider credential was never present, so J07 `codex_exec` stayed SKIP.
