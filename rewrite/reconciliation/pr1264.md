  - Green after revert: 2 tests run: 2 passed

## U6 accounts (C8, C20)

Branch `wt/pr1264-U6`, base `69f94b7c8`. Commits, in order: `b581c8528` (API refactor, behavior unchanged), `f1384e281` (tests), `808765657` (fix). Red ran in a detached worktree at `f1384e281`, green on the fix commit. Commands: `mise exec -- mbx +1.99.1 nextest run -p jackin-session --test accounts` and `... -p jackin --test cli -E 'test(/account/)'`.

### Cause

An account lives in three places: the config, the OpenShell provider of each gateway, and the host login files. Nothing owned the whole life of an account. `GatewayPlan::apply` took one `Session`, published the provider before the config write, and held the account lock only inside each gateway call. So `rm` reached one gateway of N, and the loser of a concurrent `add` could publish after the winner and leave its login on the gateway.

### Fix

- `AccountPlan::apply` and `GatewayPlan::apply` take `&Gateways` (the home session plus every other configured gateway). `Gateways::with_peers` connects the peers. A peer that is down is kept as a typed `UnreachableGateway`, and only a plan that needs it fails.
- `GatewayPlan` keeps only its edits. `apply` takes the account lock of every touched account in name order, reads the config under the lock, plans again, and only then touches a gateway. The loser of a write gets `ConfigError::DuplicateName` before any gateway call.
- Forget (account removed, or its login replaced by a key) runs on every gateway. A renewed login is published to the home gateway and to every peer that already holds the provider. A new account is published to the home gateway only. A plan that forgets or renews needs every gateway, or it fails with `AccountEditError::Unreachable(Vec<UnreachableGateway>)` before any change. A gateway call that fails is `AccountEditError::OnGateway { gateway, source }`.
- If the config write fails, the providers that this call created on the home gateway are removed. A provider that existed before is left alone. A failed removal is `AccountEditError::RollbackFailed`, which names the account and the gateway and keeps the first error.
- The CLI builds `Gateways` with `App::gateways`. `Session::forget_account` is removed.

### DESIGN text for the orchestrator (C-5)

D26, append after the sentence "An OpenShell provider (D10) exists only for accounts that an agent uses. Accounts of other providers stay on the host for usage only.":

> An account with an OpenShell provider is forgotten on every configured gateway, not only the selected one. The CLI and the console remove the provider from every configured gateway when they remove the account or replace its ChatGPT login with another credential, and they replace the provider on every gateway that already holds it when the login is renewed. A new account gets its provider on the selected gateway only. If a gateway that the edit must reach cannot be reached, the edit stops before any change and names the gateway; the operator can remove that gateway from the config and repeat. Jackin takes the lock of each touched account first, reads the config under it, publishes the provider only then, and writes the config before it releases the lock. The account that loses a concurrent write fails with the duplicate-account error and leaves nothing on any gateway. If the config write fails, jackin removes the providers that this edit created.

### Residual

- A plan that is offline at planning time (for example the removal of a key account) takes no account lock and does not read the config again. If another process turns that account into a ChatGPT login between the plan and the write, the new provider is not forgotten. Only a console edit can do this. Fixing it needs the offline path to lock and plan again, and to fail when the second plan needs a gateway.
- The removal of providers after a failed config write is best effort per account on the home gateway. A failure is reported as `RollbackFailed`, but jackin does not retry it.
- `gateway rm` still leaves the providers of that gateway behind. It is outside this unit.
- `account add` connects every configured gateway to build `Gateways`, so a slow peer slows an add that needs only the home gateway. The add itself does not fail.
