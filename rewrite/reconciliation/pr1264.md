### S1 `until_held`

- **Break a (plan):** `until_held` returns `false` at once.
  - Red: 2 tests run: 0 passed, 2 failed; `holds.rs` `the create never arrived` and `nothing had arrived yet`
  - Green after revert: 2 tests run: 2 passed
- **Break b:** the old poll comes back (2,000 polls of 1 ms, `tokio::time::sleep`).
  - Red: 1 failed, 1 passed; `the create never arrived`. The test starts paused and the create arrives after 5 s of virtual time. The poll gives up after 2 s of virtual time.
  - Green after revert: 2 passed
- The first test pins the wait to an event. The second pins the two cases where no arrival can come: no hold armed, and a release before the arrival. In both, `until_held` returns `false` at once. The old code waited 2 s of real time for them.

### S2 `sleepers`

- **Break:** `Waiter::drop` does not remove the id from `waiting`.
  - Red: 1 failed; `assertion 'left == right' failed: a dropped sleep still counts | left: 2 | right: 1`
  - Green after revert: 1 passed
- The test also drives a sleep to its end (`advance`, then poll) and expects 0 sleepers and one entry in `slept()`.

### S3 `FakeEngine::hold` and `waiters`

- **Break (plan):** `hold` returns `Ok(None)`, the trait default.
  - Red: 2 failed; `Error: "the fake engine granted no lock"` in both tests
  - Green after revert: 2 passed
- The assertions repeat the three that `crates/jackin-image/tests/image_io/lock.rs` makes for the real `BuildxEngine::hold`:
  - A second hold of one key waits until the first is dropped. Here that is `waiters` 1, then 0.
  - Different keys do not wait.
  - A waiter that is cancelled returns `Cancelled` and changes nothing for the holder: a later hold on the key still waits.
- The real engine has no `waiters`, so the fake test reads the wait from `waiters` and the real test reads it from the `contended` signal of `SignalFs`. The fake takes its exclusion from a `BTreeSet` of held tags and a `Notify`, not from a file lock. No other owned code is faked.

## U7 usage cache and atomic writes (C9)

Branch `wt/pr1264-U7`. Test commit `854096631`, fix commit `3f386d1f5`. Red ran from the test commit in a detached temporary worktree. Green ran on the fix commit. Command: `mise exec -- mbx +1.99.1 nextest run -p jackin-core --test write_atomic -p jackin-usage --test usage -E 'test(two_writers) | test(concurrent_reports)'`.

Cause: `write_atomic` named its temporary file `.<name>.tmp`, one name per target, so it was atomic for one writer only. Every caller inherited that: `Manifest::write`, `ConfigStore::edit` (safe only because it takes its own lock), the testkit runner, and the usage cache. The usage cache also kept a start-of-run snapshot across the provider fetch and wrote it back whole, so a run dropped the entries of runs that finished meanwhile and brought back entries they removed.

Fix:

- `write_atomic` writes `.<name>.<pid>-<n>.tmp` with a process-wide counter. One change fixes every caller.
- `hold_lock(fs, clock, path, plan, cancel)` in `jackin-core` `wait.rs` is the one polling lock helper, built on `poll_until`. U3 reuses it.
- `Cache` records its edits (`Set`, `Remove`). `save` takes `usage.json.lock` through `hold_lock`, re-reads the file, applies only those edits, and writes. The lock covers the read, merge, and write. It is not held across the fetch.

| U7.2 | `jackin-usage usage cache::concurrent_reports_neither_drop_nor_bring_back_cache_entries` | `kept: Err("router was not served from the cache: Unavailable(Network(\"the connection failed\"))"); removed: Err("the removed entry came back: Windows([LimitWindow { kind: FiveHour, label: \"5-hour\", ... used: Some(Percent(10.0)) ...}])")`. Both cases are red. | passes |

### Security follow-up, for test-reviewer judgement (U7-1)

Base `923275b31`. Finding U7-1 of `/private/tmp/claude-501/plans/pr1264-wave1-security.md` (Low, CWE-459): a process killed between `write_new` and `rename` left `.<name>.<pid>-<n>.tmp` for good, at mode 0600, one more copy per crash. The old fixed name healed itself. Proof of the leak: `h-u7` and `h-base` in `/private/tmp/claude-501/w1-sec/`, three SIGKILLs during a 300 MB write, three leftovers after the clean write.

Break with the fix in place: the digit test becomes `all_digits(pid) || all_digits(count)`. Red: the non-matching files `.usage.json.4242-.tmp`, `.usage.json.x-0.tmp`, `.usage.json.4242-0.5-6.tmp` and `.usage.json.lock.4242-0.tmp` (and the same four for `config.toml`) are missing from `left`. A break that drops the digit test entirely does not build (`all_digits` is dead code under `-D dead-code`). Logs: `/private/tmp/claude-501/w1-sec/u7-red.log`, `u7-green.log`, `u7-break.log`.

Fix: `write_atomic_locked(fs, path, bytes, mode, &FileLock)` in `crates/jackin-core/src/fs.rs` removes every regular file in the target's directory whose name is `.` + the target name + `.` + digits + `-` + digits + `.tmp`, then calls `write_atomic`. A directory, a symlink and every other name stay. Listing or removal errors are ignored, like the cleanup of `write_atomic` itself. `ConfigStore::edit` and `Cache::save` call it with the lock they hold. `RoleManifest::write` and the testkit runner write without a lock, so they keep `write_atomic` and never sweep.

Why the sweep cannot remove another live writer's temporary file:

- A live temporary file of a target exists only between `write_new` and `rename` of a `write_atomic` call on that target. The sweep runs in a writer that holds the target's lock, before its own `write_new`. So it can only meet a live file if a second writer of the same target writes without that lock.
- `ConfigStore::edit`: it binds `lock = self.lock()` (`config.toml.lock`, built from `self.path`) before the read and passes `&lock` to the write; the lock lives to the end of `edit`. The only non-test code that calls `write_atomic` for the config path is this method, so every writer of `.config.toml.*.tmp` takes that lock, in this process and in another jackin process (a `flock` on the same file).
- `Cache::save`: it binds `lock = hold_lock(.., usage.json.lock, ..)` before the re-read and passes `&lock` to the write. `Cache::save` is the only writer of `usage.json`.
- The signature makes the call impossible without a `FileLock`. It does not check that the lock belongs to this target. A caller that passes a lock for another file removes a live temporary file. A scratch test (not kept) showed both sides on `StdFileSystem`: writer A holds `usage.json.lock` and is parked at its `rename`; the directory lists `.usage.json.<pid>-0.tmp`; a second `fs.lock` returns `LockHeld`; A returns `Ok`. With A holding no lock and a sweep running under `other.lock`, A fails with `Io { kind: NotFound, .. .usage.json.<pid>-2.tmp }`.
- Existing tests that keep the lock honest: `config_store.rs::concurrent_edits_serialise_on_the_lock_and_lose_no_update` and `usage cache::concurrent_reports_neither_drop_nor_bring_back_cache_entries`.

Pre-existing flake found while gating: `jackin::cli usage::*` (for example `usage_shows_decimals_money_left_and_a_dash_for_no_reset`) fails with `the usage cache at .../usage.json.lock failed: timed out after 10s waiting for the cache lock` in about one of two runs of `nextest run -p jackin --test cli`. The two accounts of the test save the cache at once, and `FakeClock::sleep` advances the 10 s of virtual time while the lock holder is inside blocking file work. With the sweep disabled the same binary failed in 5 of 8 runs; with the sweep, 3 of 6. The single test passed 40 of 40 runs alone. The cause is in `hold_lock` under `FakeClock`, not in the sweep, and it is not fixed here.

Limits: the sweep is best effort and runs only on a save, so a crash is cleaned up at the next save of the same file, not at once. A leftover of a target that is never written again stays. The sweep matches only names of the target in its own directory.
