## The command

```text
xtask e2e --gateway <name> --role <dir>
          [--jackin <path>] [--codex-home <dir>] [--builder <name>] [--platform <p>]
          [--engine-port <port> --engine-certs <dir>] [--log-dir <dir>] [--sweep]
```

G-E2E: `mise exec -- mbx +1.99.1 xtask e2e --gateway jackin-local --role ../jackin-sentinel`. With the operator's D24 test engine, J15 and J16 also need `--engine-port 2376 --engine-certs ~/.local/share/jackin-e2e-engine/client`.

Operator setup for J15 and J16 (also in `xtask e2e --help`): a rootless dockerd 29.9.2 at `host.openshell.internal:2376` (`localhost:2376` on the Mac), client certificates in `~/.local/share/jackin-e2e-engine/client/`. The operator starts and stops the engine. The runner never does.

Exit codes: 0 every line PASS; 1 a FAIL or a `CLEAN FAIL`; 2 the run could not start (arguments, no A1 source, A1 lock held, stale `e2e-` resources, gateway unreachable, config build failed); 3 no FAIL and at least one SKIP; 130 interrupted. There is no `--only`.

## Decisions the brief did not specify

1. **Usage retry.** "Retried three times" is 1 + 3 retries, 4 attempts (`USAGE_ATTEMPTS`). The backoff is `Budgets.usage_backoff` (20 s in production, 5 ms in tests). `expired_login`, `no_credentials` and `unsupported` for A1 fail at once. A fixture account is judged on the first response only.
2. **J00 settles right after J03**, not after the shared probe. It runs its own `--only J00` probe and a `sha256sum` exec in sandbox S. If J03 produced no sandbox, J00 prints SKIP (blocked by J03). J05 settles after J13 (its status check spans J03 to J13). J08 settles after J17 (its needle scan covers every captured channel of the run).
3. **Dependencies.** A build failure blocks J03 to J17. A J03 FAIL blocks J04 to J14 and J16. J15 and J17 use their own sandboxes and still run. A J07 FAIL blocks J11 and J12, which need a running Codex. Nothing else blocks.
4. **Cleanup is shielded.** After a cancel the runner uses a fresh token for its host and gateway calls, so a second signal prints `cleanup in progress` and changes nothing. A sandbox delete is tried twice (`DELETE_ATTEMPTS`).
5. **Sweep.** `--sweep` needs neither A1 nor the lock, and `--role` is not required. It prints `SWEEP PASS ...` or `SWEEP FAIL ...` on stdout.
6. **Host default engine.** J15 reads the host engine id and container names over the unix socket (`DOCKER_HOST` or `/var/run/docker.sock`) with a small HTTP client, not with the `docker` binary. The repository rule keeps `docker` in `jackin-image`.
7. **Provider list.** `openshell provider list -o json` runs through `HostProcess`, because `Gateway` has no list call.
8. **PTY shell markers** use a random 6-digit nonce, computed by the shell (`$((N-7+7))`), so the typed echo can never satisfy the match and output that contains a marker-looking text is data.

## Verified live (read-only probes against `jackin-local`, 2026-11-03)

`openshell -g jackin-local sandbox create --name p81-shape --from jackin.invalid/construct:p72 --label jackin.dev/managed=true --env P81_VISIBLE=hello --detach --no-tty -o json -- sleep 300`, then `sandbox get p81-shape -o json`, then `sandbox delete p81-shape`. Keys: `annotations`, `conditions[]`, `configuration_admission`, `created_at`, `created_from_workload_template`, `current_policy_version`, `endpoint_statuses[]`, `exit_code`, `host_key_fingerprint`, `id`, `labels` (a flat string map), `last_token_grant_failure`, `main_process_instance_id`, `main_process_started_at_ms`, `name`, `next_restart_at_ms`, `phase`, `policy`, `policy_source`, `provisioning`, `resource_version`, `restart_count`, `restart_policy`, `revision`, `workspace`.
- **It does not carry the create-request environment.** The sandbox was created with `--env P81_VISIBLE=hello`; neither the key nor the value is anywhere in the JSON, the YAML or the table view. It has no provider list either.
- The decision text says J08 reads the create-request environment from this JSON. That is impossible from the CLI view, so J08 reads it through the gRPC API instead (next section). The `sandbox get -o json` record stays as a second channel: it must parse and is needle-scanned, and unreadable is a FAIL, never a SKIP. The environment as an exec process sees it (`/usr/bin/env`) is a third channel: every `CODEX_AUTH_*` value must be an `openshell:resolve:` placeholder.
- `openshell -g jackin-local provider list -o json` prints `{"next_page_token": "", "providers": []}` when empty. An entry has the keys `credential_keys`, `id`, `name`, `resource_version`, `type`, `workspace` (seen on a `jackin-p81x-a1-codex` provider that the F3 experiment created and deleted).
- The `jackin.invalid/construct:p72` image has no `codex` binary, so the F3 check was first designed with `codex sandbox`. The first live run showed that `codex sandbox` cannot run (bubblewrap needs user namespaces, which the sandbox seccomp denies). The redesign is in "The first live run" below.

## The create-request environment (`Gateway::sandbox_environment`)

- **Proto field.** `GetSandbox` returns `SandboxResponse.sandbox` (`Sandbox`). `Sandbox.spec` is field 2 (`SandboxSpec`), and `SandboxSpec.environment` is field 5, `map<string, string>`, "Environment variables injected into the sandbox runtime" (openshell v0.1.6, `proto/openshell.proto` lines 1044-1067). The CLI JSON drops `spec`; the gRPC reply keeps it.
- **API.** `Gateway::sandbox_environment(&SandboxName) -> Result<BTreeMap<EnvName, String>, GatewayError>`. `GrpcGateway` calls `GetSandbox` and returns `spec.environment` (a missing spec or an invalid variable name is a protocol error; an absent sandbox is `NotFound`). `FakeGateway` returns the environment of the stored spec (`JACKIN_LAUNCH_ID`). The contract check `sandbox_environment_is_the_create_request` and an absent-sandbox row in `absent_sandbox_is_not_found` pin both. `CORE_CHECKS` grows from 15 to 16.
- **Live result** (2026-11-03, `jackin-local`): sandbox `jackin-p81-env` created with `--env P81_VISIBLE=hello --env JACKIN_LAUNCH_ID=live-probe`, then deleted (the gateway listed no sandbox afterwards). A throw-away example (not committed) connected through `production()` and called `sandbox_environment`. It printed `JACKIN_LAUNCH_ID len=10` and `P81_VISIBLE len=5`: both variables come back through the adapter, values intact (printed as lengths only). The name has the `jackin-` prefix because `SandboxName` is a typed DNS-19 name that requires it.
- **J08.** The host compares `JACKIN_LAUNCH_ID` with the launch, scans every value for the A1 needles without logging a value (channel `J08 create environment`), and requires a credential-shaped variable (`CODEX_AUTH_*`, or a name with `TOKEN`, `KEY`, `SECRET`, `PASSWORD`) to be empty or an `openshell:resolve:` placeholder. A failure names the variable and the class (`kind other`), never the value. An unreadable call is a FAIL. No blocker report is needed, because v0.1.6 exposes the environment.

## Deviations from the approved plan v2

1. **C1, pin sources.** The row "`compatibility.lock.toml [codex]` differs from `AgentSpec`" has no test. Both values are compile-time constants (`include_str!` and a `static`), so no input of `run_e2e` can make them differ. `judge_pins` compares them at run time; only a change of either constant exercises it.
2. **C4, name of 20 characters.** `SandboxName` is a DNS-19 type, so the gateway boundary cannot return a 20-character name. The row became "a name without the `-<4>` suffix" (`jackin-main`). The 19-character name is the pass control as planned.
3. **`Fault::StallProgram` is not used.** `ScenarioGateway` answers `run_program` itself, so the stall is its own knob (`hang_probe`), and the timeout rows (B5, A4, G2a) use the real clock with small `Budgets` instead of a paused tokio clock.
4. **B5, "killed by a signal".** `ProgramOutcome` carries an exit code only, so the row cannot exist at this boundary.
5. **G3.** The sandbox half uses `Fault::FailNext { Delete }` twice, one fault for each of the `DELETE_ATTEMPTS = 2` attempts, injected after the last journey command. The provider half uses a decorator knob (`stuck_provider`), because a `FailNext { Provider }` is also consumed by `provider_state`.
6. **The default panic hook.** `run_e2e` replaces it for the run (`QuietPanics`) so a panic message cannot reach the real stderr. The default hook writes to the process stderr, which no sink sees, so the test installs its own recording hook before the run, runs a scenario whose probe panics with a token in the message, and checks that the recording hook heard nothing (`a_step_panic_never_reaches_a_panic_hook_installed_before_the_run`). Row NE-PH goes red when `QuietPanics::install` stops replacing the hook. The scrubbing of the panic text in the report is covered separately (D1).
7. **Test count.** The plan counts 59 rows. The suite has 66 test functions in `e2e` because A1, A3 and C17 are split where one function would have hidden the second case behind the first.
8. **B2.** The typed second pass is implemented as a re-validation of the failing `facts` subtree against `$defs/FactsJxx`, so the leaf pointer (`/steps/J05/facts/files/0/sha256`) is reported next to the `anyOf` pointer.
