## Class definitions

- **VALUABLE** — a feature, fix, or improvement whose content is **not** in `main`. The work still carries value and must not be lost. It is not proven contained.
- **CONTAINED** — the branch's content is **fully in `main`**, and the proof is recorded (merged PR / patch-id equality / ancestry / empty diff against main). Nothing is lost by retiring the branch.
- **DEBRIS** — logs, progress output, temporary scratch work, stash-recovery snapshots, generated artifacts, or duplicates of other branches. No unique product value.
- **VALUABLE (port candidate)** — a sub-class of VALUABLE for branches whose content is absent from `main` and therefore not landable as-is, but whose unique content may still be worth porting onto `main` by hand. Such branches are **excluded from the deletion list** and are never deleted without an explicit operator decision. **0 branches are in this state as of 2026-11-13**: the 3 branches that entered it on 2026-11-13 (`recovery/pr1230-blob-auth-77b399f1-20261027`, `recovery/stash-adoption-6a0d2f03-20261025`, `recovery/strip-tests-restore-20261030`) left it again the same day, when the **completed** portability assessment returned **DISCARD** for all three. They are recorded as **DEBRIS (superseded)** with their port reference kept — see 'Portability assessment - COMPLETED (2026-11-13)'.
- **CONTAINED candidate - UNPROVEN** — the branch is *believed* to be contained, but the proof is incomplete: the paths it changes are ABSENT from `main` and carry product code, so containment is NOT proven. Such branches are counted in the CONTAINED column for tracking only; they must be treated as VALUABLE (NOT deletable) until every absent path is proven to be scratch/archive. 5 branches were in this state, all in `jackin-project/jackin`; their verdicts are now known (2026-11-13): **exactly 4 are CONTAINED-safe-to-delete** (`codex/openshell-integration-checkpoint-20261108-122311`, `codex/openshell-verified-checkpoint-20261108`, `preserve/session-boundaries-20261109`, `preserve/w1-fixes-20261109`) and **1 (`preserve/p0.6-prototype-20261109`) is DEBRIS, not CONTAINED**, so it needs **its own ratification word**. See 'CONTAINED candidates - current verdicts (2026-11-13)'.

**Counts** are per repository, per class, and are derived from the tables below.

**Shell-safety rule - it applies to every command in this document: a branch name (or any other ref or path) is NEVER spliced unquoted into a shell command.** Every value a command needs is obtained **programmatically from the repository** and is then used only as a double-quoted expansion, so a name is handed to the command as **data** and can never be evaluated as code. The earlier revision of this document asked the operator to paste a branch name into a quoted placeholder; that is unsafe, because a git ref may contain a single quote (`git check-ref-format --branch` accepts `review/'$(id)'`) and pasting such a name into `branch='<branch>'` executes the rest of it as shell source (`branch='review/'$(id)''` runs `id`). The placeholders are therefore gone: the audited branch, the branch it is compared against, their tips, the merge base, the parent, the ref and the path are all read from the repository by the commands in 'DEBRIS audit - reproducible commands', and the operator enters only a line number - and, for a comparison branch that is no longer live and whose ref the clone does not hold, the tip SHA that the row of that branch records, which is read with `read -r` (so it is data and never shell source) and rejected unless it is hexadecimal.

### Port carve-outs (items of code, NOT branches to delete) — P1 PORT-LATER, P2 DISCARD

### DEBRIS audit - reproducible commands

The 15 rows below are backed by the one-line proofs of the 2026-11-13 DEBRIS audit. The two audit reports that produced them (`debris-ratification.md` for the 13 jackin/baseline rows and `smith-debris-verify.md` for the 2 smith rows) are **not committed to this tree** (`git ls-tree -r --name-only HEAD | grep -E 'debris-ratification|smith-debris'` = 0 hits), so every claim is reproduced here by the command that produced it and the measured output that the row cites. All of them run against the live remotes and need no private state.

**How to run them - every value is read from the repository, and every use of it is double-quoted:**

```bash
repo='jackin-project/jackin'
branch_slot=1
other_ref_slot=1
branches="$(gh api "repos/$repo/branches" --paginate --jq '.[] | [.name, .commit.sha] | @tsv')"
branch="$(printf '%s\n' "$branches" | sed -n "${branch_slot}p" | cut -f1)"
tip="$(git ls-remote --heads "https://github.com/$repo" "refs/heads/$branch" | cut -f1)"
git fetch --quiet origin "+refs/heads/*:refs/remotes/origin/*"
other_refs="$(git for-each-ref --format='%(refname:strip=3) %(objectname)' 'refs/remotes/origin' | grep -v '^HEAD ')"
other_branch="$(printf '%s\n' "$other_refs" | sed -n "${other_ref_slot}p" | cut -d' ' -f1)"
other_tip="$(printf '%s\n' "$other_refs" | sed -n "${other_ref_slot}p" | cut -d' ' -f2)"
if [ -z "$other_tip" ]; then
  IFS= read -r -p 'tip SHA of the comparison branch, as recorded in its row: ' other_sha
  case "$other_sha" in
    ''|*[!0-9a-f]*) printf 'not a hexadecimal SHA\n' >&2 ;;
    *) git fetch --quiet origin "$other_sha" && other_tip="$other_sha" ;;
  esac
fi
merge_base="$(git merge-base origin/main "$tip" || echo '')"
empty_tree="$(git hash-object -t tree /dev/null)"
base="${merge_base:-$empty_tree}"
parent="$(git rev-parse "$tip^")"
ref="$tip"
path="$(git diff --name-only "$base..$tip" | sed -n '1p')"
```

`repo` is the repository slug and the only value that is typed in: GitHub allows only letters, digits, `.`, `-` and `_` in a repository name, so it cannot carry a shell metacharacter. `branches` is the branch list of that repository as the API returns it - one `name<TAB>sha` line per branch; print it with `printf '%s\n' "$branches" | cat -n` and set `branch_slot` to the line number of the audited branch **in that list**. The comparison branch is chosen from a second list: print `other_refs` with `printf '%s\n' "$other_refs" | cat -n` and set `other_ref_slot` to the line number of the comparison branch **in that list**. The two lists have a different content and a different order, so a line number of one is never a line number of the other. `branch` is the audited branch and `tip` its live tip SHA (an empty `tip` means the branch is not live); `other_refs` is the list of the clone's remote-tracking refs - `<name> <sha>` per line, live and stale - and `other_branch` and `other_tip` are the comparison branch and its tip SHA, read from that list, `merge_base` the merge-base of the audited branch with `main` (empty for a branch that has none, e.g. the orphan `rollout/velnor-3-provider`), `empty_tree` the empty tree object (`git hash-object -t tree /dev/null` = `4b825dc642cb6eb9a060e54bf8d69288fbee4904`), `base` the merge base, or the empty tree when the branch has none, `parent` one of the parents of the tip, `ref` a ref of the repository and `path` a path of the branch. **`base` is the enumeration base on purpose**: a range whose first endpoint is missing is not an error but a different question - `git rev-parse '..<tip>'` expands to `<tip>` **and `^HEAD`**, so `git diff --name-only "..$tip"` compares the tip with the current checkout instead of enumerating the branch from its root (measured on the orphan `rollout/velnor-3-provider`, live tip `092fe1db`: the empty-tree base enumerates the 28 paths the branch carries, the `"..$tip"` form compares against `HEAD` and prints 1305 paths). **No name is pasted**: every branch name, tip, path and ref is read from the repository by the commands above, so a name that contains a single quote or a `$(...)` is data and never shell source. The fetch above is part of the setup: `git ls-remote` only **reports** a SHA and does not download the objects behind it (`git ls-remote -h` lists remote refs, `git fetch -h` fetches a refspec), so a narrowly fetched clone holds neither the tip of `main` nor the objects of the comparison branch - `git cherry "$other_tip" "$tip"` then fails with `fatal: unknown commit`, and every ancestry, `git cherry`, blob-equality and absent-path result would be computed against a stale `main`. The refspec `"+refs/heads/*:refs/remotes/origin/*"` refreshes `origin/main` and every live branch whatever the clone's own fetch configuration is, and it does **not** prune: a branch that has been deleted from the remote keeps the remote-tracking ref - and the objects - that the clone holds, so a comparison against a branch that is no longer live is possible. `other_branch` is therefore chosen from `other_refs` and not from the live branch list: for a live comparison branch `other_tip` is its live tip, and for a branch that is no longer live it is the tip the clone holds, which is the tip recorded in that branch's row. When the comparison branch is no longer live **and** the clone does not hold its remote-tracking ref, `other_tip` is empty and the block asks for the tip SHA that the row of that branch records: the value is read with `read -r`, so it is data and never shell source, and it is accepted only when it is hexadecimal. `git fetch origin "$other_sha"` then brings the commit into the clone - GitHub serves a commit that no ref points at (measured: `git fetch origin 1b77800e850c6cefda337e5229b5d9eb8b4dfa65` -> `FETCH_HEAD`), so the audit needs no private state and works in a fresh clone. The `git` commands run in the clone of the audited repository, whose remote is `origin`, and every one of them takes a resolved object id (`"$tip"`, `"$other_tip"`, `"$parent"`) or a double-quoted ref, so it also works in a clone that has only `refs/remotes/origin/<branch>` and no local branch of that name.
