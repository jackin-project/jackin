## Need 1. A named check cannot provision `reuse`

### Need

A named check must run `mise run ci:full`, which runs `mbx +1.99.1 xtask ci --no-docs`. The `Reuse` step of that command starts `reuse lint`. `reuse` is a PyPI package (`pipx:reuse` 6.3.0 with the `charset-normalizer` extra in `mise.toml`). Velnor admits qualified tools only through the `core`, `aqua`, and `cargo` backends, so no check can put `reuse` on its PATH.

Without `reuse`, a check named `repository-gates` fails at the `Reuse` step. Without the check, no CI job runs the comment, layer, and container steps, because `xtask ci` has no single-step mode (see Need 3).

### Command

Add a qualified tool with the backend the package needs, then plan:

```toml
[[qualified_tools]]
id = "reuse"
version = "6.3.0"
depends_on = []

[qualified_tools.backend]
kind = "pipx"
package = "reuse"

[qualified_tools.options]
kind = "default"
```

```sh
velnor-actions plan
```

### Output

```text
velnor-actions: .velnor/config.toml: document: TOML parse error at line 291, column 8 | 291 | kind = "pipx" | ^^^^^^ unknown variant `pipx`, expected one of `core`, `a
```

A check that lists the tool without a qualified record fails earlier:

```text
velnor-actions: .velnor/config.toml: checks[1].tools: unknown_qualified_tool:reuse
```

`docs/implemented/qualified-check-tools.md` in `velnor-new` states the closed set: `QualifiedToolBackend` supports `core` (rust, node, bun, zig, python), `aqua`, and `cargo`.

### Smallest failing case

One `[[checks]]` entry with `tools = ["reuse"]` and no way to write the matching `[[qualified_tools]]` record.

### Proposed upstream change

Add a closed `pypi` qualified-tool backend. Its record names the PyPI package and the exact version, depends on one qualified `core` Python tool, and lists every wheel with a URL and a SHA-256, sorted like the other artifact lists. Installation uses `pip install --no-index --no-deps --require-hashes` into an owned prefix, so no network resolution and no ambient index can fill a gap. The installed-tree digest and the executable probe bind the result, as for the other backends.

The input exists in this repository. `.mise/locks/pipx-reuse/6.3.0~068c1fb0/uv.lock` pins the full closure of `reuse` 6.3.0 with `charset-normalizer`. A generator command could turn that lock into the artifact list, the way `qualify-tools` turns archives into records.

When this ships, add this check and regenerate:

```toml
[[checks]]
id = "repository-gates"
task = "ci:full"
directory = "."
inputs = [".velnor/config.toml", ".cargo/config.toml", "Cargo.lock", "Cargo.toml", "clippy.toml", "deny.toml", "mise.lock", "mise.toml", "rust-toolchain.toml", "REUSE.toml"]
tools = ["cargo-deny", "cargo-nextest", "cargo-shear", "mr-boxington", "reuse", "rust"]
timeout_minutes = 20
```

The check also needs qualified records for `mr-boxington`, `cargo-nextest`, and `cargo-deny` on `linux_x64`. `velnor-actions qualify-tools` runs its version probes on the host platform, so an operator must run it on a Linux x64 host. That is a procedure, not a missing feature.

## Need 2. The generator pins `gh` itself and verifies it against the consumer lock

### Need

The generated `required` job runs `mise --no-config --no-env --no-hooks install gh@2.103.3` (`.github/workflows/ci.yml`, step "Prepare pinned tools"). The version comes from Velnor, not from the consumer. `generate` then checks that pin against the consumer `mise.lock`. When the consumer does not list `gh`, `generate` prints a warning and the install runs unverified.

This repository does not use `gh` in any gate. It keeps `gh = "2.103.3"` in `mise.toml` and `mise.lock` only to satisfy the generator.

### Command

Remove `gh` from `mise.toml` and `mise.lock`, then run:

```sh
velnor-actions generate
```

### Output

```text
tool_install_unverified:1 installs skip verification: gh@2.103.3(no_entry); install on the CI platform and commit the lock to verify them
```

### Proposed upstream change

Carry the archive digests of the tools that the generator installs for its own jobs inside the generator release, and verify against them. A consumer then needs no `mise.toml` entry for a tool that only Velnor jobs use. The consumer lock stays the authority for consumer tools.

## Need 3. A single-step selector in `xtask ci` (this repository, not Velnor)

`xtask ci` accepts only `--fast` and `--no-docs`. A CI job that needs the comment, layer, and container steps must also rerun `fmt`, `clippy`, and `nextest`, which the Rust stack already runs per crate. `--only <step>` or `--skip <step>` in `crates/xtask/src/main.rs` removes the duplicate work and lets `hk` run the D17 comment step alone. P2.4 does not change xtask code. The orchestrator decides whether a later task adds it.
