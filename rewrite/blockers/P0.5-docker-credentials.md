## Section 1. No working credential injection for a Docker engine

### Missing capability

The OpenShell proxy cannot hold a Docker engine credential and use it for the calls that `docker run` and `docker exec` need. Two credential forms exist for an engine, and neither works:

| Form | Where the credential lives | What fails |
|---|---|---|
| Bearer token in a provider, injected by the L7 proxy | Gateway. The sandbox holds a placeholder. | Attached `docker run` and `docker exec`. The BuildKit build returns `401`. |
| mTLS client certificate | Must be a file in the sandbox | Nothing fails, but the key is in the sandbox. The proxy cannot present it upstream. |

### Smallest failing case: bearer injection

Setup (operator): a dedicated dind engine on plain TCP, behind an nginx front end that returns `401` unless `Authorization: Bearer <token>` matches and that forwards `Upgrade`. A provider profile with one credential and `auth_style: bearer`, an endpoint `host.openshell.internal:<port>` with `protocol: rest`, `access: full`, binary `/usr/local/bin/docker`. A provider created from the token. A sandbox created with `--provider`. The client sends the placeholder through `HttpHeaders` in `~/.docker/config.json`.

Commands and output (lane B, [laneB:368-386](../evidence/P0.5-docker-laneB.md)). The sandbox holds only the placeholder, and the proxy swaps it:

```text
$ X p05b-inj 'echo "P05B_ENGINE_TOKEN=$P05B_ENGINE_TOKEN"; cat /sandbox/.docker/config.json'
P05B_ENGINE_TOKEN=openshell:resolve:env:v3346327621359967627_P05B_ENGINE_TOKEN
{"HttpHeaders":{"Authorization":"Bearer openshell:resolve:env:v3346327621359967627_P05B_ENGINE_TOKEN"}}
$ X p05b-inj 'export DOCKER_HOST=tcp://host.openshell.internal:12378; docker version --format "server={{.Server.Version}}"; id=$(docker run -d hello-world | tail -1); sleep 3; docker ps -a ...; docker logs $id | head -2; docker run --rm hello-world 2>&1 | tail -2'
server=29.9.2
created=f8532f47f5c5
hopeful_carson hello-world Exited (0) 3 seconds ago
Hello from Docker!
unable to upgrade to tcp, received 200
$ X p05b-inj '(config.json moved away) docker version'
<center><h1>401 Authorization Required</h1></center>
```

`X <sandbox> '<cmd>'` is `perl -e 'alarm shift; exec @ARGV' 90 openshell -g jackin-local --workspace default sandbox exec -n <sandbox> --no-tty -- sh -c '<cmd>' </dev/null` ([laneB:11-16](../evidence/P0.5-docker-laneB.md)). The placeholder is not a secret.

Reading of the output:
- Without the header the front end returns `401`. With the placeholder `docker version`, `run -d`, `logs`, `ps` and the legacy builder (`DOCKER_BUILDKIT=0 docker build`) pass. The proxy replaced the placeholder with the real token.
- The foreground `docker run --rm hello-world` pulls and creates the container, then fails with `unable to upgrade to tcp, received 200`. The proxy log shows `HTTP:POST .../containers/<id>/attach ALLOWED` ([laneB:248-251](../evidence/P0.5-docker-laneB.md)).
- Same failure without any credential, on a `protocol: tcp` endpoint with no `tls: skip` ([laneB:233-253](../evidence/P0.5-docker-laneB.md), [laneA:690-702](../evidence/P0.5-docker-laneA.md)). The failure comes from the HTTP relay, not from the credential.
- With `tls: skip` the same command passes ([laneB:255-263](../evidence/P0.5-docker-laneB.md)). A `tls: skip` tunnel is opaque, so credential rewrite does not apply to it (`docs/how-it-works/providers/overview.mdx:457-459`, `docs/how-it-works/providers/profiles.mdx:142-143`). That is why the working route needs the key in the sandbox.

Other results, with their evidence level:
- `docker exec` uses the same attach and `Upgrade: tcp` call. Both lanes report it failing under injection ([laneA:563-565](../evidence/P0.5-docker-laneA.md), [laneB:253](../evidence/P0.5-docker-laneB.md)). No lane has a raw `exec` error line. Proven for `docker run`, expected for `docker exec`.
- BuildKit `docker build` returns `401` under injection. The cause, that `docker-buildx` does not send the `config.json` header on its own connections, is inferred ([laneA:565](../evidence/P0.5-docker-laneA.md), [laneB:386](../evidence/P0.5-docker-laneB.md)). No lane has a raw transcript of the `401`.
- Lane A's committed run of the same route hit the 120 s alarm before the error line ([laneA:555-557](../evidence/P0.5-docker-laneA.md)). Lane A's L4 credentialed variant hangs at `attach`, and the cause is not established ([laneA:566-608](../evidence/P0.5-docker-laneA.md)).

### Source citations: bearer injection

- `NVIDIA/OpenShell@v0.1.6:crates/openshell-supervisor-network/src/l7/rest.rs:915` computes `is_websocket_request`. `:938` calls `strip_connection_nominated_headers(&header_bytes, is_websocket_request)`.
- `rest.rs:2310-2326`: that function removes `Connection` and `Upgrade` and restores `Connection: Upgrade` and `Upgrade: websocket` only when `preserve_websocket_upgrade` is true. A request with `Upgrade: tcp` loses both headers.
- `rest.rs:2440-2449`: the comment says "REST and WebSocket endpoints relay allowed upgrades". The code relays only the WebSocket upgrade. Observed behavior follows the code.
- `crates/openshell-supervisor-network/src/l7/relay.rs:1790`: `handle_upgrade` is a raw bidirectional relay that already exists for upgraded connections.

### Smallest failing case: mTLS

An engine that requires a client certificate cannot be used through the credentialed L7 relay, and the key cannot stay at the proxy.

```text
$ X p05b-ext 'docker -H tcp://host.openshell.internal:12376 --tlsverify --tlscacert=$SSL_CERT_FILE version'      (protocol: rest)
error during connect: Get "https://host.openshell.internal:12376/v1.56/version": EOF
$ t 60 logs p05b-ext --since 30s
[...] NET:OPEN [INFO] ALLOWED /usr/local/bin/docker(0) -> host.openshell.internal:12376 [policy:docker_engine engine:opa]
[...] NET:FAIL [LOW] host.openshell.internal:12376
```

([laneB:356-366](../evidence/P0.5-docker-laneB.md).) Lane B did not separate the two possible causes: no upstream client certificate, or an untrusted engine CA. The code shows the first cause exists either way:
- `NVIDIA/OpenShell@v0.1.6:crates/openshell-supervisor-network/src/l7/tls.rs:278-282`: `build_upstream_client_config` builds the upstream client config with `.with_no_client_auth()` (line 281). Its only inputs are root certificates and `system_ca_bundle`. No other client config in `crates/openshell-supervisor-network` presents a client certificate: the `with_single_cert` calls in that crate follow `.with_no_client_auth()` on server configs (for example `l7/tls.rs:123-124`, `:223-224`).
- With `tls: skip` the client finishes TLS itself (`docs/how-it-works/policies/network-rules.mdx:637-640`). Lane A and lane B show this passes with the key in the sandbox ([laneA:357-379](../evidence/P0.5-docker-laneA.md), [laneB:341-352](../evidence/P0.5-docker-laneB.md)). The key is a file the agent can read (`-rw------- sandbox sandbox`, [laneB:348](../evidence/P0.5-docker-laneB.md)).
- Without `tls: skip` the proxy terminates TLS with its own CA, and the client fails with `x509: certificate signed by unknown authority` ([laneA:457-477](../evidence/P0.5-docker-laneA.md)).

### Upstream change needed

Either one removes the gap:
1. Let a credentialed `protocol: rest` endpoint relay `Connection: Upgrade` with `Upgrade: tcp` as a raw bidirectional stream after the credentialed request headers. Keep the WebSocket checks. A per-endpoint list of allowed upgrade tokens would also work. The raw relay exists (`l7/relay.rs:1790`). This fixes `docker run` and `docker exec` with a bearer token. BuildKit also needs the header on its session connection, which lane A and lane B could not confirm.
2. Let a provider hold an upstream TLS client certificate and key for an endpoint, and let the proxy present them (`with_client_auth_cert` in place of `with_no_client_auth` at `l7/tls.rs:281`). This keeps the mTLS key at the proxy, and an mTLS engine needs no change.

### What jackin does until upstream changes

D24 clause: the engine credentials stay outside the sandbox when OpenShell can inject them. OpenShell cannot, so the operator-named engine must be a dedicated engine that holds nothing else. The mTLS client key lives in the sandbox ([P0.5-docker.md](../evidence/P0.5-docker.md), "Isolation facts", item 4). P5.5 records the acceptance. Re-test with the upstream change and move the key to a provider when either change lands.

## Section 2. No engine inside a sandbox (D24 source 1)

### Missing capability

OpenShell cannot run `dockerd` or rootless Docker inside a sandbox. This is not a P0.5 blocker, because source 2 works. D24 asks for source 1 first, so the gap is recorded here.

### Smallest failing cases

Both lanes ran these on the `vm` driver (kernel 6.12.109), default-style policy:

```text
$ unshare -U true
unshare: unshare failed: Operation not permitted
$ mount -t tmpfs tmpfs /tmp/m
mount: permission denied (are you root?)
$ rootlesskit --net=host --copy-up=/etc --copy-up=/run dockerd ...
[rootlesskit:parent] error: failed to start the child: fork/exec /proc/self/exe: operation not permitted
$ dockerd ...
dockerd needs to be started with root privileges.
```

([laneA:69-254](../evidence/P0.5-docker-laneA.md), [laneB:103-191](../evidence/P0.5-docker-laneB.md).) The workload has `CapEff 0000000000000000`, `NoNewPrivs 1`, `Seccomp 2` ([laneA:182-189](../evidence/P0.5-docker-laneA.md), [laneB:89-96](../evidence/P0.5-docker-laneB.md)). A policy with `run_as_user: 0` or `root` is rejected at create ([laneA:259-266](../evidence/P0.5-docker-laneA.md), [laneB:112-121](../evidence/P0.5-docker-laneB.md)). The widest filesystem policy and registry egress did not help ([laneA:279-281](../evidence/P0.5-docker-laneA.md), [laneB:176-191](../evidence/P0.5-docker-laneB.md)).

### Source citations

- `NVIDIA/OpenShell@v0.1.6:crates/openshell-sandbox/src/sandbox/linux/seccomp.rs:80`, `:129`: `no_new_privs` is set before the filters.
- `seccomp.rs:237-250`: `EPERM` for `mount`, `fsopen`, `setns`, `umount2`, `pivot_root`. `:235` `io_uring_setup`. `:267-281`: `unshare` and `clone` with `CLONE_NEWUSER`. `:165-170`: `clone3` returns `ENOSYS`. `:194-214`: sockets limited to `AF_UNIX`, `AF_NETLINK` (route only), `AF_INET`, `AF_INET6`.
- `crates/openshell-sandbox/src/sandbox/linux/mod.rs:58`, `:89`: `prepare_capability_free` and `enforce_capability_free` run Landlock, then the seccomp filters last.
- `docs/how-it-works/policies/schema.mdx:28-33`: the policy fields are `filesystem_policy`, `landlock`, `process`, `network_policies`, `network_middlewares`. None sets capabilities, seccomp or namespaces. `:92`: root is rejected.
- The guest kernel is not the limit. It lists `overlay`, `cgroup2` and `fuse`, and allows 7690 user namespaces ([laneA:190-191](../evidence/P0.5-docker-laneA.md)).

### Upstream state

- `NVIDIA/OpenShell#4970` "Add support for Docker-in-Docker": open, created 2026-10-27. It proposes the `sysbox-runc` runtime as an opt-in. Read with `gh issue view 4970 -R NVIDIA/OpenShell` on 2026-11-01 UTC.
- `NVIDIA/OpenShell#113` "feat: Secure Docker daemon inside sandboxes": closed as a duplicate on 2026-03-23.

### Upstream change needed

An opt-in sandbox mode that lets the workload run a container engine. Either of these:
- Give the workload user namespaces and the mount syscalls inside the guest. The VM already isolates the guest from the host.
- Run the engine under a sysbox-like runtime, as `#4970` proposes.

The seccomp rule set is code (`seccomp.rs`), not policy, so the change is in OpenShell, not in a policy file. The extension point `IsolationBackend` (`docs/extensibility/isolation-backends.mdx`) could carry a different backend. Lane B did not test it ([laneB:198-200](../evidence/P0.5-docker-laneB.md)).

### What jackin does until upstream changes

D24 source 1 stays first in the order and stays unproven. Re-run the source 1 test when `#4970` ships. D24 falls to source 2.
