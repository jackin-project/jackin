## How the commands were run

Every `openshell` call took stdin from `/dev/null` and ran under a hard `alarm` timeout. All sandboxes are named `p05b-*`. I deleted only mine. The shorthand below is the wrapper `t`:

```text
t <seconds> <args>  =  perl -e 'alarm shift; exec @ARGV' <seconds> /opt/homebrew/bin/openshell -g jackin-local --workspace default <args> </dev/null
X <sandbox> '<cmd>' =  t 90 sandbox exec -n <sandbox> --no-tty -- sh -c '<cmd>'
```

## Recommended settings (source 2)

Engine, started by the operator (script `rewrite/drafts/docker-laneB-engine.sh`, idempotent):

```text
docker run -d --name <name> --label jackin.engine=dedicated --privileged \
  -e DOCKER_TLS_CERTDIR=/certs -e DOCKER_TLS_SAN=DNS:host.openshell.internal \
  -v <name>-certs:/certs -p 127.0.0.1:<port>:2376 docker:dind@sha256:9e79b879...1977
```

`DOCKER_TLS_SAN` is required. Without it the sandbox client fails with `x509: certificate is valid for 12e85a87586e, docker, localhost, not host.openshell.internal`.

Sandbox policy (file `rewrite/drafts/docker-laneB-policy.yaml`; only `network_policies` can change after create, D12):

```yaml
version: 1
filesystem_policy:
  include_workdir: true
  read_only: [/bin, /sbin, /usr, /lib, /etc, /proc, /dev/urandom, /var/log]
  read_write: [/tmp, /dev/null]
landlock:
  compatibility: hard_requirement
network_policies:
  docker_engine:
    name: docker_engine
    endpoints:
      - { host: host.openshell.internal, port: 12376, protocol: tcp, tls: skip }
    binaries:
      - path: /usr/local/bin/docker
```

Create flags: `sandbox create --name <n> --from <image with /usr/local/bin/docker> --policy <file> --detach --no-auto-providers`. The image is `docker.io/library/docker:cli` here. The derived jackin layer (D06) needs the Docker client at `/usr/local/bin/docker`, because the rule matches that path. The `docker-buildx` and `docker-compose` plugins are allowed through their parent `docker` process (log below), so they need no rule of their own. Client environment: `DOCKER_HOST=tcp://host.openshell.internal:<port>`, `DOCKER_TLS_VERIFY=1`, `DOCKER_CERT_PATH=<dir with ca.pem cert.pem key.pem>`.

## Source 1. Engine inside the sandbox

### 1.1 What the sandbox restricts (upstream code and docs)

| Restriction | Source |
|---|---|
| Workload identity is never root. A numeric `run_as_user` must be `1` to `4294967294`. | `docs/how-it-works/policies/schema.mdx:92` |
| The workload runs through `prepare_capability_free` and `enforce_capability_free`. Landlock first, then the seccomp filters. | `crates/openshell-sandbox/src/sandbox/linux/mod.rs:58`, `:89` |
| `PR_SET_NO_NEW_PRIVS` is set before the seccomp filters. | `crates/openshell-sandbox/src/sandbox/linux/seccomp.rs:129` |
| Seccomp blocks `mount`, the new mount API (`fsopen` and the rest), `setns`, `umount2`, `pivot_root`, `memfd_create`, `ptrace`, `bpf`, `io_uring_setup`. | `seccomp.rs:220-250` |
| Seccomp blocks `unshare` and `clone` with `CLONE_NEWUSER`. `clone3` returns `ENOSYS`. | `seccomp.rs:272`, `:280`, `:167` |
| Seccomp allows only `AF_UNIX`, `AF_NETLINK` (route protocol 0 only) and `AF_INET`/`AF_INET6`. `AF_PACKET` and the other netlink protocols are refused. | `seccomp.rs:199-202`, `:333` |
| The policy schema has `filesystem_policy`, `landlock`, `process`, `network_policies`, `network_middlewares`. No field touches capabilities, seccomp or namespaces. | `docs/how-it-works/policies/schema.mdx:13-30`, `proto/sandbox_protocol.proto:299-309` |
| The VM has no network interface. All traffic crosses the supervisor. | `docs/how-it-works/sandboxes/runtimes.mdx:237` |
| The `vm` driver config has `default_image`, `vcpus`, `mem_mib`, `overlay_disk_mib`, `sandbox_uid`, `sandbox_gid`, proxy options, and opt-in bind mounts. Nothing for privileges. | `docs/how-it-works/gateways/configuration.mdx:1389-1460` |

I grepped the sandbox, supervisor and VM driver crates for environment switches (`seccomp`, `landlock`, `cap`, `priv`, `unconfined`, `disable`, `skip`). No switch turns the filter off.

### 1.6 Upstream state

- `NVIDIA/OpenShell#4970` "Add support for Docker-in-Docker", open, 2026-10-27. It proposes the `sysbox-runc` runtime. Read with `gh issue view 4970` on 2026-11-01.
- `NVIDIA/OpenShell#113` "feat: Secure Docker daemon inside sandboxes", closed 2026-03-23. It lists the same layers as blockers: seccomp blocks `AF_NETLINK`, Landlock paths, capabilities, network namespace.

### 1.7 What upstream would have to change (inferred, not tested)

A Docker engine in a `vm` sandbox needs an opt-in that does at least this: keep the supervisor-owned privileges for the engine process, or allow `unshare`/`clone(CLONE_NEWUSER)`, `mount`, `setns`, `pivot_root` and `umount2` in the workload filter; allow `AF_NETLINK` with the netfilter protocol or run the engine without bridge networking; allow `/sys/fs/cgroup`; and drop the `no_new_privs` dependence for `newuidmap`. The seccomp rule set is code (`seccomp.rs`), not policy, so this is an upstream code change. The extension point `IsolationBackend` (`docs/extensibility/isolation-backends.mdx`) could carry a different enforcement backend, but I did not test or build one.

### 2.3 Isolation that source 2 gives

Policy scoping works. Another port and another binary are denied:

```text
$ X p05b-ext 'DOCKER_HOST=tcp://host.openshell.internal:12376 docker version ...'      (rule names 12375 only)
permission denied while trying to connect to the docker API at tcp://host.openshell.internal:12376
$ X p05b-ext 'nc -w 3 host.openshell.internal 12375 </dev/null; echo nc_exit=$?'
nc_exit=1
$ t 60 logs p05b-ext --since 3m | grep DENIED
[...] NET:OPEN [MED] DENIED /usr/local/bin/docker(0) -> 198.18.0.3:12376 [reason:transparent_tcp_mapping_denied]
[...] NET:OPEN [MED] DENIED /bin/busybox(0) -> host.openshell.internal:12375 [reason:transparent_tcp_policy_denied]
```

What the sandbox boundary does not cover once an engine is reachable:

1. **Container egress bypasses the sandbox network policy.** The engine pulls images and runs containers with its own network. From `p05b-ext`:

   ```text
   $ X p05b-ext 'wget -q -T 10 -O - https://example.com'
   wget: can't connect to remote host (198.18.0.5): Permission denied
   $ X p05b-ext 'docker run --rm alpine:3.22 sh -c "wget -q -T 10 -O - https://example.com | head -c 120"'
   <!doctype html><html lang=en><head><meta charset=utf-8><link rel=icon href=data:,><meta name=viewport content="width=device...
   ```

   Any allowlist in the sandbox policy is void for code that can start a container. The image allowlist, the egress allowlist and the engine are one trust decision.
2. **Bind mounts name paths on the engine host.** The workspace is not visible to containers:

   ```text
   $ X ... 'ls /sandbox/w; docker run --rm -v /sandbox/w:/w alpine:3.22 ls -A /w | wc -l'
   sandbox_has:
   f
   container_sees:
   0
   ```

   So `-v $PWD:/app` gives an empty directory. Workflows that mount the workspace need another approach (`docker cp`, build contexts, volumes).
3. **The engine is shared and outlives the sandbox.** Containers started from `p05b-ext` showed in `docker ps -a` of `p05b-inj`. A container started in `p05b-final` kept running after the sandbox was deleted:

   ```text
   $ X p05b-final '... docker run -d --name p05b-leftover alpine:3.22 sleep 600'
   8614812db97d
   $ t 90 sandbox delete p05b-final
   ✓ Deleted sandbox p05b-final
   $ docker --host tcp://127.0.0.1:12376 --tlsverify ... ps        (host, dedicated engine)
   p05b-leftover alpine:3.22 Up Less than a second
   ```

   So the engine needs one instance per sandbox, or an operator cleanup, if sandboxes must not see each other's containers or images.
4. **The engine is a privileged container on the OrbStack Linux kernel.** `CapEff` of the dind container is `000001ffffffffff`. The container did not mount `/Users` or `/mnt/mac`. I did not test a privileged escape to the OrbStack VM, and I did not test whether the VM reaches the Mac files. The boundary toward the Mac is OrbStack's VM, not the engine.
5. **The loopback port is open to every local process and every sandbox whose policy names it.** There is no per-sandbox identity at the engine.

### 2.4 Credential path

Question: can OpenShell keep the engine credentials (TLS client key, token) outside the sandbox? Answer: only in a mode that breaks foreground `docker run`, `docker exec` and BuildKit. In the mode that works, the credential is in the sandbox.

**A. mTLS engine, raw relay.** The client key is a file in the sandbox. Raw relay is the only form that carries the Docker hijack, and the client must finish TLS itself (`docs/how-it-works/policies/network-rules.mdx:639`). The docs say raw relay does no credential substitution (`docs/how-it-works/providers/profiles.mdx:143`).

```text
$ t 90 policy set p05b-ext --policy policy-ext-mtls.yaml --wait        (port 12376, protocol: tcp, tls: skip)
✓ Policy version 5 loaded (active version: 5)
$ X p05b-ext 'export DOCKER_HOST=tcp://host.openshell.internal:12376 DOCKER_TLS_VERIFY=1 DOCKER_CERT_PATH=/sandbox/certs/certs; docker run --rm hello-world >/tmp/hw.out 2>&1; echo mtls_run_exit=$?; grep -c "Hello from Docker" /tmp/hw.out'
mtls_run_exit=0
1
$ X p05b-ext 'ls -l /sandbox/certs/certs/key.pem; head -c 27 /sandbox/certs/certs/key.pem'
-rw-------    1 sandbox  sandbox       3272 Nov  1 19:44 /sandbox/certs/certs/key.pem
-----BEGIN PRIVATE KEY-----
$ X p05b-ext 'unset DOCKER_CERT_PATH DOCKER_TLS_VERIFY; docker -H tcp://host.openshell.internal:12376 --tlsverify --tlscacert=/sandbox/certs/certs/ca.pem version'
error during connect: Get "https://host.openshell.internal:12376/v1.56/version": remote error: tls: certificate required
```

The first mTLS attempt failed on the server certificate name (`x509: certificate is valid for 12e85a87586e, docker, localhost, not host.openshell.internal`). The `DOCKER_TLS_SAN` setting fixed it.

**B. L7 relay with TLS termination at the proxy.** OpenShell cannot present a client certificate to the upstream. The upstream TLS configuration is built with `.with_no_client_auth()` (`crates/openshell-supervisor-network/src/l7/tls.rs:278-283`). Live result against the mTLS engine with `protocol: rest`:

```text
$ X p05b-ext 'docker -H tcp://host.openshell.internal:12376 --tlsverify --tlscacert=$SSL_CERT_FILE version'
```

**C. Provider credential injection with a bearer token.** Injection works for requests that do not hijack. I put a front (`nginx:alpine`) in front of the plain engine that returns `401` unless `Authorization: Bearer <token>` matches. I imported a provider profile (`id: p05b-docker-engine`, credential `P05B_ENGINE_TOKEN`, `auth_style: bearer`, `header_name: authorization`, endpoint `host.openshell.internal:12378` `protocol: rest` `access: full`, binary `/usr/local/bin/docker`), created the provider with the token, and created sandbox `p05b-inj` with `--provider p05b-engine`. So the real token stays at the proxy and the front accepts it. `version`, `run -d`, `logs`, `ps` and the legacy builder (`DOCKER_BUILDKIT=0 docker build`, image `sha256:1bfb1c48...`) pass. Foreground `docker run`/`exec` fail (`Upgrade` stripped, see 2.2). BuildKit `docker build` returned `401 Authorization Required` because `docker-buildx` does not send the `config.json` `HttpHeaders` on its own connections.

**Summary of the credential path.** There are three ways, none that meets D24 for a working `docker run`:

| Path | Credential location | Foreground `run`/`exec`, BuildKit | Result |
|---|---|---|---|
| mTLS, raw relay (A) | Client key file inside the sandbox | Work | Credential exposed to the sandbox. Gap. |
| Bearer front + provider injection, L7 (C) | Real token at the proxy only | Fail | Credential kept out, capability reduced. |
| Plain engine on loopback, raw relay | None (the network path is the credential) | Work | Docker `29.9.2` warns that this will become a hard failure. No authentication at the engine. |

A client certificate in the sandbox only opens the dedicated engine, and the sandbox already has full use of that engine. The loss is that a leaked key lets a local process on the Mac use it too. This is why D24 requires the engine to be dedicated and to hold nothing else.

## Blocker report content (for `blockers/P0.5-docker.md`, written by the orchestrator)

1. **No engine inside a `vm` sandbox (source 1).**
   - Command: `X p05b-rootless2 'rootlesskit --net=host --copy-up=/etc --copy-up=/run dockerd ...'`. Output: `fork/exec /proc/self/exe: operation not permitted`.
   - Smallest failing case: `unshare -U true` returns `EPERM`; `mount -t tmpfs none /tmp/x` returns `EPERM`.
   - Cause: `seccomp.rs:167-280` and the capability-free launch (`sandbox/linux/mod.rs:58`, `:89`). Policy cannot relax it, and root is rejected (`schema.mdx:92`).
   - Upstream change needed: an opt-in sandbox mode that lets the workload run a container engine (user namespaces and `mount`, or an engine process launched by the supervisor with its own privileges), tracked upstream by `NVIDIA/OpenShell#4970`.
2. **No credential injection for Docker hijack calls (source 2).**
   - The L7 relay strips `Connection` and `Upgrade` (`rest.rs:938`, `:2310-2326`) so foreground `docker run`, `docker exec` and BuildKit fail with `unable to upgrade to tcp, received 200`.
   - The raw relay does no credential substitution (`profiles.mdx:143`), so the key must be in the sandbox.
   - The upstream TLS client has no client certificate (`tls.rs:281`).
   - Upstream change needed: let an L7 endpoint pass a `tcp` upgrade (or a per-endpoint list of allowed upgrade tokens), or let an endpoint carry an upstream client certificate held by the supervisor.
   - Consequence under D24: the operator-named engine must be a dedicated engine that holds nothing else, and the client key is in the sandbox.
