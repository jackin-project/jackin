- Task: P0.5 of the jackin OpenShell rewrite, lane A (`agent-sandbox-engineer` brief, `openshell-specialist` runs lane B with the same brief). Decisions D24, D01, D06 and D13 apply.
- Driver: `vm` (libkrun microVM, guest kernel 6.12.109), the P0.2 gateway `jackin-local` at `https://localhost:17670`, OpenShell `0.1.6`. Upstream source is cited as `NVIDIA/OpenShell@v0.1.6` (commit `ac7f615cd12d5cc49cb16eb1f5f10ffeb1e90f47`, read from the local checkout at that tag).
- Run on 2026-11-01 from 19:37Z to about 20:30Z (2026-11-02 local time). The interactive exploration came first; the transcripts below are from the committed script, run from a clean state. Host: macOS 27.2, arm64, OrbStack Docker 29.8.2. Engine and client images: `docker:dind` and `docker:dind-rootless`, Docker 29.9.2.
- Every `openshell` call used stdin from `/dev/null`, a hard `alarm` timeout, `-g jackin-local --workspace default` and an explicit sandbox name. All sandboxes are named `p05a-*`; only those were created and deleted.
- No host fallback and no weakened check. The one weakened path, source 3, is a deliberate test of the host engine that D24 allows only for `xtask e2e`.
- No secret appears in this file. The token and the client private key are generated into a `0700` scratch directory and are never printed.

## Result

First working source in D24 order: **source 2, a dedicated external engine**. Source 1 cannot work on this driver and cannot be made to work by any OpenShell setting.

| Source | Verdict | One-line reason |
|---|---|---|
| 1. Engine inside the sandbox | FAILS | The workload has zero capabilities, `no_new_privs`, and a seccomp filter that denies `mount`, `setns`, `bpf` and user-namespace creation; root cannot be selected; no policy, process or driver setting changes this. |
| 2. Dedicated external engine on OrbStack | WORKS | `docker run --rm hello-world` succeeds from the sandbox over mTLS through a policy rule that permits one `host:port` for one binary; both a `--privileged` dind and a rootless dind without `--privileged` pass. |
| 3. Default OrbStack engine | WORKS, with no credential and no isolation | Needs an operator TCP bridge to the unix socket; a bind mount of the macOS home from the sandbox succeeded. |

Credential path (D24 clause 4): **OpenShell cannot keep the engine credential outside the sandbox.** The mTLS client key must live in the sandbox, because the proxy has no upstream client certificate (`l7/tls.rs:278-282`) and `tls: skip` tunnels are opaque to credential injection. A bearer token injected by the proxy works for plain API calls, but the proxy removes the `Upgrade` header that Docker uses to attach, so `docker run` (attached) and `docker exec` fail, and the BuildKit build session fails with `401` (`l7/rest.rs:938`, `:2320`). A blocker report is needed for this gap and only for this gap (see "Blocker report"). The Docker capability is not `BLOCKED`, because D24 allows a dedicated engine that holds nothing else when injection is impossible.

Recommended settings are in "Exact settings for the recommended source". The engine should be the rootless variant (no `--privileged`).

## Source 1. An engine inside the sandbox

Verdict: **FAILS**. Upstream change needed: yes (see below).

### What the sandbox restricts (upstream, at `v0.1.6`)

| Restriction | Evidence |
|---|---|
| The workload runs as one non-root identity with no Linux capabilities. | `docs/about/architecture.mdx:47-49`; `crates/openshell-sandbox/src/lib.rs:4` ("Capability-free in-workload sandbox boundary"). |
| Root cannot be selected. `run_as_user` and `run_as_group` accept `sandbox` or `1..4294967294`. | `docs/how-it-works/policies/schema.mdx:92`; gateway rejection in the transcript below. The VM driver's `sandbox_uid`/`sandbox_gid` use the same range (`crates/openshell-driver-vm/src/driver.rs:527-549`). |
| `no_new_privs` is set before the seccomp filters. | `crates/openshell-sandbox/src/sandbox/linux/seccomp.rs:75-80`. A setuid helper such as `newuidmap` cannot raise privilege. |
| Seccomp returns `EPERM` for `mount`, the new mount API (`fsopen`, `fsconfig`, `fsmount`, `fspick`, `move_mount`, `open_tree`), `setns`, `umount2`, `pivot_root`, `bpf`, `ptrace`, `memfd_create`, `io_uring_setup`, `userfaultfd`, `perf_event_open`. | `seccomp.rs:220-255`. |
| Seccomp returns `EPERM` for `unshare` and `clone` with `CLONE_NEWUSER`, and `ENOSYS` for `clone3`. | `seccomp.rs:267-281` and `:165-170`. |
| Sockets are limited to `AF_UNIX`, `AF_NETLINK` (route protocol only) and brokered `AF_INET`/`AF_INET6`. Netlink writes need `CAP_NET_ADMIN`, which the workload lacks. | `seccomp.rs:194-214`, module comment `:1-37`. |
| The VM has no network interface. All traffic goes through the supervisor on the host. | `docs/how-it-works/sandboxes/runtimes.mdx:237`; `crates/openshell-driver-vm/runtime/README.md:16`. |
| The other drivers are equally restrictive: `cap_drop: ALL` and `no-new-privileges`. | `crates/openshell-driver-docker/src/lib.rs:5200-5202`; `crates/openshell-driver-podman/src/container.rs:1337`, `:1629`. |
| Policy fields that exist: `filesystem_policy`, `landlock`, `process` (user and group only), `network_policies`, `network_middlewares`. None relaxes capabilities, seccomp or namespaces. | `docs/how-it-works/policies/schema.mdx:28-33`, `:85-102`. `sandbox create` has no privilege flag (`openshell sandbox create --help`). |
| Upstream knows the gap. `NVIDIA/OpenShell#4970` "Add support for Docker-in-Docker" (open, 2026-10-27) proposes a sysbox runtime. `#113` "Secure Docker daemon inside sandboxes" was closed as a duplicate on 2026-03-23. | `gh issue view 4970 -R NVIDIA/OpenShell`, `gh issue view 113 -R NVIDIA/OpenShell` on 2026-11-02. |

The guest kernel is not the limit. It lists `overlay`, `cgroup2`, `fuse` and `squashfs` in `/proc/filesystems` and has `user.max_user_namespaces=7690` (transcript), and its kernel config enables Landlock and seccomp (`crates/openshell-driver-vm/runtime/kernel/openshell.kconfig`). The workload still cannot use them: `/dev/fuse` is `root:root 0600` and `/sys/fs/cgroup` is a root-owned `dr-xr-xr-x` mount (transcript).

### Smallest failing cases

1. `unshare -U true` in `p05a-probe` (buildpack-deps image, default-style policy): `unshare: unshare failed: Operation not permitted`. Rootless Docker needs a user namespace first, so rootlesskit stops with `fork/exec /proc/self/exe: operation not permitted`.
2. `mount -t tmpfs tmpfs /tmp/m` in `p05a-in`: `mount: permission denied (are you root?)`. Rootful `dockerd` needs `mount`.
3. `dockerd` as the sandbox user: `dockerd needs to be started with root privileges`. The policy field that would allow root is rejected by the gateway (`run_as_user must be 'sandbox' or a numeric UID/GID in range [1, 4294967294], got '0'`).

### Settings that were tried and did not help

Filesystem policy with `/run`, `/var/run`, `/var/lib`, `/home`, `/sandbox` writable (the paths dockerd and rootless Docker use); `process.run_as_user: sandbox`; `landlock.compatibility: best_effort`; egress to `registry-1.docker.io`, `auth.docker.io` and `production.cloudflare.docker.com` for the binaries `/usr/local/bin/dockerd` and `/usr/local/bin/docker` (the file is `$DRAFTS/docker-laneA-policy-inside.yaml`); `DOCKER_IPTABLES_LEGACY=1`; `DOCKERD_ROOTLESS_ROOTLESSKIT_NET=host`. A live `policy set` also cannot remove a filesystem path once the sandbox exists (`filesystem read_write path '/run' cannot be removed on a live sandbox`, seen during the interactive pass), which matches the schema table: filesystem, landlock and process take effect at startup only.

### Upstream change needed

An opt-in runtime profile that gives the workload a nested-container capability: either user namespaces and the mount syscalls inside the guest (the VM already isolates the guest from the host), or a sysbox-like runtime. This is the content of `NVIDIA/OpenShell#4970`. Without it, source 1 is impossible on every built-in driver. This is not a blocker for the Docker capability, because source 2 works.

## Credential path

| Source | Where the credential lives | Can OpenShell keep it out of the sandbox? |
|---|---|---|
| 1 | None needed (no engine). | Not applicable. |
| 2, route A | mTLS client key and certificate, uploaded to `/sandbox/engine-certs` (`openshell sandbox upload`), mode `0600`, readable by the sandbox user, which is the agent's user. | No. `tls: skip` makes the tunnel opaque. With TLS termination the proxy would have to present the client certificate upstream, and its client config has `with_no_client_auth()` (`l7/tls.rs:278-282`). |
| 2, route B | Bearer token in the gateway provider. The sandbox holds a placeholder. | Yes for requests without a connection upgrade. No for `attach` and `exec` (connection upgrade), which `docker run` and `docker exec` need. The BuildKit session also failed (`401`, cause inferred). |
| 3 | None. The bridge has no authentication. | Not applicable. |

Two other facts bear on D24's clause "engine credentials stay outside the sandbox when OpenShell can inject them":

- The provider machinery is HTTP-only: placeholders resolve in header values, Basic auth, query, path, opted-in bodies and WebSocket text (`providers/overview.mdx:462-477`).
- `provider_files.rs` (`crates/openshell-sandbox/src/provider_files.rs`) serves provider-supplied files under `/run/openshell/providers/`. Those files are readable by the workload, so they do not keep a key out of the sandbox. I did not find a documented CLI surface for it (not verified).

Consequence under D24: because injection is impossible for the working route, the operator-named engine must be a dedicated engine that holds nothing else. Both engines in this evidence hold only what the sandbox puts there.

The `--privileged` form that was also verified end to end replaces the four security and device flags with `--privileged` and uses `docker:dind` (`$DRAFTS/docker-laneA-run.sh`, function `engine_up`). The server certificate must carry the name the client dials (`host.openshell.internal`), because the client verifies it itself.

Sandbox create (the image needs only the Docker CLI at a known real path; D06's derived layer adds the CLI and no engine for this source):

```text
openshell -g <gateway> --workspace <workspace> sandbox create --name <sandbox> \
  --from <image with /usr/local/bin/docker> --policy <policy.yaml> \
  --detach --no-tty --no-auto-providers -- <main command>
openshell -g <gateway> --workspace <workspace> sandbox upload <sandbox> <dir with ca.pem cert.pem key.pem> /sandbox/
```

Client environment in the sandbox: `DOCKER_HOST=tcp://host.openshell.internal:<port>`, `DOCKER_TLS_VERIFY=1`, `DOCKER_CERT_PATH=/sandbox/<dir>`.

Network policy rule (the whole file is `$DRAFTS/docker-laneA-policy-external-mtls-rootless.yaml`; jackin adds only this rule, and only when the capability is enabled, D12 and D24):

```yaml
network_policies:
  docker_engine:
    name: docker_engine
    endpoints:
      - host: host.openshell.internal
        port: 18478
        protocol: tcp
        tls: skip
    binaries:
      - path: /usr/local/bin/docker
```

Rules that follow from the evidence:

- `tls: skip` is required. `protocol: tcp` alone terminates TLS or parses HTTP and breaks both mTLS and the connection upgrade.
- `binaries` lists real paths. A rule also covers processes that a listed binary starts (`network-rules.mdx:72-74`; the route B log excerpt shows `docker-buildx` allowed to the engine endpoint under the `docker` rule). A separate client such as a language runtime for Testcontainers needs its own entry. Compose and Testcontainers were not tested.
- A BuildKit `docker build` needs registry egress for the `docker-buildx` plugin binary (`/usr/local/libexec/docker/cli-plugins/docker-buildx`) in addition to the engine rule, because the client resolves `FROM` metadata itself. `$DRAFTS/docker-laneA-policy-external-mtls-buildx.yaml` is the tested rule set. `docker run` and `docker pull` need no registry egress from the sandbox, because the engine pulls.
- The endpoint is `host.openshell.internal`, not an IP literal. The engine must listen on the Mac's `127.0.0.1` (or an address the host-side supervisor can reach).
- Filesystem policy needs `/sandbox` writable (the default `include_workdir: true` covers it) so the certificate files can be uploaded and read.
- The filesystem, landlock and process policy are fixed at creation. Only `network_policies` can change later, so the engine rule can be added or removed live (`policy set --wait`, transcript).
- The engine outlives the sandbox. Its images, volumes and any container started with `-d` stay after the sandbox is deleted, and concurrent sandboxes that share a certificate share the engine and see each other's containers (the second part is inferred; only one sandbox used each engine at a time). Reaping is an operator duty. D24 source 1 promised deletion with the sandbox; source 2 does not give it.

## Conflicts between sources

- `rewrite/research/openshell.md` (line 202) says "Workload seccomp blocks nested namespaces (old plan claim; not re-tested)". Re-tested here: confirmed (`unshare: unshare(0x10000000): Operation not permitted`).
- The comment at `l7/rest.rs:2444-2449` says REST endpoints relay allowed upgrades. The code at `:938` and `:2320` relays only WebSocket upgrades. Observed behavior follows the code.
- `docs/how-it-works/policies/network-rules.mdx:105-110` says that with `protocol` omitted OpenShell "relays traffic that is neither TLS nor HTTP". Plain HTTP on a `protocol: tcp` endpoint without `tls: skip` is parsed as HTTP (source 3, last transcript), which the page does not say.
