- Task: P0.6 of the jackin OpenShell rewrite. Decisions D03, D09, D27 and D28 apply.
- This file holds the part "Transport research" (the OpenShell research and the protocol-level proof) and the part "Pane prototype" (the ratatui app).
- Run on 2026-11-02 (local time) against the P0.2 gateway `jackin-local` (`vm` driver, `https://localhost:17670`, mTLS), OpenShell `0.1.6`. Upstream source cited as `NVIDIA/OpenShell@v0.1.6` (commit `ac7f615cd12d5cc49cb16eb1f5f10ffeb1e90f47`; `git describe` on the checkout prints `sdk/go/v0.1.6`, and the tag `v0.1.6` points at the same commit).
- Every sandbox was named `p06-*` and deleted at the end. No secret appears in this file. Session tokens were not printed.

## Transport research

### Result

| Pane | Transport | Proven live |
|---|---|---|
| Shell pane | gRPC `ExecSandboxInteractive` through `openshell-sdk` (`OpenShellClient::raw_grpc()`). No `ssh`, no `openshell` child process. | Yes. Start, stdin, resize, output, exit code. |
| Codex pane (sandbox main process) | `CreateSshSession` then `ForwardTcp` with an `SshRelayTarget`, then an in-process `russh` client that requests the PTY and the `openshell-main` subsystem on a session channel. The SDK's gRPC channel carries it. No `ssh`, no `openshell` child process. | Yes. Attach, replay, keys, resize, detach, reattach with replay, concurrent attach, exit code. |

`blockers/P0.6.md` is not needed. The multiplexer fallback (tmux or dtach started by `jackin-start`) was not needed and was not tried.

Seven facts change how the console must be built. Each is proven below.

1. `openshell sandbox exec` does not use SSH at v0.1.6. It calls `ExecSandboxInteractive`. D03 and the P0.2 summary say it runs over SSH. That is wrong (section "Conflicts").
2. The supervisor eats `Ctrl-D` (0x04) on a main-process attachment and detaches. A pane can never send 0x04 to Codex.
3. The supervisor holds a lone `Ctrl-P` (0x10) until the next byte arrives. The pane must flush it itself or accept the delay.
4. The replay is raw bytes from the start of a 1 MiB window. The window can start in the middle of a line, so in the middle of an escape sequence.
5. A second attachment to the main process does not kick the first. It becomes a read-only viewer. Its PTY size still resizes the shared PTY.
6. After the main process exits, a new attachment is refused. There is no final replay. The pane must show the exit from the sandbox status.
7. A shell pane has no detach and no replay. Dropping the gRPC stream kills the remote process.

### Question 1. Shell panes

#### The RPC

`rpc ExecSandboxInteractive(stream ExecSandboxInput) returns (stream ExecSandboxEvent)` (`proto/openshell.proto:293`). The comment above it says the first client message must carry the `start` variant. Authorization: bearer scope `sandbox:write`, workspace role `user` (`proto/openshell.proto:293-299`).

Request stream, `ExecSandboxInput` (`proto/openshell.proto:2040-2049`), a `oneof payload`:

| Variant | Type | Use |
|---|---|---|
| `start = 1` | `ExecSandboxRequest` | Must be the first message. |
| `stdin = 2` | `bytes` | Keystrokes. |
| `resize = 3` | `ExecSandboxWindowResize { cols, rows }` (`:2052`) | Window size change. Applied only when `tty` was true (`crates/openshell-server/src/grpc/sandbox.rs:3874-3882`). |

`ExecSandboxRequest` (`proto/openshell.proto:1946-1988`) fields used by a shell pane:

| Field | Meaning |
|---|---|
| `sandbox = 1` | Canonical sandbox name. |
| `workspace_scope = 12` | `workspace_selector("<ws>")`. Required. Pass it every time (D03). |
| `command = 2` | Must not be empty (`validate_exec_start`, `sandbox.rs:3127-3132`). The command is shell-quoted and joined, then run through the supervisor (`build_remote_exec_command`, `sandbox.rs:3551-3571`). A shell pane sends `["bash"]`. |
| `workdir = 3`, `environment = 4` | Become `cd '<dir>' && K=V cmd` (`sandbox.rs:3551-3571`). Proven live. |
| `tty = 7`, `cols = 8`, `rows = 9` | PTY request. Zero cols or rows become 80 and 24 (`pty_dimensions`, `sandbox.rs:2614`). |
| `no_login_shell = 10` | Skips login-shell startup files. |
| `request_id = 11` | Optional UUID. Duplicates never relaunch or replay (`proto/openshell.proto:1983-1988`). Leave empty for panes. |
| `execution_timeout = 105`, `stdin = 6` | Not needed. |

Response stream, `ExecSandboxEvent` (`proto/openshell.proto:2007`), a `oneof payload`: `stdout` (`ExecSandboxStdout { data }`), `stderr`, `exit` (`ExecSandboxExit { exit_code: i32 }`, `:2002`). With `tty = true` the PTY merges the streams, so only `stdout` and `exit` appear (live output below). The stream ends cleanly after `exit`. A stream that ends with no `exit` event is a failure (`exec_loop_result`, `sandbox.rs:3539-3552`; the CLI treats it as an error, `crates/openshell-cli/src/run.rs:2844`).

#### How it works inside

The gateway opens a supervisor relay (`SshRelayTarget`), starts a loopback TCP bridge, and runs an in-process `russh` client against the supervisor's SSH server. It calls `authenticate_none("sandbox")`, `request_pty("xterm-256color", cols, rows)`, then `exec(command)` (`sandbox.rs:3770-3850`: `connect_stream` `:3807`, `authenticate_none` `:3812`, `request_pty` `:3831`, `exec` `:3850`; `start_single_use_ssh_proxy_over_relay` at `:3986`). `stdin` becomes channel data, `resize` becomes `window_change`, request-stream end becomes channel EOF, `ExitStatus` becomes `exit` (`sandbox.rs:3859-3948`). If the client drops the response stream, the gateway cancels (`tx.closed()`, `sandbox.rs:3964`) and the supervisor terminates the process on channel close (`crates/openshell-supervisor-process/src/ssh.rs:495-525`).

#### Auth

Only the gRPC channel is authenticated: mTLS client certificate through `ClientConfig.client_identity` (`crates/openshell-sdk/src/config.rs:62,113`, applied at `crates/openshell-sdk/src/transport.rs:134`), then the gateway authorizes the principal against the sandbox workspace (`resolve_and_authorize_sandbox_name`, `sandbox.rs:3214`). The sandbox must be in phase `Ready` (`require_ready_sandbox`, `sandbox.rs:279-284`, called at `:3227`). There is no SSH token and no per-token limit on this RPC (the limits are in `handle_forward_tcp` only, `sandbox.rs:2841-2985`).

### Question 2. Codex pane

#### Chosen transport

`sandbox connect` is SSH over `ForwardTcp` (`crates/openshell-cli/src/ssh.rs:277-294`: `ssh -tt -o RequestTTY=force -o SetEnv=TERM=xterm-256color -s sandbox openshell-main`, with `ProxyCommand=openshell ssh-proxy ...`). A Rust client can do the same without any child process. The proof does it with `russh` 0.65.0 on top of the SDK's tonic channel. The supervisor itself is built on `russh` 0.64.1 (`crates/openshell-supervisor-process/Cargo.toml:26`); the wire protocol is the same.

Call sequence, each step proven live:

1. `OpenShellClient::connect(ClientConfig)` with `ca_cert` and `client_identity` from `~/.config/openshell/gateways/<gw>/mtls/` (`ca.crt`, `tls.crt`, `tls.key`).
2. `client.raw_grpc().create_ssh_session(CreateSshSessionRequest { sandbox, workspace_scope })` (`proto/openshell.proto:219,1794`). The response (`:1807`) has `sandbox_id`, `token` (secret), `gateway_host`, `gateway_port`, `gateway_scheme`, `host_key_fingerprint` (`SHA256:<base64>`, `:1831`) and `expiration_time` (default TTL 86400 s, `crates/openshell-core/src/config.rs:1218`). The pane ignores `gateway_host` and `gateway_port`: it rides the existing gRPC channel. The sandbox must be `Ready`, or `Completed` or `Error` with a live supervisor session (`sandbox_relay_reachable`, `sandbox.rs:3295`).
3. `raw_grpc().forward_tcp(stream)` (`proto/openshell.proto:282`). The first frame is `TcpForwardFrame { payload: Init(TcpForwardInit { sandbox, workspace, service_id, target: Ssh(SshRelayTarget {}), authorization_token: token }) }` (`:2016-2037`, `:3325`). Later frames are `TcpForwardFrame { payload: Data(bytes) }` in both directions. The proof copies the same init the CLI builds (`crates/openshell-cli/src/ssh.rs:1973-1990`).
4. Bridge the frames to a byte stream (`tokio::io::duplex` plus two pump tasks) and hand the near end to `russh::client::connect_stream(config, stream, handler)`.
5. `handle.authenticate_none("sandbox")`. The supervisor accepts any user and any key (`ssh.rs:468-478`). The real gate is the gateway (mTLS, workspace role, SSH token).
6. `handle.channel_open_session()`, then `channel.request_pty(false, "xterm-256color", cols, rows, 0, 0, &[])`, then `channel.request_subsystem(true, "openshell-main")` (`ssh.rs:604-632`, `:724-897`). The pty request must come first; the subsystem request applies its size to the main PTY.
7. Read `ChannelMsg::Data` (PTY output), `ChannelMsg::ExtendedData` (supervisor notices such as the read-only warning), `ChannelMsg::ExitStatus`, `ChannelMsg::Close`. Write keys with `channel.data(..)`. Resize with `channel.window_change(cols, rows, 0, 0)`.
8. Detach: send `0x10 0x11` or `0x04` as data (the supervisor handles them, `ssh.rs:50-72`), or just `eof()` and `close()`. Both leave the main process running.

Host key: the proof checks the server key fingerprint against `CreateSshSessionResponse.host_key_fingerprint` in `check_server_key` (`key.fingerprint(HashAlg::Sha256).to_string()`). It matched in every run. The CLI instead uses `StrictHostKeyChecking=no` (`crates/openshell-core/src/forward.rs:955-966`), so pinning is stricter than upstream.

Token use: a token is checked only when `ForwardTcp` opens (`validate_ssh_forward_token`, `sandbox.rs:2887`). At most 3 concurrent `ForwardTcp` streams per token and 20 per sandbox (`sandbox.rs:2944-2945`). A pane should mint one token per attachment.

1. **Concurrent attach works and does not kick the first client.** The supervisor keeps a count of attachments (`begin_terminal_attachment`, `main_session.rs:412`) and one input lease (`acquire_input`, `:467-475`). The first attachment owns input. A second one gets output and replay, but its input is dropped, and it receives this notice on extended data: `openshell: canonical main process already has an input owner; attached read-only; retry input after the owner disconnects; press Ctrl-C or Ctrl-D to exit`. When the owner detaches, the viewer's next keystroke takes the lease and the supervisor prints `openshell: input enabled` (`ssh.rs:975-988`). An explicit viewer sets the SSH env `OPENSHELL_MAIN_READ_ONLY=1` before the subsystem request (`ssh.rs:915-920`) and gets no notice. A viewer's Ctrl-C (0x03) closes only the viewer (`ssh.rs:953-958`).
2. **Every attachment resizes the one shared PTY, even a viewer.** The subsystem request applies the pty size (`ssh.rs:793-801`) and every `window_change` resizes the main PTY (`ssh.rs:634-661`). Two panes with different sizes, or a `jackin attach` hand-off next to a console pane, fight over the size. The last writer wins. One console pane per sandbox main process is the safe design. If a second terminal runs `openshell sandbox connect` while the console owns input, it is a read-only viewer and still resizes the PTY.
3. **A crashed client does not hold the lease.** After `kill -9` the next attachment owned input at once (section above). The supervisor also drops half-dead SSH connections: keepalive 15 s, three misses (`ssh.rs:107-108`; `SSH_PEER_TIMEOUT` 60 s at `:42`).

### Facts for the ratatui prototype

1. Both pane kinds are byte pipes into a PTY. Feed output to a terminal emulator (a `vt100` parser, or `tui-term`) sized to the pane's inner area. Send raw key bytes back (xterm encoding). Report every pane resize with `ExecSandboxInput::resize` (shell) or `Channel::window_change` (Codex).
2. Run each pane's I/O in its own tokio task and send events to the render loop. The proof reads and writes in one sequential script; a pane needs a read task and a write channel.
3. Shell pane: input chunks of at most 4096 bytes, as the CLI does (`run.rs`, stdin reader). The start message is limited to 1 MiB (`MAX_EXEC_REQUEST_BYTES`, `run.rs:1865`). Use `workdir` and `environment` instead of a `cd` in the command.
4. Codex pane, first attach: create a fresh parser, feed every byte that arrives, render continuously. The replay arrives as ordinary `Data` messages after the subsystem request, through the same cursor as live output, so the stream has no marker for the end of the replay (`main_session.rs:96-139`, output task `ssh.rs:830-862`).
5. Codex pane, redraw: after the replay, send `window_change(cols, rows - 1)` then `window_change(cols, rows)` to force a SIGWINCH. A same-size resize does nothing. Whether Codex redraws on it is for the prototype to check.
6. Detach for a pane: send `eof()` and `close()` on the channel, then drop the `Handle`. No detach keys needed. This keeps the main process running and releases the input lease at once.
7. Key handling: never forward 0x04. The console's own key binding should own detach and close. A lone Ctrl-P is delayed until the next byte; consider sending Ctrl-P with the next key press or accept it.
8. Exit: on `ExitStatus` or `Close`, stop the pane and ask `GetSandbox` for the exit code. A re-attach after the main process ended fails with exit status 1 and a message on extended data. Do not retry.
9. Errors: a refused or lost `ForwardTcp` stream surfaces as an `Err` on the response stream or a closed duplex. The CLI retries retryable transport errors for up to 60 s (`crates/openshell-cli/src/ssh.rs:65`, `sandbox_connect_supervised` at `:541`); a pane can do a bounded retry the same way.
10. Only one console pane per sandbox main process (see question 3).

- `tui-term` is the crate that "renders into a ratatui buffer", but it is one release line behind `vt100`. It has its own `Screen` and `Cell` traits for other backends (`widget.rs` in the 0.3.4 source). Using them with `vt100` 0.18 needs newtype adapters, which is about the size of the widget itself. `src/panes/term.rs` (70 lines, `TermScreen` and `cursor`) paints a `vt100::Screen` into a ratatui `Buffer` directly and keeps one dependency. If D27 prefers the `tui-term` widget, implement its two traits for `vt100` 0.18 newtypes; this was not tried.
- `alacritty_terminal` is a full terminal (grid, `Term`, event listener, PTY helpers) with no ratatui widget. ### The prototype

`prototypes/p0.6/` now has a second binary, `p06-panes`, next to the transport proof `p06-proof` (unchanged). The transport code in `src/panes/transport.rs` is copied from `src/main.rs` and reshaped into pane tasks; `main.rs` was left as run for the first part.

| Path | Content |
|---|---|
| `src/panes/main.rs` | Event loop. `ratatui::init()`, draw, drain events, `ratatui::restore()` on every exit path. `--dump DIR` writes the drawn buffer as `screen.txt` and `screen.ansi` after each draw. `--log FILE` writes the event log. `--nudge`, `--resync` are the replay repairs. |
| `src/panes/app.rs` | `App` owns all state. `AppEvent::{Term, Pane}` in, `update`, pure `render(&self, &mut Frame)`. `Pane { parser, inner size, Link, generation, rx bytes }`. `Link::{Detached, Attaching, Attached, Ended}`. Layout is one function used by render and by the size sync. |
| `src/panes/transport.rs` | Pane tasks. `spawn_main` (left) and `spawn_shell` (right). In: `PaneCmd::{Input, Resize, Detach}`. Out: `PaneEvent::{Attached, Output, Notice, Exited, Ended}`. |
| `src/panes/term.rs` | `TermScreen` widget (a `vt100::Screen` into a ratatui `Buffer`) and `cursor()`. |
| `src/panes/keys.rs` | `crossterm` key to xterm bytes, with DECCKM taken from the parser. |
| `main-tui.sh` | The main process of `p06t-main`: a full-screen bash app that paints only what changed (header rows 1 to 3 at start and on SIGWINCH, a tick row, a typed row) and has a `flood` command. |
| `drive.py` | Runs the app in a real pty (python3 `pty`), types keys, resizes the pty with `TIOCSWINSZ`, waits on the dumped screen and writes checks. |
| `run-panes.sh` | Creates the sandbox, runs `drive.py` for runs a, b, c, deletes the sandbox. |
| `captures/` | The run output (`run-*.txt`) and the app event logs (`app-*.log`) quoted below. |

Keys in the app: Ctrl-W switches focus, Ctrl-X detaches or reattaches the left pane, Ctrl-Q quits. Everything else goes to the focused pane as xterm bytes. Pane state transitions: attach starts a new generation and a fresh parser; events from an old generation are dropped. The initial pty size of each attachment is the pane's inner size. Under a floor of 20x5 inner, the pane keeps its last remote size and the widget truncates.

How the evidence was taken: a TUI cannot be watched, so `drive.py` starts `p06-panes` inside a pty of a chosen size, sends bytes to the pty master, and reads what the app dumped from its ratatui `Buffer` after each draw. The screens below are those buffers (not a re-parse of the terminal output). Colors are checked on the dumped buffer's cell styles. Run `a` is keys, resize, detach, reattach and the plain overflow case. Runs `b` and `c` repeat the overflow case with `--resync` and `--nudge`.

#### Proof 3b. The 1 MiB replay window starts mid escape sequence

The main process script `main-tui.sh` has a `flood` command: typing `flood` and Enter makes it write about 6.6 MB of in-place row repaints (1,500 frames, one `write` per frame of about 4.4 KB, mostly SGR and cursor sequences). The test repeats flood, detach, reattach until the first byte of the replay is inside a CSI sequence, then looks at the pane. The head of the first replay chunk is in the app log.

### Surprises

1. **A replay window starts anywhere.** Across the 14 replay windows taken in the final three runs, 6 started at an ESC (the window edge fell on a `write` boundary of the main process), 4 started in plain text, and 4 started inside a CSI sequence. First-chunk sizes over all attaches ranged from 14 bytes (a complete replay) to 3,968 bytes (`captures/app-*.log`, `first chunk` lines). The window edge is not aligned to any terminal-protocol boundary, and its phase depends on how the program writes. In the first versions of the flood script (one `write` per row) the edge fell on a row boundary in most attempts; one `write` per frame, with a different frame length per flood, was needed to cut sequences.
2. **A diff-painting app loses state to the window, and a parser cannot fix that.** Everything painted before the window start and never repainted is missing: header, input row, and the alt-screen switch. The nudge (rows-1 then rows, 600 ms after attach) repaired it in run c because the app repaints on SIGWINCH. A same-size `window_change` does nothing, so the nudge must change the size twice.
3. **The cut fragment is painted as text.** `7m###...` appeared on row 1 (plain), because a fresh parser starts in the ground state at the cursor home. The `vt100` parser does not mis-parse what follows: the colors of the later rows were right in every case.
4. **A tiny terminal needs a floor.** In a development run before the floor existed, the 6x3 terminal sent `window_change` 1x1 to both remotes. The shell redrew its prompt one character per row at width 1 and the pane was left with that mess after the terminal grew back, because `vt100` truncates columns on a width change (`Parser::set_size` documentation: "naively truncated"). With the floor (20x5), the remote keeps its last size and the widget truncates: no remote reflow, no panic (check 2d, 2d2). The floor does not apply to the real terminal size, only to what is forwarded.
5. **The unfocused pane keeps running.** Output of the right shell and the main process is parsed whether or not the pane is focused. The parse cost of a 6.6 MB flood on the app thread was not measured (see "Not verified").
6. **Detach closes only the channel.** `eof` plus `close` plus `disconnect` is enough: the main process kept ticking, and the next attachment owned input at once, as in the transport research.

### Recommended model

#### For `jackin-tui`

- One `App` owner of all state. The terminal, the panes' tasks and the timers send events into one `mpsc` queue (`AppEvent`). `update` changes state, `render` reads it and does no I/O. In the jackin console this queue is the baseline's "input variant for external messages" (D27 extension), and the console keeps the baseline `Application`, `Page` and `Request` loop (D27).
- A session tab holds a `Vec<Pane>` and a focus. A pane is `{ kind: Main | Shell, term: TermState, link: Link, generation, stats }`. `Link` is an enum: `Detached`, `Attaching`, `Attached(cmd_tx)`, `Exited(code)`, `Failed(reason)`. An attach creates a new generation, a new `TermState` (fresh parser) and a new task. Events carry the generation and a mismatch is dropped.
- A pane task owns the remote session and nothing else. Commands in: `Input(bytes)`, `Resize{cols, rows}`, `Detach`. Events out: `Attached`, `Output(bytes)`, `Notice(text)`, `Exited(code)`, `Ended(reason)`. The same two commands and five events fit both transports, so the pane code is the same for the Codex pane and a shell pane. Use a bounded channel with coalescing for `Output` in the real build (the prototype's channels are unbounded).
- Sizes: one function computes the pane rectangles from the terminal size; render and the size sync both call it. After every event batch, compare each pane's inner size with the last forwarded size and, if it changed and is above the floor, resize the parser and send `Resize`. Use the inner size, not the outer one.
- Detach and attach are console actions on the pane, never raw bytes: `0x04` never reaches Codex anyway (transport research, fact 2). Hold the console chords in the demo's key table (D28), not in the pane. The lone Ctrl-P delay stays; send the pending byte with the next key if it matters in Codex.
- After a Codex pane attach, run the nudge once, about 600 ms after `Attached`. This is the only repair that restores rows the window dropped. The nudge is invisible to Codex only if Codex repaints on SIGWINCH; test that with real Codex before relying on it.
- On `Exited`/`Ended` for the main process, read `GetSandbox` for the exit code and show it in the pane; do not retry the attach (transport research, fact 8). A shell pane has no replay and its process dies with the stream, so the console has to say so when it closes one.
- One console pane per sandbox main process, because every attachment resizes the shared PTY (transport research, question 3).
- Keep the optional `--resync` rule out of the first build. It removes the fragment only when the first byte is not ESC, CR or LF, and the nudge removes it as well. Add it if Codex does not repaint on SIGWINCH.

#### For a reusable baseline "terminal pane" block (D27 extension)

A block that renders from a byte stream and does no I/O, behind a Cargo feature (like the `clap` feature in D27) so the baseline library does not always depend on `vt100`:

```text
TerminalState   { fn new(rows, cols), fn feed(&mut self, &[u8]), fn resize(&mut self, rows, cols),
                  fn reset(&mut self)  /* fresh parser, for reattach */,
                  fn modes(&self) -> Modes { app_cursor, bracketed_paste, alt_screen, hide_cursor },
                  fn cursor(&self, area: Rect) -> Option<Position> }
TerminalView<'a>{ state: &'a TerminalState, focused: bool, color: bool }   // impl Widget
encode_key(KeyEvent, &Modes) -> Option<Vec<u8>>                              // input side
```

- `feed` takes any byte slice from any source; the block does not know about OpenShell, so `jackin-preview` can feed it a canned script and jackin can feed it a pane task's output.
- `resize` clamps to non-zero sizes. The floor belongs to the caller (the screen that owns the layout), not to the block.
- Colors: pass `Idx` through as ratatui `Indexed` (the terminal's own palette) and `Rgb` through unchanged. `color: false` drops fg and bg and keeps the modifiers; the caller sets it from `NO_COLOR` (the prototype does this but the `NO_COLOR` path was not run; see "Not verified").
- A function that borders and titles the pane belongs to the existing baseline pane chrome, not to this block. The prototype's focused border (thick, yellow) and the title status are the only chrome used.
- Testing: tuiscotti baselines can render the view from fixed byte fixtures with no network: a complete session, a window that starts mid-CSI (the fixture is the head `7m###\x1b[31m...` above), and a resize between two feeds. A new baseline needs `tuiscotti accept` after a `ux-specialist` review (D27). No existing baseline changes, because the block is new and feature-gated.

### Not verified

- Real Codex in the left pane: how it repaints on SIGWINCH, whether it uses the alternate screen, and what its replay window looks like. The main process here is a bash script.
- The `NO_COLOR` path (implemented in `main.rs` and `TermScreen`, not run).
- Parser throughput and UI latency under heavy output. The flood (6.6 MB, received within 3.7 s of an attach, `captures/app-a.log`) completed and the panes stayed correct, but no timing of `Parser::process` or of frames was taken.
- Mouse, bracketed paste forwarding, focus events, kitty keyboard protocol, wide characters and combining characters in the pane. The widget handles wide-continuation cells; nothing printed a wide character.
- Scrollback navigation in a pane (the parser keeps 1,000 rows; the prototype has no key for it).
- A pane over a remote or OIDC gateway; gateway restart or network loss while attached; reattach after `jackin stop`/`jackin start`.
- Windows and Linux hosts. Only macOS arm64 with a real pty from python3.
- The right pane has no reattach: a shell pane ends with its stream (as proven in "Transport research").
- `main-tui.sh` assumes bash 5 in the sandbox image (Ubuntu 24.04 base). It was not run under macOS `/bin/bash` 3.2.

### Rerun

```text
cd prototypes/p0.6 && mise exec -- mbx +1.99.1 build && ./run-panes.sh <output-dir>
```

It creates `p06t-main`, runs the three driver runs (about 5 minutes), prints `run a exit=0` and so on, and deletes the sandbox. Each driver run writes `run-<a|b|c>.txt`, an app event log, the dumped screens and the raw pty bytes. The gateway and sandbox are explicit in `run-panes.sh` and `drive.py`; every `openshell` call runs with stdin `/dev/null` under `perl -e 'alarm shift; exec @ARGV' 600`.
