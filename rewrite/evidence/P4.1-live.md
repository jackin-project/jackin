## How the calls were made

The calls are gRPC calls with `grpcurl 1.9.4` (Homebrew bottle, installed for this task with `brew install grpcurl`; the gateway has no reflection, so the v0.1.6 `proto/` directory is the descriptor source). Each call used the mTLS files of the gateway entry (`~/.config/openshell/gateways/jackin-local/mtls/{ca.crt,tls.crt,tls.key}`), stdin from `/dev/null`, a hard `alarm` timeout, and an explicit `workspace_scope.workspace = "default"` in every request. The CLI was used for three cross-checks only (marked "CLI"), also with `-g jackin-local --workspace default`.

```text
g <seconds> <grpcurl args> = perl -e 'alarm shift; exec @ARGV' <seconds> grpcurl \
    -cacert $M/ca.crt -cert $M/tls.crt -key $M/tls.key \
    -import-path <OS@v0.1.6>/proto -proto openshell.proto -emit-defaults <args> </dev/null
service name on the wire: openshell.v1.OpenShell
```

Scratch files: `/private/tmp/claude-501/p41live/` (`out/` holds every raw reply; `g`, `getsb`, `run2.sh` are the drivers). The create requests mirror what the SDK sends (`OS@v0.1.6:crates/openshell-sdk/src/client.rs:1393-1432`): `restart_policy = SANDBOX_RESTART_POLICY_NEVER`, no annotations, `workspace_scope` set. The SDK's `SandboxSpec` has no `policy` field, so the policy request in item 3 is a raw `CreateSandbox`.

grpcurl prints the gRPC status code, the message and the decoded details. It prints `grpc-status-details-bin` in the trailers when a status has details. Where no such trailer appears below, the status has no details (inferred from that absence; the one status that has them, item 4, shows the trailer).

### Setup

Two default-image sandboxes (`nvcr.io/nvidia/base/ubuntu:24.04`, which the gateway fills into `spec.template.image`). Request (run 2; run 1 used the names `p41-fail` and `p41-ok` and the same bodies):

CreateSandbox {workspace_scope{workspace:"default"}, name:"p41-ok2",

### Source that explains the capture

- `StopSandbox` is a no-op that returns the stored sandbox when the phase is `Stopped` or `Completed`, or when it is `Error` with an exit code and a `Ready=False/MainProcessFailed` condition: `OS@v0.1.6:crates/openshell-server/src/compute/mod.rs:428-436` (`QuiesceAdmission::Settled`), `:6653-6663` (`is_failed_main_process_result`), returned at `:2017-2022`. Handler: `crates/openshell-server/src/grpc/sandbox.rs:1764-1787`.
- `StartSandbox` accepts `Completed` and a failed-main-process `Error` (`compute/mod.rs:2301-2336`), commits `Starting` first (`:2383`), then calls the driver. The VM driver refuses because the VM process still exists with another generation: `OS@v0.1.6:crates/openshell-driver-vm/src/driver.rs:2018-2038` (`failed_precondition("VM sandbox is already running generation ...")`). The gateway prefixes the text with `start sandbox failed: ` and keeps the driver's code: `compute/mod.rs:2594-2599`. The `Starting` record is not rolled back in this case (live result above; `recover_failed_lifecycle` at `:2841` reconciles to the driver snapshot).
- The `already running generation` refusal belongs to the `vm` driver. The Docker and Podman drivers have the same text (`openshell-driver-docker/src/lib.rs:4438`, `openshell-driver-podman/src/driver.rs:1588`), so this probably holds on them too (inferred, not run).

## Item 2 (R5): provisioning failure

Request (`out/create-missing.txt`; the CLI sends `--from <ref>` unchanged as `template.image`: `OS@v0.1.6:crates/openshell-cli/src/run.rs:1294,1334`):

```text
CreateSandbox {workspace_scope{workspace:"default"}, name:"p41-miss",
  spec{template{image:"jackin-p41/missing:1"}, command:["sh","-c","exit 0"], restart_policy:NEVER}}
```

Create reply: OK, `phase=SANDBOX_PHASE_PROVISIONING`, conditions `ConfigurationReady False ConfigurationPending` and `Ready False ConfigurationPending`.

`GetSandbox`, polled every 8 s for 112 s. The first poll (8 s) already had the final phase. Every poll after it was identical in phase and conditions:

```text
phase=SANDBOX_PHASE_ERROR  exitCode=null (absent)
conditions:
  type=Ready              status=False reason=ProvisioningFailed
    message="failed to resolve vm sandbox image 'jackin-p41/missing:1': Not authorized: url https://index.docker.io/v2/jackin-p41/missing/manifests/1"
  type=ConfigurationReady status=False reason=ConfigurationPending
    message="Waiting for effective configuration validation before workload activation"
status.configurationAdmission.state=CONFIGURATION_ADMISSION_STATE_PENDING
status.provisioning: deadline=preparationDeadline=<create time + 30 min>, timeoutTime=null,
  cleanupCompletedTime=null, driverOperationPending=false
```

The condition order in the list is `Ready`, `ConfigurationReady` (the order changes between sandboxes; match on `type`, not on position). `resourceVersion` moved 5, 6, 7 during the poll with no change in the status above.

CLI cross-check (`out/cli-miss2.txt`, sandbox `p41-miss2`): `openshell sandbox create --from jackin-p41/missing:1 ...` exits 1 with `sandbox entered error phase while provisioning: ProvisioningFailed: failed to resolve vm sandbox image 'jackin-p41/missing:1': Not authorized: url https://index.docker.io/v2/jackin-p41/missing/manifests/1`. `GetSandbox` of that sandbox shows the same phase and condition.

Source: the VM driver reports `Ready=False` with reason `ProvisioningFailed` (`OS@v0.1.6:crates/openshell-driver-vm/src/driver.rs:1356-1362`, message built at `:3419` and `:3950`). `derive_phase` turns `Ready=False` with a non-transient reason into `Error`: `crates/openshell-server/src/compute/mod.rs:7839-7848` and `is_terminal_failure_reason` at `:8058-8070`. So `Error` follows from the reason, and `ProvisioningFailed` is not in the transient list.

`DeleteSandbox` of both failed sandboxes returned `DELETION_OUTCOME_ACCEPTED` (not `COMPLETED`); they were gone from `ListSandboxes` within 10 s.

The SDK type `SandboxRef` has `phase` and `exit_code` but no conditions (`OS@v0.1.6:crates/openshell-sdk/src/types.rs:391-408`; no `conditions` in `crates/openshell-sdk/src/*.rs`). The condition is reachable only through the raw `GetSandbox` reply (`raw::proto::Sandbox.status.conditions`).

### The two hashes

For version 2 the gateway holds two different hashes:

- `GetSandboxConfig.policyHash`, `status.configurationAdmission.policyHash` and the provider status `policyHash` are all `3a92364027d3...`. This is the hash of the effective policy after provider composition (it contains `_provider_p41_prov`). Source: `OS@v0.1.6:crates/openshell-server/src/grpc/policy.rs:2999-3017` (`compose_effective_policy`, then `policy_hash = deterministic_policy_hash(&effective_policy)`).
- `GetSandboxPolicyStatus.revision.policyHash` and the `ListSandboxPolicies` entries are the hash of the stored revision (`bcc34a91...`, no provider rule): `policy.rs:7025-7048` (`policy_record_to_revision`).
- The CLI's `policy get` without `--version` reads `GetSandboxConfig` (`OS@v0.1.6:crates/openshell-cli/src/run.rs:6096-6101,6203-6247`) and labels it `effective`. With `--version N` it reads `GetSandboxPolicyStatus` (`:6106-6114`).
- `GetSandboxPolicyStatus` always includes the policy body (`policy.rs:4912`, `policy_record_to_revision(&record, true)`); `ListSandboxPolicies` never does (`policy.rs:4917`, `false`). The request has no flag for it (`OS@v0.1.6:proto/openshell.proto:2974-2983`).
- The revision's `status == POLICY_STATUS_LOADED` together with `activeVersion == revision.version` is the loaded signal. `GetSandboxConfig` has no loaded flag.
- The effective and stored policy gained `/var/log` in `read_only` that the request did not carry. The server adds it (seen in the stored revision 2 and in `GetSandboxConfig`; `GetSandbox.spec.policy` keeps the submitted value). Where it is added was not traced.

So the status has no `BadRequest` and no `ErrorInfo`, and the message repeats the offending value. In the SDK this status becomes `InvalidConfig` with no details. Source: `OS@v0.1.6:crates/openshell-server/src/grpc/validation.rs:882-893` (`Status::invalid_argument(format!("label value exceeds 63 characters: '{value}'"))`, called at `:962` and `:1001`).

## Contradictions with the plan's R4, R5 and R6

1. **R4, the plan's reading is confirmed, and one more detail matters.** `StopSandbox` on an `Error` or `Completed` sandbox returns gRPC OK with the sandbox unchanged. It is not `FailedPrecondition`. `MainProcessFailed` appears only in the CLI's client-side wait. A server copy that returns `FailedPrecondition` to `Stop` would be wrong. The adapter has to build `MainProcessFailed` from the returned phase `Error` and the exit code, and it needs a rule for `Completed` (the plan's `M1` only names `Error`).
2. **R4, `StartSandbox` is not `Starting` then `Ready`.** On the `vm` driver both `Error` and `Completed` give `FailedPrecondition` (`VM sandbox is already running generation ...`, no details) and leave the sandbox in `STARTING` with the exit code cleared, which never ends in the observed 92 s. The plan's `M1` text "`Start` returns a `Starting` view" is wrong for the RPC reply: there is no view, there is an error, and the `Starting` state is visible only in a later `GetSandbox`. The plan also says `Completed` "follows the recorded behavior": it is the same as `Error`.
3. **R4, a second `Stop` fails.** After the failed `Start`, `StopSandbox` returns `FailedPrecondition` (`current phase: Starting`), so the failed start cannot be undone through the API; only `DeleteSandbox` removed the sandboxes. This matches `evidence/P7.1-image.md` F3.
4. **R5, the phase is `ERROR`.** The condition is `Ready` / `False` / `ProvisioningFailed`, as the plan says (type, status and reason match). The message text is not fixed: it carries the image reference and a registry error. The plan's open question 8 is answered: `Provisioning::Failed` can derive from the condition and the phase `Error` agree. Match on `type == "Ready"` and `reason == "ProvisioningFailed"`, not on list position. The curated SDK `SandboxRef` does not carry conditions, so the adapter needs the raw `GetSandbox` for this.
5. **R5, the status stays `Error` and the exit code is absent**, so a retry with the same launch ID meets an `Error` sandbox without an exit code. `StartSandbox` on it was not tried.
6. **R6, `GetSandboxPolicyStatus` has no include-policy flag in v0.1.6.** It always returns the policy body. The plan text ("returns the policy only when requested", `openshell.proto:3078`) does not match: the request message is at `openshell.proto:2974-2983`, and the body is included unconditionally at `policy.rs:4912`.
7. **R6, `GetSandboxConfig` is a user RPC.** The plan calls it "a supervisor RPC (`sandbox.proto:434`)". The proto declares it for users and supervisors (`openshell.proto:453-462`, `auth_mode: "dual"`), and it works with the mTLS client certificate. It is the RPC that returns the effective policy and its hash (the CLI's `policy get` uses it).
8. **R6, there are two hashes for the same version.** The effective hash (`GetSandboxConfig`, `status.configurationAdmission`) differs from the stored-revision hash (`GetSandboxPolicyStatus`, `ListSandboxPolicies`) as soon as a provider is attached, because the effective policy contains the `_provider_<name>` rule. `PolicyReport.hash` must name which one it carries. `version` is the same in both (2). There is no `loaded` boolean on the wire: use `revision.status == POLICY_STATUS_LOADED` with `activeVersion`, or `configurationAdmission.state == ACCEPTED`.
9. **R6, attached providers.** `ListSandboxProviders` lists the records (with redacted credentials). `GetSandbox.spec.providers` lists only the names. `GetSandboxProviderStatus` gives readiness.
10. **R13 name and label rules are confirmed.** The 20-character name has `ErrorInfo` and `BadRequest` details, with field `name`. The 64-character label value has no details and the message repeats the value, so the adapter's `InvalidArgument.field` is `""` for labels, as the plan says.
11. **R3 is confirmed live.** An unknown provider profile on `CreateProvider` is a plain `InvalidArgument` with no details. A second condition not in the plan: the provider needs `profile_workspace` set to find a workspace-scoped profile.

## Not verified

- Behavior on the `docker` or `podman` compute drivers. Item 1 and item 2 are results of the `vm` driver (the message texts name it).
- Whether a `ProvisioningFailed` sandbox can be started, or whether it leaves `Error` at its 30-minute `preparationDeadline` (not waited for).
- `restart_policy` other than `NEVER` (the SDK default and the CLI default). `ON_FAILURE` and `ALWAYS` change what happens after an exit and were not run.
- The wire form seen through the Rust SDK or `tonic`. The replies here are from `grpcurl`; the code and message are the status values, and the details come from the `grpc-status-details-bin` trailer, which `tonic` exposes the same way.
- Where the server adds `/var/log` to the read-only list.
- Anything with OIDC or bearer authentication. The gateway uses mTLS only.
