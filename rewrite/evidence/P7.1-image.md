## The `jackin-start` interface

The main command of the sandbox is `/usr/local/bin/jackin-start <agent command...>`. For Codex jackin passes the `launch_command` of the `AgentSpec` row, so the D04 command lives in one place. The script is POSIX `sh` (checked with `shellcheck -s sh`).

| Input | Meaning |
|---|---|
| `JACKIN_LAUNCH_ID` (env) | Launch id. Required. It must match `[A-Za-z0-9][A-Za-z0-9._-]*`. |
| `JACKIN_HOOK_SETUP` (env) | Absolute path of the setup hook inside the image. Empty or unset: skip. |
| `JACKIN_HOOK_PREFLIGHT` (env) | Absolute path of the preflight hook. Empty or unset: skip. |
| argv | The agent command. Required. `jackin-start` runs `exec "$@"` in `/sandbox/project`. |

Jackin sets the env with `sandbox create --env KEY=VALUE` (non-secret values only).

| Path | Written by | Meaning |
|---|---|---|
| `/sandbox/.jackin/ready-<launch-id>` | jackin (`sandbox exec`), after the upload | Releases the wait. |
| `/sandbox/.jackin/setup-done-<launch-id>` | `jackin-start`, after the setup hook exits 0 | Setup does not run again for this launch id. |

Order: create `/sandbox/.jackin`, wait for the ready marker (poll every 0.5 s, no timeout), check that `/sandbox/project` exists, run setup unless its done-marker exists, write the done-marker, run preflight, `cd /sandbox/project`, `exec` the agent command. Hooks run with `/sandbox/project` as working directory. A failed setup writes no marker, so the next start runs setup again. A crash between the setup exit and the marker write also reruns setup, so setup runs at least once and exactly once only when no crash hits that window.

| Exit code | Cause | stderr line |
|---|---|---|
| hook's own code | Setup or preflight hook exited non-zero | `jackin-start: <setup\|preflight> hook failed with exit code N: <path>` |
| 64 | No argv, or `JACKIN_LAUNCH_ID` missing or invalid | `jackin-start: missing agent command` or `jackin-start: JACKIN_LAUNCH_ID is missing or invalid` |
| 65 | Hook path is not absolute, or not an executable file | `jackin-start: <name> hook path is not absolute: <path>` or `... is not an executable file: <path>` |
| 66 | `/sandbox/project` is missing after the marker | `jackin-start: project directory is missing: /sandbox/project` |
| agent's own code | The agent command ran and exited (it replaced the script) | none from `jackin-start` |

A hook can exit 64, 65 or 66 itself, so the code alone does not name the cause. The stderr line does, but only while a client is attached (see F3).

## Findings

### F1. The cross-device warning of P0.3 disappears

With the earlier derived draft, `codex --version` in the sandbox printed `WARNING: failed to clean up stale arg0 temp dirs: Cross-device link (os error 18)` (P0.3 gap G4, and the first run of this task). The cause was the build-time `codex --version`: it ran as root with `HOME=/sandbox` and left `/sandbox/.codex/tmp/arg0-linux/...` in the image layer. The sandbox then renamed a directory from the lower layer. `derived.Dockerfile` now runs the check with `CODEX_HOME` in a temporary directory under `/root` and deletes it in the same `RUN`. The final transcript above shows `codex --version` with no warning and `/sandbox/.codex` created at first run, owned by `sandbox`. (Cause inferred from the layer listing and the before and after output, not from the Codex source.) `CODEX_HOME` under `/tmp` does not work: Codex refuses to create helper binaries under a temporary directory and warns.

### F2. A hook under `/opt` is unreadable in the sandbox

The default sandbox filesystem policy has read-only `/bin /usr /lib /proc /dev/urandom /etc /var/log`, read-write `/tmp /dev/null`, and `include_workdir: true`. Landlock denies everything else, including `/opt`. A first test role copied the hooks to `/opt/role/hooks`. The main process exited with `Exit Code: 126` and the hook never ran. ### F3. A failed main process cannot be inspected or restarted (OpenShell 0.1.6)

- The hook error line reaches only a client that is attached when it is written. After the process exits, `sandbox connect` prints `openshell: cannot connect to the canonical main process: canonical main process already finished` (seen in the first attempt of this task with the `/opt` hook). `sandbox exec` on an `Error` sandbox is refused (`sandbox 'p71-main' is not ready (phase: Error)`). So `Exit Code` in `sandbox get` is the only durable signal.
- `sandbox stop` of an `Error` sandbox fails with `MainProcessFailed: Canonical main process exited with status N while waiting for Stopped`. `sandbox start` then fails with `VM sandbox is already running generation ...` and leaves the sandbox in `Phase: Starting`, `ConfigurationPending`. A second stop is refused (`current phase: Starting`). The sandbox was still in `Starting` after a polling loop of about 80 s. `sandbox delete` removed it.
- Consequence for P5.1 and P5.2: after a hook failure the only recovery is delete and create again. DESIGN.md launch sequence says a retry with the same launch ID finds the existing sandbox and continues; that cannot work for an `Error` sandbox. The launch executor must treat `Error` as "delete and recreate" (the uploaded project is lost, so it needs ADR-010 handling) or the design must keep hook failures from ending the main process.

## Not verified

- `linux/amd64` in a sandbox. The amd64 derived image builds and its binary ran during the build, but no sandbox was created from it.
- Codex login and a model answer in this image. P0.3 proved that with the earlier image; the Codex binary, the sibling binary, the config file and the user are the same. The brief for this task needs no credential.
- That the Codex process has `/sandbox/project` as its working directory. `/proc/<pid>/cwd` is not readable from `sandbox exec`. The hook output shows `cwd=/sandbox/project`, and the script does `cd` before `exec`.
- Bit-for-bit reproducible builds. The base is pinned by digest and the Codex archive by checksum. The `apt-get` package versions float, so a rebuild at another time can change the construct digest. The cache key therefore needs the construct digest, as D05 says.
- `hadolint` or another Dockerfile linter. Only the BuildKit parser ran.
- The first-attempt sandbox with the `/opt` hooks was deleted before I repeated the capture, so F2 shows the `sandbox get` from that sandbox and the `exec` from a second sandbox on the same image.
