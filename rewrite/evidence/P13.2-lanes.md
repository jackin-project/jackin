# P13.2: three fresh lanes of the end-to-end journey

Each lane cloned jackin and jackin-sentinel from GitHub into an empty directory, checked out the pinned commits, and ran G-E2E (`mise exec -- mbx +1.99.1 xtask e2e --gateway jackin-local --role ../jackin-sentinel --builder orbstack --platform linux/arm64 --engine-port 2376 --engine-certs ~/.local/share/jackin-e2e-engine/client`) against the real OpenShell 0.1.7 gateway `jackin-local`. The lanes ran one after the other because the A1 Codex credential is one host login. Before each lane the gateway listed no sandboxes; after each lane the A1 host login file was unchanged, and no line of the output was token-shaped.

- jackin: `e4fd71f184913f0b1d595b4d0959f5dc50ec39d0`
- jackin-sentinel: `ad4776d09578363941dd53057d870394e1303583`
- Date: 2026-11-04 (lanes started 01:39, 01:44 and 01:49 local time)

An earlier attempt on jackin `e0776e988` and sentinel `96c530a` failed J08 in all three lanes. After review fix N1 the probe scanned binary files, and it found the chatgpt.com `__oailb` load-balancer cookie in Codex's SQLite log. That cookie is an ES256 JWT with `iss` edge-gateway, `aud` chatgpt.com and no `sub`, so it is no credential. The probe now flags a JWT only when it carries a `sub` claim (sentinel `ad4776d`, decisions.tsv 2026-11-10T01:20). In that attempt, lane 2 also failed CLEAN, because the orchestrator ran an `openshell` command during the lane to inspect the match; nothing touched OpenShell during the lanes below.
