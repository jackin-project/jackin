The filter returns `EPERM` for `mount`, `unshare` and `clone` with `CLONE_NEWUSER`, `setns`, `pivot_root` and `bpf`. Root is rejected by the gateway. No policy field, process setting or driver option relaxes this.
- Smallest failing case, both lanes: `unshare -U true` returns `EPERM` ([laneA:194-196](P0.5-docker-laneA.md), [laneB:128](P0.5-docker-laneB.md)). Rootless Docker stops at `fork/exec /proc/self/exe: operation not permitted` ([laneA:244](P0.5-docker-laneA.md), [laneB:168](P0.5-docker-laneB.md)).
- Root request: `run_as_user must be 'sandbox' or a numeric UID/GID in range [1, 4294967294], got '0'` ([laneA:260-264](P0.5-docker-laneA.md), [laneB:115-118](P0.5-docker-laneB.md)).
- Code: `NVIDIA/OpenShell@v0.1.6:crates/openshell-sandbox/src/sandbox/linux/seccomp.rs:80` and `:129` (`no_new_privs`), `:165-170` (`clone3` returns `ENOSYS`), `:237-250` (`mount`, `fsopen`, `setns`, `umount2`, `pivot_root`), `:267-281` (`unshare`, `clone`); `docs/how-it-works/policies/schema.mdx:28-33` (the policy has no field for capabilities or namespaces) and `:92` (root is rejected).
- The guest kernel is not the limit. It lists `overlay` and `cgroup2` and allows 7690 user namespaces ([laneA:190-191](P0.5-docker-laneA.md)). The seccomp filter and the missing capabilities are the limit.
- The other drivers share the filter in source and use `cap_drop: ALL`. Only `vm` was run.
- Upstream tracks the gap as `NVIDIA/OpenShell#4970` (open, created 2026-10-27; read with `gh issue view 4970 -R NVIDIA/OpenShell` on 2026-11-01 UTC). `#113` is closed as a duplicate (2026-03-23). See section 2 of the blocker report.

Credential path (D24 last paragraph): OpenShell cannot keep the engine credential outside the sandbox for a working engine. The mTLS client key must be a file in the sandbox. A bearer token injected by the proxy works for plain API calls but breaks attached `docker run`, `docker exec` and BuildKit. The capability is not blocked, because D24 permits a dedicated engine that holds nothing else.

## Settings the product must implement

### Engine form: rootless dind, not privileged

| | Rootless dind (lane A) | Privileged dind (lanes A and B) |
|---|---|---|
| Image | `docker:dind-rootless` | `docker:dind` |
| Container flags | `--security-opt seccomp=unconfined --security-opt apparmor=unconfined --security-opt systempaths=unconfined --device /dev/net/tun` | `--privileged` |
| Engine container state | `privileged=false user=rootless caps=[]` ([laneA:628](P0.5-docker-laneA.md)) | `CapEff 000001ffffffffff` ([laneB:332](P0.5-docker-laneB.md)) |
| `docker version`, `docker run --rm hello-world` | pass ([laneA:649-651](P0.5-docker-laneA.md)) | pass |
| Bind mount of `/Users` | refused, `mkdir /Users: permission denied` ([laneA:652](P0.5-docker-laneA.md)) | Mac home not reached, `host-home-reachable=no` ([laneA:431](P0.5-docker-laneA.md)) |
| `docker build` (BuildKit), `run -i`, `compose version` | not run | pass ([laneA:415-416](P0.5-docker-laneA.md), [laneB:265-273](P0.5-docker-laneB.md)) |
| Same sandbox policy | yes | yes |

Recommendation: **rootless dind**. It passed the P0.5 test with the least privilege, and the engine container has no capabilities and is not privileged. The three `--security-opt` flags and the tun device were needed together, because a first attempt without `/dev/net/tun` failed ([laneA:614-621](P0.5-docker-laneA.md)). The minimal subset was not isolated. These flags weaken the default seccomp and AppArmor profiles of the engine container, so rootless is "less privilege", not "no relaxation".

Limits of this recommendation:
- The rootless engine was proven with `version`, `run --rm hello-world` and one refused bind mount. Build, `run -i`, `exec` and `compose` ran only against the privileged engine, and `exec` was not run through mTLS at all.
- P5.4 must run `docker build`, `docker run -i`, `docker exec` and `docker compose version` against the rootless engine in `xtask e2e`. If one fails, record the failure and re-decide the engine form. Do not hide it with a fallback.
- Jackin never starts an engine (D24), so the engine form is operator guidance and an `xtask e2e` fixture. The jackin contract is the same for both forms: an endpoint and a client certificate directory.
- Pin the engine image by digest. Lane B pinned `docker:dind` to `sha256:9e79b879b177fbd72c34376a3dd3d91747da5db49e1f560f76aea59561471977` ([laneB:6](P0.5-docker-laneB.md)). No lane recorded a digest for `docker:dind-rootless`.
- Rootless dind on a Linux host was not run.

Operator stand-up, from [laneA:731-740](P0.5-docker-laneA.md) and [laneB:30-38](P0.5-docker-laneB.md):

```text
docker run -d --name <engine> \
  --security-opt seccomp=unconfined --security-opt apparmor=unconfined --security-opt systempaths=unconfined \
  --device /dev/net/tun \
  -e DOCKER_TLS_CERTDIR=/certs \
  -e DOCKER_TLS_SAN=DNS:host.openshell.internal \
  -p 127.0.0.1:<port>:2376 docker:dind-rootless
```

- `DOCKER_TLS_SAN` must contain `host.openshell.internal`. The client verifies the server certificate itself, because the tunnel is raw. Without the name the client fails with `x509: certificate is valid for ..., not host.openshell.internal` ([laneB:354](P0.5-docker-laneB.md), [laneB:38](P0.5-docker-laneB.md)).
- Bind the port to `127.0.0.1` of the Mac. The VM driver maps `host.openshell.internal` to host loopback (`Policy DNS mapped host.openshell.internal resolved=127.0.0.1 synthetic=198.18.0.x`, [laneA:586](P0.5-docker-laneA.md)). A loopback literal as the policy host is never authorized ([laneA:453](P0.5-docker-laneA.md), `docs/how-it-works/policies/schema.mdx:141-149`).
- Both lanes used OrbStack. A non-loopback engine, a Linux gateway host and `allowed_ips` were not tested ([laneB:475-476](P0.5-docker-laneB.md)).

### Jackin config

OpenShell has no place for an engine endpoint. The policy schema has `filesystem_policy`, `landlock`, `process`, `network_policies` and `network_middlewares` only (`NVIDIA/OpenShell@v0.1.6:docs/how-it-works/policies/schema.mdx:28-33`). The endpoint exists only as a `network_policies` rule of one sandbox. D24 says the operator names the engine "in the gateway config". That is not possible. **Jackin config names the engine**: the port on `host.openshell.internal`, and the host directory that holds the client `ca.pem`, `cert.pem` and `key.pem`. Jackin turns them into the policy rule and the upload below.

### Network policy rule

Add this rule only when the capability is enabled (D12, D24). The file is [`rewrite/drafts/docker-laneA-policy-external-mtls-rootless.yaml`](../drafts/docker-laneA-policy-external-mtls-rootless.yaml). Lane B's [`docker-laneB-policy.yaml`](../drafts/docker-laneB-policy.yaml) has the same rule with `landlock: hard_requirement`.

```yaml
network_policies:
  docker_engine:
    name: docker_engine
    endpoints:
      - host: host.openshell.internal
        port: <engine port>
        protocol: tcp
        tls: skip
    binaries:
      - path: /usr/local/bin/docker
```

- `tls: skip` is required. With `protocol: tcp` alone the proxy still parses plain HTTP and strips `Upgrade`, so `docker run` fails with `unable to upgrade to tcp, received 200` ([laneA:690-702](P0.5-docker-laneA.md), [laneB:226-253](P0.5-docker-laneB.md)). With TLS, the proxy terminates it with its own CA and the engine's client-certificate check cannot pass ([laneA:457-477](P0.5-docker-laneA.md)). `docs/how-it-works/policies/network-rules.mdx:105-110` and `:637-640` describe both cases.
- `binaries` lists real paths. The rule also covers processes that a listed binary starts (`network-rules.mdx:72-74`). The `docker-buildx` plugin and `docker compose` matched the `docker` entry ([laneB:275-281](P0.5-docker-laneB.md)). A Testcontainers runtime would need its own entry. It was not tested.
- Scoping works. Another port, another binary (`wget`, `nc`) and the loopback literal are denied ([laneA:435-455](P0.5-docker-laneA.md), [laneB:285-295](P0.5-docker-laneB.md)).
- Only `network_policies` change on a live sandbox. Filesystem, Landlock and process policy are fixed at create (`schema.mdx:28-33`), so the rule can be added or removed with `policy set --wait` ([laneA:405-421](P0.5-docker-laneA.md)).
- BuildKit registry egress. Add this second rule when the capability supports `docker build`:

```yaml
  docker_registry:
    name: docker_registry
    endpoints:
      - { host: registry-1.docker.io, port: 443, protocol: tcp }
      - { host: auth.docker.io, port: 443, protocol: tcp }
      - { host: production.cloudflare.docker.com, port: 443, protocol: tcp }
    binaries:
      - path: /usr/local/libexec/docker/cli-plugins/docker-buildx
```

  Lane A's `docker build` of `FROM busybox` failed without it (`failed to fetch anonymous token ... auth.docker.io ... connect: permission denied`) and passed with it, with no other change ([laneA:391-422](P0.5-docker-laneA.md), file [`docker-laneA-policy-external-mtls-buildx.yaml`](../drafts/docker-laneA-policy-external-mtls-buildx.yaml)). The BuildKit client fetches the registry token for the engine. `docker run` and `docker pull` need no registry rule, because the engine pulls ([laneA:772](P0.5-docker-laneA.md)).
- Filesystem policy: `/sandbox` must be writable for the certificate upload (`include_workdir: true` covers it). Lane B passed with `landlock: hard_requirement` and `read_write: [/tmp, /dev/null]` plus the workdir ([laneB:42-57](P0.5-docker-laneB.md)).

### Client certificate delivery and environment

- Delivery: upload the client directory into the sandbox, for example `openshell sandbox upload <sandbox> <dir> /sandbox/` ([laneA:343-355](P0.5-docker-laneA.md), [laneB:421-428](P0.5-docker-laneB.md)). Both lanes used the CLI. The key arrives readable by the sandbox user (`-rw------- sandbox sandbox`, [laneB:348](P0.5-docker-laneB.md)). The SDK path and the order against the agent start were not tested. P5.4 must deliver the files before the agent can run `docker`.
- Do not bake the key into the image. The image carries only the client.
- Environment in the sandbox: `DOCKER_HOST=tcp://host.openshell.internal:<port>`, `DOCKER_TLS_VERIFY=1`, `DOCKER_CERT_PATH=/sandbox/<dir>` ([laneA:751](P0.5-docker-laneA.md), [laneB:59](P0.5-docker-laneB.md)). The lanes exported them inside `sandbox exec`. Setting them for the agent process was not tested.
- Image: the Docker CLI at `/usr/local/bin/docker`, because the rule matches that path, and the `docker-buildx` and `docker compose` plugins under `/usr/local/libexec/docker/cli-plugins/`. No engine in the image.

## Isolation facts for P5.4 and the security review

1. **Container egress bypasses the sandbox network policy.** The sandbox cannot reach `https://example.com` (`Permission denied`), but `docker run --rm alpine:3.22 sh -c "wget ... https://example.com"` returns the page ([laneB:299-308](P0.5-docker-laneB.md), [laneB:448-451](P0.5-docker-laneB.md)). The engine pulls images and runs containers on its own network. Any egress allowlist is void for code that can start a container. The engine, the image allowlist and the egress allowlist are one trust decision.
2. **Bind mounts name paths on the engine host.** `-v /sandbox/w:/w` gives an empty directory ([laneB:309-319](P0.5-docker-laneB.md)). `-v $PWD:/app` does not work. Workflows need `docker cp`, build contexts or volumes.
3. **The engine outlives the sandbox and is shared.** A container started in a sandbox kept running after `sandbox delete` ([laneB:320-331](P0.5-docker-laneB.md)). Containers from one sandbox were visible from another that used the same engine. Reaping is an operator duty. D24 source 1 promised deletion with the sandbox. Source 2 does not.
4. **A client key lives in the sandbox.** The agent can read it. The key opens only the dedicated engine, and the sandbox already has full use of that engine ([laneB:396](P0.5-docker-laneB.md)). A leaked key lets a local process on the Mac use the engine too.
5. **The endpoint is open to all local processes.** It listens on Mac loopback. The only gate is the client certificate. The engine has no per-sandbox identity ([laneB:333](P0.5-docker-laneB.md)). Sandboxes with the same certificate share one engine.
6. **Engine privilege.** A privileged dind is root in a privileged container in the OrbStack VM. That VM's own engine can bind-mount the Mac home (source 3 result). A container escape from the privileged form is therefore an inferred path to the Mac, not a tested one ([laneA:783](P0.5-docker-laneA.md), [laneB:332](P0.5-docker-laneB.md)). The rootless form removes the privileged container but not the nested-container risk.
7. **Source 3 is root on the Mac.** Through a loopback bridge to the OrbStack socket, the sandbox listed other agents' containers and bind-mounted `/Users` ([laneA:709](P0.5-docker-laneA.md), [laneB:403-416](P0.5-docker-laneB.md)). OrbStack exposes its engine only as a unix socket and a policy endpoint is `host:port`, so source 3 also needs an unauthenticated operator TCP bridge ([laneA:666](P0.5-docker-laneA.md), [laneB:400](P0.5-docker-laneB.md)). Nothing in OpenShell provides the bridge.
