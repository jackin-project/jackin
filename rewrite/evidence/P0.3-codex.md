## Step 1. Draft and build the three Dockerfiles

Files: `rewrite/drafts/construct.Dockerfile`, `rewrite/drafts/role.Dockerfile`, `rewrite/drafts/derived.Dockerfile`.

Decisions made here:

- **Base image.** `nvcr.io/nvidia/base/ubuntu:24.04` is the default sandbox image. `NVIDIA/OpenShell@v0.1.6:crates/openshell-core/src/image.rs:10` (`DEFAULT_SANDBOX_BASE_IMAGE`). The docs at `docs/upgrade/0-1-0.mdx:55` say it is minimal and has no agent CLI. Its config has no `User`, `Cmd=/bin/bash`, `DEBIAN_FRONTEND=noninteractive`.
- **User.** The construct removes `ubuntu` and defines `sandbox` as the primary account with uid and gid 1000, home `/sandbox`, shell `/bin/bash`. Why: the VM driver uses the image's `sandbox` account when it exists and only appends one otherwise (`NVIDIA/OpenShell@v0.1.6:crates/openshell-driver-vm/scripts/openshell-vm-sandbox-init.sh:60-77` reads `sandbox:` from `/etc/passwd`; `:96-102` creates the account only when none exists; `docs/how-it-works/sandboxes/runtimes.mdx:363-366` "MicroVM: The image's `sandbox` account, otherwise `1000`"). With `ubuntu` kept, P0.2 saw `whoami` print `ubuntu`. With the construct below, `id` prints `sandbox`.
- **Final `USER`.** The construct ends with `USER sandbox`. A role that installs packages switches to `USER root` and back, because the construct has no `sudo`. The derived layer sets `USER sandbox` last (D05 step 4).
- **Tools.** `bash ca-certificates curl file findutils git jq less openssh-client procps ripgrep tar unzip xz-utils`. A build step fails if `sudo su-exec gosu doas iptables ip6tables nft ufw docker podman nerdctl containerd runc` is on `PATH`.
- **Codex install.** From the GitHub release asset `codex-package-aarch64-unknown-linux-musl.tar.gz` (static musl binaries), pinned by `ADD --checksum=sha256:7821b77d...`. Only `bin/codex` and `bin/codex-code-mode-host` go to `/usr/local/bin`. The checksum matches the `digest` field of the release asset (`gh release view rust-v0.166.0 -R openai/codex --json assets`). The asset is fetched in a `FROM scratch` stage and bind-mounted into the install `RUN`, so the 187 MB archive is not in any layer.
- **Auto-update.** `/etc/codex/config.toml` holds `check_for_update_on_startup = false`. `openai/codex@rust-v0.166.0:codex-rs/config/src/loader/README.md:35` lists `/etc/codex/config.toml` as the System layer. `codex-rs/tui/src/updates.rs:28` returns no upgrade when that key is false. The D04 launch command passes the same key with `-c`.

How the driver finds the image (all `NVIDIA/OpenShell@v0.1.6`):

- `crates/openshell-driver-vm/src/driver.rs:3663` `ensure_prepared_image_disk` calls `resolve_local_container_image` (`:3508`) for every image reference before it tries a registry.
- `driver.rs:5413` `connect_local_container_engine` calls bollard `Docker::connect_with_local_defaults()`. That honors `DOCKER_HOST` and otherwise uses `/var/run/docker.sock`. It falls back to a Podman socket. On this Mac `DOCKER_HOST` is empty and `/var/run/docker.sock` is a symlink to `~/.orbstack/run/docker.sock`.
- The driver runs `inspect_image(image_ref)` (`:3523`). A 404 returns `None` and the registry path is used. A non-`linux/arm64` image is a warning and a registry fallback (`:5446`, `local_image_platform_mismatch`).
- The identity is the Docker image ID. The root-disk cache key is derived from it (`:6859` `prepared_image_cache_identity`). The second create in the log has a new image ID and so a new export. Re-using a tag with new content is safe.
- The export is `docker create` of a temporary container named `openshell-vm-rootfs-export-<nanos>`, a container-filesystem export call, then forced removal (`:5470-5545`). The driver never starts the container. This is the driver's own use of the engine. Jackin starts no container.
- The export call yields a flattened root file system. The code does not read the image's `USER`, `ENV` or `WORKDIR` (no read of `inspect.config` in `driver.rs`; inferred from the code, not tested by changing `USER`). The runtime user comes from the `sandbox` account in `/etc/passwd`. Keep the account in the construct. The `USER sandbox` line in the derived image is still right for other consumers of the image.

Requirement for jackin: `/var/run/docker.sock` must exist and point at the engine that BuildKit loads into (OrbStack creates the symlink when its "docker socket" setting is on), or the gateway process needs `DOCKER_HOST`. `jackin doctor` should check it. No `--from` registry path was needed.

Sandbox log (`openshell ... logs p03-codex2`):

```text
NET:OPEN [MED] DENIED /usr/bin/curl(0) -> api.openai.com:443 [reason:transparent_tcp_policy_denied]
NET:OPEN [MED] DENIED /usr/bin/curl(0) -> chatgpt.com:443  [reason:transparent_tcp_policy_denied]
Denied staged transparent connection ... reason=binary '/usr/bin/python3.12' not allowed in policy '_provider_p03_codex' (ancestors: [/usr/bin/dash], ...)
```

So a non-Codex binary outside the Codex process tree gets neither a connection nor the credential. The result is a denial, not a 401.

Two probes on the first sandbox (`p03-codex`, deleted) show how far that protection reaches:

1. A live `policy update p03-codex --add-endpoint chatgpt.com:443:read-only:rest:enforce --binary /usr/bin/curl --rule-name p03-curl-probe` allowed `curl`. Then `curl -H "Authorization: Bearer $CODEX_AUTH_ACCESS_TOKEN" https://chatgpt.com/backend-api/wham/accounts/check` returned `http_code=200` with an account listing (not recorded here). The same `curl` without the header returned `401 {"detail":"Unauthorized"}`. So the gateway replaces the placeholder for any binary that policy allows to reach the endpoint. It does not tie the replacement to the profile's `binaries` list. The probe rule was removed (`--remove-rule p03-curl-probe`); `curl` was denied again (`http_code=000`).
2. On the final sandbox, a `curl` that Codex ran as its tool returned `200` (Step 5, last block). Network policy accepts a connection when an executable ancestor is listed (`NVIDIA/OpenShell@v0.1.6:docs/security/best-practices.mdx:83`, "Network policy can authorize either the connection-owning executable or one of its executable ancestors"). The `binaries` list therefore does not separate Codex from the commands that Codex runs. It separates Codex's process tree from everything else.

- The gateway refreshed the access token by itself at 19:43:18Z, when the first sandbox with the provider was created, and again at 20:03:12Z on request. The second refresh worked, so the gateway keeps the rotated refresh token. Lifetime is 3600 s, as in the profile.
- **The host login still works.** `codex login status` reports "Logged in using ChatGPT", the host `auth.json` is byte-identical (same hash and mtime), and a host `codex exec` answers. This proves only that the host's *access token* is valid (it expires 2026-11-12). It does not prove that the host's refresh token is still accepted. The gateway used that refresh token at 19:43:18Z. OpenAI normally rotates the refresh token on use (inferred, not tested). When the host access token expires, the host Codex will probably need `codex login` again. Testing the old refresh token would itself consume it, so it was not tested.

## Gaps

### G1. Account id placeholder does not work (Codex 0.166.0)

- Command: create a sandbox with the provider, write `auth.json` with `account_id` set to `$CODEX_AUTH_ACCOUNT_ID`, run `codex exec --skip-git-repo-check "Reply with the word ready"`.
- Output: `ERROR: Reconnecting... 2/5` to `5/5`, `warning: Falling back from WebSockets to HTTPS transport. selected workspace missing from routing discovery`, same error twice more, exit 1. The sandbox log shows `GET https://chatgpt.com/backend-api/wham/accounts/check` allowed.
- Smallest passing change: `account_id` real, everything else unchanged.
- Upstream change proposed: in `examples/codex-app-server`, take the account id out of the provider and write it as a plain value, or document that Codex 0.166.0 compares it to the account list. OpenShell needs no change. Jackin needs no secret handling change: the account id goes into `auth.json` from the host login at account import.

### G2. Codex needs `codex-code-mode-host` beside `codex`

- Smallest failing case: image with only `/usr/local/bin/codex`, `codex exec --skip-git-repo-check --sandbox danger-full-access "Run exactly this shell command ..."` gives `execution tool unavailable`.
- Not an OpenShell gap. The fix is in the derived Dockerfile (done). The PLAN item P7.1 and the `AgentSpec` row (P4.3) must carry two binaries.

### G3. Credential replacement is not scoped to the profile's `binaries`

- Smallest case: Step 6, probe 1. Allow `/usr/bin/curl` to `chatgpt.com:443` with one `policy update`, then `curl` with the placeholder in an `Authorization` header returns `200`.
- Consequence: a policy rule for any other binary on a provider endpoint hands that binary the credential. Jackin must not add allow rules for other binaries to provider hosts, and `jackin policy` must show them.
- Upstream change proposed: resolve a placeholder only when the connection matched a rule that comes from the provider that owns the credential.

### G4. Cosmetic warnings

- `WARNING: failed to clean up stale arg0 temp dirs: Cross-device link (os error 18)` at each Codex start in the VM. The TUI shows `2 warnings` (`f2`), among them the missing system `bubblewrap` (`Codex will use the bundled bubblewrap in the meantime`). With `danger-full-access` neither blocks. The warning list itself was not opened.
- `*.oaiusercontent.com` plugin icon hosts are denied by the provider rule (`NET:OPEN [MED] DENIED /usr/local/bin/codex(0) -> sdmntpr<region>.oaiusercontent.com:443`). Allowing them changed nothing for the answer (tested with a live rule, then removed). They were left out of the profile.

### G5. `sandbox exec` without a pty needs a stdin

- Inside the harness every call had stdin from `/dev/null`, so `codex exec` printed `Reading additional input from stdin...` and continued. Jackin should do the same.
