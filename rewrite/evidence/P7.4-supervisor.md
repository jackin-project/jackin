## The final `jackin-start`

`rewrite/drafts/jackin-start` (POSIX `sh`; the image `/bin/sh` is `dash`, checked in the sandbox):

```text
#!/bin/sh
# SPDX-FileCopyrightText: 2026 Alexey Zhokhov
# SPDX-License-Identifier: Apache-2.0
set -u

run=/sandbox/.jackin/run
project=/sandbox/project

fail() {
    echo "jackin-start: $1" >&2
    exit 64
}

publish() {
    printf '%s\n' "$1" >"$run/state.tmp" && mv -f "$run/state.tmp" "$run/state"
}

park() {
    [ -t 0 ] && stty sane -echo
    return 0
}

drain() {
    if [ -t 0 ]; then
        stty -icanon min 0 time 0
        dd bs=4096 of=/dev/null 2>/dev/null
        stty sane
    fi
    return 0
}

[ "$#" -gt 0 ] || fail "missing agent command"

case ${JACKIN_LAUNCH_ID:-} in
    '' | .* | *[!A-Za-z0-9._-]*) fail "JACKIN_LAUNCH_ID is missing or invalid" ;;
esac

trap : INT TERM HUP QUIT TSTP

park
mkdir -p "$run"
rm -f "$run/state" "$run/state.tmp" "$run/start" "$run/start.tmp"
publish waiting

last=0
while :; do
    attempt=
    [ -f "$run/start" ] && read -r attempt 2>/dev/null <"$run/start"
    case $attempt in
        '' | 0* | *[!0-9]* | ???????????????????*) attempt= ;;
    esac
    if [ -z "$attempt" ] || [ "$attempt" -le "$last" ]; then
        sleep 0.5 || :
        continue
    fi

    last=$attempt
    drain
    publish "running $attempt"
    rc=0
    (cd "$project" || exit 66; exec "$@") || rc=$?
    publish "exited $attempt $rc"
    park
    printf '\r\033[0m\033[?25hjackin-start: %s exited with code %s (attempt %s)\r\n' "${1##*/}" "$rc" "$attempt"
done
```

Interface:

| Item | Value |
|---|---|
| Command | `/usr/local/bin/jackin-start <agent command...>` as the sandbox main process, with a kept PTY |
| Environment | `JACKIN_LAUNCH_ID`, required, non-empty, no leading dot, only `A-Z a-z 0-9 . _ -`. It is validated and used for nothing else (F9). |
| Files | `/sandbox/.jackin/run/state` (written by `jackin-start`), `/sandbox/.jackin/run/start` (written by jackin). Each write is a temp file and `rename` (`state.tmp`, `start.tmp`). |
| Start | Removes `state`, `state.tmp`, `start`, `start.tmp`. Writes `waiting`. |
| Attempt id | A positive decimal integer of 1 to 18 digits, no leading zero. `jackin-start` accepts only an id greater than the last id it handled since it started (0 at start). Anything else is ignored: equal (repeated), smaller (stale), malformed. |
| States | `waiting`, `running <attempt>`, `exited <attempt> <code>` |
| Child | `( cd /sandbox/project && exec "$@" )` in the foreground process group of the main PTY. Before each start it drops any input queued on the PTY (`drain`). After each exit it resets the terminal (`stty sane -echo`) and prints one line: `jackin-start: <basename of argv0> exited with code <n> (attempt <id>)`. |
| Signals | Traps INT, TERM, HUP, QUIT, TSTP with a no-op handler. A handler is reset to the default in the child, so the child gets Ctrl-C. |
| Exit codes of `jackin-start` | 64 for an invalid or missing `JACKIN_LAUNCH_ID` or no argv, before the state is touched. It never exits after that. |
| Codes inside `exited <attempt> <code>` | the child's exit code; 66 when `/sandbox/project` is missing (the `cd` failed, the process keeps running); 127 when the command is not found; 128 plus n for a signal (137 for SIGKILL). |
| Hooks | None. `jackin-start` runs no hook. |

Design choices:

- **No job control.** The child stays in the process group of `jackin-start`, which is the foreground group of the main PTY (`pgid = tpgid`, step 4.5). The child keeps the default signal handling. The alternative, `set -m` and a background child, was not needed and was not tried.
- **Integer attempt ids.** A UUID can detect only a repeat. An ordered id also fences a stale write and makes two racing restarts collapse into one (both write the same next number). Jackin picks the next number as the number in the last `exited` line plus 1, or 1 after `waiting`.
- **`drain` and `park`.** Without them, bytes typed while the supervisor waits, and the answers that a terminal sends to the terminal queries in the replay, reach the next Codex run (F3, raw output in `Before drain`).
- **QUIT and TSTP are trapped as well.** D09 names INT, TERM and HUP. Ctrl-backslash would end a shell that does not trap QUIT. Reasoning only: the default action of QUIT is to terminate with a core dump; no negative control was run.

Build context layout, written by `jackin-image`: `jackin-start`, `hooks/setup`, `hooks/preflight`. Convention for hooks: the context always holds both files. A hook that the manifest does not declare is a zero-byte file. A declared hook is the role file copied under the fixed name. `COPY` fails when a file is missing, so a declared hook cannot be silently absent. The installed files are `root:root 0755`. Jackin decides from the manifest, never from the file content, whether to run a hook (D11). I chose the empty-file convention over a build argument: a `COPY` cannot depend on a build argument without a second stage, and the cache key already hashes each hook file.

## Test helper

`/private/tmp/claude-501/p7.4/helper/` (scratch) is a small Rust binary built with `mise exec -- mbx +1.99.1 build --release`. It reuses the P0.6 transport code (`wt/P0.6:prototypes/p0.6/src/main.rs`): `OpenShellClient` with the gateway mTLS files, `ExecSandboxInteractive` for `exec` (non-PTY, `environment`, `workdir`, stdin chunks, drop of the stream), and `CreateSshSession` + `ForwardTcp` + `russh` with the pinned host key and the `openshell-main` subsystem for `attach`. `attach` renders the PTY output into a `vt100` screen, answers the terminal queries (cursor position, DA1, OSC 10 and 11) like a real terminal, and runs timed operations (`send`, `resize`, `wait`, `screen`, `expect`). `--no-answer` turns the answers off. The openshell CLI was used for `sandbox create|get|exec|stop|start|upload|download|delete|list`.

Notes on reading the output:

- `[exec exit N]` is the exit event of the helper's `ExecSandboxInteractive`. `[exit N]` is the exit code of an `openshell` CLI call.
- `attempt <n>` lines come from a shell function that writes the id to `start.tmp` and renames it, through exec, as the jackin side would.
- The child in steps 1 to 3 is `/sandbox/child.sh` (written through exec stdin): it prints its pid, process group, foreground group and tty, appends `run <pid>` to `child.log`, prints the PTY size on every SIGWINCH, exits 130 on SIGINT, sleeps `secs` seconds and exits with the code in `/sandbox/.jackin/code`.
- `ps` columns: `pid ppid pgid sid tpgid tty stat etime args`. `exec` processes show `hvc0`; the main process tree shows `pts/0`.

## Findings

Findings that qualify or contradict the text of D09, D11, D05 or the Launch sequence:

- **F1. Codex asks to trust `/sandbox/project`** (step 4.3). With a login and no trust entry, the first screen is `Trust this folder?`, not the prompt. A `[projects."/sandbox/project"]` table with `trust_level = "trusted"` in `/sandbox/.codex/config.toml` removes it (step 4.4). D04, D05 and D10 do not mention this. The launch must write the entry (through exec stdin, like `auth.json`) or the derived layer must carry it. Whether `/etc/codex/config.toml` (the system file of D05) honours a `projects` table was not tested.
- **F2. The prompt needs a login of some kind.** With no `auth.json`, Codex shows the login menu (step 4.2). The prompt of step 4.4 appeared with a placeholder API key because Codex does not check it at start. With the placeholder ChatGPT `auth.json` of P0.3 and no provider, Codex exited with `Error: account/read failed during TUI bootstrap: ... workspace routing discovery failed` and `jackin-start` printed `exited with code 1` (seen once in an exploratory run; the raw output was not kept). A real launch has the provider and the network rule of D10, so this is not a defect, but "first prompt on attach" holds only after `auth.json` and the trust entry exist.
- **F3. Replay and typed input leak into the PTY queue.** The replay holds old terminal queries (cursor position, DA1, OSC 10 and 11). A terminal answers them again on every attach, and the answers go into the PTY as input. While Codex runs it ignores them (the composer stayed clean). While `jackin-start` waits they are echoed and queue up, and the next Codex run read them (`Before drain`). The final `jackin-start` drops queued input before each start. A running Codex still receives the replay answers; D09 should tell `jackin attach` to drop terminal replies that answer replayed queries, or to start answering only after the replay.
- **F4. Stop costs 4 s more.** `sandbox stop` took 5 s with `jackin-start` as main process and 1 s with `sleep 3600`. Cause is inferred: `jackin-start` ignores SIGTERM, so the stop waits for a kill timeout.
- **F5. A request written while the child runs executes after the exit.** The launch sequence writes an attempt id only after it saw `waiting` or `exited` (step 7 to 9), so this does not happen in the normal flow. D09 should say that jackin must not write while the state is `running`, because the request is not dropped.
- **F6. "New attempt ID" is an increasing integer.** D09 and the Launch sequence say "a new attempt ID". The proven rule is an integer greater than the last handled one (F5 and step 2). After a stop and a start the number may start again at 1.
- **F7. Exit 64/65/66 of P7.1 changed.** `jackin-start` now exits only with 64. 65 (hook) no longer exists. 66 is now a child result (`exited <n> 66`) and not a process exit.
- **F8. Parallel creates from a new image can fail.** In two batches of three simultaneous sandbox creations from the freshly built image, one create failed in the first batch and two in the second, all with `ProvisioningFailed: wait for image preparation: Operation not permitted (os error 1)` (scratch files `out/step1-failed-create.txt`, `out/step4-failed-create.txt`). The same creates worked when repeated one at a time. This is a gateway fact for the launch executor (retry, or serialize the first create of an image); it does not involve `jackin-start`.
- **F9. `JACKIN_LAUNCH_ID` has no use in `jackin-start`.** It is validated and ignored. The state files do not carry it. D09 could drop the variable, or the state file could carry it so a client can check that it talks to the right launch. I did not add a use.

Observations that do not change the design:

- A Ctrl-Z typed in Codex does nothing (raw mode), and a Ctrl-Z on the waiting PTY did not stop `jackin-start` (step 3.2). The main process group has parent pid 1 in another session, so it is an orphaned group, for which the kernel discards stop signals (inferred, not tested).
- The `sh` message `Killed` appears on the PTY when Codex is killed by SIGKILL (step 4.9). The exit line follows it.
- A write of 5 MiB through exec stdin worked once the helper opened the stream before sending (an earlier helper version blocked on a full channel; that was a helper bug, not a gateway limit).
