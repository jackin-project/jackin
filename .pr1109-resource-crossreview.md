# PR #1109 resource/concurrency cross-review

- Repository: `jackin-project/jackin`
- Base: `310e644832193232344ca99838ccf599f28faf53`
- Head: `a6c85ba8a154ccce224dce80d1ed5ef8fa03bc6e`
- Review mode: read-only source comparison. No tests, builds, Git mutations, or PR mutations.
- Severity assumes a same-UID local process can write a private launch directory. A Capsule is treated as hostile only where it can send requests through the relay; it cannot choose the relay-owned credential scope.

## Executive verdict

The five requested concerns are real with these qualifications:

1. **Scoped proof memory and detached relay tasks:** PR-introduced weighted payload amplification; detached relay fanout is inherited. The 1 MiB frame cap bounds one broker request, but the coordinator's 256-item queue is count-only and the relay has no request-task semaphore.
2. **Route discovery:** PR-introduced route fanout and repeated global-env cloning. The stated account×workspace×role×route Cartesian product is too strong: `Agent::ALL` is a fixed route bound, and roles are scanned only in workspaces that reference the account. The resolver's lock-held source I/O and unbounded cache are inherited and amplified.
3. **Private catalog read:** PR-introduced high local availability risk. The hash in the filename does not bound or validate bytes before `read_to_end`; the read occurs under the new Codex lock.
4. **fs4 lock:** PR-introduced blocking local availability risk. `O_NONBLOCK` is used for `openat`, while `FileExt::lock` remains blocking and has no deadline.
5. **Lock-path replacement:** PR-introduced same-UID race. `O_NOFOLLOW` protects only the open; the pathname is not pinned to the locked inode.

## Findings

### R1 — Heavy unbounded scoped proof payload in a count-only queue; unbounded relay request tasks

**Severity: Medium PR risk; High if a hostile Capsule can drive a launch relay.**

**Head evidence:**

- `crates/jackin-protocol/src/usage_broker.rs:81-100` defines `UsageCredentialScope.sources` as an unbounded `BTreeSet` of owned strings. There is no proof count, field length, or serialized-size check in this type.
- `crates/jackin-usage/src/coordinator.rs:356-363` adds the owned scope to every `ProbeJob`; `:686-713` accepts it; `:775-795` moves it into `mpsc::sync_channel(config.queue_capacity)`. The default queue is 256 (`:148-155`), bounded only by item count.
- `crates/jackin-usage/src/coordinator.rs:1185-1197` retains the scope until worker execution and passes it to `probe_scoped`.
- `crates/jackin-runtime/src/usage_relay.rs:731-775` bounds only the response channel at 128. Each input frame clones `credential_scope` (`:745-749`) and calls `tokio::spawn` through `spawn_stream` (`:750-775`); the handle is dropped. `crates/jackin-telemetry/src/spawn.rs:229-235` confirms `spawn_stream` is an unbounded `tokio::spawn`, and `:429-436` shows each broker call then enters `spawn_blocking`.
- The broker wire cap is aggregate only: `USAGE_BROKER_MAX_FRAME_BYTES = 1 MiB` at `crates/jackin-protocol/src/usage_broker.rs:12-16`, checked by `UsageBrokerClient::execute_scoped` at `crates/jackin-usage/src/host/broker.rs:1117-1139`. `request_refresh_scoped` itself has no such bound for in-process callers.

**Base comparison:** the `UsageCredentialScope` transport and relay task fanout are present at base. The PR adds scope ownership to coordinator jobs and scoped provider execution. Thus the task leak is inherited; the heavy per-task/per-queue scope retention is new amplification.

**Reachability and impact:** a hostile Capsule can send valid allowlisted operations repeatedly. With enough distinct capabilities to admit concurrent generations, a scope near the 1 MiB wire ceiling can occupy roughly 256 queued jobs before `try_send` rejects more, plus active worker/task/request copies. A large host configuration can create many proofs or long account/source strings. The `<1000` instance check in `crates/jackin-runtime/src/runtime/launch/capsule_setup.rs:225-230` happens after scope construction (`crates/jackin-runtime/src/runtime/launch/launch_pipeline/launch_core/orchestrate.rs:781-788`), so it does not bound the new scope builder. The frame cap prevents an unbounded single network frame, but does not make the queue memory-weighted or cap detached tasks. This is resource exhaustion, not a proof-forgery path.

**Structural fix:** bound scope proofs and aggregate bytes before cloning/queueing; pass an immutable shared scope or compact token; add a semaphore/backpressure for relay requests and `spawn_blocking` work.

### R2 — Route discovery repeats scans and clones global env per route

**Severity: Medium host-side performance/DoS risk; PR-introduced.**

**Head evidence:**

- `crates/jackin-config/src/accounts.rs:1295-1362` adds `credential_descriptors_for_account`. Per account it scans all `agent_configurations` (`:1320-1324`), global bindings (`:1332`), every workspace membership (`:1333-1339`), and every role binding in matching workspaces (`:1336-1338`), then synthesizes all compatible `Agent::ALL` routes (`:1341-1355`).
- `crates/jackin-usage/src/host/discovery.rs:779-847` calls that method for every enabled account and loops every returned route (`:847-925`). Each route clones the complete `config.env` (`:872-875`), inserts an alias/value (`:876-879`), and invokes the resolver.
- The env clone happens before entering the resolver mutex. The resolver call itself acquires the mutex at `crates/jackin-usage/src/host/credential_resolver.rs:168-181`, then calls `resolve_secret` while holding it (`:182`) and pushes an unbounded cache entry (`:222-230`).

**Base comparison:** base selected one registry route and cloned/resolved once per account (`crates/jackin-usage/src/host/discovery.rs` at base `:794-824`). The all-route method and per-route loop are PR additions. The resolver lock-across-source-I/O and `Vec` cache existed at base.

**Complexity correction:** this is not a full account×workspace×role×route Cartesian enumeration. `Agent::ALL` is a fixed compile-time set; workspaces are scanned per account, and roles only inside workspaces whose `accounts` list contains that account. The actual worst case is still account × (all agent configurations + all workspaces + matching roles) plus one resolver call/env clone per compatible fixed route. Config sizes and env string sizes have no field-level bounds in this path.

**Reachability and impact:** host broker activation/discovery repeatedly executes this path. Large operator config can cause quadratic-ish membership/role scans and repeated allocation of every global env value. `RuntimeSecretSource` (`crates/jackin-runtime/src/usage_relay.rs:73-120`) can perform protected-env/1Password work while the resolver state mutex is held. A host config or provider source controls this; the Capsule does not directly choose the host config. Route count is finite, so this is amplification and lock convoying rather than an infinite route loop.

**Structural fix:** precompute account→route descriptors once per immutable config snapshot; clone only the required declaration; do not hold the resolver mutex across source I/O; cap or evict the secret cache.

### R3 — Hash-named private catalog is read without a bound while the lock is held

**Severity: High local availability risk; PR-introduced.**

**Head evidence:**

- `crates/jackin-runtime/src/runtime/launch/account_config.rs:251-260` opens a regular mode-600 file and calls unbounded `read_to_end`.
- `:396-415` calls that helper before publishing a catalog. If the expected hash-named file exists with different bytes, it reads the entire file before rejecting (`:406-413`). The name is derived from the small generated content at `:816-823`; the existing payload is never hash-checked before allocation.
- `configure_codex_with_publish_hook` takes the new lock at `:724-725`, reads config, and calls `publish_catalog` at `:769-803`; therefore the catalog `read_to_end` runs under the lock. The ordinary `config.toml` read at `:726-744` is also unbounded through the same helper (that read was inherited, but is now lock-held).

**Reachability and impact:** a same-UID writer with access to the private slot directory can precreate the known `account-models-<sha256>.json` name, mode 600, containing a huge regular or sparse file with wrong bytes. Launch reads/allocates it, then bails; repeated attempts remain blocked. Memory/IO exhaustion and lock hold time are unbounded by this code. `O_NONBLOCK` does not limit regular-file reads. This requires local same-UID write access; it is not a remote frame attack.

**Structural fix:** enforce a small maximum before allocation (`take(limit + 1)`), reject oversize, and avoid holding the inter-process lock during untrusted-size reads. Validate the content hash/size before accepting an existing catalog.

### R4 — Codex private-config lock can block forever

**Severity: Medium/High local availability risk; PR-introduced.**

`crates/jackin-runtime/src/runtime/launch/account_config.rs:227-248` opens the lock path with `O_NONBLOCK` but then calls blocking `FileExt::lock` at `:247`; there is no deadline or `try_lock` loop. The guard spans config read, parse/quarantine, catalog read/write, hooks, fsync, and config publication (`:724-813`). A same-UID process can hold the advisory lock indefinitely, or a hung reader/provider filesystem can keep the owner in the critical section. A crashed owner releases a kernel advisory lock, so this is not a permanent stale-crash lock.

**Structural fix:** acquire with a deadline/nonblocking retry and bound all file work inside the critical section; do not treat `O_NONBLOCK` on `openat` as lock nonblocking.

### R5 — Same-UID replacement of the lock pathname defeats serialization

**Severity: Medium integrity/availability risk; PR-introduced.**

`private_config_fs::lock` (`crates/jackin-runtime/src/runtime/launch/account_config.rs:227-248`) opens `LOCK_FILE`, validates the opened fd, syncs, then locks it. There is no parent-directory pin or inode identity check after pathname lookup. `O_NOFOLLOW` only protects that single `openat`; a same-UID process can unlink/rename the path and create a replacement inode after the first open. The next launcher locks the replacement while the first still holds the old inode, so two `configure_codex` calls can publish concurrently. `ensure_mode` (`:353-393`) checks/fixes mode but does not establish pathname ownership.

**Impact:** last-writer-wins config/catalog updates and quarantine/publication interleavings can violate the intended pair serialization. The writes use temp files and rename, so this is an ordering/integrity race rather than a torn-file read. Requires same-UID directory access.

**Structural fix:** use a lock inode whose lifetime/name cannot be replaced by an untrusted same-UID writer, or use an atomic create/descriptor-identity protocol and verify link count/identity before proceeding.

### R6 — Timed-out provider work detaches OS threads; PR retains more scope in each

**Severity: Medium inherited resource risk; PR-amplified.**

`crates/jackin-usage/src/host/broker/probe.rs:42-56` is byte-for-byte the same pattern in base and head: `thread_joined_named` starts a fresh OS thread, `recv_timeout` returns on expiry, and the worker is detached. `crates/jackin-telemetry/src/spawn.rs:525-535` confirms a new `std::thread` per call. Repeated provider timeouts can therefore accumulate detached threads over time; `max_concurrency` bounds broker workers, not detached lifetime.

Head `probe_with_scope` (`crates/jackin-usage/src/host/broker.rs:1335-1377`) additionally clones the resolver, task capability, and launch scope (`:1340-1344`) into the detached closure. A timeout returns before the closure ends, so a large scope and resolver references remain live until the adapter returns. Adapter-level timeouts may eventually bound individual providers, but the broker budget itself does not cancel arbitrary source work. This is not a PR-introduced detach bug; the PR increases retained data and adds more rediscovery/route work that can hit the path.

### R7 — Resolver lock/cache architecture is inherited, but route fanout multiplies its cost

**Severity: Medium inherited structural risk; PR-amplified.**

`CachedProviderCredentialResolver::resolve_one` (`crates/jackin-usage/src/host/credential_resolver.rs:168-182`) holds `state: Mutex<ResolverState>` while invoking `source.resolve_secret`, which can run protected env/1Password resolution. The cache is an unbounded `Vec` of entries containing optional secret strings (`:222-230`). Base already had both properties. PR route discovery invokes this path once per compatible route and adds dispatch-key variants, increasing lock acquisitions, serial source waits, and cache cardinality. This can convoy discovery or retain secrets; it is not a new remote authorization bypass.

### R8 — Detached rediscovery can overwrite newer binding state

**Severity: Medium inherited race; PR-amplified.**

Head `probe_with_scope` snapshots `bindings` (`crates/jackin-usage/src/host/broker.rs:1335-1343`), may rediscover in a detached worker (`:1344-1365`), then blindly replaces the shared map when the result returns (`:1367-1373`). Base `probe` had the same snapshot/late-write sequence; the PR changes each map value from one binding to a route group (`Vec`) and makes rediscovery wider.

There is no catalog-generation/CAS check on the late install. A concurrent `reconcile_catalog_revision` can install a newer map (`:1474-1509`), after which an older successful scan can replace it. Config revision fencing protects many config-file changes because `capability_for_binding` includes the catalog revision (`:2821-2844`), but runtime secret rotation or an unchanged config generation can still leave a stale material/source map. Scoped fingerprint checks may fail closed; unscoped background refresh can use stale binding data or repeatedly fail until the next scan.

**Structural fix:** attach discovery generation/catalog revision to the snapshot and install only with compare-and-swap/fence equality.

### R9 — OpenCode lock omission is not an actionable race by itself

**Disposition: Not a confirmed finding.**

`configure_opencode` (`crates/jackin-runtime/src/runtime/launch/account_config.rs:889-956`) does not call `private_config_fs::lock`, but `publish_atomic` writes a private temp file, fsyncs, and atomically `renameat`s it (`:462-515`). Concurrent writers can last-writer-win, but readers see a complete JSON document and the leaf rename does not follow a symlink. No read-modify-write pair or partial-file exposure was found. Elevate only if product semantics require serializing concurrent OpenCode writers to the same slot.

### R10 — Quarantine source check has a pathname TOCTOU

**Severity: Medium/Low same-UID integrity/availability risk; PR-introduced.**

`quarantine` first opens/checks the source and drops the fd (`crates/jackin-runtime/src/runtime/launch/account_config.rs:266-275`), reserves a target, unlinks the reservation (`:294-319`), then calls pathname-based `renameat` (`:320-321`). A same-UID writer can replace `name` after the check and before the rename; the code then moves the replacement inode, contrary to the comment's claim that it quarantines the inspected payload. It can quarantine a valid new config or an attacker-controlled file and force regeneration/DoS. No secret disclosure was found. Descriptor-pinned rename or an inode-identity check is required.

## Additional inherited resource issue found

### R11 — Projection state load has no byte bound

**Severity: Medium inherited local availability risk.**

`crates/jackin-usage/src/coordinator/state.rs:174-195` uses `fs::read(&self.path)` for host `usage-broker/projection.json` with no size limit before JSON parsing/quarantine. The same code is present at base. By contrast, account state loading uses `MAX_ACCOUNT_STATE_BYTES` and `take(limit + 1)` (`:293-324`). A same-UID writer of the host broker data directory can force an arbitrarily large allocation/read during broker startup. This is outside PR #1109's delta, but should not be mistaken for a new scoped-queue issue.

## Boundaries and negatives

- Broker request/frame parsing has an aggregate 1 MiB cap and the host broker's connection queue is bounded at 128; these reduce, but do not eliminate, weighted scope/task amplification.
- No direct Capsule-controlled replacement of `credential_scope` was found: the relay owns and clones the host scope, then applies its capability allowlist.
- No additional PR-introduced unbounded route cardinality beyond the finite `Agent::ALL` set was found.
- No merge authority; this report is evidence for the parent review only.
