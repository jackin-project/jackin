**Status**: Partially implemented

**Current state**: historical dev releases shipped signing artifacts, and the retired operator verifier passed against `jackin-dev-v0.1.13` on 2026-07-04. The repository now contains a strict immutable-preview receipt and capsule verification path, but the checked-in Velnor configuration does not yet enable publication. Live release and clean-cache download proof remain outstanding.

## Problem

jackin❯ closed two credibility gaps with this work:

- **Undocumented security implementation.** Symlink rejection in <RepoFile path="crates/services/jackin-instance/src/auth.rs">crates/services/jackin-instance/src/auth.rs</RepoFile>, `shellfirm` and `tirith` in the construct image, and the YOLO-flag contract in <RepoFile path="docker/runtime/entrypoint.sh">docker/runtime/entrypoint.sh</RepoFile> were enforced in code but invisible to operators, role authors, and contributors who reason about the trust boundary.
- **Unsigned capsule binary.** `jackin-capsule` is downloaded into every container at runtime (<RepoFile path="crates/adapters/jackin-image/src/capsule_binary.rs">crates/adapters/jackin-image/src/capsule_binary.rs</RepoFile>) and was verified by SHA256 only — no signing, no SLSA provenance, no SBOM. A tampered artifact matching the expected SHA256 would go undetected.

## Shipped

The verification implementation and historical signed-release evidence remain available. Current generated CI has no signed archive or capsule-manifest publication jobs; restoring publication through the generator remains required. Operator and contributor detail lives in canonical docs:

- **Security implementation** — threat model, the six `auth.rs` security functions, `shellfirm`/`tirith` rationale, and the YOLO-flag contract for all six launch branches → [/reference/security-implementation/](/reference/security-implementation/).
- **Release verification** — cosign keyless verification, SLSA provenance, SBOM inspection, and capsule-manifest auditing → [/getting-started/verifying-releases/](/getting-started/verifying-releases/).
- **Historical CI signing** — the former `release.yml` account in source snapshot `81a26f7e8511b2f19c9ba5a59a85b3ef0bbc804a` described cosign bundles, GitHub build attestations, CycloneDX SBOMs, and signed capsule manifests. Those records describe the historical workflow only.
- **Historical operator verification** — the retired `cargo xtask release-verify` gate checked the published `.sha256`, cosign bundle, GitHub attestation, and SBOM. It passed against `jackin-dev-v0.1.13` on 2026-07-04; that result does not validate current Velnor receipts.
- **Preview capsule verification code** — <RepoFile path="crates/adapters/jackin-image/src/release_evidence.rs">release_evidence.rs</RepoFile> verifies an immutable `v<version>` release receipt, exact payload/companion digests, Sigstore bundles using the production TUF trust root, and provenance for the fixed `binary-preview.yml` identity. A verifier implementation does not establish that a current publisher exists or that a live download has succeeded. `JACKIN_CAPSULE_BIN` and test builds bypass remote download verification.

## Remaining

- **Enable signed publication.** The current <RepoFile path=".velnor/config.toml">.velnor/config.toml</RepoFile> selects Rust validation without a release publisher. Enable generated archive signing, attestations, SBOMs, and capsule manifests only after repository credentials, required checks, and the exact-head feedback completion provider are qualified. Do not restore former workflow YAML by hand.

- **Clean-cache capsule download gate.** Historical evidence used `jackin-dev-v0.1.13` (2026-07-02). Verify a live immutable preview only after publication is enabled and an eligible release exists. Unit and integration tests may bypass the remote path; do not treat them as live download proof:

  ```bash
  rm -rf ~/.jackin/cache/jackin-capsule/
  unset JACKIN_CAPSULE_BIN
  cargo run --bin jackin -- console --debug
  ```

  `JACKIN_CAPSULE_BIN=/path/to/jackin-capsule` selects a local binary and bypasses remote release verification.
- **Trust-root maintenance.** The verifier refreshes production Sigstore trust through TUF; monitor and test trust-root updates as part of the release verification maintenance.

This item retires once signed publication is enabled and proven, the capsule download path has been clean-cache verified end to end, and remaining verification residuals are either fixed or explicitly accepted.

## Non-goals

- No hostile multi-tenant safety claim from Docker hardening alone — that is [Docker runtime hardening contract](/roadmap/docker-runtime-hardening-contract/) scope.
- No microVM replacement — [smolvm backend research](/research/platform/isolation/smolvm-backend/) tracks that separately.
- No retroactive signing of historical releases — provenance starts from the first release produced by the native workflow.
