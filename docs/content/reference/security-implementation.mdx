## Credential security functions

Functions below live in <RepoFile path="crates/jackin-instance/src/auth.rs">auth provisioning</RepoFile>. Launch executes the provisioning paths relevant to the selected account and integration, rather than calling every function unconditionally.

### `reject_symlink` and `reject_auth_path`

`reject_symlink` inspects the final path with `symlink_metadata`, without following it. `reject_auth_path` also checks existing parent directories, rejecting symlinks and non-directories while allowing the documented macOS platform root aliases. A pathname precheck alone is not a race-proof write boundary.

On Unix, the `auth_directory` module supplies the stronger boundary: locked directory descriptors, no-follow opens, descriptor-relative operations, ownership/type validation, and inode identity checks. Source credential reads use this boundary too; changing only a final-path symlink check cannot replace it.

### `repair_permissions`

Restricts an existing credential file to `0o600` on Unix through `auth_directory::repair_file_permissions`. Missing optional files are allowed. Inspection, chmod, or verification failure returns an error and aborts provisioning; callers must propagate that error.

### `write_private_bytes` / `write_private_file`

On Unix, `write_private_file` delegates to `write_private_bytes`, then `auth_directory::replace_private_file`. The implementation creates a private temporary file relative to the locked parent, writes and syncs it, renames within that parent, and syncs the directory. Identical existing content is verified and its permissions repaired without replacing the inode. The non-Unix branch checks the path and writes directly; it does not supply the same atomic replacement guarantee.

### `create_private_file_if_absent`

Seeds private skeleton state without replacing existing content. Unix uses descriptor-relative `O_CREAT|O_EXCL|O_NOFOLLOW` creation. On an existing-file collision it validates ownership, regular-file type, and identity before accepting the existing file. A symlink or invalid file is not a successful collision.

### `host_home_is_real`

Gates host-binary credential shellouts on whether the supplied home matches the operating system's real home directory. Temporary-home tests therefore do not read the operator's `gh` or macOS Keychain credentials. This is an isolation gate for host integration, not account authorization.

### `parse_gh_hosts_yml`

Parses GitHub CLI state using `serde_yaml_ng` and accepts a nonempty token for `github.com`. Malformed or absent token data returns `None`. GitHub credentials remain separate from coding-agent account authorization.

## Shell guard controls

<RepoFile path="docker/construct/Dockerfile">The construct image</RepoFile> installs shellfirm from pinned source in a builder stage and tirith from a checksum-verified release archive. <RepoFile path="docker/construct/zshrc">zsh</RepoFile> and <RepoFile path="docker/construct/fish-config.fish">fish</RepoFile> initialize their shell hooks by default.

- **shellfirm:** shell command guard initialized by `shellfirm init`. Set `JACKIN_DISABLE_SHELLFIRM=1` before shell startup to skip that hook.
- **tirith:** shell command guard initialized by `tirith init --shell`. Set `JACKIN_DISABLE_TIRITH=1` before shell startup to skip that hook.

These hooks apply in shells that load the configuration. Direct process execution, other shells, and agent tool calls need not pass through them. They are advisory command guards, not container runtime scanners or an enforcement boundary against a malicious agent. Disabling a hook changes shell guarding; it does not alter mount validation, credential authorization, Landlock rules, or the selected Docker network policy.

## Agent approval settings

<RepoFile path="docker/runtime/entrypoint.sh">The runtime entrypoint</RepoFile> contains these explicit launch branches:

| Agent | Approval setting |
|---|---|
| Claude Code | `--dangerously-skip-permissions` plus `skipDangerousModePermissionPrompt: true` |
| Codex | `--dangerously-bypass-approvals-and-sandbox` |
| Amp | `--dangerously-allow-all` |
| Kimi | `--yolo` |
| OpenCode | `OPENCODE_CONFIG_CONTENT='{"permission":"allow"}'`; per-session setup in <RepoFile path="crates/jackin-capsule/src/runtime_setup.rs">runtime setup</RepoFile> |
| Grok | `--always-approve` |

This table describes those source branches; it does not establish launch behavior for every runtime in the agent registry. Inspect the runtime's actual adapter before extending the table.

Approval bypass permits edits and tool calls without the agent's usual approval prompts. Authentication, user questions, planning, updates, and runtime failures may still require attention. To change the flags, customize the runtime entrypoint in the derived image; role arguments are not proof that an earlier bypass flag was removed.

## Container and session boundary contract

The operator chooses mounts, authorized accounts, and Docker grants. Writable mounts permit intentional agent edits. Session isolation confines agents to admitted roots and separates credential slots; the capsule supervisor remains trusted. The role launch does not mount the host Docker socket; an explicitly enabled Docker-in-Docker integration is a separate capability.

Agent approval settings and shell guards provide different controls. Neither determines the effective network grant, repairs an unsafe mount, authorizes an account, or protects against a kernel escape. Security changes must preserve the enforcing function's fail-closed behavior and identify the exact boundary and residual risk they change. See the [Security model](/guides/security-model/) for the operator-facing contract.
