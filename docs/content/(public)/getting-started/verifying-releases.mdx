---
title: "Verifying Releases"
---

Jackin uses native Velnor-generated workflows for two release channels. Preview
publication follows successful exact-commit `main` CI and replaces the assets
of the single rolling `preview` tag and release. Stable publication starts only
through manual workflow dispatch and creates a permanent, immutable `v<version>`
tag and release. Builds, signing, publication, and Homebrew writes have separate
permissions. Configuration and generated workflows define these boundaries;
inspect the actual release and workflow run before treating them as live proof.

## Automatic capsule verification

Remote capsule acquisition requires a native application build containing an
explicit release channel and full source commit. Version text alone, including
a source build with a release-looking version override, does not authorize a
remote download. Local builds require a matching local or packaged capsule.

For an eligible native build, the downloader authenticates the canonical
`release.json` receipt, the selected capsule's detached signature, and the signed
`capsule-manifest.json`. It refreshes production Sigstore trust through TUF and
checks certificate identity, transparency evidence, GitHub provenance, the exact
source commit, and the complete declared provenance subject inventory. Preview
uses `binary-preview.yml`; stable uses `binary-release.yml`, both from Jackin's
fixed repository and workflow policy.

The downloader also admits the original exact-attempt successful producer and
signing jobs and source CI. Before executing or installing a downloaded capsule,
it rechecks the current receipt, signature, complete release asset inventory,
and tag. Preview requires the configured release ID and committed publication
journal; stable requires an immutable release and a permanent version tag.
Superseded, partial, mixed, or source-mismatched publications are rejected.
Native caches are isolated by channel and full source commit from local caches.

`JACKIN_CAPSULE_BIN` explicitly selects a local executable and bypasses remote
release verification. Homebrew includes matching capsule resources, so a normal
Homebrew installation can load its packaged capsule without a GitHub download.
A packaged load or a unit test is not evidence of a live remote verification.

## Release assets

The signed `release.json` receipt defines the exact inventory, sizes, SHA-256
checksums, source commit, build version, and signing/provenance identities.
Jackin's six payloads comprise four host platform/architecture archives and two
Linux capsule archives. Host archives include `jackin`, `jackin-role`, and
`jackin-usage-broker`; capsule archives include `jackin-capsule`.

Supporting assets include checksum sidecars, CycloneDX SBOMs, detached Sigstore
bundles, and `capsule-manifest.json`. The manifest binds both Linux target
checksums to the same release version. Verify the receipt and its bundle before
trusting metadata or selecting assets; checksums alone do not authenticate them.

## Verify GitHub provenance

Install the `gh` CLI separately if needed; Homebrew's Jackin formula does not
imply that GitHub CLI is installed.

```sh
gh attestation verify <file> --repo jackin-project/jackin
```

This verifies the attestation for the selected file against the named repository.
It does not by itself validate the complete Jackin receipt, detached signatures,
asset inventory, exact source/workflow/run policy, or current publication state.
There is no current `cargo xtask release-verify` command. Its recorded success
against `jackin-dev-v0.1.13` on 2026-07-04 is historical evidence only.

## Inspect the SBOM

The `.sbom.json` files are CycloneDX JSON documents describing the payload.

```sh
jq . <file>.sbom.json

# Requires cyclonedx-cli, installed separately.
cyclonedx validate --input-file <file>.sbom.json
```

## Download release assets

Preview assets use
`https://github.com/jackin-project/jackin/releases/download/preview/<asset>`.
The tag moves to the newly published source commit and the release retains only
that generation's assets once publication commits. GitHub's asset listing may
be transient during replacement; only a complete signed generation with a
committed publication journal is accepted. Always audit that receipt and
publication; an older native preview cannot fetch a replacement capsule from a
newer source commit merely because the URL is unchanged.

Stable assets use
`https://github.com/jackin-project/jackin/releases/download/v<version>/<asset>`.
Stable tags and published versions are never moved or replaced.

Homebrew installs prebuilt archives through `jackin-preview` and `jackin`.
Native tap promotion creates a PR rather than pushing tap `main`, and requires
validated metadata, required checks, and exact-head review completion before
merge. Initial tap promotion remains disabled during structural bootstrap;
workflow generation alone does not establish that installation or automatic
promotion has completed.
