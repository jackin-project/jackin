**Research state:** Current

## Summary

Snapshot **2026-10-24 01:15:00 UTC**. Prefer native behavior and narrow upstream reuse, with Rust for Jackin-owned scope, recovery and evaluation contracts. Start complex/stateful backends as pinned processes. The earlier preferred Headroom dependency, blanket RTK Apache extraction, Caveman BSL rejection and full-public LemonCrow assumption do not survive current evidence. No component is a complete-task winner by default.

## Question and scope

For each capability, should Jackin preserve a native feature, depend on a library, package a CLI/sidecar, adapt instructions, contribute upstream, maintain a narrow fork/kernel, or implement its own control? Language, popularity and source availability alone cannot decide.

## Method

Use the six refreshed product dossiers, exact build/package/fixture records, current component licenses and independent source checks of RTK/LeanCTX. Inspect current Jackin Cargo/usage/runtime boundaries rather than the old proposed crate layout. Pinned product versions and dates are centralized in the [release register](/research/context/tools/08-current-release-register/).

## Findings

### Seven choices for each capability

| Choice | Best fit | Evidence before selection |
|---|---|---|
| Existing agent-native behavior | Execution/editing, provider connection, native discovery/compaction and exact reads | Verify installed host/version/defaults; measure a genuine native baseline |
| Direct upstream library | Small typed operation with explicit state/runtime and supported feature graph | Locked target build, license, API stability, cancellation, allocator/native linkage and fidelity |
| Pinned CLI or isolated sidecar | Broad dependencies, process-global state or a useful existing stdin/MCP API | Artifact/source identity, OS confinement, lifecycle, exact IO/status contract and overhead |
| Selectively adapted instruction asset | Concise role guidance or reuse-first policy without an engine | Effective content/precedence, activation cost, off/resume behavior and separate task arm |
| Upstream API/feature contribution | A useful backend missing a narrow boundary or lifecycle contract | Minimal reproducer, proposed contract, regression tests and maintainer discussion |
| Narrow fork or licensed kernel extraction | A demonstrated blocker remains and upstream cannot meet the required boundary | Applicable terms, owner, synchronization policy, corpus and retirement plan |
| Jackin-native implementation | Supervisor admission, observation scope, durable recovery, qualification and task receipts | Reuse current architecture; do not recreate a full search/compression platform without evidence |

A process boundary is not automatic security; a library boundary is not automatic portability. Shared types must remain Jackin-owned and backend-neutral so a better backend can replace the first one without changing task/authorization semantics.

### Rust and process feasibility

| Candidate | Executed or inspected result | Practical consequence |
|---|---|---|
| Headroom no-default-features core | Locked Linux x86_64 check passed on Rust 1.99.1; 185 normal package/version nodes including root; no ort/fastembed/magika | Feasible selected worker; still C grammars/Oniguruma/bundled SQLite/tokenizer/network dependencies. No cross-platform or combined Jackin build claimed. |
| RTK engine | 286 unit + one guide test passed; public Block/Method/pipeline contracts | Technical reuse exists, with BUSL and unpublished API ownership to resolve. Root application library does not expose private command filters. |
| LeanCTX facade | Source confirms own two-worker Tokio runtime, explicit broad features and static `Once` setting four process-wide directories | Multiple facade instances are not independent tenants; avoid in-process default. Locked check interrupted by disk pressure, not passed or upstream-defective. |
| LeanCTX consumer plus Jackin SQLite | Full-facade offline metadata attempt stopped on missing registry `rmcp` before resolving the graph | Not a successful consumer build; upstream workspace patches are not automatically inherited by a consumer. |
| Extracted SQLite constraints | Metadata-only minimal graphs combining Jackin 0.40.2 with rusqlite 0.39, 0.34 or 0.32 each failed explicitly on `links = "sqlite3"` | Demonstrated constraint collisions for these pairs, not full product builds. Sem default disk-cache-off and RTK engine-only are separate paths. |
| LemonCrow Lite client | 87 packaged client files matched source; 45 selected tests and root-isolation fixtures passed | Useful Python process candidate with small lexical baseline; no language-only rejection or full advanced-engine reproducibility claim. |
| Caveman engine | Current local Go/CGO build and focused package tests/probes recorded by product workstream | Licensed process reuse deserves comparison; not a Rust rewrite requirement. Full release artifact/signature parity remains separate. |

Native linkage must be checked at the actual consumer feature set. Jackin pins rusqlite 0.40.2; Headroom's reviewed lock also resolves 0.40.2. LeanCTX uses 0.39, RTK's application 0.34, and sem's optional disk-cache path 0.32. The isolated minimal resolver probes reached and reported incompatible SQLite `links` for those three pairs. Their exact manifests/results are in the <RepoFile path="docs/content/research/context/techniques/tools/refresh-2026-10-24/jackin-architecture/linkage-constraint-results.json">constraint record</RepoFile>; this does not establish every full dependency graph or target. Separate processes avoid combining those native link graphs. <RepoFile path="Cargo.toml">Jackin dependencies</RepoFile> and the product manifests provide the exact constraints.

LeanCTX also sets process environment from a safe builder using `unsafe set_var`; starting before its own runtime threads does not establish that an embedding host has no other readers. [Rust 1.99.1 safety requirements](https://doc.rust-lang.org/std/env/fn.set_var.html) make this an additional non-Windows caller-thread prerequisite, source-inspected rather than a reproduced race. Prefer injected configuration or environment set before child-process startup.

Ordinary primitives remain viable: published `sem-core` 0.28.1 has disk cache off by default; `mq-lang`/`mq-markdown` 0.9.3 expose narrower parsing/query choices; fff-search 0.11.0 has a ripgrep default with native git/LMDB dependencies. The current Rust MCP SDK `rmcp` 3.7.0 and tree-sitter 0.27.1 are candidates, not dependencies introduced by this research. Confirm package/source correspondence, features, IO sandboxing and real target builds before adding them. [Adjacent assessment](/research/context/techniques/03-prior-art-and-market-scan/).

### What Jackin should own

Own admission from existing capsule/session metadata, context epochs, observation/recovery identity, authorization, durable acknowledgement, one-transform composition, cancellation/deadlines, effective configuration and outcome receipts. Reuse native command/edit/provider behavior and compatible algorithms. The existing secure-exec MCP server is not a substitute for these contracts, and a PTY cannot reveal every model request.

Keep stateful engines out of render/control critical paths initially. Use a worker's explicit input/output contract and narrow capabilities, not an unconstrained shell or arbitrary upstream global installer. Shared immutable source indexes are a later optimization after source/security identity; model-exposure state remains consumer-scoped. [Architecture](/research/context/engine/02-architecture/).

| Caveman | Skill/full-runtime boundaries and runtime pin differ; warmer broadens record-mode effects | Component/artifact manifest, explicit no-warm/no-credential baseline, stable engine adapter/recovery contract |
| Ponytail | Exact policy useful, but plugin mode/map scope changes across lifecycle | Session-scoped persistent opt-out, bounded file IO and complete path handling; exact policy vs plugin activation tests |

These are proposed briefs, not claims that maintainers accepted work. No external issue/comment was posted without authorization. Coordinate overlap with upstream fixes before creating a fork.

### Fork and kernel policy

A narrow fork is justified only by a reproduced blocker on the selected treatment and a documented upstream attempt/decision. Assign a named maintenance owner during implementation, pin a clean base, preserve notices, review upstream releases on a defined cadence, and carry a small regression corpus for the changed boundary. Re-run it on every sync and before promotion. End the fork when a supported upstream API meets the contract or when measured benefit no longer pays its ownership cost.

Do not extract BUSL, GPL, Elastic or Dual Use code under an Apache assumption. Current Serena's separable MIT SolidLSP and historical MIT releases are distinct options from its GPL application; current jCodeMunch redistribution/commercial terms differ from the old assumption. License-compatible local use is not automatically license-compatible redistribution or hosted service. [Adjacent license register](/research/context/techniques/03-prior-art-and-market-scan/).

## Implications for jackin❯

Proceed with the small Rust control/recovery/evidence contracts and a pinned OSS diagnostic-worker qualification. Compare one restricted retrieval process at a time against native tools, with unchanged stubs disabled when epoch continuity is unknown. Package concise instruction assets separately. Reassess preferred algorithms from current complete-task results rather than committing early to Headroom, LeanCTX or LemonCrow.

## Limitations and unknowns

No combined Jackin dependency build, cross-platform worker suite, real host activation or paid accepted-task comparison qualifies any of these as an automatic external default. Source-level dependency risks and incomplete attempts are explicitly labeled. The design can proceed on interfaces and narrow prototypes without inventing the missing outcomes or rewriting entire upstream products.
