## Summary

Tool-state cutoff: **2026-09-23 UTC**. **Reuse before rewrite, with Jackin-owned boundaries.** None of these decisions changes Cargo dependencies or activates a runtime. The [integration plan](/research/context/tools/11-jackin-integration/) defines implementation gates; the [release register](/research/context/tools/08-current-release-register/) fixes versions.

## Question and scope

Which capabilities should Jackin depend on, bundle, adapt, extract, or implement itself?

## Method

Distinguish current source APIs from published/stable SDK contracts, then assess execution ownership, recovery, isolation, licensing, dependency cost, and release-matched outcome evidence. A missing stable SDK favors an adapter or process boundary; it does not automatically justify a complete rewrite.

### What Jackin should own

Own operator configuration, qualification records, typed result envelopes, artifact completeness/provenance, raw recovery, session/context-epoch exposure state, isolation, worker lifecycle, and actual-versus-estimated usage. Extend the existing workspace rather than duplicating execution, provider, or telemetry infrastructure. <RepoFile path="Cargo.toml">Workspace components</RepoFile> and <RepoFile path="crates/jackin-capsule/src/runtime_setup.rs">capsule-local setup</RepoFile> anchor this plan.

No whole-product rewrite is presently justified by the inspected evidence. Headroom already supplies relevant Rust source; LeanCTX supplies an experimental facade; LemonCrow can be evaluated as a process. A working sidecar can be better than a forced Rust port if accepted-task behavior is superior.

### When to extract or build a kernel

First try the narrow public API or subprocess and measure its boundary. Then propose an upstream change that makes the required feature pure, independently testable, or configurable. Extract a licensed kernel only when the existing boundary demonstrably cannot meet Jackin's requirements or upstream support is unavailable. Record source commit, notices, local modifications, regression corpus, and upstream-update review ownership.

Build new logic where it encodes Jackin's own contract or where no suitable implementation meets fidelity, isolation, or recovery requirements. Do not mistake a faster implementation of the wrong semantics for a successful optimization. Do not port BSL code into an Apache-only implementation while labeling it an independent reference design.

### Embedding is not automatic compatibility

The Headroom core and LeanCTX embedding facade use internal version 0.1.0; the facade is unpublished and owns a Tokio runtime. Their product release numbers are not interchangeable Cargo versions. Disabling defaults on the LeanCTX facade's engine dependency still enables several substantial features explicitly. See its [README](https://github.com/yvgude/lean-ctx/blob/v3.10.2/rust/crates/lean-ctx-embed/README.md).

Pin a commit and lock dependencies. Compile every supported target and selected feature combination, including native-library resolver constraints. Avoid exposing upstream types as durable Jackin APIs. A separately supervised worker is the initial fault-containment boundary, not a claim that crashes or deadlocks cannot occur.

## Implications for jackin❯

### Acceptance bar

A candidate becomes an automatic default only after source/license and build checks, actual host activation, fidelity and raw recovery, parallel-worktree isolation, and controlled accepted-task evaluation pass. The proposed 20% net-improvement target is a gate to validate, not a measured promise or a reason to ignore correctness. Predeclare quality margins and outcome statistics; keep failed attempts in the denominator. [Current protocol](/research/context/tools/07-evidence-and-claims/).

No full global installer, provider interception, model downgrade, or effort downgrade is required for the initial architecture. Complementary capabilities can compose only with explicit ownership and a separately measured combined profile.

## Limitations and unknowns

Crate builds and installed-agent conformance were not run in this research environment. Adjacent retrieval libraries described in other feature sketches are not requalified by this six-tool review; their versions and features must be verified before reuse. This page supersedes dependency assumptions in those sketches, without claiming their implementations exist.
