## Summary

**Research state:** Current

**Snapshot:** 2026-10-24 01:15 UTC. Fleet reuse depends on an identical eligible prefix **inside an authorized provider cache scope**. A shared repository, model name or organization does not by itself establish reuse.

The old chapter contradicted itself by documenting Claude workspace isolation while recommending pooling across separate workspaces. That recommendation is withdrawn. This refresh uses current provider/host contracts and executed synthetic arithmetic; no provider fleet, paid fan-out or quota experiment ran.

Provider cache reuse is a compute mechanism. It is not a data-sharing interface. Do not merge credentials, workspaces or user histories to chase hit rate.

## F1 — Stable workspace identity

Native hosts can include working directory, environment, repository metadata, tool definitions and instructions near the beginning of a request. Stable paths and deterministic initialization can preserve a longer common prefix across repeated authorized jobs.

Paths must still resolve to the correct checkout and permissions. Giving different repositories the same displayed identity or deleting repository state can change behavior. Compare the actual request prefix or supported native cache diagnostics, not just launch arguments.

The executed byte fixture shows a shared prefix of 20 bytes with a changing path first versus 4,320 with the fixed instructions first. These are **synthetic byte lengths**, not provider tokens or a production rewrite recommendation. They demonstrate the mechanism only.

## F2 — Dynamic system sections and instruction authority

The Claude SDK's [system-prompt controls](https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts) include `excludeDynamicSections`. Moving environment information out of a system prompt can improve reuse while changing its authority and placement. Make that an explicit application design decision with behavioral tests.

Do not freeze a false date, stale Git status, removed permission or unavailable tool. Separate genuinely immutable project guidance from current task state while preserving their intended authority. A cache-optimized lie is still incorrect context.

Current provider append controls can preserve prior prefixes for supported mid-conversation system, effort and tool additions. The SDK or native host must expose the control correctly; an API feature alone does not authorize rewriting a host's hidden prompt.

## F3 — Warm then fan out

A first request or explicit prewarm can make an eligible common prefix available before workers start. It may reduce repeated creation, but it adds startup delay and billed work. Concurrent requests can race before the entry is available; the exact number of writes is an observation, not a fixed concurrency law.

The offline scenario uses ten requests and a normalized prefix with a 1.25× write and 0.05× read:

| Assumed schedule | Prefix cost units |
| --- | ---: |
| Ten independent writes | 12.50 |
| One useful pioneer, then nine reads | 1.70 |
| Extra prewarm, then ten reads | 1.75 |
| Ten separate isolated workspaces | At least ten initial workspace writes under this scenario |

The calculation excludes divergent task tails, output, expiration, latency, retries and paid tool work. It does not establish an 86.4% total-task saving or a tenfold fleet capacity improvement. Source assumptions and exact commands are in the [offline bundle](/research/context/techniques/tools/#october-24-provider-evidence).

Prewarming must use the actual common prefix and compatible model/settings. Claude's zero-output warm-up and OpenAI's `prewarm` API are billable. Do not create a hidden keepalive loop, warm when optimization is off, or spend across idle tenants without authorization.

## F4 — Subagents and native cache behavior

Fresh subagents may have different system instructions, tools, repository snapshots and task messages. Forks inherit more parent context but also more input. Existing subagent sessions can preserve useful state; creating a new worker is not automatically cheaper.

Current [Claude Code caching](https://code.claude.com/docs/en/prompt-caching) documents host behavior, and [subagent documentation](https://code.claude.com/docs/en/sub-agents) documents lifecycle and model resolution. Record actual cache reads/creation by worker and host version. The former issue-specific claim that subagent caching is universally disabled or broken is not promoted to a current product fact without a reproduced applicable version.

Current Claude Workflow already staggers same-prefix fan-outs behind the first request for up to five seconds by default. This is a native baseline feature, not a new Jackin saving. A concurrency ceiling limits the number of live workers; it does not cap RPM, generated output, total spend or the workload's cache misses. Provider account limits and native depth/budget controls remain separate. Native Explore can change models on particular connection modes, so a presumed shared model prefix needs verification.

## F5 — Tenant and team boundaries

Sharing a stable public instruction prefix within an authorized scope can be useful. Sharing customer history, tool results or credential-dependent context requires the correct data boundary even when the text happens to match.

Include tenant/workspace identity, model/endpoint, prompt/schema version, policy version and permission scope in an application's cache eligibility decision. Hashes are identifiers, not permission checks. Missing identity should not silently widen reuse. For response caching, include mutable source revisions and invalidation as well; a prefix-cache rule is insufficient for replaying an answer.

Avoid raw private prompts in ordinary fleet telemetry. Aggregate token classes and latency can often diagnose hit behavior without storing full contents; exact captured evidence belongs in a separately scoped, access-controlled recovery store with retention/deletion rules.

## F6 — Launcher policy and rollout

Jackin currently has twelve registry/adapters but only six launch-dispatch cases at the pinned baseline. Its native hosts have different hook and provider contracts. A global “fleet optimizer on” switch cannot substitute for versioned per-host eligibility; see the [portability matrix](/research/context/techniques/23-cross-agent-portability).

A proposed launcher policy should record the resolved host/model/effort, auth route, cache scope, stable-prefix identity, optional warm policy and effective off mode. Preserve current isolation and approval behavior. Do not introduce a shared proxy or process-wide cache that leaks across sessions because the repository was launched from one supervisor.

Roll out only after cold/warm, concurrent, tenant-separated, resume and failure cases satisfy the [validation gates](/research/context/techniques/16-validation-harness). Keep the unmodified native path available when identity, versions or cache contracts are unknown.

## Decision and evidence limits

Prefix stability is a useful candidate with narrow semantics. The benefit must be measured per tenant and accepted task, including paid warms, idle expiry, output, retries and queue latency. A high aggregate fleet hit rate can hide poor performance for a small tenant or a hot-worker bottleneck.

No production tenant-isolation execution, actual cache sharing, native subagent hit rate or paid fleet saving was measured here. The old distinct-workspace pooling claim, universal warm-start multiplier and unresolved issue-to-current-product inference are withdrawn. All six prior fleet topics remain covered, with explicit [source and claim dispositions](/research/context/techniques/tools/#october-24-provider-evidence).
