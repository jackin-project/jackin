## Summary

**Research state:** Current

**Snapshot:** 2026-10-24 01:15 UTC; primary sources retrieved October 24. Model routing and effort changes are **separate optional treatments**. They do not count as context compression in Jackin's main comparison, which preserves the user's selected model and reasoning effort.

A cheaper model can lower unit prices while increasing tokens, retries, review or failure rates. A router can also spend tokens making its decision, lose an existing cache prefix, or silently fall back during an error. Evaluate all attempts per accepted task and report the actual model/effort used on every request.

## Method and price baseline

This refresh reopened native model/subagent documentation, current API prices, RouteLLM, LLMRouterBench and LiteLLM's current AutoRouter. No paid model comparison or capability benchmark ran. The old repository tokenizer ratios and account-session dollar totals were not reproduced and are not evidence for current tier selection.

The [provider chapter](/research/context/techniques/12-provider-features) and [machine-readable rate register](/research/context/techniques/tools/#october-24-provider-evidence) distinguish ordinary input, cache reads, lifetime writes and output. For example, current standard short-context GPT-6 Astra is $10/$50 per million input/output tokens and GPT-6.1 Sol $2/$10, while their cached input rates are $1/$0.10. Those prices describe different models; the ratio does not predict equivalent accepted work. Claude's current cache-read ratios likewise vary by generation.

## Actual routing surfaces

| Surface | What changes | Current qualification |
| --- | --- | --- |
| Explicit native subagent `model` | Worker model and potentially tokenizer/cache | Supported by the host; preserve inheritance in the main experiment |
| Built-in Explore / Plan | Native specialization and sometimes model | Record exact native defaults, connection mode, aliases and overrides |
| Claude `opusplan` | Opus in planning, Sonnet in execution | Still documented; explicitly a multi-model workflow |
| Effort controls | Reasoning allocation within a model | A capability/cost intervention even when the model string is unchanged |
| Advisor/executor design | Cheap executor plus additional stronger-model requests | Include advisor prompts, responses, escalation, failures and coordination |
| Gateway complexity routing | Chooses a model from a configured set | Requires accuracy/cost calibration and explicit route observability |
| Availability fallback | Replaces a failed or unavailable route | Operationally useful, but changes the experimental treatment |

Sources: [Claude model configuration](https://code.claude.com/docs/en/model-config), [subagents](https://code.claude.com/docs/en/sub-agents), [effort](https://platform.claude.com/docs/en/build-with-claude/effort), [LiteLLM AutoRouter](https://docs.litellm.ai/docs/auto_router/).

### Built-in models are connection-dependent

The earlier “Explore always runs Haiku” claim is stale. Current documentation says Explore normally uses the main model. With a Fable parent, subscription, Console and `ANTHROPIC_BASE_URL` gateway connections use the current `opus` alias for Explore; Bedrock, Google, Foundry, Claude Platform on AWS and Claude apps gateways retain the main model. A custom agent named Explore, explicit model settings and force-subagent configuration can override this.

Plan normally inherits the parent. Other helper agents can have their own defaults. Record the resolved model identifier rather than assuming an alias or launch setting reaches every worker. If native behavior changes the selected model, label it as a native mixed-model baseline; it cannot certify a same-model compression result. No override was installed in this refresh.

### Effort and budgets are not interchangeable

Current Claude effort defaults differ by model: Opus 5.5 and Haiku 5.5 default to medium, while other supported models can default to high. Opus 5.5 has always-on thinking. An omitted effort field is not a cross-model constant. Preserve the resolved setting in the primary comparison.

A hard per-request output limit, a soft cross-loop task budget and a host-enforced spend limit are different controls. Lowering any can produce an early stop or reduced validation. [Claude task budgets](https://platform.claude.com/docs/en/build-with-claude/task-budgets) are advisory; [Agent SDK spend limits](https://code.claude.com/docs/en/agent-sdk/subagents#cap-subagent-depth-concurrency-and-spend) enforce a different query lifecycle. Their existence does not justify a silent reasoning downgrade.

## Routing economics and failure modes

A routing policy must include classification cost, every worker request, cold-prefix writes, retries, strong-model rescue and final verification. Compare it with simple baselines: always use the selected model; always use a specified cheaper model; a transparent rule by task category; and a random or fixed mixture at matched budget.

Use a task-level decision boundary where possible. Reusing an existing model's cache after switching models is not generally guaranteed. Switching back can also leave signed thinking or provider state incompatible. Current Claude and OpenAI offer append-only configuration changes for some controls, so “every effort change destroys every cache layer” is also too broad. Model switching remains a separate operation from those documented append controls.

Tokenizer differences require measuring the same messages with each actual tokenizer. The old Opus-boundary measurements do not establish a universal additional discount. A model can generate a longer answer or need more turns, and strict formatting can change both tokenization and correctness.

Fan-out can reduce wall time while multiplying work. A nominal worker-price discount does not make speculative duplication free. Set task ownership, concurrency, completion criteria and cancellation; preserve raw results from losing branches for cost accounting even when they are not used in the final answer. See [multi-agent protocols](/research/context/techniques/11-multi-agent-protocols).

## What the routing evidence supports

[RouteLLM](https://arxiv.org/abs/2406.18665) supplies an open research framework for learning a cost/quality routing boundary. Its model pairs, training distributions and benchmark outcomes do not establish a policy for the current Claude/GPT generations or long coding sessions.

[LLMRouterBench](https://aclanthology.org/2026.findings-acl.1881/) evaluates more than 400,000 instances from 21 datasets and 33 models, with ten representative routing baselines. The authors find useful model complementarity, but many sophisticated methods perform similarly and several recent/commercial routers do not reliably beat a simple baseline. This supports demanding matched baselines and held-out task strata, rather than adopting a router because its architecture is sophisticated.

The old references misidentified arXiv `2504.11154` as LLMRouterBench and `2408.11348` as OrcaRouter. Those papers concern other subjects; their routing claims are withdrawn. The corrected source and citation dispositions are tracked in the [literature chapter](/research/context/techniques/24-fresh-literature-and-market-delta).

LiteLLM now documents an [AutoRouter add-on](https://docs.litellm.ai/docs/auto_router/) with heuristic, LLM/JEV and custom classifier paths, session pinning and escalation controls. The former description of LiteLLM as load balancing only is stale. Its published coding-task and classifier examples are first-party evaluations with narrow denominators; they do not establish equal quality for Jackin's portfolio. OpenRouter/Martian and similar services remain separately qualified external routing options, not defaults endorsed by this review.

Advisor/executor designs and `opusplan` remain plausible experiments. The earlier “measured negative-cost” label and universal team-token multiplier are withdrawn as general conclusions. A published advisor result can motivate a trial but cannot establish unchanged review depth, architecture quality or completion reliability on a different workflow.

## Failure, policy and observability

Fallback must be explicit in the result ledger: requested model, resolved model, reason, effort, retry count, cache classes and acceptance outcome. Do not allow a provider's 429, unavailable model, safety response or budget exhaustion to masquerade as a successful same-model run. A fallback should preserve user permissions and tool constraints; lowering a model is not authority to broaden them.

A classifier error is not the only risk. Routing can change context limits, multimodal support, structured-output contracts, tool syntax, data handling and account billing. Validate these before permitting a route. Cross-model signed thinking or opaque state needs the provider's documented compatibility rules.

## Decision and unknowns

Keep routing off in the core compression comparison. If a user explicitly chooses it, evaluate a separate arm with held-out tasks, a fixed budget and complete rescue costs. Use the [canonical validation gates](/research/context/techniques/16-validation-harness) and publish uncertainty instead of a small pilot's apparent winner.

No current model capability parity, tokenizer discount, advisor advantage or production router reliability was established by execution here. Preserve useful routing surfaces; retire stale prices, incorrect citations, fixed Explore pricing, arbitrary fan-out multipliers and conclusions derived from unreproduced account observations.
