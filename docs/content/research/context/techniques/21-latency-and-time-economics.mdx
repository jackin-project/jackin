**Research state:** Current

Source cutoff **2026-10-24T01:15:00Z**. Current provider contracts were reopened; no paid speed comparison or user-workload timing experiment was run.

## Summary

Optimize accepted-task cost and completion time together. A faster model response can be worth paying for when it shortens the critical path and a person is actually blocked. Neither condition follows from a token reduction or a vendor throughput headline.

The earlier unconditional recommendation to buy fast mode for interactive work is withdrawn. The old 100-RPM token-count limit, universal cache latency percentages, fixed developer-minute valuation, and 2.5× whole-task speedup are also withdrawn. Current native speed modes, caching and batching remain useful, with workload-specific break-even tests.

## Question and scope

Which time savings reach the user, what do they cost, and when does optimization add more waiting than it removes?

## Method

Separate provider documentation, our short component timings, published agent experiments, and conditional arithmetic. Keep exact model and effort fixed. Measure task start through independent acceptance, including retries, queueing, startup, human review and recovery. The [canonical protocol](/research/context/techniques/16-validation-harness/) defines the cold/warm and paired comparisons.

## Findings

### The current price ladder is a service-mode comparison

For Opus 5.5, current standard API input/output rates are $4/$20 per million tokens; Message Batches discount those classes by 50%; Claude Code fast mode lists $8/$40. Cache classes, service availability and authentication route still require their own accounting. Fast-mode usage credits are separate from included subscription usage. [Pricing](https://platform.claude.com/docs/en/about-claude/pricing), [batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing), [fast mode](https://code.claude.com/docs/en/fast-mode).

| Mode at fixed Opus 5.5 | Fresh input / output per MTok | Time contract | Suitable experiment |
|---|---:|---|---|
| Standard | $4 / $20 | Observed baseline, no universal whole-task duration | Interactive and autonomous control |
| Batch | $2 / $10 | Asynchronous; requests can expire after 24 hours | Independent offline evaluation or document jobs |
| Fast | $8 / $40 | Vendor says up to 2.5× faster responses with the same capabilities | Blocked interactive tasks, measured against standard |

“Same capabilities” is a provider claim about the model, not evidence that nondeterministic task outputs are identical. The 24-hour batch horizon is not a completion guarantee. Availability and billing modes for the other selected models are maintained in [provider features](/research/context/techniques/12-provider-features/) and [subscription economics](/research/context/techniques/19-subscription-and-quota-economics/).

### The time-value model

Let <code>v</code> be the user's chosen value of one blocked minute, <code>Δt_blocked</code> the measured reduction in blocked time, <code>ΔC</code> the additional all-attempt monetary cost, and <code>ΔC_ops</code> the amortized operating cost. A speed treatment is economically favorable when:

~~~text
v × Δt_blocked > ΔC + ΔC_ops
~~~

This is a decision model, not a claim about the user's salary or utilization. Autonomous work may have no blocked person but still have a deadline or downstream delay worth pricing. Conversely, five minutes of wall-clock time may contain almost no blocked human time.

A model response acceleration only shortens the fraction of the critical path spent waiting for that response. If fraction <code>f</code> of baseline task time can accelerate by factor <code>a</code>, the idealized time ratio is:

~~~text
candidate_time / baseline_time = (1 − f) + f / a
~~~

**Illustration, not measurement:** with a five-minute task, <code>f = 0.60</code> and <code>a = 2.5</code>, completion falls to 3.2 minutes, saving 1.8 minutes. If all that saved time was blocked, the extra cost is $0.50, and the chosen value is $1 per blocked minute, the net modeled benefit is $1.30. Tool execution, extra turns, queueing or a cache miss can change every input.

### L1. Speed modes need task-level evidence

Record time to first token, generation duration, tool execution, total turns, task completion, acceptance and user waiting separately. Compare the exact supported service modes at the same selected model and effort; do not lower effort or switch models to manufacture a latency improvement.

Pin the mode at the start of each comparison and record any cache invalidation or fallback. Current Claude Code documents a persistent cache-key header when fast mode is first enabled: that first request misses, while later toggles and rate-limit fallback retain the header. Enabling it on an unsupported model also changes the model, which would violate this comparison. Do not generalize those host rules to Codex or Gemini CLI. [Fast-mode contract](https://code.claude.com/docs/en/fast-mode), [Claude Code caching](https://code.claude.com/docs/en/prompt-caching).

### L2. Measure the optimizer's time and resource cost

Claude's input-counting endpoint is free and has limits separate from message creation. Current documentation lists Start/Build/Scale limits of 5,000/10,000/20,000 requests per minute; the old 100-RPM Tier-1 claim is obsolete. Counting estimates input and does not execute caching logic. It adds a network operation whose actual latency must be measured. [Token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting).

Prefer local byte/structural thresholds for cheap dispatch, then validate against provider receipts offline. Do not call a counting endpoint on every step merely to draw a live savings graph. A local tokenizer is also work and is not automatically the provider's billing tokenizer.

Measure process spawn, index load/build, model download/load, transform, serialization, archive write/read, and CPU/RAM contention independently. Keep cold start and warm steady state separate. The product probes report bounded examples: LeanCTX's first-content and repository-map timings in this shared container are useful feasibility observations, not p95 estimates for production. [LeanCTX evidence](/research/context/tools/04-leanctx-design/).

### L3. Parallel work shortens independent paths and multiplies shared demand

For independent work, ideal completion approaches the longest branch plus fork/join overhead; total token cost remains the sum of branches, coordination, repeated context and repairs. Dependent work cannot benefit from that ideal bound.

Shared provider limits, disk, memory, build locks and repository mutations can turn fan-out into queueing or retries. Track per-branch wait and actual accepted contributions. Cancel redundant branches explicitly and include work already billed. A single broad research benchmark's speedup or token multiplier does not establish coding-agent fleet economics.

The SDK now exposes depth, concurrency and spend controls; their precise scope and exceptions matter. They constrain demand but do not prove a chosen fan-out is faster. Use [delegation economics](/research/context/techniques/10-model-routing-and-delegation/), [multi-agent protocols](/research/context/techniques/11-multi-agent-protocols/) and the [governance chapter](/research/context/techniques/25-meta-cost-governance-and-online-quality/) for ownership and accounting.

### L4. Cache preservation can improve both price and throughput

A cache hit can reduce prompt processing, but it does not eliminate output generation, tool time or network latency. The old 79% TTFT and 75% session figures are not current general predictions. Measure fresh input, writes, reads, TTFT and end-to-end latency in matched cold and warm arms.

Claude cache reads normally do not count toward input-token rate limits, with a documented legacy Haiku 3.5 exception. Fresh input and writes still count; request and output limits still apply. **Conditional arithmetic:** if reads are 80% of input, a purely input-limited workload could admit five times as many total input tokens at the same fresh/write rate. It does not follow that task throughput increases fivefold. [Rate limits](https://platform.claude.com/docs/en/api/rate-limits).

Structural stability matters: a short changed prefix may create more paid writes than a longer stable prefix. Current OpenAI API paid-write classes and Codex credit billing differ, so a historical Claude-only latency/cost model cannot be transferred unchanged. [Cache economics](/research/context/techniques/07-caching-exploitation/).

### L5. Batch independent work when its deadline permits

Batching can reduce model charges for independent evaluations and offline processing. It is a poor replacement for an interactive tool loop whose next request depends on the current result. Record submission, completion/expiry and partial failures; retry costs remain part of the job.

Claude batches process requests asynchronously and concurrently, so shared-prefix cache hits are best effort. A nominal batch discount and a separate cache discount cannot be multiplied as if every request hit. Price the actual returned classes and expiry/retry history. [Batch contract](https://platform.claude.com/docs/en/build-with-claude/batch-processing).

### L6. Quota-edge decisions preserve the chosen capability

At a quota boundary, compare waiting for the applicable reset, using an explicitly authorized paid route, or pausing with a recoverable handoff. Do not assume every plan has a five-hour window or translate remaining subscription capacity into API dollars.

A cheaper model or lower effort is a separate quality experiment and outside this refresh's fixed-model optimization scope. A documented gateway fallback capability is not authorization to change the user's model. Preserve task state and make any unresolved continuation cost explicit. [Current quota contracts](/research/context/techniques/19-subscription-and-quota-economics/).

### What to record

| Layer | Required measurements | Common interpretation error |
|---|---|---|
| Provider | Queueing, TTFT, generation, usage classes, fallback, throttles | Treating response speed as task speed |
| Optimizer | Cold/warm load, transform, archive, retrieve, resource contention | Calling startup or async work free |
| Agent | All turns, children, tool waits, retries, compaction, acceptance | Counting only successful visible attempts |
| Human | Blocked time, review, repair, handoff, deadline cost | Pricing every elapsed minute as human labor |
| Fleet | Throughput, p50/p95 completion, concurrent load, budget queue | Multiplying isolated speedups |

## Implications for jackin❯

Use the native agent baseline first. Introduce timers around existing execution boundaries and separate provider, optimizer and user-visible durations. Prefer the smallest isolated intervention whose critical-path benefit is plausible, then run randomized/interleaved cold and warm pairs.

The proposed confirmation gate is whole-task p95 latency no more than 10% worse, unless an explicit tradeoff profile is accepted. It is a policy target, not a current observed result; pilot samples cannot establish a stable tail. Cost and acceptance gates remain those in the [evidence ledger](/research/context/tools/07-evidence-and-claims/).

## Limitations and unknowns

No current paid latency experiment was executed. Public benchmark timings span different agents, models, tasks, service modes and hardware; the [benchmark audit](/research/context/tools/07-evidence-and-claims/) does not pool them into a speed ranking. Local smoke timings are retained with their configuration and never used to claim universal seconds saved.
