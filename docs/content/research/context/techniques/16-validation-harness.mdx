Source cutoff: **2026-10-24T01:15:00Z**. This is a proposed paid-task protocol plus executed offline/component evidence. It does not claim that new model trials ran.

## Summary

A candidate must preserve correctness and permission boundaries, reduce the cost of accepted work after failures and overhead, and fit the latency profile. A small pilot can discover decisive failures. It cannot prove equivalence because a significance test did not reject the null.

The previous automatic 5-point non-inferiority gate at 12/30 tasks is withdrawn. The canonical default-promotion gates for a new complex optimizer are in [tools 07](/research/context/tools/07-evidence-and-claims/): zero identified new critical failures; one-sided 95% acceptance lower bound above −1 point; one-sided 95% upper bound on its all-attempt cost-per-accepted-task ratio at most 0.80; and whole-task p95 no worse than +10%, absent an explicitly chosen tradeoff profile. Insufficient precision leaves the optimizer experimental or provisional. Native or simple changes retain proportionate conformance checks.

## Question and scope

How should Jackin test the actual proposed integration without substituting local token counts, easy task completion or a proxy health check for useful accepted work?

## Method

Use staged gates. Keep selected model, reasoning effort and auth route fixed within a comparison. Pin agent/optimizer builds, instruction/schema hashes, task commits, native tool behavior and outcome criteria before executing the task matrix. Any model-routing experiment requires its own separately authorized treatment.

## Findings

### Stage 1: eligibility and activation

Verify license/distribution mode, reproducible package identity, runtime features and host support. Start in a disposable explicit configuration directory and worktree. Capture which hooks fire and exactly what reaches the model. A listening process or reduced dashboard number does not prove the intended mechanism activated.

Separate the arms:

| Arm family | Treatments kept distinct |
|---|---|
| Native | Real host tools, existing truncation/cache/compaction/discovery; no optimizer |
| Output/implementation policy | Actual Caveman skill, actual Ponytail plugin, Jackin adaptation |
| RTK | OSS stdin diagnostic filter; actual command-rewriting hook; BUSL engine/proxy if separately eligible |
| Headroom | Selected Rust transforms with recorded features; full proxy with recorded cache/retrieval mode |
| LeanCTX | Restricted read/search MCP; Preview embedded facade after feasibility gates |
| LemonCrow | Current Runtime Lite restricted retrieval; full authorized runtime only as its own product surface |
| Caveman input | Eligible engine/proxy separately from response skill |
| Composition | Individual qualified components plus their exact combined order and state policy |

Do not compare a proxy in aggressive token mode against a cache-preserving library and label them the same treatment. Do not replace the baseline's bounded read with an imaginary full-file dump.

### Stage 2: free conformance and decisive failure probes

| Risk | Required fixture and outcome |
|---|---|
| Execution semantics | Quotes, pipes, redirects, environment, cwd, command substitution, &&/||, exit status, stdout/stderr, signals, partial output; native producer executes once |
| Exact bytes | CRLF, Unicode, missing final newline, binary/invalid UTF-8, machine JSON/porcelain, over-size output; declared passthrough or explicit failure |
| Code and diff fidelity | Header-like hunk content, truncated patch, renamed files, compiler context, successful warnings, malformed syntax; no misleading complete result |
| Retrieval | Missing, expired, refused and oversized handles; path/version/hash provenance; reconstruction outcome visible |
| Model exposure | Repeat read, changed content, compaction, resume with a fresh model context, new epoch, different agent, branch switch and concurrent worktree |
| Permissions | Denied read stays denied; no executable fallback bypass; tool output cannot escalate into policy; full read cannot disclose another scope |
| Operations | Cold start/index build, warm calls, restart, cancellation, interrupted writes, resource caps, stale cache and uninstall/rollback |

Existing RTK/LeanCTX and the other product probes cover specified subsets; their exact records are linked on the product pages. Missing host paths remain unexecuted. Any critical corruption or permission/recovery regression blocks an arm before paid trials.

The structured Headroom BFCL checker inspection illustrates why the grader also needs a probe: its published function accepted a wrong function call containing just one expected argument substring. Our offline counterexample is retained in the evaluation artifacts.

### Stage 3: representative pilot, then confirmation

Use 12–30 diverse tasks as a **pilot design range**, not a universal sample-size requirement. Sample from intended work, including:

| Task family | Acceptance evidence |
|---|---|
| Rust error-path repair | Reported failure reproduced; focused regression fails before/passes after; relevant existing checks remain green |
| Multi-crate rename/refactor | All affected public callers/config/tests updated; architectural review; build and behavior checks |
| TUI/input/rendering change | Event/state and visual behavior checked; no lost accessibility or interaction requirement |
| TypeScript/Java investigation | Correct causal explanation and source evidence; no guessed location accepted by keyword alone |
| CLI/configuration change | Exact stdout/stderr/exit semantics, malformed input, compatibility requirement and docs behavior |
| Long-session continuation | Facts needed after compaction/restart recovered with correct provenance |
| Concurrent worktrees/delegates | Distinct roots, permissions and exposure histories; no cross-task contamination |
| Docs/explanation/review | Complete factual requirements and caveats under a blinded rubric; readability and verification quality |
| Large diagnostics/retrieval | Relevant warning/failure preserved and acted on; native truncation control included |
| No-op/small task | Optimizer overhead and nonactivation counted without excluding the case |

A fixed expected patch is appropriate only when the task truly requires that exact edit. Ignoring whitespace is unsafe for whitespace-sensitive formats. Merely naming a function or repeating commit nouns is insufficient for explanatory acceptance. Hidden tests are valuable but do not prove security, maintainability or requirement coverage alone.

### Randomization and isolation

Pair task starts by repository commit and dirty patch. Randomize arm order within task/round, or use a recorded interleaving schedule when full randomization is impractical. Repetitions are clustered within task; multiple seeds on one task remain one task family. Separate pilot tuning data from held-out confirmation.

Cross two conditions: genuinely cold first use, including index/model loading and cache writes; and warm repeated use with explicitly retained state. Avoid giving the candidate warmed provider prefixes while always running the baseline first. Control machine load, concurrency, provider route, timeout budget, agent version and model alias date. Record deviations rather than silently replacing the affected attempt.

Use separate disposable worktrees instead of destructive reset of the user's checkout. Treat task prompts and repository files as untrusted input to the runner. Invoke approved checker argv, not an arbitrary shell expression taken from an unreviewed task row.

### Statistical plan

Let acceptance difference be candidate minus baseline. Predeclare a paired or clustered non-inferiority method and power target based on pilot discordance, expected effect and intended task distribution. A one-sided 95% lower bound above −0.01 is the statistical uncertainty gate. Zero identified critical new failures remains a separate hard condition; a favorable average cannot buy off a known defect.

A simple caution comes from a different, elementary endpoint: with zero observed independent failures, the exact one-sided 95% upper bound on their probability is <code>1 − 0.05^(1/n)</code>. It is about 22.1% at n=12, 9.5% at n=30 and 1.0% at n=299. This is **not** the paired acceptance sample-size calculation; it shows why thirty clean examples cannot establish a tiny rare-failure probability. Repeated correlated tasks weaken that inference further.

For economics, resample paired **task clusters**, preserving all repetitions, failures and child costs. Compute total spend divided by accepted outcomes inside each resample; handle zero acceptances explicitly. Report the point estimate, upper confidence bound, equal-task-weighted sensitivity and outlier contributions. Unknown receipts prevent a complete economic qualification. Do not replace missing bills with a local character estimate.

Use an interval method appropriate to the acceptance data; a naïve bootstrap on all-identical pilot outcomes can produce a misleading zero-width interval. Small task counts need conservative methods and more representative data, not more bootstrap iterations.

Predeclare multiplicity handling for many arms and stopping rules for pilot failures. Tune on pilots, then freeze. Do not change acceptance margins, exclusions or configuration after seeing confirmation outcomes. Report both all-attempt intent-to-treat economics and any clearly labeled diagnostic clean subset.

### Latency, human review and online signals

Measure end-to-end task completion, p50/p95 with uncertainty, provider TTFT, tool latency, recovery, cancellation, index/build time and parallel contention. Sum of all agent runtimes is not elapsed wall time. Assign absolute cold/warm startup and transform budgets before trials, based on the chosen deployment profile.

Blind reviewers to arm names and randomize output order. Deterministic checks lead where they encode the requirement; rubric review fills their gaps. An LLM judge may assist after calibration against human-labeled cases, but it cannot overrule a failing objective requirement. Count its tokens and human review time.

After offline promotion, deploy narrowly with activation/escape/recovery counters, sampled accepted-patch review and rollback triggers. Online monitoring does not repair an invalid offline comparison. [Governance](/research/context/techniques/25-meta-cost-governance-and-online-quality/).

## Implications for jackin❯

The smallest decisive next experiments are:

1. Native captured diagnostic versus RTK OSS stdin filter, with actual host output caps and exact diff/machine-output escape paths.
2. Native exact read/search versus one scoped retrieval backend on tasks requiring repeated reads across compaction and worktree changes.
3. Native tool discovery versus selected schema strategy, including extra lookup turns and changed cache writes.
4. Native concise-complete guidance versus the actual upstream style/policy, including required caveats, full caller coverage and readable code.
5. Only then, the combined candidate versus native, with all overhead and failure costs retained.

These are proposed work packages. Current evidence authorizes prioritization, not a fabricated completed paid experiment.
