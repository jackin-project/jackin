**Research state:** Current

Source cutoff **2026-10-24T01:15:00Z**. Provider and gateway documentation was reopened. The controls below were researched, not installed or exercised against paid services.

## Summary

An optimizer must repay its implementation, runtime, measurement and recovery costs while preserving accepted-task quality. Budget control and quality assurance address different failures: a spending cap can stop useful work, and a cheap output can still be wrong.

The earlier claim that Anthropic workspace spending controls are alert-only is incorrect. Current Console workspaces support monthly caps, and the Agent SDK exposes a task-loop spend limit with explicit overshoot semantics. The earlier claim that every useful dollar control must live in a third-party gateway is withdrawn.

## Question and scope

Which controls actually stop expenditure, what remains in flight, and how can live quality monitoring detect regressions without becoming the largest new expense?

## Method

Distinguish documented enforcement from measured behavior; monthly organizational caps from per-task budgets; advisory token targets from dollar admission control; and independent acceptance from LLM-judge scores. No new API keys, budgets, subscriptions or external monitors were configured.

## Findings

### A. Price implementation, runtime and guard overhead

Use the all-attempt cost per accepted task from [economics](/research/context/techniques/01-economics-and-measurement/). Add the optimizer and its guard explicitly:

~~~text
net benefit per accepted task
  = baseline cost − candidate execution cost
    − measurement/judge cost − recovery cost
    − (build + maintenance cost) / accepted-task volume
~~~

This is an amortization model, not evidence that deployment volume or developer time has a known value. Count judge input/output, trace ingestion/storage, count requests, CPU/RAM, latency, review and false alarms. A free endpoint can consume time and request capacity. Native features usually require less additional infrastructure, but their validation and operations are not literally free.

For default promotion of a new complex optimizer, this dossier requires the proposed one-sided 95% upper bound on its all-attempt monetary cost-per-accepted-task ratio to be at most 0.80, together with the acceptance and latency gates in the [canonical protocol](/research/context/tools/07-evidence-and-claims/). That 20% hurdle justifies additional complexity; it is not a measured benefit or a requirement to remove existing native features. Insufficient precision keeps the candidate experimental or provisional.

### B. Budget governance: scope and enforcement matter

| Mechanism | Current documented control | Boundary that must remain visible |
|---|---|---|
| Claude Console workspace | Monthly spend cap plus configurable alerts; workspace rate limits separately constrain RPM/input/output | Monthly fleet/workspace control, not a task-local reservation |
| Claude Enterprise Spend Limits API | Per-member monthly usage-credit limits with inherited defaults and user overrides | Enterprise with usage credits enabled; a group default is per member, not pooled spend |
| Claude Agent SDK <code>maxBudgetUsd</code>/<code>max_budget_usd</code> | Accumulated loop/child spending; stops work with a budget result | Checked after responses; can overshoot by a response and already running children |
| Messages <code>task_budgets</code> | Advisory cross-loop token budget | Soft target, not a dollar cap; includes tool traffic and thinking |
| Messages <code>max_tokens</code> | Hard maximum output per request, including thinking where applicable | Can truncate useful work; does not cap input, retries, children or whole-task spend |
| Usage and Cost API | Reporting by organization/workspace and time | Usually about five-minute availability, possibly longer; reporting is not admission control |
| LiteLLM budgets | Configurable proxy/team/key/session enforcement | Database-backed configuration matters; DB-less global budget fails open |
| Cloudflare AI Gateway spend limits | Rejects over-limit requests, with documented routing options | Eventual consistency and concurrent/in-flight requests allow overshoot |
| Portkey / Prisma AIRS AI Gateway | Integration/provider budget controls; exhaustion blocks further use | Plan and pricing coverage matter; unpriced models do not consume a dollar budget |

Sources: [workspaces](https://platform.claude.com/docs/en/manage-claude/workspaces), [Enterprise spend limits](https://platform.claude.com/docs/en/manage-claude/spend-limits-api), [SDK loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [task budgets](https://platform.claude.com/docs/en/build-with-claude/task-budgets), [usage reporting](https://platform.claude.com/docs/en/manage-claude/usage-cost-api), [LiteLLM](https://docs.litellm.ai/docs/proxy/users), [Cloudflare](https://developers.cloudflare.com/ai-gateway/features/spend-limits/), [Portkey](https://portkey.ai/docs/product/ai-gateway/virtual-keys/budget-limits).

Do not call every row a strict pre-authorized ceiling. The Enterprise API even warns that its informational spend reading can temporarily report zero when unavailable. Missing cost is unknown, not free. Likewise, a rate limit controls throughput and can induce retries; it is not a monetary task budget.

### G1. Use native controls before introducing a gateway

For an SDK-owned loop, the native spend/depth/concurrency controls may provide the needed boundary without a new proxy. The SDK's <code>result.usage</code> covers the main loop; <code>modelUsage</code>/<code>model_usage</code> includes subagents. Use whole-tree accounting and retain raw calls when a crash leaves incomplete summaries. Accumulated budgets and the effect of <code>/clear</code> must match the intended task boundary. [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop).

The documented complete subagent controls require the supported SDK/Claude Code versions; current defaults include depth 3 and concurrency 20, with an ultracode concurrency exception. Defaults are neither a quality guarantee nor a universal fleet limit. [Subagent caps](https://code.claude.com/docs/en/agent-sdk/subagents#cap-subagent-depth-concurrency-and-spend).

For Jackin-owned execution, a proposed stronger controller would reserve a conservative allowance before spawning work, reconcile actual receipts, and release unused reservations. It must define in-flight cancellation, unknown prices, retries, boundary reset and interrupted recovery. This design is not implemented or proven here. Native provider/SDK stops remain valuable even when reservations exist.

### G2. Keep token targets, output bounds and spending limits distinct

The Messages task-budget beta is a soft cross-loop target with a minimum budget of 20,000 tokens. Supplying the full conversation repeatedly does not mean a caller should subtract that replayed history again from its own remaining-budget value. Such double subtraction can distort behavior and the cache prefix. It is an API control, not an assumed Claude Code setting. [Task-budget contract](https://platform.claude.com/docs/en/build-with-claude/task-budgets).

A reasonable <code>max_tokens</code> is a valid per-request rail. An arbitrarily tight value can truncate a tool call or answer, causing billed retry and repair work. A context-window stop reason also does not certify completion or enforce a dollar budget. Preserve the stop reason and incomplete result; only the independent task grader decides acceptance. [Stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons).

These controls may intentionally stop a legitimate task. Their quality effect is not automatically neutral: count the unfinished attempt and provide a recoverable state rather than silently treating the stop as success.

### C. Online quality checks complement offline acceptance

A production judge observes sampled traces after a task; it does not retroactively prevent a bad action or prove the unobserved traffic was correct. Deterministic tests, permission checks, exact evidence preservation and recovery checks should remain primary where available. Use model judging for residual properties such as missing caveats, unsupported claims or incomplete handoffs, after calibration against reviewed examples.

| System | Current documented capability | Relevant limitation |
|---|---|---|
| LangSmith | Filtered and sampled online evaluation; feedback-aware automation | A rule's position does not guarantee another asynchronous evaluator has finished |
| Braintrust | Asynchronous production scoring, with span/trace scopes and sampling | Trace scoring can wait for an idle period; later spans may require rescoring |
| Phoenix | SDK and server evaluation over traces, including production trace workflows | Evaluation support is not identical to a fully configured alerting/incident system |
| Helicone | Attaches and aggregates externally computed scores | It is not itself the judge; its score analytics can lag |

Sources: [LangSmith](https://docs.langchain.com/langsmith/online-evaluations-llm-as-judge), [Braintrust](https://www.braintrust.dev/docs/evaluate/score-online), [Phoenix](https://arize.com/docs/phoenix/evaluation/llm-evals/evaluator-traces), [Helicone](https://docs.helicone.ai/features/advanced-usage/scores). The old blanket statement that OSS Phoenix cannot evaluate production traces is withdrawn. These are documented capabilities, not a comparative product qualification.

### G3. Calibrate the judge and preserve a native canary

Use a labeled seed set containing actual failure modes: missing final-newline markers, omitted success warnings, stale read stubs after compaction, reordered critical log lines, incorrect tool arguments and lost source attribution. Validate judge sensitivity and false positives before relying on its trend. The structured Headroom benchmark audit found a substring grader that accepted a wrong tool with one matching argument; executing a grader is not proof that it measures the intended behavior. [Benchmark audit](/research/context/tools/07-evidence-and-claims/).

Keep a small randomized native control where authorized, with matched task strata and exact model/effort. Track acceptance, repair, recovery, stop reasons and cost drift rather than only average judge scores. Retain configuration epochs so an alert can identify the actual optimizer build and policy.

### G4. Choose sampling from detection needs and measured guard cost

The old fixed 1–10% / 50–100% sampling tiers are not universal evidence-based defaults. Select rates from task volume, failure prevalence, consequence, judge sensitivity and detection deadline. Stratify rare high-impact paths; preserve the sampling probabilities so aggregate rates can be interpreted.

For independent events, if <code>p</code> is the failure prevalence, <code>s</code> the sampling fraction, and <code>r</code> judge sensitivity, the chance of at least one detected failure in <code>N</code> events is:

~~~text
1 − (1 − p × s × r)^N
~~~

This planning equation assumes stable independent events and calibrated sensitivity. Correlated failures and biased sampling invalidate a naive calculation. It does not establish a safe deployment threshold.

Async judging removes a synchronous dependency from the user's request, but it still consumes capacity, storage and budget and introduces detection delay. Bound its queue and measure resource contention; do not promise zero tail-latency impact. Reuse deterministic outcomes where possible and include the judge's failed attempts in guard cost.

### G5. Budget exhaustion preserves model choice and task state

The selected model and reasoning effort remain fixed. A gateway may support fallback to another model, but automatic downgrading is a separate capability tradeoff and is not authorized by a savings goal.

On exhaustion, stop new discretionary work, cancel what the execution contract permits, retain the patch/evidence and publish an incomplete checkpoint with the observed cost and continuation requirements. Waiting or moving to an explicitly authorized paid route is different from changing the model. [Subscription and quota economics](/research/context/techniques/19-subscription-and-quota-economics/).

### G6. Bound recursion, shared demand and recovery work

Apply per-task depth/concurrency controls alongside fleet limits, not as substitutes. A branch can spend on startup, duplicated context, tool execution and partial results before cancellation. Each receipt needs a task/branch parent, and repairs belong to the original treatment's denominator.

Before rollout, test budget exhaustion, simultaneous admissions, a missing price, failed accounting storage, crash/restart, late child completion and rollback to the native path. These can use synthetic receipts and local workers before any provider spend. Do not infer enforcement from a dashboard value or default setting alone.

## Implications for jackin❯

Use the shared [validation gates](/research/context/tools/07-evidence-and-claims/): zero observed new critical correctness/security/permission/provenance/recovery failures; a powered acceptance comparison with at most one percentage point of statistical uncertainty tolerance; and predeclared cost and latency criteria.

Rollback immediately for a known new critical failure. For noncritical drift, use a predeclared task-cluster analysis and investigation threshold rather than repeatedly testing noisy daily averages until a favorable result appears. Restore the native path and preserve a reproducible incident fixture. Monitoring supplements the pre-deployment gate; it does not license known quality loss.

## Limitations and unknowns

No gateway cap, live judge or subscription stop was exercised in this refresh. Provider and gateway counters can be delayed, misconfigured or incomplete; no claim of a universally exact hard ceiling follows from their documentation. The actual maintenance burden, judge accuracy and beneficial sampling rate remain workload measurements.
