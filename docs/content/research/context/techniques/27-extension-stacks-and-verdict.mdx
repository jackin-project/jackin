**Research state:** Current

Source cutoff: **2026-10-24T01:15:00Z**. This verdict integrates the refreshed product, provider, benchmark and frontier evidence. It is a decision framework, not a measured current Jackin savings forecast.

## Summary

**No universal 2.5×, 5–6.2× or 10× accepted-task improvement is established.** The former daily workload and composed multipliers were not independently recovered or validated. That does not prove large gains impossible on a particular wasteful workload; it requires measuring the real native baseline and the deployed treatment.

Start with supported native behavior and small, inspectable improvements. Evaluate one runtime intervention at a verified observation boundary before composing it with another. Preserve the selected model, effort, authentication, execution, editing and permission policy. Report API cost, credits, subscription utilization, task acceptance and waiting time as distinct outcomes.

## Question and method

What can Jackin adopt or investigate after accounting for current capabilities, quality, recovery, cache classes, failed attempts, overhead and maintenance? The [benchmark audit](/research/context/tools/07-evidence-and-claims/) separates first-party, competitor and independent results; [composition](/research/context/techniques/15-composed-stacks/) avoids duplicate credit.

No paid six-product benchmark, personal quota experiment or current full-stack accepted-task comparison ran in this refresh. Executed source/build/fixture checks establish narrower component facts. A current research page is not a production qualification stamp.

## Dollar and multiplier verdict

A measured stack multiplier is the baseline's all-attempt cost per accepted task divided by the candidate's corresponding cost, on representative task clusters with comparable acceptance. Failed attempts, recovery, retries, extra schemas/instructions, compaction, auxiliary calls and local operating costs belong in that comparison. Missing costs remain unknown.

For an unchanged trajectory, removing fraction <code>r</code> of an addressable cost share <code>f</code> with overhead share <code>h</code> gives the illustrative ratio <code>1 − f·r + h</code>. Perfectly eliminating a 10% cost slice cannot make the whole task ten times cheaper. Conversely, a better trajectory can eliminate repeated failures or unnecessary exploration; that causal benefit must be observed rather than inferred from a frozen replay.

Useful context still has a processing price on a hosted route, and generation remains billable under its contract. These are accounting facts, not a universal workload floor. Their relative shares vary by task, cache policy, model, host and billing route. A provider's self-hosted memory reduction or a local 90% payload cut cannot identify those shares.

Current evidence is mixed: the release-matched RTK study improved its small Claude answer score while increasing reported cost; historical fuller-runtime LemonCrow results cannot be transferred to public Runtime Lite 0.8.0; competitor studies use other versions, configurations and exclusions. None establishes an all-six current winner. [Study methods and recomputations](/research/context/tools/07-evidence-and-claims/).

## Quota verdict

For an included plan, measure **accepted tasks per relevant window**, observed utilization points per accepted task, time waiting and any paid spill. Record plan, model, effort, connection mode, reset times and other activity sharing the balance. Use multiple matched windows because delayed/quantized observations can overwhelm a small difference.

Prefix stability, smaller useful observations and fewer unnecessary turns are candidates, not a published cap-weight formula. Cache hits can lower API prices without proving the same proportional quota change. Extra subagents can improve completion time while consuming a shared limit faster. Fewer calls can be harmful if they remove verification or retrieval required for acceptance.

Current Max/Team monthly API credits do not automatically cover every headless/native run; Codex credits do not inherit OpenAI API cache-write billing. Keep those distinctions from [chapter 19](/research/context/techniques/19-subscription-and-quota-economics/). Waiting, enabling paid spill, changing accounts and changing models are different policies. Preserve the user's existing authorization.

## Stack guidance

### Native-preserving profile

Use the host's current precise reads/search, normal edits, tool discovery, cache handling and compaction as the starting point. Remove demonstrably duplicated instruction/hook delivery, use concise complete narration, and retain requirements, diagnostics and provenance. Audit actual model-visible context before imposing a size budget.

These improvements can be worthwhile without a 20% savings target or a new runtime. They still need proportionate correctness checks: a partial read can miss a condition and a terse response can omit a failed test. Preserve normal escalation and full-read options.

### Guarded runtime experiment

Select one narrow implementation: RTK OSS diagnostic filtering, selected Headroom transforms, scoped LeanCTX retrieval or LemonCrow Runtime Lite retrieval. They overlap at important boundaries; installing all four is not a composition strategy.

Require caller-owned original capture, producer status and completeness, explicit repository/worktree/session/context epoch, durable recovery acknowledgement, bounded transform time and a genuine host replacement channel. Retain native execution, edit and approval contracts. Current product probes identify concrete promotion blockers: RTK Git compaction omissions, Headroom duplicate-key/recovery boundaries, LeanCTX persisted exposure state and process-global embedding configuration, and LemonCrow failed-spill unchanged markers.

Compare native + A, native + B and native + A + B only after individual activation and fidelity gates. Full proxy, full upstream tool replacement, skill/plugin and restricted Jackin adaptations remain separately named arms. See [product boundaries](/research/context/tools/05-head-to-head/) and [integration](/research/context/tools/11-jackin-integration/).

### Quota- or latency-constrained profile

First make the constraint observable. Defer authorized discretionary work when useful; bound fan-out; preserve native same-prefix staggering; choose an explicit supported speed or warm policy only when its whole-task tradeoff is favorable.

Keep deadline misses, cold starts, unused warms, output, validation and retries in the ledger. Do not treat autonomous work as having zero time value or an attached human as valuing every second equally. A higher API bill may be acceptable under an explicit latency preference; it is not token compression or a universally better stack.

### Separate routing or training research

Another model, lower effort, advisor policy, fine-tune or self-hosted deployment can change quality and cost substantially. These require separate user-authorized policy and acceptance evidence. Preserve the selected model/effort in the primary optimizer study, include escalation/verification and do not relabel a routing gain as a context-transform result.

## Qualification and promotion

For a **new complex optimizer**, apply the proposed canonical gates to the entire deployed composition:

- Zero observed new critical correctness, security, permission, provenance or recovery failures.
- Representative paired/task-cluster acceptance evidence with a one-sided 95% lower bound above −1 percentage point. This is an uncertainty tolerance, not permission to knowingly sacrifice correctness.
- At least 20% lower all-attempt cost per accepted task to justify added deployment/maintenance, with a one-sided 95% upper cost-ratio bound at or below 0.80 using paired task clusters. Insufficient precision leaves the optimizer experimental or provisional; default promotion cannot waive this bound.
- Whole-task p95 latency no more than 10% worse unless an explicit tradeoff profile is accepted; also predeclare absolute cold/warm overhead budgets.

These are proposed decision criteria, not results achieved by the six products. A 12–30-task pilot can expose problems but cannot certify a tight margin; confirmation needs power and representative independent task clusters. Small native-preserving improvements are not retroactively required to clear a new-engine economic threshold. [Canonical protocol](/research/context/techniques/16-validation-harness/).

## Cross-layer decisions and rejected claims

| Claim or mechanism | Current treatment |
|---|---|
| Stable prefixes and concise complete instructions | Useful candidates; preserve truth, instruction authority and actual native loading |
| Request reduction | Remove demonstrably unnecessary work; retain verification and recovery |
| Uncontrolled fan-out | Reject as a default economic assumption; measure total tree and critical path |
| Vision routing, cropping or text extraction | Conditional; preserve evidence and fixed-model treatment identity |
| Local recovery implies provider-cache reuse | Reject: storage/recovery and provider prefix identity are different systems |
| Compression is safe because the original exists | Reject: original must be durable, scoped, discoverable and usable by the current consumer |
| Hosted KV compression automatically lowers API tokens | Reject: serving memory and provider billing are different denominators |
| Async judge makes aggressive compression safe | Reject: sampling and delayed detection cannot prevent every failure |
| Stack percentages can be multiplied globally | Reject: overlap, changed trajectories and overhead require direct measurement |
| No observed universal 10× means 10× is impossible | Reject: absence of suitable evidence is not an impossibility proof |

Price ratios as well as absolute dollars can change. Recheck model, endpoint, cache policy, host, billing route and effective date through [chapter 28](/research/context/techniques/28-drift-delta/).

## Implications and remaining unknowns

Jackin's next useful work is a qualified native profile, an instrumented baseline, and a small restricted intervention with an explicit owner and exit condition. A full proxy, general installer, broad policy rewrite or historical-engine fork carries a separate maintenance and permission boundary; source availability alone does not justify it.

Unknowns include current task distributions, billed cache classes and quota observations, actual host delivery, long-session recovery and latency/resource tails. Resolve those with the smallest experiment that can change the decision. Frontier [K1–K16](/research/context/techniques/14-frontier-ideas/) and [V1–V8](/research/context/techniques/26-extension-frontier/) remain available mechanisms with explicit dispositions, rather than silently discarded ideas or promised savings.
