## Summary

Optimize **total cost across all attempts per accepted task**, with correctness and latency constraints. A removed character, a tokenizer estimate, a provider token and a subscription credit are different units. The current accounting rules also differ across providers: new OpenAI API models bill cache writes separately; Claude compaction can add sampling iterations; Gemini Interactions reports output and thought tokens separately.

No current private-session raw receipts were recovered. The earlier $17/$22 daily workload and inferred 54.8% thinking share are withdrawn as measured baselines. [Chapter 02](/research/context/techniques/02-baseline-audit/) preserves their conditional arithmetic and missing-evidence disposition.

## Question and scope

Which billable classes can a mechanism change, how should they be measured, and when does a local reduction produce an economic gain?

### Three receipt contracts

| API contract | Disjoint input classes | Priced generation |
|---|---|---|
| OpenAI Responses, paid-write models | <code>input_tokens − cached_tokens − cache_write_tokens</code>; reads; 30m writes; 12h writes | <code>output_tokens</code>; reasoning is a subset |
| Claude Messages | <code>input_tokens</code>; <code>cache_read_input_tokens</code>; creation split into 5m/1h | <code>output_tokens</code>; thinking is a subset when reported |
| Gemini Interactions | <code>total_input_tokens − total_cached_tokens</code>; cached reads | <code>total_output_tokens + total_thought_tokens</code>; these are disjoint |

Official contracts: [OpenAI cache usage](https://developers.openai.com/api/docs/guides/prompt-caching), [Claude cache](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [Claude thinking](https://platform.claude.com/docs/en/build-with-claude/adaptive-thinking), [Gemini thinking](https://ai.google.dev/gemini-api/docs/thinking). Do not reuse Gemini generateContent field names for Interactions.

For OpenAI, both lifetime counts must sum to <code>cache_write_tokens</code>; cached reads exclude charged writes. A receipt containing 12,000 input, 4,000 reads and 7,000 writes has 1,000 ordinary input tokens. Adding writes to the full input total would double-count them; treating all noncached input at the ordinary price undercounts paid writes. Earlier API models without paid writes use ordinary input = total minus cached. **Codex credit billing has no separate cache-write charge**, so API-key accounting cannot be applied to Codex credits; see [Codex pricing](https://learn.chatgpt.com/docs/pricing).

For Claude, when <code>usage.iterations</code> is present, sum its entries **instead of adding the top-level usage again**. Top-level input/output exclude compaction iterations. A compaction-only request can have zero top-level usage but billable iteration usage. Reapplying a stored compaction block is different from producing a new summary. [Compaction usage](https://platform.claude.com/docs/en/build-with-claude/compaction).

For Gemini Interactions, the documented example is 62 input +171 output +297 thought =530 total. Pricing only 171 output misses the 297 thoughts. For OpenAI/Claude, adding their reported reasoning subset to total output instead overcounts it. Missing reasoning detail remains unknown; output-minus-input-replay is not a calibrated estimator.

### Cost equation and economic denominators

For each request, with disjoint classes, compute:

~~~text
request_cost = U·pU + R·pR + sum(W_lifetime·pW_lifetime) + O·pO + fees
attempt_cost = all requests + child agents + recovery + retries + auxiliary models
cost_per_accepted_task = sum(cost of all attempts) / number of accepted outcomes
~~~

Rates are per token in this equation; divide USD/MTok inputs by one million. Report installation/index CPU and storage separately, then amortize them over observed use. Keep unknown costs unknown rather than dropping their attempts. An arm with no accepted outcomes has an undefined/infinite cost per accepted outcome, not zero.

Show both total spend per acceptance and an equal-task-weighted comparison. Expensive tasks can dominate a pooled result; task weighting can change its sign, as the [Quesma study](/research/context/tools/07-evidence-and-claims/) illustrates. A success-only cost subset is a secondary diagnostic, because it discards costly failures.

Subscription economics require accepted outcomes per observed usage window, actual credit draw, throttling and reset behavior. API-equivalent dollars may be a transparent scenario, never a measured quota conversion.

### Exchange rates and cache break-even

The old universal “one output token equals 50 cache reads” is stale. At listed rates it is 200 reads for Fable/Mythos 5.1, 100 for Opus/Sonnet 5.5 and GPT-6.1 Sol, and 50 for GPT-6 Astra. Which class dominates a real bill still depends on its volume.

For an unchanged prefix used once to write and then read <code>n</code> times, caching beats repeated ordinary input when:

~~~text
write_multiplier + n·read_multiplier < 1 + n
n > (write_multiplier − 1) / (1 − read_multiplier)
~~~

This assumes eligibility, successful creation, matching content/model/scope and reads within the lifetime. It excludes storage fees and changes in trajectory. A failed cache hit or unnecessary prewarm can reverse the result. The [cache chapter](/research/context/techniques/07-caching-exploitation/) treats provider-specific lifetimes and breakpoints.

A transform's approximate fixed-trajectory benefit is removed tokens times their actual future write/read exposure, minus schema/instruction/recovery overhead and any lost prefix reuse. A new trajectory can change turns, output and acceptance, so this estimate cannot replace a paired task experiment.

### Measurement instruments and failure modes

| Instrument | What it can establish | What it cannot establish |
|---|---|---|
| Provider final usage, with response ID and request metadata | Reported billable classes and iteration totals | Complete account bill if child/failed calls are missing |
| Invoice or provider cost/usage export | Charged account totals within its scope | Per-task attribution without correlated request IDs |
| Host JSONL/OTel | Recorded call, session and agent usage; activation and timing | Unrecorded subagents, hidden quota weighting or a true counterfactual |
| Provider token-count endpoint | Model-specific input estimate for supplied content | Output reasoning, cache hit/write outcome or exact invoice |
| Local tokenizer / bytes | Reproducible payload estimate | Cross-model billed tokens or quality |
| Optimizer gain counter | Its own eligible/transformed slice | The native agent's baseline or accepted-task savings |

Claude token counting is free, has a separate quota, and currently documents Start/Build/Scale limits of **5,000/10,000/20,000 RPM**. It estimates content without cache accounting. Earlier 100 RPM and 2,000/4,000/8,000 tables are retired. [Counting documentation](https://platform.claude.com/docs/en/build-with-claude/token-counting).

Deduplicate repeated usage blocks by scoped response ID. Treat cumulative streaming updates as replacements, reject decreasing/conflicting receipts, and retain unknown write lifetime. Count schemas, system instructions, tool arguments, recovery markers, compaction and child sessions. Tokenizer/package versions and exact UTF-8/newline inputs belong in the record.

Host summaries have their own scope: Claude SDK `result.usage` covers the main loop, while `modelUsage`/`model_usage` includes subagents. Include the whole tree without adding a parent total to the same child calls again; incomplete crash summaries require raw-call reconciliation. [SDK accounting](https://code.claude.com/docs/en/agent-sdk/agent-loop).

## Implications for jackin❯

Record provider/auth route before choosing an accounting adapter. Preserve exact receipts and price-card version per request; keep estimator counters separately named. Attribute one accepted task across the entire agent tree and every repair attempt. Use [the canonical gates](/research/context/tools/07-evidence-and-claims/) before deploying complex transformations.

The offline tests now cover paid OpenAI writes, Gemini disjoint thought/output, Claude compaction iteration replacement, duplicate responses, unknown TTLs and malformed accounting. They verify our arithmetic contracts, not provider billing correctness or a production integration.

## Limitations and unknowns

No current workload mix, per-task bill, tokenizer-family equivalence or thinking proportion is assumed. The historical daily stack forecasts cannot be rescued by substituting today's prices. A new observed baseline is required before assigning achievable 2×, 5× or 10× savings.
