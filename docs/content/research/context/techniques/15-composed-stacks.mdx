**Research state:** Current

Source cutoff: **2026-10-24T01:15:00Z**. This chapter gives a decision model and experimental sequence, not a measured daily savings forecast.

## Summary

A stack earns a multiplier only from its own **all-attempt cost per accepted task**, measured against the real native baseline. Multiplying independent marketing percentages is invalid when mechanisms overlap, change agent behavior or affect different token classes.

The former $17/$22 day, 1.06× conservative, 2.5× aggressive and 5–6.2× frontier projections are retired. Their raw workload, thinking split and per-technique multipliers were not recovered or validated. This does not prove large gains impossible. It means their magnitude and quality must be established on the intended task mix.

## Question and scope

Which interventions can compose without duplicate credit, and what evidence would make a 2×, 5× or 10× claim credible?

## Method

Keep model and effort fixed, start with current native host behavior, identify the traffic actually reached, and measure incremental effects. [Provider economics](/research/context/techniques/01-economics-and-measurement/) supplies disjoint classes; [the benchmark audit](/research/context/tools/07-evidence-and-claims/) supplies observed study limits.

## Findings

### Baseline and composition rules

Let the observed baseline cost be <code>C0</code>. For each request, retain ordinary input, each cache-write lifetime, cache reads, total generation, tool fees and auth route. Keep acceptance, retries and latency beside them. Do not split reasoning from output using a replay-count residual.

For a fixed trajectory only, a candidate mechanism has an approximate incremental cost:

~~~text
C1 = C0 − eligible_cost_removed
        + instructions_and_schemas
        + extra_recovery_and_rereads
        + lost_cache_reuse
        + auxiliary_models_and_local_runtime
~~~

For an actual alternative trajectory, recompute the whole ledger. Changing the number of turns, the chosen tools or the implementation invalidates a fixed-history extrapolation. An optimizer's output can be larger than a native truncated preview yet lead to a better answer; that is a quality/traffic change, not a failed byte counter.

Evaluate a second mechanism against the **already modified** transcript. If it removes 50% of the original payload and another also targets those same bytes, the combined saving is not 100%. If each removes half of what remains, the combined payload reduction is 75%; bill reduction still depends on the addressable class and changed behavior.

### The addressable-cost bound

For a fixed trajectory, suppose a technique can affect fraction <code>f</code> of baseline cost and removes fraction <code>r</code> of that slice, with overhead fraction <code>h</code>:

~~~text
C1 / C0 = 1 − f·r + h
multiplier = 1 / (1 − f·r + h)
~~~

A 90% tool-payload cut affecting 10% of cost, with 1% overhead, yields 8% net saving and about 1.087× throughput per dollar under unchanged acceptance. These are **illustrative inputs**, not a Jackin workload estimate.

Even perfect removal with zero overhead requires at least 90% addressable cost for a 10× result, 80% for 5× and 50% for 2×. These bounds do not apply when the treatment improves the task trajectory or changes model prices; those changes need direct outcome evidence. They do explain why a large local shrink ratio cannot by itself justify a global multiplier.

### Conservative stack: preserve semantics and native advantages

| Component | Intended benefit | Evidence required |
|---|---|---|
| Remove observed duplicate instruction/hook delivery | Avoid repeated identical prompt overhead | Actual model-bound injection traces, not duplicate files on disk |
| Bounded exact reads and precise search | Avoid collecting irrelevant content | Representative answer/patch acceptance; easy full-read fallback |
| Native edit-over-rewrite when appropriate | Avoid regenerating unchanged code | Exact patch application, formatting and caller/test coverage |
| Stable tool schemas and cache-friendly instruction order | Preserve reusable prefixes | Provider receipts across normal turns and session changes |
| Concise but complete narration/reuse guidance | Avoid restatement and unnecessary new code | Activation plus reviewer checks for omitted caveats or required edits |

These can be small, valuable improvements without clearing the new-engine 20% maintenance threshold. They are not categorically zero risk: a short instruction can become ambiguous, a partial read can miss a dependency and an edit may need a full rewrite. Preserve normal escalation.

### Aggressive stack: one qualified runtime change at a time

An experimental stack may add an RTK OSS diagnostic stdin filter, selected Headroom Rust transforms, a scoped LeanCTX read backend, or LemonCrow Runtime Lite retrieval. They are alternative implementations in important paths; installing all of them does not establish complementarity. Keep the native executor, permission authority and exact patch tools.

First measure each treatment's reach, local overhead, raw retention and recovery. Then compare native + A, native + B, and native + A + B on the same task clusters. If B merely transforms A's markers, or both replace a read with different retrieval semantics, reject or redesign that composition.

The full upstream proxy, skill, tool replacement, registry, memory policy and telemetry remain distinct treatment settings. Current first-party results using one bundle do not qualify a restricted Jackin adaptation, and vice versa. [Integration boundaries](/research/context/tools/11-jackin-integration/).

### Interaction matrix

| Combination | Potential benefit | Failure or hidden cost | Decisive check |
|---|---|---|---|
| Shell filtering + host truncation | Relevant diagnostics fit before host cutoff | Longer summary than existing preview; machine output changes | Capture actual model-visible baseline and transformed result |
| Retrieval backend + native edit | Small exploration context with exact writes | Host requires native read, causing double retrieval; stale lines | Read-before-edit conformance, exact reread/patch retry counts |
| Stable compression + provider cache | Persistently smaller reusable prefix | Nondeterminism, scope or host reserialization breaks prefix | Receipt read/write delta and byte-level prefix continuity |
| Masking/compaction + optimizer stubs | Smaller long-session history | Model no longer saw the content represented by “unchanged” | Compaction/resume/epoch canary, explicit recovery |
| Multiple recovery stores | More available originals | Wrong store/session/version, hidden expiry and duplicate markers | Provenance-bound handle routing and missing/expired distinctions |
| Terse style + reuse policy | Less narration and smaller patches | Omitted rationale, validation or required callers | Blinded acceptance and architecture/security review |
| Parallel delegates + shared index | Shared parse cost, faster independent work | State leakage, lock contention, duplicated schemas and work | Concurrent worktrees/agents with distinct roots and epochs |
| Batching + caching | Lower rate for latency-tolerant API work | Expiry, retries, deadline misses and different auth billing | Observe completed batches and actual cache classes |
| Model/effort change + any optimizer | Potentially large price/trajectory change | Confounds compression and changes quality | Separate authorized experiment; excluded from fixed-model comparison |

Current RTK and LeanCTX probes specifically motivate these boundaries: Git diff compaction is not the structural diff parser, and a persisted unchanged-read stub is not proof of present model exposure. See [RTK](/research/context/tools/03-rtk-design/) and [LeanCTX](/research/context/tools/04-leanctx-design/).

### Frontier stack and the 10× question

There are several plausible ways to reach large gains on a **particular** workload: avoid repeated failed approaches, reuse an already verified result, perform selective retrieval in a very wasteful baseline, eliminate a recurring environment defect, or move appropriate offline work to cheaper service tiers. They change different denominators and cannot be added without measuring their interaction.

A tenfold claim at unchanged model/effort must show that the baseline actually spends most of its budget on avoidable work, and that removing it retains acceptance and recovery. A smaller model plus frontier verification is a separate model-routing policy with the verification/retry cost included; it is not demonstrated quality-preserving compression. This research did not change the configured model or effort.

Ask for the task mix, native baseline, all failed attempts, current release/configuration, price/auth route, acceptance rubric and confidence interval. “Up to 90% smaller” on selected repeated logs answers none of those questions.

### Improvements that may reduce cost and improve quality

Structured retrieval can prevent native truncation from hiding decisive evidence. Concise complete instructions can reduce contradictions. Exact edits can avoid accidental changes in unrelated code. A well-designed handoff can keep a specialist focused. These mechanisms deserve tests because both cost and quality can improve; they do not inherit a universal negative-cost label.

The evidence is mixed and scoped: current RTK's small external task study improved seven-answer accuracy while increasing Claude cost; historical LemonCrow Verified improved both under its full runtime; Lite and other studies show different quality directions. Literature and vendor self-evaluations establish candidate mechanisms, not automatic transfer to Jackin. [Evidence ledger](/research/context/tools/07-evidence-and-claims/).

## Implications for jackin❯

Promote a small native-policy improvement after focused correctness checks when its risk and upkeep justify that path. For a new complex runtime, apply the canonical critical-failure, one-point acceptance uncertainty, cost and latency gates to the **whole deployed composition**. Default promotion requires a one-sided 95% upper all-attempt cost-per-accepted-task ratio at most 0.80; inadequate precision leaves the composition experimental or provisional. Requalify when a source release, schema, model, cache policy or recovery boundary changes materially.

Use three ledgers: observed baseline, candidate as a whole, and marginal incremental effect. Retain a no-optimizer escape route. A mechanism with no meaningful activation on the workload should be removed rather than maintained for a theoretical percentage.

## Limitations and unknowns

No observed current Jackin task distribution supports a numerical stack forecast. Unknown savings are not zero; proposed percentages are not measurements.
