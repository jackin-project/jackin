## Summary

Cutoff: **2026-09-23 UTC**. Reviewed release: [RTK v0.49.0](https://github.com/rtk-ai/rtk/releases/tag/v0.49.0), release commit `b1c0dc00649c50fbe8930f849c800d4d6ca12091`. RTK is a Rust command-output optimizer with a current recall facility. It is neither a universal input proxy nor an established embeddable filter SDK.

## Question and scope

Where can command-specific filtering help Jackin without changing shell semantics, approval behavior, or the meaning of diagnostic evidence?

## Method

Inspect the tagged manifest and changelog; explicitly distinguish released fixes from independently reproduced behavior. Assess shell reach separately from native file tools and provider history.

## Findings

### Current capabilities

The [0.49.0 changelog](https://github.com/rtk-ai/rtk/blob/v0.49.0/CHANGELOG.md) records a content-addressed SQLite recall store, selectable retriever behavior, recall-efficiency counters, signal-handling work, and command-routing corrections. The description that RTK can recover only by rerunning the original command is no longer adequate.

The same release records a structural region parser for unified diffs, budget-owned hunks, raw fallback, and subsequent filename and no-newline handling corrections. The prior prefix-classifier failure is not a valid blanket rejection of the current parser. These are **upstream released corrections**; this review did not execute the regression corpus.

### Recovery is scoped, not universal

The release differentiates tee and SQLite modes and failure/truncation-driven recovery. Do not infer that every successful command's full original is stored, that all entries survive indefinitely, or that recall has zero context overhead. Qualification must record the exact retriever mode, retention, capacity, and which bytes were actually captured.

### Integration boundary

```text
agent shell request -> optional rewrite/wrapper -> real command
                   -> filter + optional recall -> agent observation
```

Native agent reads and searches outside that route are not automatically covered. Reducing a newly produced result avoids rewriting an existing prompt prefix, but does not prove favorable provider cache accounting or unchanged agent behavior. Deterministic filtering can still omit a crucial detail.

### Rust packaging

The [manifest](https://github.com/rtk-ai/rtk/blob/v0.49.0/Cargo.toml) identifies an Apache-2.0 CLI with Rust minimum 1.91. No library target is declared, and `src/lib.rs` was absent in the inspected tag. Do not propose `use rtk::...` as a supported integration. A command-line package on a Rust registry is not automatically a reusable library.

## Implications for jackin❯

**Best part:** its command-specific catalog and now-explicit recall design. Start with measured noisy command families, not all shell traffic.

**Integration choice:** package a pinned executable for a controlled arm, or seek an upstream pure-filter API. Extract a small reviewed Apache-2.0 kernel only if the executable boundary cannot preserve Jackin's contract. Keep attribution and regression fixtures. A permanent full fork is not the default choice.

**Default decision:** avoid blanket command rewriting. Prefer a host-supported post-execution seam when available; otherwise qualify exact commands, arguments, consumers, exits, and signals. Keep mutation output, security findings, and review diffs raw until their individual fidelity gates pass. Do not disable all current RTK features solely because a superseded parser was wrong.

## Limitations and unknowns

No independent accepted-task evaluation of 0.49.0 was established. New recall changes the treatment, so older external studies do not measure this release. Permission matching, pipelines, quoted arguments, non-UTF-8 bytes, partial capture, and kill handling require real producer tests. Gross gain and recall counters are diagnostics, not provider-billed savings.
