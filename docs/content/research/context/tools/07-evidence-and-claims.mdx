## Summary

Cutoff: **2026-09-23 UTC**. This review established current mechanisms, not a current six-way performance winner. No independent, release-matched accepted-task experiment for the six entries in the [register](/research/context/tools/08-current-release-register/) was established. A new release containing an old benchmark document does not make the experiment current.

## Question and scope

What constitutes proof that an optimization helps Jackin, and which apparent validations fail that bar?

## Method

Prefer original studies, open task artifacts, tagged source, and release metadata. Require a matching tool version, configuration, host, model, reasoning level, workload, baseline, and grader before assigning a current performance claim. Older-release outcomes are excluded rather than projected forward. Their original sources can inform test design without entering the current ranking.

This refresh used direct repository and public-source reads. No delegated research runtime was available; no independent subagent review, paid model benchmark, complete upstream compilation, or installed-host conformance run is claimed.

### External validation eligibility

| Original source | What makes it useful | Why it does not qualify today's default |
|---|---|---|
| [JetBrains: RTK](https://blog.jetbrains.com/ai/2026/07/rtk-claude-code-token-savings/) | Paired task costs, effort sensitivity, reach and native-truncation analysis | Superseded RTK release and different host/model treatment |
| [JetBrains: Ponytail](https://blog.jetbrains.com/ai/2026/07/ponytail-skill-claude-tested/) | Explicit policy activation and paired task outcomes | Superseded release; emulated delivery differs from some full plugin behaviors; not a security-equivalence test |
| [JetBrains: Caveman](https://blog.jetbrains.com/ai/2026/07/speak-to-ai-agents-like-cavemen-tosave-tokens/) | Distinguishes visible output, cost, and outlier sensitivity | Skill experiment, not the current full input runtime or a six-way test |
| [Quesma: RTK cost study](https://quesma.com/blog/does-rtk-make-ai-coding-cheaper/) | Independent repeated terminal-heavy tasks, cache-aware costs, task-weighting analysis | Tests a superseded RTK release; trajectories offered on request, not verified as an openly downloadable complete dataset here |
| [Dasein benchmark adapter](https://github.com/daseinlabs/code-compression-bench/blob/master/arms/headroom.py) | Inspectable actual launch configuration | Explicit token-mode proxy; cannot qualify current selected-transform or cache-preserving treatment |
| [LemonCrow benchmark repository](https://github.com/lemoncrow-lab/benchmarks) | Public author-produced data and trajectory/patch artifacts | First-party, historical treatment; openness is not independent replication |

The JetBrains articles do not evaluate LemonCrow. A positive result for a policy does not validate another product that combines related ideas. A competitor-published benchmark can be useful evidence, but its interests, version pins, actual adapter, exclusions, and raw data need inspection. No superseded performance percentage is reused as a current estimate.

### Evidence classes

**T1:** release/source/API evidence, with executed conformance explicitly separated from inspection. **T2:** independent controlled current-release task outcomes. **T3:** observational reports or fixed-trajectory replay without a real alternative agent run. **T4:** first-party or competitor-owned experiments and claims. Openness, release match, and experimental control are separate dimensions, not one score.

A replay can prove how many bytes a transform removes on that captured trajectory. It cannot prove what the agent would subsequently do. A health endpoint can prove a process responds, not that the intended transform ran. Source parity can prove agreement with an implementation, not semantic fidelity.

## Implications for jackin❯

### Reproducible arms

Hold the model and reasoning level fixed. Keep the actual upstream configurations distinct from the proposed Jackin integrations:

| Arm | Treatment |
|---|---|
| A | Native agent, no optimizer |
| B | Actual Caveman skill only |
| C | Actual Ponytail policy/plugin with recorded activation |
| D | Restrained Jackin-native narration/reuse policy |
| E | RTK current executable with exact command/retriever configuration |
| F | Headroom selected Rust transforms, ML disabled initially |
| G | Headroom full proxy in an explicitly recorded cache-oriented configuration |
| H | LeanCTX restricted read/search/symbol/outline backend |
| I | LemonCrow restricted code-search/read backend |
| J | LemonCrow full upstream runtime/persona |
| K | Caveman input stack only, subject to license and protocol approval |

Start with conformance and smoke runs; do not run expensive task trials on a treatment that never activates. Add a LeanCTX embedding arm only after the process backend is understood. Combined arms follow individual qualification, not the reverse.

### Workloads and controls

Use representative Jackin Rust tasks, build/test diagnosis, multi-crate refactors, TUI correctness, TypeScript/Java investigation, configuration and docs changes, long-session continuation, and simultaneous worktrees. Pair starting commits and working-tree contents. Randomize arm order and repeat tasks; repetitions are clustered within a task, not additional independent task diversity.

Record agent and optimizer commit/digest, profile and instruction hashes, native tool/schema surface, provider/auth route, model, reasoning effort, timeouts, permissions, index state, cache conditions, and machine resources. Include a truly cold first-use path and a warm repeated-use path. Preserve host-native truncation as the baseline: a deliberately bounded read must not be compared with an imaginary whole-file dump.

### Required measurements

| Class | Required fields |
|---|---|
| Outcome | Hidden or predeclared acceptance tests, reviewer findings, requirement coverage, regressions |
| Provider usage | Fresh input, cache reads, cache writes, output and reasoning where reported; retain raw receipts |
| Local estimates | Tokenizer/version, measured bytes, estimate method, eligible share, actually transformed share |
| Agent behavior | Turns, calls, retries, exact rereads, recovery requests, compactions, context-limit exits |
| Self-cost | Instructions, tool schemas, discovery calls, recovery markers, auxiliary model calls |
| Runtime | End-to-end time, transform p50/p95/p99, startup/index time, CPU/RAM/disk, parallel contention |
| Reliability | Installation/activation failures, timeouts, cancellation, bypass correctness, retention and rollback |

Do not double-count provider fields whose totals include reasoning or cached tokens. Unknown quota accounting remains unknown; do not derive subscription savings from a dollar-equivalent estimate.

### Acceptance and open artifacts

Primary metric: total spend across **all** attempts divided by accepted outcomes; alternatively accepted outcomes per observed subscription window, with separate token and latency reports. Include rejected patches and infrastructure failures. Publish exclusion reasons before aggregation and show both aggregate and task-weighted effects with confidence intervals.

Predeclare the quality non-inferiority margin and statistical plan. A nonsignificant difference is not equivalence. The engine's proposed 20% improvement target is a design gate to test, not a fact about obtainable savings; do not lower a declared gate after seeing results. Correctness and isolation remain hard constraints regardless of the measured saving.

Publish the harness revision, task list, sanitized inputs/configs, per-attempt usage, patches, grader outputs, traces needed to verify activation, and the aggregation code. Never publish credentials or unrestricted private source. A Rust-native harness can orchestrate existing official graders without rewriting those graders in Rust.

## Limitations and unknowns

The review stopped after current release/API, licensing, key contradiction, host-boundary, and study-eligibility questions were covered. Remaining uncertainties require executable conformance or current controlled runs, not more popularity comparisons. No universal savings number is justified.
