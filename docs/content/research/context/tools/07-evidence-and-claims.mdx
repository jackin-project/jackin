## Summary

**There is no established six-product winner for Jackin.** Fresh source, package and executable evidence supports narrower integration decisions. External experiments are informative, including a release-matched RTK 1.0.1 study, but none measures the six current products under one representative, quality-controlled Jackin protocol.

We reopened the original reports, inspected public runners and raw records where available, and reproduced inexpensive aggregations. Publication date, current repository commit, experiment date and tested product release are separate fields. Repetition improves precision on a task; it does not create additional task diversity.

## Question and scope

Which claims survive scrutiny of their actual treatment, accounting, acceptance checks and denominator? What experiment would justify deploying a new optimizer?

## Method and executed evidence

The <RepoFile path="docs/content/research/context/techniques/tools/refresh-2026-10-24/evaluation/README.md">benchmark audit and reproduction record</RepoFile> contains exact repository pins, source hashes, extraction code, numeric rows, reproduced totals and unresolved provenance. Sources outside the public repositories were reopened as original articles; unavailable raw trajectories remain unavailable.

### What these results establish

Payload reduction, task cost, acceptance and subscription capacity are separate outcomes. A tool may shrink its eligible slice while increasing total traffic through extra turns, exact rereads, schemas or lost cache reuse. A native preview may already be smaller than an optimizer's structured summary. Conversely, a useful summary can improve an answer by fitting evidence under the host limit. Both directions occurred in inspected evidence.

No old-release negative is automatically a present defect. No released fix erases the need to retest its exact path. No small positive study establishes zero regression probability. Openness improves auditability; commercial independence, representative tasks and release match still require their own checks.

## Implications for jackin❯

### Canonical acceptance gates: proposed, not observed

| Gate | Requirement for a new complex optimizer |
|---|---|
| Critical behavior | Zero observed new critical correctness, security, permission, provenance or recovery failures; any identified case blocks promotion until fixed and retested |
| Representative acceptance | One-sided 95% lower confidence bound for candidate minus baseline acceptance above **−1 percentage point**, using task clusters and a predeclared plan |
| Economics | **At least 20% lower all-attempt cost per accepted task**, with a **one-sided 95% upper confidence bound** on the candidate/baseline ratio at most **0.80**, using paired task clusters |
| Time | Whole-task p95 latency at most **10% worse**, unless a distinct, explicitly accepted tradeoff profile applies; predeclare absolute cold/warm local budgets |
| Operations | Demonstrated activation, cancellation, fallback, bounded resources, provenance and rollback in the actual host adapter |

The 1-point margin bounds statistical uncertainty; it is not permission knowingly to sacrifice correctness. The 20% threshold pays for a new optimizer's complexity and maintenance. Insufficient cost precision leaves that optimizer experimental or provisional; it does not waive the bound for default promotion. Existing native caching, bounded reads and other low-impact improvements receive proportionate conformance checks, without an arbitrary retroactive 20% hurdle.

A 12–30-task pilot can reject broken candidates and estimate variance. It cannot establish a one-point non-inferiority claim by count alone. Confirmation requires a power calculation using expected paired discordance and representative task clusters. The previous 5-point/n=30 automatic qualification is withdrawn.

### Arms and measurements

Keep the selected model and effort fixed. Distinguish native control, actual Caveman skill, actual Ponytail plugin, Jackin's adapted policy, RTK OSS filter versus full hook, Headroom selected Rust transforms versus full proxy, LeanCTX restricted MCP versus facade, LemonCrow Lite restricted retrieval versus historical/full authorized runtime, and Caveman input engine. Test combinations only after their individual activation and fidelity gates.

Randomize or interleave matched task starts; cross cold/warm index and cache conditions. Keep real native truncation, caching, discovery and edits in the baseline. Include failed setup, rejected patches, timeouts, retries, retrieval, auxiliary models and all child sessions in cost. Report observed invoice/credit outcomes separately from API rate estimates and local tokenizer counts.

Publish pinned binaries, config/instruction/schema hashes, host/auth/model/effort, task commits, accepted-outcome rubric, failure reasons, per-attempt receipts, patches, grader results, aggregation code, task-cluster intervals and sensitivity analyses. Unknown receipts stay unknown. The [validation harness](/research/context/techniques/16-validation-harness/) specifies workloads and staged experiments.

## Limitations and unknowns

This review reproduced public arithmetic and focused component behavior, not the underlying paid benchmark runs. Missing raw records, undocumented historical effort/settings and unpublished private runtimes remain evidence gaps. There is enough evidence to prioritize narrow experiments; no basis to claim a universal multiplier, a LemonCrow global win, or six-way quality equivalence.
