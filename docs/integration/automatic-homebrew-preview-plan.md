# Automatic Homebrew preview publication

**Superseded preview identity:** [Immutable preview publication and migration](immutable-preview-publication.md) records the selected `preview-<full40-source-sha>` tag, unchanged `P-preview.N+sha7` package version, signed receipt-envelope binding, and non-overwriting migration rules. Treat tag and retry recommendations below as historical where they conflict; stable release requirements remain unchanged.

Research date: 2026-10-18. Status: reviewed implementation proposal; no publishing implementation has been made.

Design refinement: [Native Velnor preview release and Homebrew promotion](velnor-native-preview-design.md) compares the current release APIs and proposes extending `binary_release` with a preview policy plus a separate distribution adapter. That document supersedes the illustrative sibling `binary_preview` naming below; no preserved or handwritten workflows are proposed.

Security refinement: [Three-agent security review](velnor-native-preview-security-review.md) records accepted findings. The native design's stricter evidence, exact signer, formula literal-only validation, task isolation, and partial-publication recovery requirements supersede less specific wording in this original plan. They remain implementation acceptance conditions, not completed security proof.

## Objective

After an eligible commit reaches `jackin-project/jackin` main and passes CI, GitHub Actions should build and publish an immutable preview, open a version-update PR in `jackin-project/homebrew-tap`, and merge that PR after its checks and feedback gates pass. A user should then obtain that preview through the official tap with `brew update` and `brew upgrade`.

All workflows in the proposed publishing implementation must be generated by `velnor-actions`, as requested. Changes to missing workflow capabilities belong in `tailrocks/velnor-new` first, followed by a released generator update and regeneration of consumer outputs. This is a project requirement, not a claim that Velnor cannot preserve explicitly allowlisted handwritten workflows.

“Latest main tip” means the latest eligible, successfully built and verified main commit. A failed tip must not be published. While main changes, publication is eventually consistent; stale candidates must not overwrite newer formula versions.

## Existing capabilities and constraints

### Jackin

- `.velnor/config.toml` currently configures generated CI under `consumer-v1`.
- `.velnor/release-manifest.json` pins official Velnor 0.1.8 assets and checksums.
- [`.github/AGENTS.md`](../../.github/AGENTS.md) reserves the entire `.github/workflows/` namespace for Velnor and prohibits local workflow workarounds.
- [`crates/tools/jackin-xtask/src/release_archive.rs`](../../crates/tools/jackin-xtask/src/release_archive.rs) builds four CLI payloads and two Linux capsule payloads. Its version argument sets `JACKIN_VERSION_OVERRIDE`.
- Preview payload names can remain unversioned within distinct immutable release tags; omitting `--archive-version` preserves the current verifier/updater naming contract.
- `crates/tools/jackin-xtask/src/release_verify/package.rs` verifies source identity, exact payload/supporting asset inventories, archive contents, and versions. Release verification also covers checksums, signatures, attestations, and SBOMs.
- [`crates/adapters/jackin-image/src/capsule_binary.rs`](../../crates/adapters/jackin-image/src/capsule_binary.rs) currently routes preview capsule, manifest, and sidecar downloads through the mutable `preview` release. This must migrate with publishing.
- Existing cross-build tooling uses `cargo zigbuild`; macOS cross-compilation downloads an SDK whose acquisition is not checksum-pinned in the inspected code. Pin and verify that SDK, or use a qualified macOS runner/SDK path before relying on these builds.

### Homebrew tap

- `Formula/jackin-preview.rb` has macOS/Linux ARM64 and x86-64 CLI URLs, plus two Linux capsule resources.
- `scripts/package-update.sh` already validates preview source repository, `refs/heads/main`, full commit identity, preview version shape, release-tag resolution, hashes, required assets, and binary version.
- The updater currently insists on `VELNOR_PACKAGE_RELEASE_TAG=preview` and emits mutable rolling-release URLs.
- `scripts/test-package-update.sh` contains preview fixtures and stable formula/Cask coverage. Preview changes must preserve stable behavior.
- Auto-merge is enabled. Main ruleset `15170998` requires `DCO` and `Required`, squash merges, linear history, and resolved review threads. It requires zero approvals and has no bypass actors.
- Zero required approvals means checks alone do not wait for review bots or establish that general comments have been addressed.

### Velnor

Fresh source/API audit on 2026-10-18 confirmed that main still matches v0.1.12 at `f1b044a606b6bc469f9718644f5c0ed88bf965b6`. GitHub reports that release as immutable, with official Linux x86-64 and macOS ARM64/x86-64 generator binaries. The product-release run and CI run at that SHA succeeded. README discussion of an older v0.1.4 publisher failure is historical evidence, not proof that v0.1.12 publication failed.

The implemented consumer binary-release contract is disabled by default. It selects one Cargo package and binary, supports only `aarch64-apple-darwin`, runs through `workflow_dispatch`, checks exact-source CI, and publishes an attested immutable release.

It explicitly checks the protected `consumer-binary-release` environment for a required reviewer and prevention of self-review. That gate blocks fully automatic per-main previews. Its Cargo-version-derived release identity also cannot publish every commit without version changes.

The current typed task model does not provide a generic publishing shell hook. Existing policy rejects `repository_dispatch` and `pull_request_target`. Do not bypass those constraints with custom consumer YAML, arbitrary shell injection, or a source-build bootstrap workaround.

The generated-file contract and preservation implementation explicitly support the last row, while generated [`.github/AGENTS.md`](../../.github/AGENTS.md) still uses blanket namespace-reservation wording. That documentation inconsistency must not be presented as absence of the feature. The requested fully generated implementation remains the selected approach; using preservation would require handwritten publishing logic and would not meet that request.

For generated workflow IR, the audited event allowlist is `pull_request`, `push`, `merge_group`, `schedule`, and `workflow_dispatch`. `workflow_run` and review/comment triggers are explicitly restricted; `repository_dispatch` is unsupported. This policy is not evidence that preserved workflow bytes are parsed through the same IR: preservation copies repository-owned files.

No first-class consumer preview publication, Homebrew formula update, cross-repository App-authenticated update PR, or feedback-aware tap auto-merge API was found. The four workflows discussed in chat are a proposed division of responsibilities; they are not existing Velnor templates. A separate merge-readiness workflow versus a job remains a design choice constrained by the allowed events and trusted review-completion integration.

## Reviewed design

### 1. Add an explicit preview channel upstream

Add a disabled-by-default typed preview capability to Velnor. A name such as `[stacks.rust.binary_preview]` is illustrative, not an existing supported API. Finalize the configuration and contract upstream before writing consumer configuration.

The typed model must represent:

- Default-branch preview eligibility and automatic publication authorization.
- Required Cargo products, targets, package layout, and a closed asset inventory.
- Deterministic preview version and immutable tag identity.
- Checksums, SBOMs, signatures, attestation identity, and package manifest requirements.
- A Homebrew destination repository, formula path, and restricted PR lifecycle policy.
- Credential references and protected preview-environment requirements.
- Generated tap verification and merge-readiness behavior.

Reuse common immutable publication, checksum, receipt, and provenance primitives. Keep stable/manual authorization and preview/automatic authorization separate. Do not weaken the stable publisher's required-reviewer policy or copy its entire implementation into a second publisher.

Relevant extension points include typed configuration, binary-release orchestration, workflow rendering, publisher helpers/scripts, workflow policy validation, and executable publisher tests.

### 2. Bind builds and publication to exact main identity

Generate a preview workflow triggered by pushes to the configured default branch. Capture the full candidate SHA and use it for every source checkout and build.

Before publication, require the correct CI workflow's successful push run for that exact SHA, including exactly one successful required aggregate job in the same run attempt. Validate repository identity, event type, default branch, workflow authority, and candidate checkout. A green PR run or a different green main commit is insufficient.

Use bounded waits and serialized publication. Recheck candidate eligibility and current main before release mutations and before opening/updating the tap PR. Do not cancel a publisher midway through a mutation; reject or skip obsolete candidates safely. Publication remains eventually consistent when main advances during a run.

Build jobs must have no repository write token. Attestation and publication must remain separate privileged boundaries. The final publisher must not build or execute the packaged application.

### 3. Use deterministic versions and immutable releases

Preserve the existing preview version contract:

```text
<Cargo-version>-preview.<N>+<sha7>
```

Derive `N` using full-history `git rev-list --count <candidate-sha>`. Require `fetch-depth: 0`, append-only main ancestry, and no force-pushed history. At the inspected SHA, the resulting version would be `0.6.4-preview.1306+a12e73a`; this is an example, not a release to publish after main changes.

Homebrew's installed Ruby version comparator was exercised with the existing version shape: increasing the numeric preview sequence and increasing the base version both compare as upgrades. Git metadata remains in the existing seven-character format; provenance must bind the complete SHA.

Use release tag `v<full-preview-version>`, for example `v0.6.4-preview.1306+a12e73a`. Create it without force at the exact candidate SHA. Keep these fields distinct:

- Source provenance ref: `refs/heads/main`.
- Source identity: full candidate SHA.
- Release locator: the immutable version tag.

Upload the complete verified asset set into a draft, then publish it as an immutable prerelease. Formula URLs must reference permanent GitHub release assets, not expiring Actions artifacts.

Retries must not create another version for the same SHA. If the exact release already exists, verify its identity, immutable status, expected assets, hashes, and provenance before proceeding to PR reconciliation. Mismatched or partial identities must fail closed; never replace published bytes or move tags. Define recovery for an interrupted draft explicitly in the upstream contract.

### 4. Preserve and qualify Jackin's package contract

The required payload inventory remains:

1. `jackin-aarch64-apple-darwin.tar.gz`
2. `jackin-x86_64-apple-darwin.tar.gz`
3. `jackin-aarch64-unknown-linux-gnu.tar.gz`
4. `jackin-x86_64-unknown-linux-gnu.tar.gz`
5. `jackin-capsule-aarch64-unknown-linux-gnu.tar.gz`
6. `jackin-capsule-x86_64-unknown-linux-gnu.tar.gz`

Preserve the existing required executable layout, role binaries, capsule manifest, checksums, per-payload SBOM/signature files, and supporting provenance contract. Derive the authoritative inventory from the existing package verifier rather than duplicating an inconsistent list in YAML.

Define a generic, typed Velnor packaging integration that can reuse Jackin's archive and verification tools. Do not hardcode Jackin repository behavior inside Velnor or introduce an unrestricted shell-task escape hatch. The exact integration is an upstream design item requiring implementation and tests.

Qualify both macOS architectures and both Linux architectures. Existing archive code demonstrates intended build routes, but does not prove that current hosted generated workflows can execute the complete build successfully. Verify SDK integrity, runner availability, target dependencies, archive layouts, and the installed runtime behavior.

### 5. Migrate runtime preview resolution completely

The same preview version must select the same immutable release in both Homebrew and Jackin's capsule downloader.

Change preview download bases to `/releases/download/v{version}/`, retaining the unversioned payload names above. Migrate capsule manifest, checksum, signature sidecars, error/help links, documentation, and tests together.

Inspect the legacy preview migrator and all remaining rolling-tag references; remove obsolete behavior instead of adding a fallback. Preserve unrelated stable release behavior. Retire the rolling preview publication/download path only as part of this complete migration.

Old installed preview binaries that depend on the rolling release may lose capsule download functionality when that release is retired. The project's breaking-change policy permits this; document that users must upgrade or reinstall the new preview. Do not introduce a compatibility period or maintain dual publishing paths.

### 6. Generate the tap PR with restricted credentials

After immutable release verification, a generated publication job should prepare the formula update against trusted tap main, then obtain a GitHub App installation token restricted to `jackin-project/homebrew-tap` with `contents:write` and `pull_requests:write`. Metadata read is implicit. Do not grant bypass or administration permissions to this token.

Never expose this token to build/test jobs or execute PR-controlled scripts with it. Use trusted tap main code and verified release data when generating the formula. An App token also allows bot-created PRs to trigger the normal PR workflows; repository `GITHUB_TOKEN` event suppression is unsuitable for this cross-repository flow.

Update the preview branch of `scripts/package-update.sh` to:

- Require the canonical immutable tag corresponding to the verified preview version.
- Verify the tag peels to the manifest's full source SHA.
- Preserve source repository, `refs/heads/main`, version, inventory, hash, and executable-version validation.
- Require verified immutable release/provenance evidence through the typed handoff contract.
- Generate all CLI and capsule-resource URLs using that tag.
- Reject older formula identities and skip an identical already-applied identity.

Create an idempotent PR branch for the source identity with a DCO-signed-off commit. Limit the diff to the preview formula unless a reviewed contract change requires more. Reconcile existing PRs without discarding review feedback. Recheck current tap version and source freshness before mutation or merge to prevent rollback.

Update updater tests for immutable tags, mismatches, retries, downgrade rejection, and formula resources. Preserve the stable formula/Cask test cases and behavior.

### 7. Gate automatic merge on checks and feedback

Generate tap CI covering updater tests, formula syntax/style as applicable, release/provenance validation, archive verification, installation, binary version, and capsule resources. Make these checks feed the required aggregate gate; a skipped check must not silently satisfy publication readiness.

Auto-merge must preserve `DCO`, `Required`, squash-only merging, linear history, and resolved threads. Add a generated merge-readiness gate that waits for configured review completion at the current head and checks all reviews, review threads, review comments, replies, and general PR comments.

Review completion needs an explicit trusted signal; an empty review list or a quiet waiting period is not completion. Implement or integrate a trusted review controller that reports a dedicated `Preview review complete` check for the exact PR head SHA only after every configured reviewer has finished and its findings/dispositions have been recorded. Validate the check's producing App/workflow identity, not just its name. A new head invalidates completion; missing, failed, timed-out, or stale completion blocks merge. The provider and its completion protocol must be selected and tested during implementation; no such signal was established by this research. Until that integration exists, leave update PRs open for reviewed manual merge rather than enabling automatic merge.

Ordinary GitHub auto-merge cannot determine whether feedback has a justified disposition. Under the repository instructions, findings require independent verification, evidence-backed replies, and fixing commit links when accepted. Leave the PR pending when that disposition cannot be established automatically. Do not resolve feedback automatically merely to make a PR mergeable.

With that trusted completion integration in place, clean routine update PRs should merge automatically. For findings, perform the required review/fix/disposition workflow, rerun checks, and re-fetch feedback at the final head before enabling merge. Avoid granting auto-merge before the feedback gate exists, because zero required approvals would otherwise allow checks to finish before reviewers respond.

## Repository configuration prerequisites

- Publish an official Velnor release containing this capability; upgrading only to 0.1.12 does not provide it.
- Update both consumers' `.velnor/release-manifest.json` through the supported official release workflow and regenerate owned outputs.
- Configure a separate protected preview environment whose explicit typed policy permits automatic publication from the protected default branch. Keep stable release reviewer requirements intact.
- Enable immutable GitHub releases and supply the required narrowly scoped Administration-read credential for the immutable-release status preflight, separate from the tap writer.
- Verify preview tag creation is allowed for the intended publisher while tag replacement/deletion remains prohibited.
- Install the restricted tap GitHub App, configure its credentials, and verify DCO identity/signoff behavior.
- Keep existing tap auto-merge/protections; add the generated validation and feedback gates without bypasses.
- Review actual runner/toolchain/SDK availability and review-bot completion semantics during implementation. Do not treat these as already configured or proven.

## Implementation order

1. Agree and implement the generic Velnor preview/package/PR contracts, policies, rendering, and tests.
2. Independently review upstream changes; address all feedback, merge, and publish an official generator release.
3. Update Jackin's generator pin/configuration, qualify package builds, and complete immutable runtime/download migration.
4. Update the tap's generator pin/configuration and preview updater/tests; generate verification and PR merge gates.
5. Configure environments, immutable-release prerequisites, credentials, and publisher tag permissions.
6. Inspect generated diffs and verify the first exact-main preview end to end.
7. Publish a second eligible main commit and prove that the resulting PR merges and Homebrew upgrades correctly.
8. Retire all obsolete rolling-preview paths and confirm no runtime or publishing fallback remains.

## Acceptance and verification

### Generator and security tests

- Preview disabled by default; generation deterministic; unsupported configuration fails closed.
- Only trusted default-branch pushes can publish; PR/fork events and wrong source/workflow identities fail.
- CI must match source SHA and run attempt; failed, skipped, stale, or ambiguous required jobs fail.
- Build jobs cannot access publication/App credentials; publisher does not execute packaged binaries.
- Preview authorization does not weaken stable required-reviewer behavior.
- Missing immutable-release settings, environment restrictions, or required credentials fail before mutations.
- Missing/extra assets, wrong targets, malformed manifests, invalid attestations/signatures, and hash/version mismatches fail.
- Retries, interrupted drafts, concurrent builds, already-open PRs, stale tips, and newer tap versions have deterministic safe outcomes.
- Unresolved threads, changes-requested reviews, unaddressed general comments, or changed PR heads prevent merge.

### Jackin and tap tests

- All six payloads and supporting files satisfy the existing release package contract.
- Version/tag/source identity agrees across CLI, capsule, manifest, release, and formula.
- Preview runtime downloads and signature verification use immutable version tags without rolling fallback.
- Updater tests cover canonical immutable URLs, tag/source mismatch, bad hashes, missing assets, idempotency, and downgrade rejection.
- Stable formula/Cask behavior remains correct.
- Both Homebrew CPU branches and capsule resource selections point at the correct artifacts.

### Local macOS proof

Use the documented alias or the fully qualified canonical formula consistently:

```sh
brew tap jackin-project/tap
brew install jackin-project/tap/jackin@preview
jackin --version

# After a second main preview has published and its tap PR has merged:
brew update
brew upgrade jackin-project/tap/jackin@preview
jackin --version
```

The canonical alternative is `jackin-project/tap/jackin-preview`. If stable Jackin is installed, account for the existing formula conflict when switching to preview.

Inspect `brew info --json=v2` and the installed executable: both must match the published manifest version. Verify actual capsule loading and its signature checks, not only `--version`. Demonstrate that the first preview remains downloadable after the second publishes, proving that URLs are immutable.
